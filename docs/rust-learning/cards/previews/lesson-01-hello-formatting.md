## 01. Rust 的 println! 末尾带感叹号，是宏而不是函数。它为什么必须是宏？对着一行 println!("{} days, {:?}", days, Structure(3))，编译期做了哪几件事，运行期还剩什么？

类型：技术问答 · 层级：机制 · 等级：A

选入理由：面试常问“println! 为什么是宏”，要能讲出编译期与运行期的分工。

### 答案

**结论**：因为它要在编译期读懂格式串：格式对不对、参数个数对不对、类型能不能这样打印，都在编译期解决，运行期只剩加锁和按模板写出。

- **为什么不能是函数**：函数只能拿到运行期的值，看不到格式串的内容，也看不到参数的个数和类型；普通的 Rust 函数还没有可变参数和重载。
- **编译期**：宏展开成 \_print(format\_args!(…))；解析格式串并核对占位符与参数的个数；按占位符选 trait，{} 要 Display，{:?} 要 Debug，类型没实现就是编译错误；最后把格式串编成模板，连同参数表装进 fmt::Arguments。
- **运行期**：锁住标准输出，顺着模板写，遇到占位符就调用那个类型的 fmt。参数是以引用的形式放进参数表的，打印不会拿走它们。

**边界**：代价是格式串必须是写在源码里的字面量，把它存进变量再传给 println! 编译不过。

### 锚点

编译期读格式串：展开、解析、选 trait、生成模板；运行期只按模板写

## 02. 打印时少传了一个参数：格式串里有两个占位符，却只给了一个值。这个错误在 C 的 printf、C++ 的 cout &lt;&lt;、Rust 的 println!（以及 C++20 的 std::format）里各在什么时候暴露？由此说明 Rust 这条路换来了什么、付出了什么。

类型：技术问答 · 层级：机制 · 等级：A

选入理由：面试里比较 Rust 与 printf、cout 的格式化设计时的核心论据。

### 答案

**结论**：printf 要到运行期才出问题，而且可能只是输出乱码；cout 没有格式串；Rust 和 std::format 在编译期就报错。

- **printf**：格式串是普通的运行期字符串，函数签名只能写成一个字符串加若干类型未知的参数，个数和类型对不上语言本身发现不了。gcc 的 -Wformat 警告是编译器额外做的检查，把格式串放进变量后连警告也没有。
- **cout**：放弃格式串，每个值用一次重载的 &lt;&lt;。类型安全有了，自定义类型也能接入，但输出长什么样不再集中写在一处，宽度和精度要靠有状态的操纵符。
- **Rust**：格式串留下，但要求是字面量，由宏在编译期读它；类型怎样接入交给 trait，每种占位符对应一个 trait。
- **换来与付出**：换来的是格式和参数对不上的错误不可能留到运行期，运行期也不必再解析格式串。付出的是格式串必须写死在源码里，每一种打印方式都要逐个类型实现。

**边界**：“运行期才发现”还依赖两个前提：那一行真的被执行到；运行期有专门的检查。Python 会抛 IndexError，C 则表现为乱码。

### 锚点

printf 运行期、cout 无格式串、Rust 编译期；代价是格式串必须是字面量

## 03. Rust 里 {:?} 用的 Debug 可以写 #\[derive(Debug)\] 让编译器生成，{} 用的 Display 却必须手写，标准库甚至不给 Vec 实现 Display。为什么？

类型：技术问答 · 层级：机制 · 等级：A

选入理由：“Display 和 Debug 有什么区别、为什么 Vec 不能用 {} 打印”是常见面试题。

### 答案

**结论**：Debug 的输出有一条不需要理解含义的机械规则；Display 是给用户看的，怎么写取决于含义。

- **Debug**：照着类型的定义，写出类型名，再依次写出每个字段的名字和字段自己的 Debug 输出，所以每个字段都必须有 Debug。
- **Display**：同一个 Vec&lt;T&gt; 没有对所有元素类型都合适的写法：路径列表也许该用冒号分隔，数字列表也许该用逗号。标准库不替你决定，所以用 {} 打印 vec!\[1, 2, 3\] 是编译错误，用 {:?} 则打印 \[1, 2, 3\]。
- **日常分工**：几乎每个类型都顺手 derive 一个 Debug，只有要给人看的少数类型才手写 Display，多数是状态枚举和错误类型。

**边界**：要让别人的类型（如 Vec）按你的方式用 {} 打印，得包一层自己的类型，再为它实现 Display。

### 锚点

Debug 照定义机械生成；Display 的写法取决于含义

## 04. Rust 把给用户看的输出和给开发者看的输出分成 Display 和 Debug 两个 trait，而不是一个。两者对输出各作了什么承诺？这对写测试和协议意味着什么？

类型：技术问答 · 层级：原子 · 等级：B

### 答案

**结论**：Display 的输出算作类型对外行为的一部分；derive 出来的 Debug 只供调试，格式不稳定。

- **Display**：面向用户，写出值的内容，写法由类型的作者决定并负责。
- **Debug**：把值写成它在源码里的样子，比如字符串带引号、制表符写成反斜杠加 t；格式可能随 Rust 版本变化。
- **后果**：不要让程序去解析 Debug 的输出，也不要把它的精确文本写进测试断言或协议。

**边界**：Python 的 \_\_str\_\_ 和 \_\_repr\_\_ 是同样的分工。

### 锚点

Display 是对外行为，Debug 只供调试且不稳定

## 05. 一个结构体里有密钥或令牌字段，定义上写了 #\[derive(Debug)\]。把它用 {:?} 打进日志会发生什么？应该怎么改？

类型：技术问答 · 层级：原子 · 等级：A

选入理由：防止把密钥或令牌打进日志这种代价很高的错误。

### 答案

**结论**：密钥会原样出现在日志里：derive 的 Debug 会打印所有字段。

- **原因**：derive 生成的 fmt 很机械，写出类型名后依次写出每个字段的名字和它的 Debug 输出，不会区分哪些字段敏感。
- **改法**：手写 Debug，只列出想公开的字段，例如用 f.debug\_struct("Router").field(…) 逐个挑。推理路由器 ATOMesh 的 Router 就是这样手写的。

**边界**：同理，不要依赖 Debug 输出的精确文本，它不保证稳定。

### 锚点

derive 的 Debug 打印所有字段；敏感类型手写 Debug

## 06. 为自己的类型实现 Display 时，要写的是 fn fmt(&self, f: &mut fmt::Formatter) -&gt; fmt::Result，在里面用 write!(f, …) 往 f 里写。为什么设计成往 f 里写，而不是返回一个字符串？格式化本身不会失败，为什么还要返回 Result？

类型：技术问答 · 层级：机制 · 等级：A

选入理由：“Display::fmt 为什么不返回 String”是考察设计理解的面试题。

### 答案

**结论**：往同一个 f 里写，内容一路直通目的地，中间不产生临时字符串；返回 Result 只是为了把底层写入的失败传回去。

- **不返回字符串**：返回字符串意味着每一层都要分配一块内存再拼接，嵌套的类型层层如此。往 f 里写则没有中间分配，同一个 fmt 还能同时服务 println!、format! 和写文件，它不需要知道目的地是什么。
- **Result**：格式化本身是不会失败的操作，可能失败的是往底层的流里写。所以规矩是只传递 f 报的错，不要自己制造错误。
- **怎么传**：Rust 没有异常，错误是普通的返回值：中间的 write! 后面加问号，失败就立刻带着错误返回；最后一个 write! 不加分号，直接作为返回值。

**边界**：实现了 Display 就自动有 to\_string()，标准库为所有实现了 Display 的类型提供了它。

### 锚点

往 f 里写：无中间分配、不关心目的地；Result 只传递写入失败

## 07. struct Id(u32) 手写了 Display。调用方写 println!("\[{:&gt;10}\]", Id(7))，希望右对齐到 10 个字符宽。fmt 的函数体有四种写法：一是 write!(f, "{}", self.0)；二是 fmt::Display::fmt(&self.0, f)；三是 write!(f, "{:&gt;6}", self.0)；四是 f.pad(&self.0.to\_string())。四种写法各输出什么？为什么？

类型：技术问答 · 层级：机制 · 等级：A

选入理由：“我的 Display 为什么不对齐”是常见的排错题，课上在这里出过两次错。

### 答案

**结论**：宽度、对齐这些格式说明记在 f 里，由每个类型自己的 fmt 执行。只有把同一个 f 交下去，或者用 f.pad，外层的要求才会生效。

- **写法一**：输出 \[7\]。write! 另起了一个格式串，里面的 {} 是不带宽度的新占位符，没有人去看 f 里的 10。
- **写法二**：把带着宽度的同一个 f 交给 u32 的 fmt，右对齐到 10 位，没有额外的分配。
- **写法三**：右对齐到 6 位：用的是自己格式串里写死的宽度，调用方的 10 被忽略。
- **写法四**：先转成字符串，再让 f.pad 按 f 里的宽度、对齐和填充字符写出，右对齐到 10 位，但多一个临时字符串。

**边界**：标准库的类型都会执行格式说明；自己写的 Display 默认不会，需要对齐时要么这样处理，要么让调用方先 to\_string() 再打印。

### 锚点

格式说明记在 f 里；谁拿着 f，谁决定是否执行

## 08. println!("{:&gt;8.3}", x) 里的宽度和精度，为什么设计成交给 x 的类型自己的 fmt 去执行，而不是由 println! 拿到输出后统一补空格？

类型：技术问答 · 层级：机制 · 等级：B

### 答案

**结论**：因为同一个说明对不同类型含义不同，而且统一补空格必须先把输出存进临时字符串。

- **含义不同**：{:05} 打印 -7 得到 -0007，0 要补在符号后面；{:.2} 对浮点数是保留两位小数，对字符串 abcdef 则是截成 ab。只有类型自己知道该怎么做。
- **临时字符串**：统一补空格需要先拿到这个参数的完整输出才知道长度，那就得先把它存起来，和直接往目的地写的设计冲突。
- **流程**：编译器在编译期解析说明并写进模板，运行期它经由 f 交到每个类型的 fmt 手里。

**边界**：所以自己写的 Display 默认不理会宽度和对齐，需要时用 f.pad，或者把 f 转交给字段的 fmt。

### 锚点

含义因类型而异；统一补齐需要临时字符串

## 09. Rust 的格式串必须是字面量，但 println!("{id:&gt;width$}") 里的宽度却可以取自变量 width。为什么宽度可以到运行期才确定，格式串本身不行？

## 10. 手写 Display 时，通常应该直接往 f 里写，而不是先拼成字符串。什么情况下先把内容放到一个缓冲区里反而是合理的？Rust 1.97.1 标准库的 Ipv4Addr 是怎样做的？

**结论**：要把整段输出当作一个整体来对齐的时候。

## 11. Rust 里 println!("{:x}", 255) 输出 ff，而 println!("{:x}", 1.5f32) 是编译错误。为什么？“一种占位符对应一个 trait”这种设计换来了什么？想看浮点数的位模式该怎么做？

## 12. 一个导出工具在循环里用 println! 输出 100 万行，使用者把它接到 head -n 20 上只看前 20 行，结果看到一段崩溃信息。发生了什么？如果是标准输出被重定向到的磁盘写满了，又会怎样？应该怎么改？

类型：技术问答 · 层级：机制 · 等级：A

选入理由：命令行工具和服务日志里的真实故障，面试常以“println! 有什么坑”出现。

### 答案

**结论**：println! 写失败时不把错误交给你，而是直接 panic。

- **管道**：head 读够 20 行就退出，管道的读端关闭；工具下一次写时操作系统返回 Broken pipe，println! 内部拿到这个错误就 panic。
- **磁盘写满**：同样是写失败，信息变成 No space left on device。panic 发生在主线程，整个进程以退出码 101 结束；发生在别的线程，默认只有那个线程终止，它正在处理的请求就丢了。
- **改法**：改用 writeln!，它把 Result 交还给你：先锁住标准输出 let mut out = io::stdout().lock();，循环里判断 writeln!(out, …) 是否出错，出错时自己决定怎么办，比如安静地结束循环。

**边界**：诊断和进度信息用 eprintln! 写到标准错误，不要和要交给管道的数据混在一起。

### 锚点

println! 写失败就 panic；要处理就用 writeln! 拿 Result

## 13. 一个推理路由器用 64 个线程处理请求，每处理完一个请求就用 println! 打一行访问日志。请求量很大时这一行会带来什么问题？对照 Rust 1.97.1 标准输出的实现说明原因，并给出改法。

类型：技术问答 · 层级：机制 · 等级：A

选入理由：推理服务里“打日志拖慢请求”的排查题，贴近 AI 基础设施岗位。

### 答案

**结论**：标准输出在整个进程里只有一个，每次 println! 都要先拿到它的锁，而且每行做一次系统调用。

- **锁**：本来互不相干的 64 个线程到了这一行要排成一队，日志写得多慢，请求就被拖多慢。等锁的线程是阻塞，前一个写完就能继续，不是死锁。
- **按行缓冲**：标准输出外面包着一层按行缓冲的写入器，每遇到一个换行就把这一行真正交给操作系统，也就是每行一次系统调用。
- **改法**：需要大量输出时自己先把锁拿住，再用 writeln! 往里写，整个循环只加一次锁；要减少系统调用，再包一层更大的缓冲区。

**边界**：只锁住句柄并不能减少系统调用，因为它仍然按行缓冲。

### 锚点

全进程一把锁，按行缓冲；只锁一次并加大缓冲

## 14. 一个 Display 实现把写入错误悄悄丢掉了，但所有比较输出文字的测试都通过。为什么这类测试发现不了？怎样设计测试，才能测到“写入失败时返回 Err 并且不再继续写”？

## 15. 假设 Rust 把 println 做成普通函数，像 C 的 printf 那样到运行期才解析格式串。这样做反过来能换来什么现在得不到的灵活性？

选入理由：把这条取舍说错，会在“编译期检查换来什么、放弃什么”的设计题上答偏。

### 场景

第 01 课节点 2 的检查题第 3 问。

### 正确

格式串本身可以是运行期的值，来自配置文件、翻译文件或用户输入。

### 错误

由于此时编译期不检查个数和类型对不对的上，可以将某些参数以另一种类型的方式进行打印出来。

## 16. Worker 的 Display 里，先写 let s = format!("w{}: {:.1}", self.id, self.load); 再写 write!(f, "{}", s)。调用方用 println!("\[{:&gt;12}\]", w) 要求右对齐到 12 个字符宽。这个实现能对齐吗？最小的改动是什么？

### 场景

第 01 课综合验收第 3 题：比较先拼字符串的版本和直接 write! 的版本。

### 正确

不能对齐，两种写法都输出 \[w7: 0.5\]；保留 format!，把最后一行换成 f.pad(&s)。

### 错误

同事写的这个版本由于先转成了字符串，而字符串可以对齐。但我改后的版本不行。最小的改动是使用f.pad，改成write!(f, f.pad(“w{}: {:.1}”), self.id, self.load)。

## 17. Shard 是自己定义的类型，pool.shards 的类型是 Vec&lt;Shard&gt;。println!("{}", pool.shards) 编译不过，因为 Vec&lt;Shard&gt; 没有 Display。最小的修法是什么？能不能直接为 Vec&lt;Shard&gt; 实现 Display？

## 18. List 的 Display 要分多次 write! 写出各个元素。编译器对没人用的 Result 给了警告，并提示可以写成 let \_ = write!(f, …); 来消掉它。照着改之后测试全过。这样写有什么问题？只把 let \_ = 去掉行不行？

类型：真实纠错 · 层级：机制 · 等级：A

选入理由：照编译器提示消警告却吞掉错误，是隐蔽而代价高的错误。

### 场景

第 01 课练习的 Review：List 的 fmt 把每次写入的结果都丢掉了。

### 正确

只去掉不行；中间的 write! 后面加问号把错误传出去，最后一个 write! 不加问号也不加分号，作为返回值。

### 错误

但我该怎么改呢？就去掉“let \_ = ”就可以了吗？

### 说明

**结论**：let \_ = 只是让警告闭嘴，写入错误照样丢了：中间丢了一段内容，函数却报告成功。

- **证据**：用一个第 3 次写入会失败的输出目的地打印 List(vec!\[1, 2, 3\])：原实现一直写完 12 次，留下 \[0, 1: 2, 2: 3\]，返回 Ok；用问号的实现在第 3 次后停止并返回 Err。

**边界**：往字符串里写永远不会失败，所以只检查输出文字的测试发现不了这个问题。

## 19. WorkerId(u32) 的 Display 为了支持对齐，先 format!("w{}", self.0) 再 f.pad。这里有堆分配吗？原因是什么？能不能省掉？

有堆分配；因为 format! 返回的 String 的内容总是放在堆上，和长度定不定无关。

### 错误

因为长度不定，有堆分配。

### 说明

**结论**：是否堆分配取决于用的容器类型，不取决于长度是否已知。

- **长度其实有上界**：u32 最大是 4294967295，加上前面的 w 一共 11 个字节。
- **怎么省**：像标准库的 Ipv4Addr 那样，先写进一个固定大小的栈上缓冲区，再 f.pad。

**边界**：长度没有上界时，才必须用 String 这类把内容放在堆上的容器。

## 20. 请用 60–90 秒向面试官讲清 Rust 的格式化输出是怎样设计的：一行 println! 在编译期和运行期各做什么；一个类型怎样接入；和 C 的 printf 相比换来了什么、付出了什么；实际使用时要小心什么。

类型：综合口述 · 层级：综合口述 · 等级：A

选入理由：这就是综合验收的口述题，也是面试里最可能被问到的整体题。

### 参考回答

**结论**：println! 是宏，编译期读懂格式串并核对参数，运行期只按模板写出；类型通过实现 Display 或 Debug 接入。

- **编译期**：宏展开后由编译器内建的 format\_args! 解析格式串，核对占位符和参数的个数，再按占位符选 trait，类型没实现就是编译错误；结果是一段模板加一张参数表。
- **运行期**：锁住标准输出按模板写，遇到占位符就调用那个类型的 fmt；fmt 往传进来的 Formatter 里写，不返回字符串，所以没有中间分配。
- **接入**：Debug 面向开发者，输出照类型定义机械生成，可以 derive；Display 面向用户，写法取决于含义，必须手写。
- **取舍**：和 printf 比，格式和参数对不上的错误不会留到运行期，运行期也不必解析格式串；代价是格式串必须是字面量。

**边界**：使用时要小心：每次调用都要锁标准输出，写失败会直接 panic，需要处理时改用 writeln!。

### 评分锚点

- 说出它是宏，以及编译期的解析、核对个数、按占位符选 trait
- 说明运行期只是加锁并按模板调用各类型的 fmt
- 区分 Debug 可以 derive 与 Display 必须手写，并说出原因
- 说出相对 printf 的收益和“格式串必须是字面量”这一代价
- 至少说出一条使用边界：加锁，或写失败会 panic

## 21. 面试官问：你的 Rust 推理服务和命令行工具里直接用 println! 打日志、输出数据，有哪些要小心的地方？各自怎么处理？请用约 60 秒回答。

类型：综合口述 · 层级：综合口述 · 等级：A

选入理由：把这一课的运行期边界落到推理服务的真实场景，是工程向面试题。

### 参考回答

**结论**：三件事：写失败会 panic；每次调用都要抢同一把锁，并且按行写出；用 {:?} 可能把敏感字段打进日志。

- **写失败**：管道被对方关闭或磁盘写满时 println! 直接 panic；要自己处理，就锁住标准输出后用 writeln!，拿到 Result 再决定。
- **锁与缓冲**：标准输出全进程只有一个，多线程在这一行排队，每行还是一次系统调用；大量输出时只加一次锁，并加大缓冲。
- **泄露**：derive 的 Debug 打印所有字段，带密钥的类型要手写 Debug，只列出想公开的字段。

**边界**：panic 发生在工作线程时，默认只终止那个线程，它正在处理的请求会丢。

### 评分锚点

- 指出写失败会 panic，并给出管道关闭或磁盘写满这样的触发场景
- 给出改用 writeln! 并处理 Result 的做法
- 说明全局锁和按行缓冲对多线程吞吐的影响及缓解办法
- 指出 derive 的 Debug 会泄露敏感字段，以及手写 Debug 的做法
