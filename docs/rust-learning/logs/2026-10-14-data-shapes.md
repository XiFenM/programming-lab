## 开课与贯穿案例

- [要点] 这一课针对 C 的哪个老问题，Rust 的总体办法和代价是什么？——C 的类型只管“这几个字节怎么解释”，很多关键信息不在类型里：数组传进函数就退化成指针，长度丢了；`union` 当前存的是哪个成员靠另一个字段配合；宽度、符号不同的整数混着算时悄悄转换。Rust 把这些信息放回类型或值里再让编译器检查：数组长度写进类型，切片随身带着长度，“多选一”的数据把标签和内容绑在一起，数值转换必须写出来。代价是多写转换和分支，运行时多了越界检查。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] 贯穿案例里的 safetensors 文件长什么样，库把一条文件头读成什么？——文件分三段：8 字节的长度 N、N 字节的 JSON 文件头、首尾相接的数据区。Qwen2.5-7B-Instruct 的第一个分片是 3,945,441,440 字节，文件头 9,368 字节，登记了 82 个张量；embedding 表是 152,064 × 3,584 的 BF16，占数据区第 0 到第 1,089,994,752 字节。库把每一条读成 `TensorInfo { dtype: Dtype, shape: Vec<usize>, data_offsets: (usize, usize) }`，校验后交出一个 `TensorView`，其中的数据是 `&[u8]`。（来源：`msg-97d8638f34a2cf38e0a7`。）

## 标量类型与数值规则

- [要点] Rust 的标量类型和 C 的怎样对应，哪几处容易带错习惯？——位宽写在名字里，不随平台变：`i8` 到 `i128`、`u8` 到 `u128`、`f32`、`f64`。`usize` 和指针一样宽，长度、下标、偏移都用它。`bool` 只有 `true` 和 `false`，整数不能当条件，`if n` 编译不过。`char` 占 4 字节，是一个 Unicode 字符；C 的 `char` 对应的是 `u8`。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] 一个数字字面量的类型是怎么定的？——后缀定类型，如 `1u32`、`2.5f32`。不写后缀就按上下文推断，推不出来时整数取 `i32`、浮点取 `f64`。还可以写成 `0xff`、`0b1010`、`1_000_000`、`1e6`。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] `let nbits: u64 = numel * 16;`（`numel` 是 `u32`）为什么编译不过，C 的同一行会怎样？——Rust 报 E0308：expected `u64`, found `u32`，不同数值类型之间没有隐式转换。C 的 `uint64_t nbits = numel * 16;` 能编译，`-Wall -Wextra` 下也没有警告，它先在 32 位里乘，溢出后才扩成 64 位：544,997,376 × 16 在本机得到 130,023,424，正确值是 8,719,958,016。Rust 要你写出在哪个宽度里算：`u64::from(numel) * 16` 或 `numel as u64 * 16`。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] `as` 在放不下的时候会怎样，它和 `u64::from` 有什么区别？——`as` 总能编译，放不下时不报错：`300i32 as u8` 得 44，是截断；`-1i32 as u32` 得 4294967295；`1e10 as i32` 得 2147483647，卡在上限。`u64::from(x)` 只在不丢信息的方向上存在，方向写反了编译不过。所以 `as` 只该用在确知放得下、或者本来就要截断的地方。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] 整数溢出在 Rust 里是什么行为？——它不是未定义行为，而是有明确规定的程序错误。常量溢出如 `1u32 - 2` 直接是编译错误。运行时才知道的值看构建方式：调试构建 panic，信息如 `attempt to multiply with overflow`；发布构建回绕，只留下低位。有符号、无符号是同一条规则；C 的有符号溢出则是未定义行为，编译器可以假设它不发生。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] 为什么调试构建检查溢出，发布构建不检查？——Rust Reference 把溢出定性为程序员的错误：开了调试断言的构建必须检查并 panic，其他构建由实现决定是 panic 还是回绕，回绕时结果必须是确定的二进制补码。Cargo 的默认值是 `dev` 开、`release` 关，省掉的是每次运算后的一次判断。推论是默认的发布构建里溢出是静默的。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] 想自己决定溢出时怎么办，有哪几组方法，各用在哪？——`checked_add`、`checked_sub`、`checked_mul` 返回 `Option`，溢出时是 `None`，用在输入不可信、算的又是大小或偏移的地方，让溢出变成一个必须处理的值。`wrapping_*` 明确要回绕，用在回绕本身是算法一部分的地方，例如哈希。`saturating_*` 卡在上下限。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] 不做隐式数值转换的代价是什么，惯例怎样应对？——代价是啰嗦，每次变宽度、变符号都要写出来。惯例是尽早统一成一种类型：`TensorInfo` 的 `shape` 和 `data_offsets` 全是 `usize`，因为它们最终要当下标用，而下标只接受 `usize`，拿 `u32` 做下标是 E0277。“读的人能看到哪里可能丢信息”这个动机是助手的推断。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] safetensors 校验文件头时怎样防溢出，防的是什么？——`nelements.checked_mul(info.dtype.bitsize()).ok_or(SafeTensorError::ValidationOverflow)?`：元素个数乘每个元素的位数，溢出得到 `None`，`.ok_or(错误)` 把它换成一个错误，`?` 提前返回。这里宽度和检查各管一半：64 位的 `usize` 让真实模型不会溢出，`checked_mul` 防的是恶意文件头，比如把 shape 写成两个 2⁴⁰。（来源：`msg-97d8638f34a2cf38e0a7`。）

## 元组与节点 1–2 检查

- [要点] 元组是什么，和 Python 的元组差在哪，什么时候不该用？——它把固定个数、类型可以不同的几个值捆成一个值，用 `.0`、`.1` 按位置取，或者用 `let (start, end) = offsets;` 解构。个数和每个位置的类型都写在类型里，`(usize, usize)` 和 `(usize, usize, usize)` 是两个不同的类型。代价是位置没有名字：`data_offsets: (usize, usize)` 是（起，止）还是（起，长度），从类型上看不出来，所以成员有独立含义、或者多于两三个时该用带字段名的 struct。（来源：`msg-97d8638f34a2cf38e0a7`。）

- [要点] 一个按 `(u32, u32)` 的（起，止）算 `end - start` 的函数，遇到被改成 `[100, 40]` 的文件头会怎样，哪种更危险？——学习者答：“在调试构建下会panic，发布构建就会按补码回绕。对调用它的程序来说，发布构建的补码回绕更危险，因为会得到异常的结果，且没有报错。”判断正确。改法也答对了方向：“需要用checked_函数来包装这个减法计算。当溢出时返回None，处理None转为报错信息。”（来源：`msg-32a6172bdcb9c6620fa4`、`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 把减法改成 `end.checked_sub(start)` 之后，为什么调用方没法忽略这个问题？——返回类型变成了 `Option<u32>`，调用方拿到的不再是 `u32`，不把 `Option` 拆开就用不了里面的数。safetensors 的真实代码用的是等价的另一种写法，先比较再减：`if s != start || e < s { return Err(…) }`，之后的 `e - s` 就不可能溢出。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [纠错] 场景：节点 1–2 检查第 3 问，把 `usize` 的偏移各用 `as u32` 转一下再传进去会引入什么风险。我说“as u32是强制类型转换，也可能导致溢出。”→ 正确：`as` 的截断不归溢出检查管，它在调试构建里也不 panic，两种构建都静默截断。原因：所以它比减法溢出更隐蔽，减法至少会在测试里炸，`as` 连测试都不报；出现条件我答对了，是偏移达到 2³²，也就是超过 4 GiB 的文件。（来源：`msg-32a6172bdcb9c6620fa4`、`msg-4e7e07c8eb9203af5dd6`。）

## 数组与切片

- [要点] 数组和切片各把长度放在哪里？——数组 `[T; N]` 的长度写在类型里，值就是 N 个元素本身，`[i32; 5]` 是栈上 20 字节。切片 `&[T]` 是借来的一段连续元素，长度不在类型里，和指针一起带在值里：`&xs[1..4]` 是两个机器字，指针指向第 1 个元素，长度是 3，共 16 字节。这种比普通指针多带一个字的指针叫胖指针。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 按下标访问切片时发生了什么，这个检查在发布构建里会关掉吗？——`s[i]` 先比较 `i < 长度`，不成立就 panic，成立才去读。`s.get(i)` 不 panic，返回 `Option`。对数组用常量下标越界直接是编译错误。越界检查在发布构建里也不关，这和溢出不同：溢出只是算错一个数，越界读写会碰到不属于你的内存，这是 Rust 承诺安全代码里绝不发生的事。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 为什么切片要做成“指针加长度”？——要解决的问题是一个函数想处理任意长度的一段元素。长度留在类型里不行，`fn sum5(a: [i32; 5])` 传 `[i32; 4]` 是 E0308。C 的做法是丢掉长度：`sizeof(xs)` 在 `main` 里是 20，在被调函数里是 8，把只有 4 个元素的数组传给 `sum5` 能编译，运行时读到了数组之外。Rust 把那对 `(指针, 长度)` 做成一个值，长度永远跟着指针，每次下标访问都有东西可比；取子切片只算出一个新指针和一个新长度，不复制。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 切片的代价是什么，哪种访问方式没有这个代价？——引用占 16 字节而不是 8，每次按下标访问多一次比较。`for x in s` 这样逐个遍历不经过下标，没有这次比较，标准库的切片迭代器存的就是头尾两个指针。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] `[T; N]`、`Vec<T>`、`&[T]` 三者怎样区分？——数组的长度在编译期确定，值里是元素本身。`Vec<T>` 的长度运行期可以增长，值里是指针、容量、长度共 24 字节，数据在堆上并归它所有，从别处的数据造一个就要复制。`&[T]` 的值里是指针和长度共 16 字节，不拥有数据，是借别人的。函数参数写成 `&[T]`，数组和 `Vec` 都能传进来。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] safetensors 取出一个张量的那一行说明了什么？——`data: &self.data[info.data_offsets.0..info.data_offsets.1]`。对 embedding 表它是一个 16 字节的值，指针指向数据区开头，长度 1,089,994,752，1.09 GB 的权重一个字节都没复制；库文档里的用法是把整个文件 mmap 进内存，所以这段数据甚至还没从磁盘读进来。`shape` 用 `Vec<usize>`，是因为维数运行时才知道所以不能是数组，`TensorInfo` 又要自己保存它所以不能是借来的切片。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 切片表示不了什么？——它只能表示连续的一段。步长视图 `a[::2]` 和多维视图表示不了，NumPy 的视图为此多带了 strides。（来源：`msg-4e7e07c8eb9203af5dd6`。）

## struct、布局与节点 3–4 检查

- [要点] struct 的三种写法各用在哪里？——带字段名的是常规情况。元组结构体如 `struct Pair(i32, f32);` 用在字段含义一目了然、或者只包一个值来得到一个新类型的时候，后者叫 newtype，`WorkerId(u32)` 占 4 字节，和 `u32` 一样大但不会和别的 `u32` 混用。单元结构体 `struct Unit;` 没有字段，占 0 字节，只需要一个类型名的时候用。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 构造和嵌套 struct 有哪些规则？——构造必须写全，漏一个字段是 E0063，不存在未初始化的字段。变量名和字段名相同时可以简写成 `Person { name, age }`；`Point { x: 10.3, ..another_point }` 让没写的字段取自另一个值。嵌套是内嵌：`Rectangle` 里的两个 `Point` 直接挨着放，共 16 字节，中间没有指针，这和 C 一样，和 Python 的对象引用不同。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] Rust 默认怎样摆 struct 的字段，为什么敢重排，代价是什么？——`struct Plain { a: u8, b: u32, c: u8 }` 按 C 的规则是 a 在 0、b 在 4、c 在 8，共 12 字节；Rust 默认把它排成 b 在 0、a 在 4、c 在 5，共 8 字节。C 的字段顺序是和外界的约定，编译器不能动；Rust 默认不做这个承诺，Reference 只保证字段不重叠、各自对齐。代价是默认布局的 struct 不能直接交给 C，也不能把内存里的字节原样写进文件再指望别的程序读回来；需要固定布局时加 `#[repr(C)]`。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 字段公开与否怎样成为设计的一部分？——`TensorInfo` 的三个字段都标了 `pub`，`TensorView` 的一个都没标。没标 `pub` 的字段，库外面读不到也没法直接构造，只能通过 `TensorView::new(dtype, shape, data)` 得到一个值，而 `new` 会检查 `data` 的长度和 dtype、shape 对得上。所以拿到 `TensorView` 的人可以相信三个字段是一致的。（来源：`msg-4e7e07c8eb9203af5dd6`。）

- [要点] 把 `TensorView` 的 `data` 从 `&[u8]` 换成 `Vec<u8>`，或者拆成 `ptr: &u8` 和 `len: usize`，各失去什么？——学习者答：`Vec` 的数据在堆上，“从权重文件中读取就会导致复制一份到堆上”，对 1.09 GB 的 embedding 开销很大；拆成两个字段“就变成和C的做法一样”，长度和指针是否匹配“只能看调用方了”。两条都对。助手补了后一条可以说得更重：`&u8` 是指向一个字节的引用，安全代码里根本没法拿它去读后面的字节。（来源：`msg-2450b13b0da7ae696c41`、`msg-18a7160c822873723b89`。）

- [纠错] 场景：节点 3–4 检查，`data` 字段改成 `[u8; 1089994752]` 会失去什么。我说“这样就写死了长度，如果换一个模型，长度变了就会类型不匹配报错。”→ 正确：只答到一半。问题比“换模型”来得更早：同一个文件里 82 个张量大小各不相同，而且读完文件头才知道，数组长度却必须是编译时的常数。更重的一条是这 1.09 GB 就装在 `TensorView` 这个值里，造它要把数据复制进来，本机 8 MB 的栈也放不下。原因：数组的值就是元素本身，中间没有指针。（来源：`msg-2450b13b0da7ae696c41`、`msg-18a7160c822873723b89`。）

- [要点] Rust 把默认布局的记录原样写进文件，由 C 程序按声明顺序读，会出什么问题，怎么修？——学习者答：Rust 的默认布局会调整字段顺序，`start` 很可能被排到开头，C 按 `dtype`、`start`、`flag` 的顺序读就会出错，而 Rust 自己写、自己读用的是同一种布局，所以测不出来；加 `#[repr(C)]` 固定布局，修完之后 struct 变大，从 16 字节变成 24 字节。全部正确，两个数与本机实测一致。（来源：`msg-2450b13b0da7ae696c41`、`msg-18a7160c822873723b89`。）

- [高价值问题] “胖指针多带的一个字就是长度吗？还是说这里的切片将多带的一个字定义为了长度，而不是每个胖指针多带的一个字都是长度？”——不总是长度，它是什么由指针指向的类型决定。大小编译时就知道的类型，指针一个字就够；大小要到运行时才知道的类型，指针得把缺的那份信息带上。Reference 列了三种：指向切片 `[T]` 带元素个数，指向 `str` 带字节数，指向 `dyn Trait` 带虚表的地址。`Box` 遵守同一条规则，`Box<u8>` 是 8 字节，`Box<[u8]>` 是 16 字节。（来源：`msg-2450b13b0da7ae696c41`、`msg-18a7160c822873723b89`。）

- [要点] Rust 和 C++ 把虚表指针放在哪里，差别带来什么？——C++ 把虚表指针放在每个对象的开头，Rust 把它放在指针里。所以一个 `i32` 平时还是 4 字节，不用为了能被这样调用而多存一个指针。（来源：`msg-18a7160c822873723b89`。）

## enum 与 match

- [要点] enum 是什么，变体的载荷有哪三种写法？——它定义一个“几选一”的类型，值在任一时刻恰好是其中一个变体，内存里是标签加载荷。载荷的写法和 struct 的三种一一对应：不带数据的 `PageLoad`，像元组结构体的 `KeyPress(char)`，带字段名的 `Click { x: i64, y: i64 }`。C 的 `enum` 只有标签，带数据要自己配一个 `union`；C++ 的对应物是 `std::variant`；Python 3.10 的 `match … case` 语法上最像，但不检查有没有漏。（来源：`msg-18a7160c822873723b89`。）

- [要点] `match` 有哪三条规则？——每个分支是“模式 `=>` 表达式”，模式里的名字在匹配成功时绑到载荷上，只在这个分支里可用。必须穷尽，漏一个变体是编译错误 E0004，`_ => …` 是匹配其余所有情况的兜底分支。`match` 是表达式，有值，一个函数体可以整个就是一个 `match`。（来源：`msg-18a7160c822873723b89`。）

- [要点] 几种常见 enum 的值各占多少字节，规律是什么？——`Device { Cpu, Cuda(u32) }` 是 8 字节，标签 4 加载荷 4，`Cuda(3)` 是 `01 00 00 00 03 00 00 00`。`Option<u32>` 也是 8 字节。`Option<&i32>` 和 `Option<Box<T>>` 是 8 字节，没有额外的标签。教程的 `WebEvent` 是 24 字节，和最大的变体 `Paste(String)` 一样大。只有不带数据的变体的 `Number` 是 1 字节。规律是大小等于最大的变体加标签，再按对齐凑整；编译器找得到永远不会出现的取值时，就把标签藏进去。（来源：`msg-18a7160c822873723b89`。）

- [要点] 不带数据的 enum 和整数怎样互相转换？——所有变体都不带数据时，enum 就是一个整数，默认从 0 开始，`Number::One as i32` 是 1，也可以自己指定值。只能单向转：enum 转整数用 `as`；整数转 enum 不行，`1i32 as Number` 是 E0605，因为不是每个整数都对应一个变体。（来源：`msg-18a7160c822873723b89`。）

- [要点] 类型别名和 newtype 有什么不同？——`type Km = f64;` 只是同一个类型的另一个名字，值能直接当 `f64` 用，对应 C 的 `typedef`。`struct Meters(f64);` 是一个新类型，它的值不能当 `f64` 用。两者正相反。另外 `Self` 在 `impl` 块里指正在实现的这个类型。（来源：`msg-18a7160c822873723b89`。）

- [要点] C 的“标签加联合”有哪三个洞，Rust 怎样逐个堵上？——标签和载荷可以不一致：把标签改成“点击”，载荷还是按键 `'x'`，读出来是 `clicked at x=120, y=0`，没有任何警告。`switch` 漏分支只有开了 `-Wall` 才有警告。任何整数都能当枚举值，`enum Kind k = 42;` 能编译。Rust 的做法是：载荷只能在 `match` 的对应分支里拿到；漏分支是编译错误；整数不能 `as` 成 enum。（来源：`msg-18a7160c822873723b89`。）

- [要点] 穷尽性检查最大的用处是什么，enum 这套设计的两条代价是什么？——最大的用处在改代码的时候：给 enum 加一个变体，所有逐个列出变体的 `match` 都会报错，等于编译器给了一张“还有哪些地方要改”的清单。代价之一是每个值按最大的变体占空间，一个 `PageLoad` 也是 24 字节。代价之二是 `_` 会把那张清单关掉：加变体后带 `_` 的 `match` 照常编译，新变体被悄悄归进“其余”。（来源：`msg-18a7160c822873723b89`。）

- [要点] Rust 的 enum 和 C++ 的 `std::variant` 比怎么样？——两者都把标签和载荷绑在一起。`std::visit` 漏分支同样编译不过，但报的是一长串模板错误。`std::get<Paste>` 取错了成员要到运行时才抛 `bad_variant_access`。大小上，本机 `std::variant<PageLoad, KeyPress, Paste>` 是 40 字节，比最大的成员 `std::string` 多 8 字节；Rust 的 `WebEvent` 和它最大的成员一样大。（来源：`msg-18a7160c822873723b89`。）

- [要点] `#[non_exhaustive]` 做了什么取舍？——safetensors 的 `Dtype` 有 22 个不带数据的变体，库内的 `bitsize` 是一个 22 个分支、没有 `_` 的 `match`，以后加一种 dtype 而忘了写位数，库自己就编译不过。定义上的 `#[non_exhaustive]` 则要求库外的代码对它做 `match` 时必须写 `_`，这样库加新 dtype 不会让使用者的代码编译失败。它把“要清单”和“要兼容”按库内、库外分开处理了。（来源：`msg-18a7160c822873723b89`。）

- [要点] 带数据的 enum 在真实代码里是怎样用的？——`atom/mesh` 的 `WorkerType { Regular, Prefill { bootstrap_port: Option<u16> }, Decode }`：只有 Prefill worker 才有 bootstrap 端口，所以端口放在 `Prefill` 变体里，而不是给所有 worker 一个可能没用的字段。标准库里 `Ordering` 是不带数据的，`IpAddr { V4(Ipv4Addr), V6(Ipv6Addr) }` 带数据。enum 的变体集合是封闭的，库外的人不能给它加变体，要开放扩展用 trait。（来源：`msg-18a7160c822873723b89`。）

## 递归类型与 Box

- [要点] 递归类型为什么必须隔一层 `Box`？——Rust 的值就是数据本身，enum 的载荷也放在值里面。写成 `Cons(u32, List)`，一个 `List` 里就要放下另一个完整的 `List`，大小等于 4 加它自己的大小，无解，编译器报 E0072 并建议插入 `Box`。写成 `Cons(u32, Box<List>)`，里面放的是 8 字节的指针，大小和它指向什么无关，教程的 `List` 是 16 字节。C 也一样必须写成 `struct Node *next`，差别是 C 的指针可以为空、可以悬空、要手工释放。（来源：`msg-18a7160c822873723b89`。）

- [要点] 教程链表示例里的 `self`、`&self`、`*self` 和 `ref` 各是什么意思？——`prepend(self, elem)` 的参数是 `self`，把原来的链表整个拿走，所以 `main` 里写的是 `list = list.prepend(1);`。`len(&self)` 只是借来看；`match *self` 里的 `*` 取出引用指向的那个 `List`，相当于 C 的 `*p`；`ref tail` 让 `tail` 成为指向载荷的引用，而不是把载荷拿走。现在可以直接写 `match self { Cons(_, tail) => …, Nil => 0 }`，编译器自动按引用处理，新代码用这种。（来源：`msg-18a7160c822873723b89`。）

- [要点] `Box` 的代价是什么，它除了递归类型还常用在哪里？——代价是一次堆分配，访问时多跳一次。换来的是大小固定，被指的东西可以很大而指针很小。所以它常用来给 enum 减肥：`atom/mesh` 的任务队列 `Job` 把大的配置对象写成 `AddWorker { config: Box<WorkerConfigRequest> }`，每个 `Job` 里只留 8 字节的指针。代码如此，这样做是为了让队列里的每个 `Job` 都不大，这个动机是助手的推断。（来源：`msg-18a7160c822873723b89`。）

- [要点] 教程的链表写法放到实际代码里有什么问题？——每条链表要多分配一个只装 `Nil` 的节点，更常见的写法是 `struct Node { elem: u32, next: Option<Box<Node>> }`，`Option<Box<Node>>` 只有 8 字节。递归还要吃栈：本机栈 8 MB，100 万个节点时调试构建下 `len()` 栈溢出，释放这条链表在两种构建下都栈溢出，因为释放是一层套一层进行的。实际代码里存一串元素几乎总是用 `Vec`。（来源：`msg-18a7160c822873723b89`。）

## 作答前的追问：字符串、Box、模式、标签与 Option

- [高价值问题] “"héllo" 只有 5 个字符，为什么字节数是6？”——因为 `é` 这一个字符占 2 个字节。Rust 的字符串统一按 UTF-8 存，不同的字符占 1 到 4 个字节：ASCII 是 1，带重音的拉丁字母是 2，汉字是 3，emoji 是 4。`&str` 第二个字里存的是字节数，`s.len()` 返回 6，字符数要用 `s.chars().count()` 数，得 5。单独的 `char` 按最宽的情况留了 4 字节，字符串里不这样存。（来源：`msg-27d57faffa1543ffb25e`、`msg-d358e54430078c027be9`。）

- [要点] 字符串按 UTF-8 存，给下标带来哪些限制？——`s[1]` 编译不过，报 E0277：第 1 个字符从哪个字节开始要从头数才知道，Rust 不提供一个看起来很快、实际要扫描的下标。按字节范围切可以，但要切在字符边界上，`&s[0..2]` 会从 `é` 中间切开，运行时 panic。要第几个字符就用迭代器，`s.chars().nth(1)` 得到 `Some('é')`。（来源：`msg-d358e54430078c027be9`。）

- [转折] “Box是什么？这个也是后面才会讲的内容吗？”——助手核对后承认：`Box` 就是本课节点 6 的内容，但讲胖指针时已经先用了它，比解释它的地方早了两节，顺序排反了。随后先给了一个够用的模型。这是“名词先解释再使用”这条约定在第 02 课的一次违反；同一轮追问里，`Option` 和 `Some` 也是先用后讲，见下面的两条纠错。（来源：`msg-4fef151f903b7584c21a`、`msg-3fe9f3a2fe48464bf763`。）

- [要点] `Box<T>` 够用的最小模型是什么？——它是一个指针，指向堆上的一个 `T`，并且独占这个值，由它负责释放。它本身只是一个地址：`Box<u32>` 是 8 字节，`Box<[u64; 100]>` 也是 8 字节，而 `[u64; 100]` 本身是 800 字节。它不会是空。它所在的 `{}` 结束时，堆上的值跟着释放，恰好一次。`let c = b;` 是把它交给 `c`，之后再用 `b` 报 E0382；C++ 里 `std::move(p)` 之后再写 `*p` 能编译，本机运行时段错误。（来源：`msg-3fe9f3a2fe48464bf763`。）

- [转折] 学习者的追问让助手更正了自己的说法。——节点 5 的讲义写“读取只能用 `match`”。学习者问：“那对于所有枚举的东西，我都需要且只能通过match来进行处理吗？”助手回答“不是”，承认上一条说窄了，准确的规则是：要拿到载荷，必须经过一个写明变体的模式；`match` 只是最完整的一种写法。（来源：`msg-628ca6d2269a6b28b9b9`、`msg-c6ac97c7a326c1225271`。）

- [要点] 拿 enum 的载荷有哪几种写法，各用在什么时候？——每个变体分别处理，或者希望以后加变体时被编译器提醒，用不带 `_` 的 `match`。只关心一个变体用 `if let WebEvent::KeyPress(c) = &e { … }`。不是这个变体就提前返回用 `let WebEvent::KeyPress(c) = &e else { return; };`。只要一个布尔结果用 `matches!(e, WebEvent::KeyPress(_))`。后三种简写都不做穷尽检查，相当于 `match` 里写了 `_`：加一个新变体后代码照常编译，新变体被悄悄跳过。（来源：`msg-c6ac97c7a326c1225271`。）

- [要点] 为什么不提供 `e.0` 这种直接取载荷的写法？——一个 enum 值里有哪些字段，取决于运行时它是哪个变体，`e.0` 里没有地方写“我认为它是哪个变体”。编译器只剩两条路：不检查，这就是 C 的 union，读错了没人知道；或者运行时偷偷检查，不对就崩，而代码上看不出这里可能崩。Rust 两条都不走，要求把“判断是哪个变体”和“取出数据”写成一步，这一步就是模式。（来源：`msg-c6ac97c7a326c1225271`。）

- [要点] `Option` 的 `unwrap` 和 `is_some` 内部是什么？——仍然是模式。标准库里 `unwrap` 的函数体是一个两分支的 `match`，`is_some` 只有一行 `matches!(*self, Some(_))`。`unwrap` 的意思是“我断定它是 `Some`，不是就让程序崩”，对 `None` 调用时 panic，信息是 ``called `Option::unwrap()` on a `None` value``。（来源：`msg-c6ac97c7a326c1225271`。）

- [要点] 真实代码里 `match` 和它的简写各用多少？——`atom/mesh/src` 的 185 个 `.rs` 文件按 grep 粗略数，`match` 和 `if let` 各约 520 处，`matches!` 约 90 处，`let … else` 约 40 处，简写和 `match` 一样常用。`core/worker.rs` 里连着的两段正好是两种选择：给每种 worker 起名字的那段逐个列出，以后加一种会报错；取端口的那段只有 `Prefill` 有端口，其余用 `_`。（来源：`msg-c6ac97c7a326c1225271`。）

- [高价值问题] “总而言之就是必须要检查对吧？”——对。检查省不掉，但检查不通过时怎么办由你选：`match` 是每种情况都处理，`if let` 是其余的忽略，`let … else` 是提前返回，`unwrap` 是直接崩。只有拿载荷才需要检查，把整个值传走、存起来、打印都不用。检查本身发生在运行时，就是读一下标签再比较；编译器在编译时做的事，是保证每个取载荷的地方都有这次检查。（来源：`msg-2df933d3a6af018df4e7`、`msg-e80fbb7ce966aa268f61`。）

- [高价值问题] “标签就是C中枚举的整数，载荷就是rust引入的给变体添加的数据。是吗？”——两句都对。补充是：C 里任何整数都能塞进枚举变量，Rust 的标签只会是声明过的那几个变体。载荷 C 里也能带，做法是自己在枚举旁边配一个 `union`；Rust 新加的是把两者做成一个类型并且绑死，标签说是哪个变体，载荷就只能按那个变体读。（来源：`msg-bd6afa4a70c63fecd4e7`、`msg-b1dd9bf95ed9f6464f3c`。）

- [高价值问题] “这个例外是什么意思？说的明白一些。”——指标签不一定单独占字节。`u32` 的每一种取值都是合法的数，没有哪个能空出来表示“没有”，所以 `Option<u32>` 要另外放一个标签，是 8 字节，`Some(0)` 是 `01 00 00 00 00 00 00 00`。`Box` 里存的是一个一定有效的堆地址，永远不会全是 0，编译器就把 0 分给 `None`，`Option<Box<u32>>` 还是 8 字节。规则是通用的：`bool` 只用 0 和 1，所以 `Option<bool>` 只占 1 字节，`None` 是 `02`。（来源：`msg-19e044c3673836939a01`、`msg-fb6afd372b4ec87db9df`。）

- [要点] `Option<Box<T>>` 和 C 的可空指针是什么关系？——内存里一模一样，`NULL` 表示没有。差别只在类型上：C 的指针可以不判空直接用，`Option<Box<u32>>` 必须先过模式才能拿到里面的 `Box`。这种省标签的做法对写代码没有影响，照样要先确认变体。（来源：`msg-fb6afd372b4ec87db9df`。）

- [纠错] 场景：听完“标签就藏在载荷用不到的取值里了”这个例外之后理解 `Option<u32>`。我问“你的意思是定义了一个枚举类型，其中某一个标签带的载荷的类型是Option<u32>？”→ 正确：`Option<u32>` 本身就是那个枚举类型，不是别的枚举里的载荷；它有两个变体，`None` 不带载荷，`Some` 的载荷是一个 `u32`。带载荷的是变体，不是标签，标签只是记录“是哪个变体”的那个整数。原因：助手一直直接拿 `Option` 举例，没有把它拆开讲；标准库的定义是 `enum Option<T> { None, Some(T) }`，尖括号里填具体类型。（来源：`msg-aa5559b9f8fed182468f`、`msg-87ee5451fbf38ff76d11`。）

- [纠错] 场景：接着上一问。我问“Some又是什么？是Option定义的标签？”→ 正确：`Some` 是 `Option` 定义的两个变体之一，另一个是 `None`；标签是内存里记录“现在是哪个变体”的那个整数，`Some` 对应的标签是 1。原因：`Some` 之于 `Option`，就是 `Cuda` 之于 `Device`；`Some(7)` 看起来像函数调用，其实是在造这个变体的值，和 `Device::Cuda(3)` 是同一种写法。不用写 `Option::` 前缀，是因为标准库替每个程序预先 `use` 了 `Some` 和 `None`。（来源：`msg-b4782e76a907e549fa87`、`msg-c4081539b69c71352a9c`。）

- [要点] 为什么要用 `Some` 包一层，这和 Python 有什么不同？——`u32` 和 `Option<u32>` 是两个不同的类型，前者一定有一个数，后者可能没有。不包不行，`let x: Option<u32> = 7;` 报 E0308；不拆也不行，`x + 1` 报 E0369。Python 里有值的情况不用包，所以也没有东西拦着你对一个可能是 `None` 的变量直接做 `x + 1`。（来源：`msg-c4081539b69c71352a9c`。）

## 作答前的追问：Box 与 &mut

- [高价值问题] “Box和& mut的区别是什么？”——两个都是 8 字节的指针，都能改指向的值，同一时刻也都只有它一个能碰那个值。区别在值归谁：`Box<T>` 拥有它指向的值，值在堆上，`Box` 用完值就释放，它可以从函数返回、存进 struct。`&mut T` 只是把别人的值临时借来改，值在哪里都行，用完什么都不发生，而且不能比原主存在得久。两者不是二选一，`add_one(&mut *b)` 就是把 `Box` 里的值借出去改。（来源：`msg-52765f8e00fcc6d95af5`、`msg-f8d38d56ed32a796bc74`。）

- [要点] `Box` 和 `&mut` 的区别在哪两处看得出来？——函数里造的值，`Box` 能带出来，`&mut` 不能：返回局部变量的 `&mut` 报 E0106，因为借的东西必须有主；C 里这样写只有一个警告，本机运行时段错误。借出去期间，原主自己也不能碰：引用还在用的时候写 `a += 1;` 报 E0503，同时再借一次报 E0499。（来源：`msg-f8d38d56ed32a796bc74`。）

- [要点] 为什么链表的节点用 `Box`，而 `fmt` 的参数用 `&mut`？——链表里“剩余部分”必须有主：用 `Box`，每个节点拥有下一个节点，头节点释放时整条链跟着释放；写成 `&mut List`，被指的节点就得归链表之外的某个东西。`fmt` 的 `f: &mut fmt::Formatter` 是调用方的，借给你往里写，写完归还，你不负责释放它。选择的依据是：值需要一个主人并且要放在堆上用 `Box`，常见于字段；值已经有主、只是让别人临时改一下用 `&mut`，常见于函数参数。（来源：`msg-f8d38d56ed32a796bc74`。）

- [高价值问题] “是生命周期上的区别是吗？&mut借来用，“释放”动作还是由原主来管是吧？如果借出去了的时候，原主被销毁了，那么借出去的这个也会被释放吗？”——前两句都对，生命周期是结果，根源是值归谁。第三种情况在 Rust 里写不出来：借出去的不是另一份东西，`&mut` 只是原主那个值的地址，原主销毁之前借用必须已经结束。原主的作用域先结束报 E0597，手动 `drop` 原主之后还用引用报 E0505。借用的结束点是引用最后一次被使用的地方，不一定是 `}`。（来源：`msg-d36957431b4974d30447`、`msg-f5e79a41191663f194e6`。）

- [要点] 原主销毁后还用指针，在 C 和 C++ 里会怎样？——C 里 `free(b)` 之后 `*p += 1`，不加选项没有任何提示，加 `-Wall` 才有警告。C++ 里 `b.reset()` 之后通过引用写，`-Wall -Wextra` 没有任何提示。两个程序本机都没崩，只是悄悄读写了已经释放的内存，打印出垃圾值。Rust 把这类错误挪到了编译期。（来源：`msg-f5e79a41191663f194e6`。）

## 节点 5–6 检查

- [要点] 用一个带 `kind: u8` 的 struct 表示请求的四种状态，允许了哪些不该出现的值？——学习者答：“同事的这种写法会导致状态上出现不该有的信息。比如已完成状态却有错误信息变量，排队中却有total总token数变量。”这一类答对了。助手补了更直接的另一类：`kind` 本身是 `u8`，可以是 7，而 7 不对应任何状态。实际出事常在状态切换时，比如失败后重试，`kind` 改回 0，`error` 里还留着上次的信息。（来源：`msg-50e2ef249332a7e1ee3c`、`msg-13c2837161134f04e441`。）

- [要点] 学习者把四种状态改写成的 enum 是什么样，还能怎样改进？——学习者写的是 `Queuing(u64)`、`Running(u32, u32)`、`Finished(u32)`、`Failed(String)`，并说明读失败原因必须先检查状态，如 `RequestState::Failed(s) => …`。它能编译，本机 24 字节，同事的 struct 是 48 字节。改进点是 `Running(u32, u32)` 的两个位置类型相同，写反了编译器发现不了，这种情况用带字段名的变体 `Running { worker: u32, generated: u32 }`。（来源：`msg-50e2ef249332a7e1ee3c`、`msg-13c2837161134f04e441`。）

- [纠错] 场景：节点 5–6 检查，以后加一种状态“已取消”，带 `_` 的 `match` 会发生什么。我说“而如果带有_的match，也至少有了兜底的处理方法。”→ 正确：`_` 的兜底是在新状态出现之前写的，对新状态不一定对，而且编译器不再提醒。原因：本机试了一个判断“请求是否还在进行”的函数，写成“完成和失败返回 `false`，`_` 返回 `true`”，加入“已取消”后照常编译，已取消的请求被判成还在进行；逐个列出的写法在同一处报 E0004。（来源：`msg-50e2ef249332a7e1ee3c`、`msg-13c2837161134f04e441`。）

- [纠错] 场景：节点 5–6 检查，`enum Tree { Leaf(u32), Node(Box<Tree>, Box<Tree>) }` 一个值多大。我说“值大小由最大的情况两个Box决定。标签4字节+两个Box 2 * 8字节 = 20字节。”→ 正确：“由最大的变体决定，和树有多深无关”是对的，数字是 16。按规则算也不是 20 而是 24，大小要凑成对齐 8 的整数倍；实际是 16，因为 `Box` 不会是 0，编译器用“第一个指针的位置是 0”表示 `Leaf`，`Leaf(7)` 的前 8 字节全 0，7 放在后面。原因：漏了按对齐凑整，也没有用上刚问过的那个“例外”，而我在同一题的 (c) 里把 `Option<Box<Chunk>>` 算成 8 字节时用的正是这一条。（来源：`msg-50e2ef249332a7e1ee3c`、`msg-13c2837161134f04e441`。）

- [要点] `struct Chunk { data: [u8; 1024], next: Option<Box<Chunk>> }` 一个值多大？——学习者答 1024 加 8 共 1032 字节，正确。这一条同时说明上一轮留下的“数组的值就是元素本身”已经掌握。不加 `Box` 的 `Node(Tree, Tree)` 不能编译，学习者的理由是“载荷变成了自身，递归嵌套了”，大小无穷，也正确。（来源：`msg-50e2ef249332a7e1ee3c`、`msg-13c2837161134f04e441`。）

- [高价值问题] “噢enum里载荷还能带名字啊。请你把带字段名的变体的RequestState以及Tree { Leaf(u32), Node(Box<Tree>, Box<Tree>) } 的内存布局情况添加到图解页对应位置里。”——图解页的 enum 一节加了这两个类型。字段名只存在于代码里，不占内存，`Running(u32, u32)` 和 `Running { worker, generated }` 两种写法本机都是 24 字节。`RequestState` 里 `Failed { error: String }` 占满 24 字节，其余三个变体的标签借用了 `String` 容量用不到的取值。（来源：`msg-0cf7fc085bd0aa95fb68`、`msg-a8130ec5db55a3d85d23`。）

## 对齐规则

- [纠错] 场景：在图解页上看了几个类型的字节之后。我问“我发现这些内存都是对齐8的。所以大小都是对齐8吗？”→ 正确：不是。对齐是 8 的只是含有指针、`usize` 或 `u64` 的类型，最近看的几个类型恰好都含有这些。规则是三条：每个基本类型有自己的对齐，一般等于它的大小；复合类型的对齐等于它的字段里最大的那个对齐；大小是对齐的整数倍。原因：本机 `struct Rgb { r: u8, g: u8, b: u8 }` 是 3 字节、对齐 1，`struct Pair { a: u16, b: u8 }` 是 4 字节、对齐 2，`Device` 大小碰巧是 8、对齐只有 4，而 `{ a: u8, b: u128 }` 的对齐是 16。（来源：`msg-97462ac8d0e72c5cd74f`、`msg-ce0a1a1c4ca3e7128585`。）

- [要点] 为什么一个类型的大小必须是它对齐的整数倍？——为了放进数组。数组里第 i 个元素在偏移 i × 大小处，大小是对齐的整数倍，每个元素才都落在对齐的地址上。本机 `[Pair; 2]` 的两个元素地址相差 4，`[Rgb; 2]` 的相差 3。（来源：`msg-ce0a1a1c4ca3e7128585`。）

- [高价值问题] “对齐的是最大的字段的基本类型大小是吗？复合类型里面有一个[u32;100]，对齐的是u32，而不是100个u32是吗？”——对，取的是 `u32` 的对齐，数组的对齐等于它元素的对齐，和有多少个元素无关。说法要收紧一点：比的是各字段的对齐，不是大小，对齐会一层层往里传。本机 `struct S { tag: u8, data: [u32; 100] }` 是 404 字节、对齐 4；嵌了两层的 `struct Deep { flag: u8, items: [Pair; 10] }` 是 42 字节、对齐 2。（来源：`msg-93223c9ac10d2cbc4bb7`、`msg-c522c11bdb14556b99a7`。）

- [要点] “基本类型的对齐等于它的大小”是谁的规定？——是平台的规定，不是语言的规定。在 32 位 x86 上，`u64` 是 8 字节，对齐却是 4。所以判断时看对齐，不要拿大小代替。32 位 x86 这一条来自该平台的 C ABI 约定，本机没有试。（来源：`msg-c522c11bdb14556b99a7`。）

## const 与 static、串讲

- [要点] `const` 和 `static` 的区别是什么？——两者都是写在函数外面、全程序可见的有名字的值，区别在有没有固定的内存位置。`const` 是编译期常量，编译器把它的值抄到每个用到它的地方，它自己不占固定的位置。`static` 是一块固定地址的内存，从程序启动存在到程序结束，全程序只有一份，在可执行文件自带的数据区里。对照是 C++ 的 `constexpr` 和全局变量。（来源：`msg-13c2837161134f04e441`。）

- [要点] `const` 和 `static` 有哪些共同的规则？——必须写类型，不能让编译器推断。初始值必须在编译时就能算出来，调用普通函数报 E0015，字面量、算术和 `const fn` 可以。不能赋值，对 `const` 赋值报 E0070，对 `static` 赋值报 E0594。名字按约定全大写。`const` 可以用在要求编译时已知的位置，比如数组长度，而 `let n = 5; [0u8; n]` 报 E0435。（来源：`msg-13c2837161134f04e441`。）

- [要点] `const` 和 `static` 怎么选，全局可变状态怎么做？——默认用 `const`。Reference 列了三种该用 `static` 的情况：数据量大，不想每个使用处各抄一份；需要一个唯一的地址；需要全局的、会被修改的状态。可变的 `static mut` 直接改报 E0133，必须写在 `unsafe` 块里，实际代码不用它，而是给 `static` 一个原子类型，如 `atom/mesh` 的 `static ACTIVE_HTTP_CONNECTIONS: AtomicU64 = AtomicU64::new(0);`。这个项目按 grep 有 143 个 `const`、27 个 `static`、0 个 `static mut`。（来源：`msg-13c2837161134f04e441`。）

- [要点] safetensors 读一个分片的过程怎样把七个节点串起来？——整个文件是一个 16 字节的 `&[u8]`。`buffer.get(..N_LEN)` 配 `let … else` 取出文件头长度，文件不足 8 字节时得到 `None`，其中 `N_LEN` 是一个 `const`。这个数来自文件不可信，先和 `MAX_HEADER_SIZE` 比，再用 `checked_add` 算结束位置。9,368 字节的 JSON 变成 82 个 `TensorInfo`，逐个校验时用 `checked_mul` 和 `Dtype::bitsize` 的 `match`。最后 `&self.data[s..e]` 切出张量装进 48 字节的 `TensorView`，数据一个字节都没复制。（来源：`msg-13c2837161134f04e441`。）

- [要点] 这一课反复出现的三件事是什么？——信息放在类型里还是带在值里：`[u8; 8]` 的长度编译时就知道，`&[u8]` 的长度运行时才知道。值是数据本身还是隔一层指针：struct、数组、enum 的载荷都直接内嵌，切片、`Box`、`Vec` 里放的是指针，前者省一次跳转，后者让大小固定。C 里靠约定的事 Rust 写进了类型，由编译器或运行时的检查来保证，代价是运行时多几次检查，代码里多写几个分支。（来源：`msg-13c2837161134f04e441`。）

## 综合验收

- [纠错] 场景：综合验收口述，C 的 `(指针, 长度)` 和可空指针在 Rust 里对应什么、多保证了什么、代价是什么。我说“代价是增加了更多编译器检查。”→ 正确：编译期的检查不花运行时间，真正的代价有两样：运行时的边界检查，每次 `data[i]` 都要比较一次；以及必须写出来的分支，`None` 的情况不处理就拿不到数据。原因：我答对的部分是对应 `&[u8]` 和 `Option<&[u8]>`、指针不会为 0 所以仍是 16 字节、长度与地址绑定、“没有”不再靠约定；题里那个单独的可空指针 `T *p` 对应 `Option<&T>` 或 `Option<Box<T>>`，是 8 字节。（来源：`msg-c96deb5158620d358d83`、`msg-668b8a559c4c4b9c28c6`。）

- [要点] `TokenChunk` 有 `Partial` 和 `Complete` 两个变体，字段合计分别是 48 和 188 字节，一个 `Partial` 值占多少，token id 放在哪？——学习者答：“一个Partial也占Complete全部字段的188字节。但由于还要对齐8，所以还要多4个字节。总共占192字节。”token id 在 `Vec<u32>` 指向的堆上。两点都对，上一轮漏掉的“按对齐凑整”这次用上了。（来源：`msg-c96deb5158620d358d83`、`msg-668b8a559c4c4b9c28c6`。）

- [纠错] 场景：综合验收，想让每个 `Partial` 变小该怎么改 `TokenChunk`。我说“可以尝试将TokenLogprobs、MatchedStop、Usage等自定义的类型用Box取指针，而不是整个类型放在里面。”→ 正确：要缩小的是最大的那个变体。本机三种改法：只把 `Partial` 里的字段装箱，整个 enum 仍是 192 字节；把自定义类型的字段逐个装箱是 136 字节，每个 `Complete` 最多多 4 次堆分配；把 `Complete` 的全部字段整体装进一个 `Box` 是 48 字节，只多 1 次分配。原因：enum 的大小由最大的变体 `Complete` 决定，只动 `Partial` 没有用；`Usage` 只有 12 字节，装箱后指针就占 8 字节还多一次分配，不划算。方向、代价和“成了瓶颈才改”的判断是对的。（来源：`msg-c96deb5158620d358d83`、`msg-668b8a559c4c4b9c28c6`。）

- [要点] 一个用 `_ => false` 兜底的 `is_normal_end`，在 enum 新增了语义上也算正常结束的变体之后会怎样？——学习者答：编译器不会有提示，“因为match里写了_的情况判断”，程序跑起来会把新变体也判成非正常结束；当初应该逐个情况判断，这样增加变体时编译器会要求消费处增加处理，“代价是多写一些啰嗦代码”。全部正确，上一轮留下的“`_` 的代价”复查通过。（来源：`msg-c96deb5158620d358d83`、`msg-668b8a559c4c4b9c28c6`。）

- [纠错] 场景：综合验收预测题，把 `static ACTIVE: AtomicU64` 改成 `const`（程序仍然能编译），两次 `fetch_add(1)` 之后 `load` 打印多少。我说“Const是编译期内联，main里面的两行代码相当于都变成AtomicU64::new(0).fetch_add(1, Ordering::Relaxed)。就做了两次0+1，输出变成1.”→ 正确：输出是 0。原因：“每次使用都是一份新的 `AtomicU64::new(0)`”这个机制我说对了，漏的是第三行，`ACTIVE.load(…)` 也是一次使用，读的是又一份新的 0；前两份各自加到 1，然后就被丢掉了。（来源：`msg-c96deb5158620d358d83`、`msg-668b8a559c4c4b9c28c6`。）

- [高价值问题] “把 Complete 的全部字段整体装进一个 Box是怎么做到的？”——分两步：先把 `Complete` 的字段原样搬进一个单独的 struct，比如 `CompleteData`，再让这个变体只带一个指向它的 `Box`，写成 `Complete(Box<CompleteData>)`。必须先有 struct，是因为 `Box<T>` 的尖括号里要填一个类型，而变体本身不是类型，写 `Box<X::A>` 报 E0573。`Complete` 的数据没有变小，只是搬到了堆上，值里只留 8 字节的指针；读取时 `data.usage` 里的 `.` 会自动穿过 `Box` 去取字段。（来源：`msg-016aa475ea98c2e531a5`、`msg-2c2d15636e81e61cdbf0`。）

## 练习：约定、求助与 Review

- [高价值问题] “transpose需要原地修改转置还是转置成一个新矩阵？”——转置成一个新矩阵并返回。签名 `transpose(matrix: Matrix) -> Matrix` 已经定了这一点：参数按值传入，结果通过返回值交出去；`Matrix` 的定义上有 `Clone, Copy`，传进函数时是复制了一份，调用方手里的矩阵不受影响。原地修改会是另一种签名 `fn transpose(matrix: &mut Matrix)`。助手承认约定里“变成”这个词有歧义。（来源：`msg-6501e3fb24f8bc8e3f6e`、`msg-de8b0bd4128c15aa097c`。）

- [纠错] 场景：练习里 `a5_byte_len` 的一项失败，期望 `None`，实际得到 `Some(18446744073709551608)`。我说“我在byte_len方法最后写了checked_mul了，不明白为什么还是溢出了”→ 正确：代码没有溢出，`checked_mul` 也在正常工作，失败是因为运算顺序和约定不一样。约定是先乘位数、再除以 8，`usize::MAX / 8` 个 `F64` 元素乘 64 超出 `usize`，应返回 `None`；我写的是先把位数除以 8 再乘，乘 8 没有超出，于是返回了 `Some`。原因：约定按位算是照着真实的 safetensors 定的，它有不足一个字节的类型，`Dtype::F4` 只有 4 位，`bitsize() / 8` 等于 0，整个张量会被算成 0 字节。（来源：`msg-56bf677ab7272d5a4948`、`msg-bf42230613be34976fbf`。）

- [要点] `cargo test` 只显示了一个测试文件的失败，怎样一次看全？——它默认在第一个失败的测试文件处停下，加 `--no-fail-fast` 可以一次看全。发布构建下的测试用 `cargo test --release` 跑。（来源：`msg-bf42230613be34976fbf`、`msg-78cf887d33ff48c1722a`。）

- [高价值问题] “嵌套解构是什么？这个结构体也能解构？”——能。解构就是写一个和值形状相同的模式，一次把里面各部分取出来并起名字：`let Size { w, h } = s;`，改名写 `let Size { w: width, h: height } = s;`，只要一部分写 `let Size { w: only_w, .. } = s;`。嵌套的意思是模式里面再套模式，如 `let TensorInfo { dtype, shape, data_offsets: (start, end) } = info;`。和字段访问比，解构多出一项检查：模式里必须把字段列全，漏了报 E0027，要么补上，要么写 `..` 表示不要。（来源：`msg-2a07e0316f731046e7b8`、`msg-6fd922fe20a4f59d331b`。）

- [转折] Review 发现的两处都被判为约定的问题，而不是学习者的失误。——F1 是 `slice` 把位于缓冲区末尾的空张量拒绝了，比如 28 字节的缓冲区里偏移 `(28, 28)`；助手的测试只在缓冲区中间放了空张量，所以 29 项测不出来。F2 是 `rect_area` 用了字段访问，而交付说明要求嵌套解构，验收表却没有检查。助手把两处都作为约定澄清提出版本 2，并在学习者接受之前不动测试文件。（来源：`msg-412ba83ca0dd176041b8`、`msg-cbdfd5d6bfcce3620c2c`。）

- [转折] 学习者质疑嵌套解构的必要性，这项要求被撤回。——学习者问：“为什么经常说要用嵌套解构获取内部元素呢？嵌套结构比起字段访问有什么优势吗？rect_area 用嵌套解构，还需要预先多一步声明变量，字段访问可以直接开始计算边长了。”助手承认在 `rect_area` 里嵌套解构没有优势，约定这样写只是照搬了教程 Activity 的提示。F2 撤回，`rect_area` 保持原样，嵌套模式的练习挪到 A9 的 `match` 里。（来源：`msg-cf93b007d7d71dd18ae9`、`msg-9fca43ce5d8409733b35`。）

- [要点] 字段访问、解构和嵌套模式各适合什么情况？——带字段名的 struct 读几个字段，用字段访问，名字已经有了。元组和元组结构体用解构，因为 `.0`、`.2` 看不出含义。enum 的载荷只能用模式，字段访问进不去。要同时判断好几层的形状用嵌套模式，它真正的用武之地在 `match` 里。运行时没有实质差别，本机 `-O` 下 `rect_area` 两个版本的指令数是字段访问 7 条、解构 8 条。（来源：`msg-9fca43ce5d8409733b35`。）

- [要点] 嵌套模式怎样把 `match` 套 `match` 压平？——`atom/mesh` 打印 `WorkerType` 的代码是先匹配 `Prefill { bootstrap_port }`，再对端口做一次 `match`。压平后是并列的 `WorkerType::Prefill { bootstrap_port: Some(port) } => …` 和 `WorkerType::Prefill { bootstrap_port: None } => …`。`bootstrap_port: Some(port)` 一次做了三件事：确认是 `Prefill`，确认端口是 `Some`，把端口取出来叫 `port`。穷尽检查照样管用，删掉 `None` 那一行报 E0004。上游用的是第一种写法，两种在真实代码里都常见。（来源：`msg-9fca43ce5d8409733b35`。）

- [要点] `WorkerType` 只有 4 字节，两层判断在内存里记在哪？——合在开头的 2 个字节里：0 和 1 是 `Prefill` 的端口为 `None` 和 `Some`，2 是 `Regular`，4 是 `Decode`。`Option<u16>` 自己的标签只用 0 和 1，编译器把另外两个变体记在了同一个位置上。本机 `Prefill { bootstrap_port: Some(8998) }` 是 `01 00 26 23`。学习者看到压平的写法后说“对于这种多层match的判断就可以一次性优雅地完成”，并要求把这个例子加进图解页。（来源：`msg-b3a5e17e328478215b02`、`msg-40b92ee8c2b4186e0951`。）

## 结课前的答疑：括号、引用与 Copy

- [高价值问题] “写练习的过程中我常常遇到一些问题：1. 有的enum里元素用大括号，有时候用小括号。不知道什么时候该用什么？2. 有的地方用&，有的地方不用。有的地方还要用*。我知道&有借用的含义，但不知道为什么要用*才能取到值。3. 对TensorInfo启用和其他类型一样的#[derive(Debug, Clone, Copy, PartialEq)]时，编译期报错Copy不行。不知道为什么。”——助手说明第 1 个问题属于本课，后两个的系统讲解在第 04、08、10 课；它们的写法练习里必须用到，约定里却只零散提过，这是练习设计的疏漏。三个问题各讲了大概，见下面几条。（来源：`msg-8ffcff81d33b86814591`、`msg-867a1ae035bab5754c0f`。）

- [要点] enum 的变体该用圆括号还是花括号？——用别人的类型时没有选择，定义里是哪种，构造和 `match` 就写哪种。自己定义时这是约定：只有一个数据、看变体名和类型就知道是什么，用圆括号，如 `Cuda(u32)`；两个以上数据，或者光看类型不知道是什么，用花括号，如 `Loaded { device, bytes }`。理由是圆括号里的含义全靠位置，写成 `Click(i64, i64)`，把 x 和 y 写反了编译器也不会报错。两种写法的内存布局相同。（来源：`msg-867a1ae035bab5754c0f`。）

- [要点] `&` 和 `*` 的核心模型是什么？——`u32` 和 `&u32` 是两个不同的类型：前者是数本身，4 字节；后者是一个地址，8 字节，叫引用，相当于 C 的 `const uint32_t *p`，但保证有效、不为空。`&x` 取地址，`*r` 顺着地址读出值，叫解引用。规则只有一条：要的是 `u32`，手里是 `&u32`，就写 `*`。`.` 会自动解引用，所以 `*` 主要出现在传参、返回和构造值的时候。（来源：`msg-867a1ae035bab5754c0f`。）

- [要点] 练习代码里的三处引用各是从哪来的？——`for s in &self.shape` 里的 `&` 表示只借 `shape` 来遍历，所以 `s` 是 `&usize`。`checked_mul(*s)` 的参数要的是 `usize`，去掉 `*` 报 E0308。`Device::Cuda(index) => Some(*index)` 最不直观：`self` 是引用，对着引用做 `match`，拆出来的 `index` 也是引用，整个值是借来的，里面的部分也只能借。`*index` 能读出值，是因为 `u32` 是 `Copy`；对 `&Vec<usize>` 写 `*r` 是想取走整个 `Vec`，报 E0507。（来源：`msg-867a1ae035bab5754c0f`。）

- [要点] `TensorInfo` 为什么不能 derive `Copy`？——`Copy` 是一个标记，意思是“这个类型的值只要把字节照抄一份就算复制好了”，所有字段都是 `Copy`，类型才能是 `Copy`。`Vec<usize>` 的值是指针、长度、容量共 24 字节，元素在堆上；照抄这 24 字节，就有两个 `Vec` 指向同一块堆内存，各自释放一次就是重复释放，所以 `Vec` 不是 `Copy`，编译器报 E0204 并指着 `shape` 这个字段。学习者随后复述“TensorInfo不能Copy是因为里面的shape这个Vec没有Copy”，正确。（来源：`msg-867a1ae035bab5754c0f`、`msg-7237b36187fb0770cd31`、`msg-a5a587d7b5df939cdd1e`。）

- [要点] `b = a` 对一个动态数组，在 C++、Python 和 Rust 里各做了什么？——C++ 的 `std::vector` 悄悄调用复制构造，做了深复制。Python 的 `list` 是两个名字指向同一个列表。Rust 的 `Vec` 是移动，`a` 失效；要一份副本得显式写 `a.clone()`，它新分配一块内存并把元素抄过去。（来源：`msg-867a1ae035bab5754c0f`。）

- [要点] `Eq` 比 `PartialEq` 多了什么，什么时候能加？——`PartialEq` 提供 `==`。`Eq` 不增加任何功能，只是一个承诺：任何值都等于它自己。浮点数做不到，`f32::NAN == f32::NAN` 是 `false`，所以带 `f32` 的类型不能加 `Eq`；只有整数字段的 `Dtype`、`Device`、`TensorInfo` 可以加。用处是标准库有些功能要求 `Eq`，比如做哈希表的键。（来源：`msg-867a1ae035bab5754c0f`。）

- [纠错] 场景：理解 `data.get(start..end)` 和下标 `&data[start..end]` 的区别。我说“所以data.get相比于直接的[start,end]，可以多给出异常情况的检查，异常时返回None是吧？”→ 正确：返回 `None` 对，“多了检查”不对。下标也做同样的检查，区别只在检查不通过之后：下标 panic，`get` 返回 `None`。原因：标准库 `core/src/slice/index.rs` 里 `get` 和 `index` 用的是同一个条件，`end - start` 不溢出且 `end <= len`。范围是自己的程序算出来的、越界说明程序有 bug，用下标；范围来自外部，比如文件头里的偏移，用 `get`。我的 `slice` 先手写了三个比较，等于同一个检查做了两遍。（来源：`msg-7237b36187fb0770cd31`、`msg-a5a587d7b5df939cdd1e`。）

- [要点] 学习者问能否理解成“rust里就没有C++的引用这个东西，只有指针地址”，这个理解对吗？——方向对，要补两点。Rust 的 `&T` 用法像指针，是一个可以存、可以改指向的值：`let mut r = &a; r = &b;` 之后读到的是 `b`，`Vec<&u32>` 能编译；C++ 的 `r = b` 则是把 `b` 的值写进 `a`。但它不是 C 的指针：不能为空，没有指针加减，借出去期间的规则由编译器检查。和 C 完全一样的是裸指针 `*const T`，解引用必须放在 `unsafe` 里。（来源：`msg-7237b36187fb0770cd31`、`msg-a5a587d7b5df939cdd1e`。）

## 结课前的答疑：用 byte_len 走查 & 和 *

- [高价值问题] “最后我想再以一个例子认真过一下&和*这些标记。就以TensorInfo的byte_len方法为例。这里传入参数是&self与传入self有什么区别，对后续使用有什么区别。遍历时in &self.shape和in self.shape又有什么区别？最后*s和s的区别。”——助手给的一句话模型是：每个位置先问“这里放的是东西本身，还是指向它的地址”；写 `&` 是只给地址，写 `*` 是顺着地址读值，什么都不写是把东西本身交出去。三处对比见下面三条。（来源：`msg-9f8845415cb916e79061`、`msg-58cb1ae6194152f0e843`。）

- [要点] 方法的参数写 `&self` 和写 `self` 有什么区别？——`&self` 是 `self: &TensorInfo` 的简写，传进去的是 8 字节的地址，调用之后 `info` 照常可用。`self` 传进去的是 48 字节的值本身，`info` 被移动，方法返回时 `shape` 的堆内存被释放，调用方再用 `info` 报 E0382，在一个 `&self` 的方法里调用它报 E0507。`self` 适合两种情况：方法要把这个值消耗掉，如 `Option::unwrap(self)`；或者类型很小而且是 `Copy`，如 1 字节的 `Dtype`。（来源：`msg-58cb1ae6194152f0e843`。）

- [要点] `for s in &self.shape` 和 `for s in self.shape` 有什么区别，和 C++ 的范围 `for` 一样吗？——带 `&` 时循环每轮给一个元素的地址，`s` 是 `&usize`，循环之后 `Vec` 还在。不带 `&` 是把整个 `Vec` 交给循环，`s` 是 `usize`，循环之后 `Vec` 没了；在 `&self` 的方法里这样写报 E0507，因为 `self` 本身是借来的。这里和 C++ 不一样：`for (size_t s : shape)` 是把每个元素抄一份，`shape` 还在。（来源：`msg-58cb1ae6194152f0e843`。）

- [要点] `info.byte_len()` 和 `self.dtype.bitsize()` 里一个符号都没有，完整写法是什么？——`.` 自动做了两件事。`info.byte_len()` 就是 `TensorInfo::byte_len(&info)`，`.` 替你加了 `&`。`self.dtype.bitsize()` 完整写出来是 `Dtype::bitsize(&(*self).dtype)`：`(*self)` 是顺着 `self` 找到 `info`，外面的 `&` 是因为 `bitsize` 要的是 `&self`。（来源：`msg-58cb1ae6194152f0e843`。）

- [要点] 直接传参默认是移动吗，调用处有哪三种写法？——学习者问“直接穿参默认都是移动语义是吗？”，对，而且不只是传参，`let b = a;`、作为返回值、放进 struct 或 `Vec` 都一样，`Copy` 类型例外。两种情况在机器层面都是把值的字节抄过去，区别只在编译器之后还让不让你用原来那个。调用处的三种写法是 `f(info)` 移动、`f(&info)` 借出、`f(info.clone())` 先造一份副本再把副本移动进去；只是读数据时首选借出。（来源：`msg-7a5ce29ba71a141617f3`、`msg-86cf158320d152286670`。）

- [要点] `for s in self.shape` 把 `Vec` 移动进循环，它的堆内存什么时候释放？——学习者的理解“循环结束就释放了”是对的。精确地说，`Vec` 移动给了循环背后的一个隐藏的值，由它持有那块内存并逐个交出元素，循环结束时这个值被销毁。本机量到 `vec![2, 3]` 的 16 字节堆内存在循环最后一轮还在，循环结束后归零；用 `?` 或 `return` 提前跳出循环时也一样会释放。（来源：`msg-7a5ce29ba71a141617f3`、`msg-86cf158320d152286670`。）

- [要点] `&self.shape` 的完整写法是什么，其中“取字段”这一步复制了东西吗？——学习者自己推出完整写法是 `&((*self).shape)`，正确，`.` 比前缀的 `&` 和 `*` 结合得更紧，和 C 里 `&p->x` 是 `&(p->x)` 相同。要补的是 `(*self).shape` 在这里指的是那个字段所在的位置，不是把它的值读出来，`&` 取的是这个位置的地址，中间没有复制也没有移动。所以 `&self.shape` 在借来的 `self` 上也能写，而 `self.shape` 单独当值用就是移动。（来源：`msg-7a5ce29ba71a141617f3`、`msg-86cf158320d152286670`。）

- [要点] Rust 的 `.` 取代了 C 的 `->` 吗，它还多做了什么？——学习者的这个判断是对的，Rust 取字段和调方法只有 `.`，写 `r->x` 编译器会直接报错并提示 `.` 会自动解引用。它比 `->` 多做两件事：有几层解几层，通过 `&T`、`&&T`、`Box<T>` 都能直接取字段；调方法时自动补 `&`。限制是自动解引用只发生在 `.` 上，传参和运算时仍然要自己写 `*`，裸指针也不会自动解引用。（来源：`msg-7a5ce29ba71a141617f3`、`msg-86cf158320d152286670`。）

- [转折] “我发现rust中有好多简写，这还挺令人迷惑的。”——助手把到目前为止碰到的简写和它们唯一的展开方式列成一张表，并说明只在展开方式唯一的地方才允许省略，深复制和数值类型转换必须写出来。学习者回复“明白了。加进去吧”，这张表进了[《Rust 基础知识》](../attachments/00-rust-basics/rust-basics.html#shorthand)，同时提前补入了本课的 35 个名词。（来源：`msg-d4f4ab88867cbd27083e`、`msg-339f62cef30401af3b7e`、`msg-63c7964ba490c8da0200`、`msg-1a092e383875b239cbf4`。）

- [要点] 看不清一个变量是什么类型时，有什么不依赖工具的办法？——临时把它赋给一个类型明显不对的变量，让编译器告诉你。写一行 `let probe: () = s;`，本机报 E0308：expected `()`, found `&usize`，看完删掉这一行。（来源：`msg-339f62cef30401af3b7e`。）
