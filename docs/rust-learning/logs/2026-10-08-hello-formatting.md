## 开课与全流程骨架

- [要点] 把一个值打印成文字要解决哪两件事，C、C++ 和 Rust 各怎么处理？——一是输出长什么样，二是每种类型怎样把自己变成文字。C 的 `printf` 把前者交给运行期才解析的格式串，后者写死在 `%d`、`%s` 里，对不上照样能编译，自定义类型也接不进来。C++ 的 `cout <<` 靠重载得到了类型安全和扩展，放弃了格式串。Rust 两样都要：宏在编译期读懂格式串，trait 让类型声明“我能这样打印”。（来源：`msg-b5b0b7af51f3f5c8c411`。）

- [要点] 一行 `println!` 从源码到输出经过哪六步？——第 1 步是源码。编译期四步：宏展开（`println!` 变成 `_print(format_args!(…))`）；解析格式串，切成字面文字和占位符并核对个数；按占位符选 trait（`{}` 要 `Display`，`{:?}` 要 `Debug`）并检查参数类型是否实现了它；把格式串变成模板字节，连同参数表装进 `fmt::Arguments`。运行期只有第 6 步：锁住标准输出按模板写，遇到占位符就调用那个类型的 `fmt`。（来源：`msg-b5b0b7af51f3f5c8c411`。）

- [要点] 同一个 hello world，Rust 的可执行文件为什么比 C++ 的大得多？——本机 `rustc` 1.97.1 编出的是 4.35 MB，`g++` 的是 16 KB。差别来自链接方式：Rust 默认把标准库连同调试符号静态链接进来，运行时只依赖 libc。去掉符号后是 343 KB，改成动态链接标准库后是 8.6 KB；C++ 加上 `-static` 也会涨到 2.3 MB。（来源：`msg-b5b0b7af51f3f5c8c411`。）

- [要点] 用 `rustc` 直接编译单个文件时有什么坑？——它默认按 edition 2015 处理，而教程示例按 2021 写，单文件试验要加 `--edition 2021`；用 `cargo` 时 edition 写在 `Cargo.toml` 里，没有这个问题。另外 Rust 的块注释可以嵌套，这一点和 C 不同。（来源：`msg-b5b0b7af51f3f5c8c411`。）

## println! 为什么是宏

- [要点] `println!` 为什么必须是宏，不能是函数？——格式串对不对、参数个数对不对、这个类型能不能这样打印，都要在编译期解决。函数只能拿到运行期的值，拿不到格式串的内容，也拿不到参数的个数和类型；普通的 Rust 函数还没有可变参数和重载。能在编译期运行、看到字面量内容和参数列表的只有宏。（来源：`msg-b5b0b7af51f3f5c8c411`。）

- [要点] 编译器把 `println!("{} days, {:?}", days, Structure(3))` 展开成了什么？——先变成 `::std::io::_print(format_args!("{0} days, {1:?}\n", days, Structure(3)))`。`println!` 只是标准库里一个两条规则的宏，真正读懂格式串的是编译器内建的 `format_args!`。再往下有三件事：参数以 `&days`、`&Structure(3)` 的形式借用，打印不会拿走它们；`{}` 被翻译成 `new_display`、`{:?}` 被翻译成 `new_debug`，类型检查就发生在 `T: Display` 这个约束上；格式串变成 13 个字节的模板，花括号已经不存在了。（来源：`msg-b5b0b7af51f3f5c8c411`。）

- [要点] “少传一个参数”这个错误，在 C、C++ 和 Rust 里各在什么时候暴露？——`printf("%d %s\n", 1)` 在本机 gcc 13.3 下只有一条 `-Wformat` 警告，照样编译通过，运行时输出 `1` 加一串乱码；把格式串放进变量后连警告也没有，那条警告是编译器针对 `printf` 额外做的检查，不是语言的规则。`cout <<` 放弃了格式串，类型安全有了，但“输出长什么样”不再集中写在一处，宽度和精度要靠有状态的操纵符。Rust 和 C++20 的 `std::format` 走同一条路：格式串必须是字面量，少传参数直接是编译错误。（来源：`msg-b5b0b7af51f3f5c8c411`。）

- [要点] Rust 这条路换来了什么、付出了什么？——换来的是：格式和参数对不上的错误不可能留到运行期，运行期也不必再解析格式串。付出的是：格式串必须写死在源码里；每一种打印方式都是一个 trait，类型要逐个实现。（来源：`msg-b5b0b7af51f3f5c8c411`。）

- [纠错] 场景：节点 2 检查第 3 问，假设把它做成运行期才解析格式串的函数，反过来能得到什么灵活性。我说“由于此时编译期不检查个数和类型对不对的上，可以将某些参数以另一种类型的方式进行打印出来。”→ 正确：换来的灵活性是格式串本身可以是运行期的值，来自配置文件、翻译文件或用户输入。原因：同一个值换一种写法（如 `{:x}`）在现在的设计里就能安全做到；把一种类型的字节当成另一种类型来读是未定义行为，不是能力，Python 的运行期方案同样不允许。助手同时说明这一问问得太宽，责任在题目。（来源：`msg-473b8d01e5d6dde85701`、`msg-1a91f55d93237981ffd2`。）

- [要点] “运行期才发现错误”实际上依赖哪两个前提？——一是那一行真的被执行到，写在错误处理分支里的打印语句可能上线很久才第一次运行。二是运行期有专门做检查：Python 做了，`"{} {}".format(1)` 抛 `IndexError`；C 没做，表现为乱码。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 格式要到运行期才确定时，Rust 里怎么办？——交给运行期的模板引擎。真实的例子是 Infera 的 router 依赖 `minijinja`：chat template 是运行时才从模型配置里读到的数据，不可能写成 `format!` 的字面量。占位符写错只能在运行期发现，更稳妥的做法是在启动、读入配置的那一刻就把模板解析一遍并用一条样例记录试着渲染，把错误提前到启动时。（来源：`msg-1a91f55d93237981ffd2`、`msg-6e7cca7d2bf13c4cf1e7`。）

- [要点] `println!` 在使用上有哪三条边界？——格式串必须是字面量，存进变量再传会报 `format argument must be a string literal`。每次调用都要给标准输出加锁，很热的循环里可能成为瓶颈。写失败会 panic，所以输出要交给管道的命令行工具通常改用 `writeln!`，诊断和进度信息用 `eprintln!` 写到标准错误。（来源：`msg-b5b0b7af51f3f5c8c411`。）

## Display 与 Debug

- [要点] 占位符和 trait 是怎样对应的？——标准库定义了 9 个格式化 trait，占位符里冒号后面的内容决定用哪个。`{}` 是 `Display`，只有数字、`bool`、`char`、字符串、`Ipv4Addr` 这类有公认写法的类型才有。`{:?}` 是 `Debug`，标准库里几乎所有类型都有。`{:x}`、`{:X}`、`{:o}`、`{:b}` 是 `LowerHex` 等四个，只对整数开放；`{:e}` 是 `LowerExp`，`{:p}` 是 `Pointer`。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 为什么 `Debug` 可以 derive，`Display` 不行？——`Debug` 的输出有一条不需要理解含义的规则：照着类型的定义，把名字和字段写出来。`Display` 是给用户看的，怎么写取决于含义：路径列表也许该用冒号分隔，数字列表也许该用逗号。同一个 `Vec<T>` 没有对所有元素类型都合适的写法，所以标准库不替你决定，`println!("{}", vec![1, 2, 3])` 报 E0277，`{:?}` 则打印 `[1, 2, 3]`。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 为什么分成 `Display` 和 `Debug` 两个 trait？——读者不同，承诺也不同。`Display` 面向用户，输出算作类型对外行为的一部分。derive 出来的 `Debug` 只供调试，格式不稳定，可能随 Rust 版本变化，不该被程序解析，也不适合写进测试断言或协议。Python 的 `__str__` 和 `__repr__` 是同样的分工。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 同一个字符串用 `{}` 和 `{:?}` 打印有什么差别？——`println!("{} / {:?}", "Bob", "Bob")` 打印 `Bob / "Bob"`。内容换成带制表符的 `"a\tb"`，`{}` 打出一个真的制表符，`{:?}` 打出 `"a\tb"`。`Debug` 把值写成它在源码里的样子，`Display` 写出它的内容。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] `#[derive(Debug)]` 生成了什么，用它时要小心什么？——它生成一个很机械的 `fmt`：写出类型名，再依次写出每个字段的名字和字段自己的 `Debug` 输出，所以每个字段都必须有 `Debug`。它会打印所有字段，结构体里有密钥或令牌时 `{:?}` 进日志就是泄露，这时要手写 `Debug` 只列出想公开的字段；ATOMesh 的 `Router` 就是手写的，用 `f.debug_struct("Router").field(…)` 挑了 4 个字段。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 真实工程里 `Debug` 和 `Display` 各用多少？——ATOMesh 的 `atom/mesh/src` 里有 132 处 derive 了 `Debug`，手写的 `Display` 只有 9 处，多数是状态枚举和错误类型。熔断器的 `CircuitState` 就是 derive `Debug` 加手写 `Display`，用在日志 `info!("Circuit breaker state transition: {} -> {}", from, to)` 里。日常的分工是：几乎每个类型都顺手 derive 一个 `Debug`，只有要给人看的少数类型才手写 `Display`。（来源：`msg-1a91f55d93237981ffd2`、`msg-6e7cca7d2bf13c4cf1e7`。）

- [要点] `println!("{:x}", w.load)`（`load` 是 `f32`）为什么编译不过，想看浮点数的位模式怎么办？——学习者答“因为load是浮点数，与x的整数格式不符”，方向对。更准确的说法是 `{:x}` 需要 `LowerHex`，标准库只为整数实现了它；`f32` 和 `LowerHex` 都属于标准库，自己也不能替它补上。要看位模式先转成整数：`println!("{:x}", 1.5f32.to_bits())` 输出 `3fc00000`。（来源：`msg-9a99fc184540ef850de2`、`msg-6e7cca7d2bf13c4cf1e7`。）

- [要点] 一个没有任何 derive 和 `impl` 的 struct，要让 `{:?}` 和 `{}` 能用，各自最少补什么？——`{:?}` 只要加一行 `#[derive(Debug)]`，前提是每个字段都有 `Debug`。`{}` 不能 derive，必须手写 `impl fmt::Display`。学习者四行能否编译的判断全对，缺的正是这个“最少要补什么”的区别。（来源：`msg-9a99fc184540ef850de2`、`msg-6e7cca7d2bf13c4cf1e7`。）

## 自己实现 Display

- [要点] 手写 `Display` 时，`fmt` 的签名各部分是什么意思？——`&self` 是只读地借用自己，所以打印不会消耗这个值。`f: &mut fmt::Formatter` 是调用方准备好递进来的输出目的地。返回值 `fmt::Result` 是 `Result<(), fmt::Error>` 的别名，成功时没有值，失败时只表示“写不进去了”。函数体里用 `write!(f, …)` 写，它展开为 `f.write_fmt(format_args!(…))`，也就是六步流水线又走了一遍；最后一行不加分号，它的值就是返回值。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 为什么 `fmt` 是往 `f` 里写，而不是返回一个字符串？——返回字符串意味着每一层都要分配一块内存再拼接。往同一个 `f` 里写，内容一路直通目的地，中间不产生临时字符串；同一个 `fmt` 也因此能同时服务 `println!`、`format!` 和写文件，它不需要知道目的地是什么。C++ 的 `operator<<(ostream&, const T&)` 是同一个形状，Python 的 `__str__` 则是每层返回一个新字符串。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 格式化本身不会失败，`fmt` 为什么还要返回 `Result`？——标准库文档的说法是 string formatting is an infallible operation，返回 `Result` 只是因为往底层的流里写可能失败，需要一条把错误传回去的路。所以规矩是只传递 `f` 报的错，不要自己制造错误。Rust 没有异常，错误是普通的返回值，要往上传就得写出 `?`，它相当于把 C 里的 `if (ret < 0) return ret;` 压成一个字符。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 实现了 `Display` 之后白得什么？——`to_string()`。标准库里有一条对所有实现了 `Display` 的类型生效的实现 `impl<T: fmt::Display + ?Sized> ToString for T`，本机 `MinMax(0, 14).to_string()` 得到 `(0, 14)`。（来源：`msg-1a91f55d93237981ffd2`。）

- [要点] 外层写了 `{:>10}`，为什么自己写的 `Display` 没有对齐？——`println!("[{:>10}]", minmax)` 输出 `[(0, 14)]`。宽度记在 `f` 里，而 `fmt` 里用 `write!` 另起了一个格式串，没有理会它。先 `to_string()` 再打印就对齐了，因为那时拿着宽度的是 `String` 自己的 `fmt`。（来源：`msg-1a91f55d93237981ffd2`。）

## 格式说明

- [要点] 宽度、精度这些格式说明是谁执行的？——不是 `println!`，是各个类型自己的 `fmt`。编译器在第 3 步解析它并写进模板，运行期它经由 `f` 交到每个类型的 `fmt` 手里。对比：同一个状态名用 `{:>10}` 打印，`write!(f, "{}", name)` 的实现输出 `[Closed]`，`f.pad(name)` 的实现输出 `[    Closed]`。标准库的类型都会执行这些说明，自己写的 `Display` 默认不会。（来源：`msg-6e7cca7d2bf13c4cf1e7`。）

- [要点] 为什么把格式说明交给类型自己执行，而不是由 `println!` 统一补空格？——同一个说明对不同类型含义不同：`{:05}` 打印 `-7` 得到 `-0007`，0 要补在符号后面；`{:.2}` 对浮点数是保留两位小数，对字符串 `"abcdef"` 是截成 `ab`。另外统一补空格需要先拿到完整输出才知道长度，就得先存进一个临时字符串，和“直接往目的地写”的设计冲突。（来源：`msg-6e7cca7d2bf13c4cf1e7`。）

- [要点] 为什么宽度可以取自变量（`{id:>width$}`），格式串本身却不能是变量？——因为前者的形状是固定的：一个占位符，带一个宽度，变的只是一个数，编译器仍然知道有几个占位符、各自用哪个 trait。形状必须在编译期确定，数值可以留到运行期。占位符里的名字也在编译期解析，作用域里没有这个名字时报 E0425。（来源：`msg-6e7cca7d2bf13c4cf1e7`。）

- [要点] 一个占位符的完整形状是什么，默认怎样对齐？——形状是 `{谁:怎样}`。“谁”可以省略、写位置如 `{0}`、或写名字如 `{who}`。“怎样”的语法是 `[[fill]align][sign]['#']['0'][width]['.' precision][type]`，例如 `{:*^8.3}` 把 3.141592 打成 `*3.142**`，`{:08.3}` 打成 `0003.142`，`{:#x}` 给 255 加上前缀成 `0xff`。数字默认右对齐，字符串默认左对齐。（来源：`msg-6e7cca7d2bf13c4cf1e7`。）

- [要点] 带了格式说明的占位符，在编译出的模板里长什么样？——不带说明的占位符是单独一个 `\xc0`。给 `days` 加上 `{:>5}` 之后，它变成 `\xc3` 加 6 个字节：4 个字节记着填充字符是空格、对齐是右对齐，2 个字节记着宽度 5。说明在编译期就被解析成了数据，运行期由 `i32` 的 `fmt` 读到“右对齐、宽 5”后写出三个空格加 `31`。（来源：`msg-6e7cca7d2bf13c4cf1e7`。）

## 综合验收与复查

- [转折] 综合验收的口述主线完整，但“要小心的地方”只讲了一条。——学习者讲清了编译期的展开、解析、选 trait、生成模板和运行期的加锁、按模板调用 `fmt`，并补上了上次差的“格式串必须是字面量”这一代价；注意事项只说了“实际使用时要小心Debug输出时的变量打印，会打印出所有的变量”。运行期的两条边界没有提，后面用复查题专门检查。（来源：`msg-a92c977bf7b5176ee8c5`、`msg-95e700ecfc2e9485eb29`。）

- [纠错] 场景：综合验收第 2 题，`println!("{}", pool.shards)`（类型是 `Vec<Shard>`）编译不过，问最小的修法。我说“最小的修法就是为Vec<Shard>实现Display trait和derive struct Pool Debug trait。”→ 正确：不能为 `Vec<Shard>` 实现 `Display`，报 E0117；可行的是改用 `{:?}`，或者包一层自己的类型，为 `Pool` 实现 `Display` 并在 `fmt` 里逐个写出。原因：实现一个 trait 时，trait 和类型里至少有一个必须是自己的 crate 定义的，`Display` 和 `Vec` 都属于标准库，哪怕里面装的 `Shard` 是自己的也不行。没有这条规则，两个互不知情的库可以各写一份实现，编译器无法决定用哪一份。（来源：`msg-a92c977bf7b5176ee8c5`、`msg-95e700ecfc2e9485eb29`。）

- [纠错] 场景：综合验收第 3 题，要把 `Worker` 右对齐到 12 个字符宽，判断同事的原版（先 `format!` 再 `write!(f, "{}", s)`）和自己改的版本（直接 `write!`）哪个能对齐。我说“同事写的这个版本由于先转成了字符串，而字符串可以对齐。但我改后的版本不行。最小的改动是使用f.pad，改成write!(f, f.pad(“w{}: {:.1}”), self.id, self.load)。”→ 正确：两个版本都不能对齐，本机输出都是 `[w7: 0.5]`；最小的改动是保留 `format!`，把最后一行换成 `f.pad(&s)`。原因：宽度 12 记在 `f` 里，`write!(f, "{}", s)` 里的 `{}` 是新写的、不带宽度的占位符，没有人去看 `f` 里的 12；`f.pad` 接收的是一段已经写好的文字，不是套在格式串外面的东西，而且格式串必须是字面量。关键是谁手里拿着那个宽度。（来源：`msg-a92c977bf7b5176ee8c5`、`msg-95e700ecfc2e9485eb29`。）

- [要点] 什么情况下先拼成一个字符串反而是合理的？——要把整段输出当作一个整体来对齐的时候。补多少空格取决于总长度，而总长度要等全部内容写完才知道，所以必须先放在某个地方。标准库的 `Ipv4Addr` 就是这样做的：没有宽度和精度要求时直接 `write!`；有的话先写进一个 15 字节的栈上缓冲区再 `fmt.pad`，15 是最长地址 `255.255.255.255` 的长度，连堆分配都省了。（来源：`msg-95e700ecfc2e9485eb29`。）

- [要点] 用 `{:>10}` 打印 `Id(7)`，`fmt` 的四种写法各输出什么？——`write!(f, "{}", self.0)` 输出 `[7]`，忽略了宽度。`fmt::Display::fmt(&self.0, f)` 把同一个 `f` 传给 `u32` 的 `fmt`，右对齐到 10 位。`write!(f, "{:>6}", self.0)` 右对齐到 6 位，因为格式串里写死了。`f.pad(&self.0.to_string())` 也右对齐到 10 位，但比第二种多一个临时字符串。学习者四种全部答对，并指出第二种比第四种少一个临时字符串。（来源：`msg-99a61767174da5eb5fb8`、`msg-e3165ba1314965bfde0d`。）

- [纠错] 场景：复查第 2 题，判断 `impl fmt::Display for (u32, u32)` 为什么被拒绝。我说“第二行是为基本类型u32进行实现Display。”→ 正确：这一行的类型是元组 `(u32, u32)`，不是 `u32`；结论（被拒绝）是对的，理由要改。原因：元组不是任何 crate 自己定义的类型，`Display` 也不是自己的，两边都不是自己的，所以被拒绝；`impl fmt::LowerHex for Worker` 能过，是因为类型 `Worker` 是自己的，哪怕 trait 属于标准库。（来源：`msg-99a61767174da5eb5fb8`、`msg-e3165ba1314965bfde0d`。）

- [转折] 复查第 3 题学习者答“不知道”，换来了一次重讲。——题目是循环里用 `println!` 输出 100 万行再接到 `head -n 20` 上会遇到哪两个问题。学习者写：“不知道。我猜测可能会出现输出pipe提前结束的问题。因为head -n 20只看完前20行就可以结束了。不知道该怎么改。”助手认为这是有用的信息：这部分上次是在节点 2 末尾用三条要点带过的，讲得太密；于是对着标准库里 `print_to` 和 `STDOUT` 的源码重讲，再换场景复查。（来源：`msg-99a61767174da5eb5fb8`、`msg-e3165ba1314965bfde0d`。）

- [要点] `println!` 的输出接到 `head` 上，为什么会看到一段崩溃信息？——`println!` 最终调用的 `print_to` 只有一句话：取得标准输出，`write_fmt` 写进去，写失败就 `panic!("failed printing to {label}: {e}")`。`write_fmt` 返回的是 `Result`，但 `println!` 没有把它交给你。`head` 读够就退出，管道的读端关闭；程序下一次写时操作系统返回 `Broken pipe`，于是 panic。（来源：`msg-e3165ba1314965bfde0d`。）

- [要点] 标准输出的锁和缓冲是怎样的，循环里大量输出该怎么写？——`STDOUT` 的类型里要看两个词：`ReentrantLock` 是一把锁，每次 `println!` 都要先拿到它；`LineWriter` 按行缓冲，每遇到一个换行就做一次系统调用。改法是自己先 `io::stdout().lock()` 把锁拿住，再用 `writeln!` 往里写：整个循环只加一次锁，写失败时得到一个 `Result`，由自己决定怎么办，比如安静地 `break`。每行一次系统调用还在，要再包一层更大的缓冲区。（来源：`msg-e3165ba1314965bfde0d`。）

- [要点] 64 个线程各自用 `println!` 打访问日志，会带来什么问题？——学习者答出了加锁和按行缓冲会加大开销，并说一个线程迟迟不放锁“可能会导致其他线程也输出不了而卡死”。助手补了用词：其他线程是在等那把锁，前一个写完就能继续，属于阻塞，不是死锁。后果是本来互不相干的 64 个线程到了这一行要排成一队，日志写得多慢，请求就被拖多慢。（来源：`msg-702c8dc4765a5f943253`、`msg-cfb15cd060a250cfeaa6`。）

- [要点] 标准输出被重定向到磁盘上的日志文件，磁盘写满之后会发生什么？——下一个要打印日志的线程写失败，`println!` 触发 panic；用 `/dev/full` 模拟时的信息是 `failed printing to stdout: No space left on device (os error 28)`。panic 发生在主线程，整个进程以退出码 101 结束；发生在别的线程，默认只有那个线程终止，它正在处理的请求就丢了。学习者答对了前半。（来源：`msg-702c8dc4765a5f943253`、`msg-cfb15cd060a250cfeaa6`。）

## 练习与 Review

- [高价值问题] “练习中有用到几个点，我还没有学到，需要先了解一下：判断分支、获取Vec的长度、循环遍历Vec的方式、从RGB的三个数字如何得到类似于0x80FF5A的表示。”——前三个是第 02 到 04 课的语法，练习提前用到了，助手承认这是设计练习时该先交代的，并用一个与练习无关的类型给了够用的最小版本；第四个是 A3 的核心，只讲清了这个表示是什么。之后的约定是：练习只需要讲过的语法，否则在练习约定里先交代。（来源：`msg-5a3dc99e6b146c3acc13`、`msg-219f330c5ff60b977968`。）

- [要点] Rust 的 `if` 和 C++ 的有哪三处不同？——条件不用加括号，花括号不能省。条件必须是 `bool`，整数不会自动当成真假，`if n { … }` 报 E0308，要写成 `if n != 0`。`if` 是表达式，可以有值，相当于三目运算符：`let label = if x >= 0.0 { "non-negative" } else { "negative" };`。（来源：`msg-219f330c5ff60b977968`。）

- [要点] 在 `fmt(&self, …)` 里遍历 `self.0` 这个 `Vec`，为什么 `&` 不能省？——`self` 是借来的，无权把里面的 `Vec` 拿走，写成 `for x in self.0` 报 E0507。够用的模型是：`for x in v` 把 `v` 整个交出去，`for x in &v` 和 `for x in v.iter()` 只是借着看。同时要下标和元素时写 `for (i, s) in self.0.iter().enumerate()`。（来源：`msg-219f330c5ff60b977968`。）

- [要点] `0x80FF5A` 这种颜色写法是怎么来的，打印时容易漏什么？——它不是把三个数做了运算，只是把每个 `u8` 分量各写成两位十六进制数再依次排开：128、255、90 是 `80`、`FF`、`5A`。分量小于 16 时只有一位十六进制数，`{:X}` 打印 3 得到 `3`，`{:02X}` 得到 `03`，不补 0 就会少一位。（来源：`msg-219f330c5ff60b977968`。）

- [纠错] 场景：练习提交后 Review 发现 `List` 的 `fmt` 用 `let _ = write!(f, …);` 把每次写入的结果丢掉了，测试却全部通过。我问“但我该怎么改呢？就去掉“let _ = ”就可以了吗？”→ 正确：只去掉不行，没人用的 `Result` 会被警告，A6 把警告当错误；要在中间的 `write!(…)` 后面加 `?`，最后一个不加 `?` 也不加分号，作为返回值。原因：`let _ =` 只是让警告闭嘴，错误照样丢了。用一个第 3 次写入会失败的假输出打印 `List(vec![1, 2, 3])`，原实现一直写完 12 次、留下 `[0, 1: 2, 2: 3]`、却返回 `Ok(())`；用 `?` 的实现在第 3 次后停止并返回 `Err`。（来源：`msg-5d312a839a5371148e84`、`msg-d67dd60057940232abcd`、`msg-90055b5a89b1f2735f60`。）

- [要点] 一个 `Result` 有哪三种去处？——丢掉，写 `let _ = write!(…);`，意思是“我知道可能失败，故意不管”。传出去，写 `write!(…)?;`，失败了就立刻让当前函数带着这个错误返回。当场处理，用 `if` 或 `match` 判断，自己决定失败后做什么。`fmt` 里要的是第二种。（来源：`msg-90055b5a89b1f2735f60`。）

- [要点] 只检查输出文字的测试为什么发现不了“丢掉写入错误”，怎样才能测到？——往字符串里写永远不会失败，所以错误路径从来没有被走到。办法是自己写一个输出目的地：`fmt::Write` 是只要求 `write_str` 一个方法的 trait，实现它的类型就能当 `write!` 的目的地，让它在指定的第几次调用时返回 `Err(fmt::Error)`。一个 `write!` 会拆成好几次 `write_str`，字面文字和每个占位符的内容是分开写的。测试让第 1 次到最后一次轮流失败，每次都要求 `fmt` 返回 `Err`，并且失败之后没有再写。（来源：`msg-5d312a839a5371148e84`、`msg-90055b5a89b1f2735f60`。）

- [转折] 这个问题被判为约定的疏漏，而不是学习者的失误。——助手说明版本 1 的 A2 只检查了输出的文字，没有检查出错时的行为，于是提出版本 2，在 A2 上增加“底层写入失败时，`fmt` 返回 `Err`，并且不再继续往下写”。学习者接受后才加测试。由于改法是助手直接说的，“写入失败时返回 `Err`”这一项的独立性由 A8 的无提示变式补回。（来源：`msg-5d312a839a5371148e84`、`msg-d67dd60057940232abcd`、`msg-90055b5a89b1f2735f60`。）

- [纠错] 场景：A7 说明 `WorkerId` 选的写法有没有堆分配。我说“因为长度不定，有堆分配。”→ 正确：有堆分配，是因为 `format!` 返回的是 `String`，而 `String` 的内容总是放在堆上，和长度定不定无关。原因：这里的长度其实有上界，`u32` 最大是 4294967295，加上前面的 `w` 一共 11 个字节，完全可以像 `Ipv4Addr` 那样先写进固定大小的栈上缓冲区再 `f.pad`，把这次分配也省掉。（来源：`msg-786df6ecef89a6c30cec`、`msg-ce42c64e4144128917cf`。）

- [要点] Review 里两条不阻塞的观察各说明了什么？——`Complex` 用 `{:.1}` 会丢位数，1.25 和 0.125 被打印成 `1.2 +0.1i`；符号手工拼接时，虚部为 `-0.0` 会输出 `+-0.0i`，格式说明里的 `+` 能替你处理符号。`Color` 用 `format!` 再 `.to_uppercase()` 多出两个临时字符串，`{:02X}` 本身就能直接输出大写。学习者随后把两处都改了，`Color` 里用 `{0}`、`{1}`、`{2}` 重复引用同一个参数。（来源：`msg-5d312a839a5371148e84`、`msg-d67dd60057940232abcd`、`msg-90055b5a89b1f2735f60`。）

- [转折] A8 在没有提示的情况下完成。——新类型 `Vector(Vec<f64>)` 要求输出 `(+1.5, -2, +0.25)`，写入失败时返回 `Err` 并停止。学习者一次写对：中间三处用 `?` 传出，符号用 `{s:+}`，还顺手去掉了 `List` 里多余的 `is_empty` 判断。（来源：`msg-ce42c64e4144128917cf`、`msg-8032afff6c5ea7b25af5`、`msg-ab30df9badf5c1b77429`。）
