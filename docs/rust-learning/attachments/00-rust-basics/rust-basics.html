语法6 个

let 与 mut 绑定

let x = 5; 给一个值起名字，这叫绑定。绑定默认不能再改；要改就写 let mut x = 5;。类型通常由编译器推断，也可以写成 let x: i32 = 5;。

对应你熟悉的：C++ 的 const auto x = 5; 与 auto x = 5;，只是默认值反过来：Rust 默认不可变。

fn 函数签名

fn area(w: f64, h: f64) -> f64 { w * h } 定义一个函数：参数写成“名字: 类型”，-> 后面是返回类型。没有 -> 表示不返回有意义的值。

对应你熟悉的：C++ 的 auto area(double w, double h) -> double；Python 的 def area(w: float, h: float) -> float。

对应你熟悉的：C++ 里的三目运算符是表达式；在 Rust 里，代码块和 if 也都是。

宏 macro

对应你熟悉的：C 的 #define。区别是 Rust 的宏处理的是语法片段而不是文本，展开结果还要经过完整的类型检查。

impl 实现块

给类型添加方法的代码块，写作 impl Type { … }；或者为类型实现某个 trait，写作 impl Trait for Type { … }。

写在 impl 块里、第一个参数是 self 的函数。&self 表示只读地借用调用它的那个值，&mut self 表示可以修改它。

对应你熟悉的：C++ 成员函数里的 this，&self 相当于 const 成员函数；Python 的 self。

derive 派生

一种属性。#[derive(Debug)] 让编译器按类型的定义自动生成 impl Debug。只有规则机械的 trait 才能这样生成。

对应你熟悉的：Python 的 @dataclass 自动生成 __repr__。

第 01 课出现第 10 课展开教程 §16.1 Derive

孤儿规则 orphan rule

为类型实现 trait 时，这个 trait 和这个类型至少有一个要是当前 crate 自己定义的。所以不能直接给标准库的 Vec<T> 实现标准库的 Display，编译器会报 E0117；常见做法是用元组结构体把它包一层。

对应你熟悉的：C++ 没有这条限制：谁都可以给别人的类型重载 operator<<，两个库各写一份就会冲突。这条规则让这种冲突不可能发生。

所有权与引用2 个

借用 引用 &T 与 &mut T

&T 是只读的引用，&mut T 是可写的引用。拿着引用只是借着用，值的主人没有变。编译器会检查引用不会比它指向的值活得更久。

对应你熟悉的：C++ 的 const T& 与 T&，区别是 Rust 在编译期检查它们的有效性。

对应你熟悉的：C++ 的 std::move，区别是 Rust 的编译器禁止再使用被移走的变量。

格式化宏 format!、println!、write!

format! 得到一个 String；print! 和 println! 写到标准输出；eprintln! 写到标准错误；write! 和 writeln! 写到你指定的目的地，并用 Result 报告成败。它们用同一套格式串。

第 01 课出现教程 §1.2 Formatted print

格式串与占位符

println! 的第一个参数那段字面量叫格式串，里面的 {}、{:?} 是占位符，依次换成后面的参数。格式串必须是字面量。每种占位符对应一个 trait：{} 是 Display，{:?} 是 Debug，{:X} 是 UpperHex。

对应你熟悉的：printf 的格式串与 %d；Python 的 str.format。

占位符里冒号后面的部分，例如 {:>8.3}，可以写对齐、填充字符、宽度、精度和进制。它由每个类型自己的 fmt 来执行。

对应你熟悉的：printf 的 %8.3f；Python 的格式规格。

对应你熟悉的：Python 的 __repr__。

对应你熟悉的：没有直接的对应物。可以想成编译器替你把 printf 的格式串预先解析好、并核对过参数之后的结果。

      04版本选择小实验

      假设终端找到的是 rustup 的代理入口。改变条件，看看哪项配置最终决定工具链。

      优先顺序：+版本 → RUSTUP_TOOLCHAIN → 最近目录中的 override／工具链文件 → 全局默认。

      选用 1.97.1

      cargo build

      目录规则：从当前目录向上找。目录 override 和 rust-toolchain.toml 按距离共同判断；同一目录两者都有时，override 优先。上面的第③项合并表示这一步的结果。此实验只演示选择规则，不检查本机是否安装该版本。

      选择本次实际使用的工具链

      # rust-toolchain.toml
[toolchain]
channel = '1.97.1'

      由 rustup 读取。1.97.1 是具体版本；stable 是通道名称，更新后其具体版本可能变化。

      声明项目最低支持的 Rust 版本

      # Cargo.toml
[package]
rust-version = '1.85'

      由 Cargo 使用的最低支持版本声明；它不会把当前编译器固定到 1.85。edition = '2024' 则表示语言版本规则，也不是编译器版本号。

      实测编译停在链接入口：linker `cc` not found。需要可用的链接驱动及配套系统开发文件。

      为什么有 rust-lld，仍然会报找不到 cc？

      当时的工具链目录中有 rust-lld，但 GNU/Linux 的默认配置仍通过 cc 驱动安排链接。实际链接器文件存在，不能自动补上驱动和系统配套。该问题与 Rust 代码能否通过类型检查属于不同环节。

      从首次安装到验证，标准流程怎样衔接？
      1. 准备系统构建环境

        Ubuntu 通常安装 build-essential；同时准备 curl 用于下载。系统安装由有权限的用户完成。

      2. 运行官方 rustup 安装器

        默认安装会准备 rustup、工具代理和 stable 工具链；default profile 还包括 rustfmt、Clippy 和本地文档。

      3. 让命令路径生效

        重新打开终端，或在 Bash 中执行 source "$HOME/.cargo/env"。终端应能找到 rustup 的代理入口。

      4. 确认版本和当前选择

        rustup show、rustc --version、cargo --version 检查工具是否可以启动。

      5. 真正编译并运行最小项目

        在仓库外创建临时 Cargo 项目并执行 cargo run。这一步进一步验证编译、链接和运行完整链路。

      当时这台机器已经有工具链文件，这种情况下配置时应先复用它们。仓库 host 脚本固定使用 1.97.1；本页只是教学说明，没有执行安装或修改环境。
