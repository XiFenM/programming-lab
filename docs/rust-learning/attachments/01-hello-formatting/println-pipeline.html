一行 println! 在编译期和运行期各发生什么

整页只用一个 7 行的例子。它定义一个只包着一个 i32 的结构体 Structure，让编译器为它生成 Debug；在 main 里把整数 31 绑定到 days，再用一行 println! 打印两样东西：days 用 {}，Structure(3) 用 {:?}。程序输出 31 days, Structure(3)。这一行由教程 Formatted print 和 Debug 两节里的两个示例合成。

结论：格式串的解析、参数个数的核对、类型能不能这样打印，全部在编译期完成。运行期只剩两件事：锁住标准输出，按一张已经算好的模板把内容写出去。

本页的展开结果、报错和输出都是 2026-10-07 在本机用 rustc 1.97.1 (8bab26f4f 2026-07-14) 实际得到的，标准库源码取自同一版本。换一个 Rust 版本，展开出来的内部函数名和模板编码可能不同。

先补概念

三个前置概念

流水线里会反复出现这三个词。每个都先用 C、C++ 或 Python 里已有的东西对上号。

宏：编译期的代码改写

名字后面带 ! 的是宏调用，不是函数调用。编译器在做类型检查之前，先把每个宏调用替换成它展开出来的代码。

对照：C 的 #define 也在编译前改写代码，用 gcc -E 能看到结果。区别在于 C 的宏替换的是文本；Rust 的宏接收和产出的是语法片段，展开结果还要经过完整的类型检查。

trait：对类型能力的约定

Display 是一个 trait，只有一个方法 fmt，意思是“这个类型知道怎样把自己写成给人看的文字”。一个类型实现了它，才能用 {} 打印。

对照：C++ 里为类型重载 operator<<，或者为 std::format 特化 std::formatter<T>。Python 里是 __str__，而 Debug 对应 __repr__。

编译期与运行期

编译期指 rustc 运行的时候，运行期指编译出来的程序运行的时候。同一件事放在哪一边做，决定了错误什么时候暴露、代价什么时候付。

对照：C 的 printf 到运行期才解析格式串。C++20 的 std::format 把这件事挪到了编译期。Rust 一开始就放在编译期。

主线

六步流水线

从你写下的那一行，到终端上出现文字，一共六步。第 1 步是你写的源码，第 2 到第 5 步由编译器完成，第 6 步才是程序运行时做的。

源码 你写的 编译期 rustc 运行时 运行期 ./probe 运行时
第 1 步

你写下的一行

源码

一次宏调用，带一个格式串和两个参数。格式串里有两个占位符：{} 和 {:?}。此刻它们的区别还只是两段不同的文字。

第 2 步

宏展开

编译期

println! 是标准库用 macro_rules! 写的一个普通宏。它自己不懂格式串，只做一件事：把参数原样交给 format_args!，再把结果传给函数 _print。

展开之后，整个文件变成下面这样。#[derive(Debug)] 也在这一步变成了一段真正的 impl。

  • 占位符被编上了号：{} 成了 {0}，{:?} 成了 {1:?}。
  • 换行符 \n 被拼进了格式串，println! 比 print! 多的就是它。

对照：这相当于 gcc -E 看到的预处理结果。

第 3 步

解析格式串，核对参数

编译期

format_args! 是编译器内建的宏，真正读懂格式串的是它。它读取格式串这个字面量，切成字面文字和占位符，然后核对两件事：每个占位符都能找到参数吗？每个参数都被用到了吗？

顺序片段种类对应的参数
1{0}占位符，没有写格式说明第 0 个：days
2" days, "字面文字，7 个字节无
3{1:?}占位符，格式说明是 ?第 1 个：Structure(3)
4"\n"字面文字，1 个字节无

两个占位符，两个参数，一一对上，这一步通过。前提是格式串必须是字面量，因为编译器要在这一步读它的内容。

对照：C 的 printf 把这一步留到运行期，每次调用都重新扫描一遍格式串。

第 4 步

按占位符选 trait，检查类型

编译期

每种占位符对应一个 trait：{} 是 Display，{:?} 是 Debug，{:x} 是 LowerHex，以此类推。编译器为每个参数生成一次函数调用，选哪个函数由占位符决定。

这两个函数的签名里写着对类型的要求：

  • T: Display 这个约束就是类型检查发生的地方。days 是 i32，标准库为它实现了 Display，通过。Structure 有 derive 出来的 Debug，也通过。
  • 参数以 &days、&Structure(3) 的形式传入，是借用而不是拿走。所以打印之后 days 还能继续用。
  • 每个参数最终被存成两样东西：一个指向值的指针，一个指向它的 fmt 函数的指针。

对照：相当于 C++ 在编译期决议“这个类型有没有 std::formatter<T> 的特化”。

第 5 步

生成 fmt::Arguments

编译期

格式串被翻译成一段模板字节，和上一步的参数表一起装进一个 fmt::Arguments。到这里花括号已经不存在了。

模板里的字节含义
\xc0一个使用默认选项的占位符，取参数表里的下一个参数（第 0 个）
\x07 加 7 个字节字面文字 " days, "，前面是它的长度
\xc0又一个占位符，取下一个参数（第 1 个）
\x01 加 1 个字节字面文字 "\n"
\x00模板结束
  • 两个占位符在模板里是同一个字节 \xc0。用 Display 还是 Debug 不记在模板里，而记在参数表的函数指针里。
  • 模板是一段只读数据，参数表在栈上。println! 不会先在堆上拼出一个字符串；会分配字符串的是 format!。

模板编码的依据是 library/core/src/fmt/mod.rs 中 Arguments 结构体上方的注释。这是 1.97.1 的内部表示，不属于稳定接口。

第 6 步

运行：写出结果

运行期

程序运行到这一行时，_print 取得标准输出，顺着模板走：字面文字直接写出；遇到占位符，就通过参数表里的函数指针调用那个类型的 fmt。对 days 调用的是 i32 的 Display::fmt，对 Structure(3) 调用的是第 2 步里 derive 出来的 Debug::fmt。

  • 每次调用 println! 都要给标准输出加一次锁。标准库文档提醒：在很热的循环里这可能成为瓶颈，这时应当先 stdout().lock()，再往锁住的句柄里写。
  • 写失败时没有返回值可以检查，print_to 直接 panic!。最常见的触发方式是下游提前关闭了管道，见下一节最后一个例子。

取舍

和 C、C++ 对照

同样是“少传一个参数”和“打印一个没有定义打印方式的类型”，四种做法的反应不一样。

做法格式串何时解析少传一个参数自定义类型怎样接入
C 的 printf运行期，每次调用都解析能编译。格式串是字面量时 gcc 给一条 -Wformat 警告，放进变量后连警告也没有。运行时去读不存在的参数，本机输出了 1 加一串乱码不能。只能自己拆成基本类型再传
C++ 的 std::cout <<没有格式串不存在这种错误，每个值各写一次 <<重载 operator<<，没有重载就是编译错误
C++20 的 std::format编译期编译错误特化 std::formatter<T>，没有特化就是编译错误
Rust 的 println!编译期编译错误实现 Display，或 derive Debug；没有实现就是编译错误

C 和 C++20 两行是 2026-10-07 在本机用 gcc 与 g++ 13.3.0 实测的；std::cout 一行是语言规则，没有另做实验。读不存在的参数在 C 里是未定义行为，输出什么都有可能。

Rust 这样做换来的是：格式和参数对不上的错误不可能留到运行期；运行期也不用再解析格式串。付出的是：格式串必须写死在源码里，想在运行时换格式得用别的办法；每一种“打印方式”都是一个 trait，类型要一个个去实现。

小结

带走三句话

它必须是宏。函数拿到的只是运行期的值；格式串的内容、参数的个数和类型都是编译期才有的信息，只有宏能用上。
占位符决定 trait，trait 决定能不能打印。{} 要 Display，{:?} 要 Debug；这个约束写在 new_display、new_debug 的签名里，由编译器检查。
运行期只做两件事。加锁，按模板写出。写失败就 panic；需要自己处理写入错误时，改用 writeln! 往一个锁住的句柄里写，它会返回 Result。
