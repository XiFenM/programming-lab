libdevice.asin 编译链路

一行 y = libdevice.asin(x)，编译完成后变成了 GPU 上的哪些指令？本页用本机 Triton 3.7.1 的真实编译产物（目标 sm_90，只编译、不运行），一站一站跟着它走。节点 1、2（接口模块替换、按 dtype 查表）已经讲过，这里从 TTIR 往下讲；最后两节对比四条实现路线和两个后端。

先记住主线：前端只记下“要调用 __nv_asinf”；布局决定每个线程负责几个元素，每个元素变成一次调用；到 LLVM IR 阶段，才从 libdevice 里把函数体拷进来并内联；GPU 运行时执行的只是展开后的普通指令。

前置 · 四个编译器概念

先补四个概念

节点 3、4 只用到下面四个概念。每个都附一个 C/C++ 里的对应物，后面各节会反复用到。

AIR 与逐层降级

编译器不会一步把 Python 变成机器码，而是依次翻译成几种“中间表示”（IR），每一种都更接近硬件。往下翻译一层，叫降级（lowering）。

每层描述的粒度不同：TTIR 说的是“整块张量”；TTGIR 加上“哪个线程负责哪些元素”；LLVM IR 写的是“一个线程要执行的标量指令和函数调用”；PTX 是 NVIDIA 的虚拟汇编；cubin 是具体 GPU 的机器码。

对应物：torch.compile 先把 Python 捕获成 FX 图，再由 Inductor 降级成 Triton 代码，是同一种思路。所有翻译都在编译期完成，运行期 GPU 不再查表、链接或调用 Python。

B声明、定义与链接

声明只有名字和签名，定义才有函数体。链接就是按名字，把调用接到定义上。

对应物：C++ 头文件里写 float asinf(float);，函数体在数学库里；链接器找不到就报 undefined reference to 'asinf'。bitcode 就是以二进制保存的 LLVM IR，所以 libdevice 能直接并进 kernel 的 LLVM 模块，Triton 的 link_extern_libs 扮演链接器。

C内联

内联是把“调用一个函数”换成“在调用处放一份函数体”。好处：省掉调用本身的开销，放进来的代码能和前后代码一起优化、交错排布。代价：有几个调用处，就有几份代码。

对应物：C++ 的 inline、CUDA 的 __forceinline__。本例从 libdevice 链接进来的 __nv_asinf 带 alwaysinline 属性，要求编译器必须内联。

D编译期分支

有些 if 的条件在编译时就知道答案。编译器会把条件换成常量，删掉走不到的那一支，运行时不付任何代价。

// libdevice 里 fabsf 的写法（示意）
if (__nvvm_reflect("__CUDA_FTZ"))   // Triton 让它 = 1
    y = fabs.ftz(x);   ← 保留
else
    y = fabs(x);       ← 编译期删除

对应物：C++ 的 #ifdef FAST_MATH 或 if constexpr。__nvvm_reflect 在编译期回答一个参数的值：__CUDA_FTZ 取自 Triton 写进模块的标志，没有设置的参数一律当作 0（LLVM NVPTX 文档）。

    节点 3
    
布局决定每个线程的元素，一个元素一次调用

    
TTGIR 给张量加上布局，规定 1024 个元素怎样分给 128 个线程。降级到 LLVM IR 时，编译器是在替一个线程写程序：这个线程持有几个元素，就生成几次标量调用。

  


  

    
BLOCK_SIZE
一个 program（一个线程块）处理的元素数，本例 1024

    
num_warps
线程块里的 warp 数，本例 4；每个 warp 32 个线程

    
S
sizePerThread：每个线程一次持有的连续元素数，由 Triton 自动选，本例 4

    
E
每个线程持有的元素总数 = BLOCK_SIZE ÷ (32 × num_warps)

  


  

  

  
为什么是标量调用：libdevice 函数的签名是 float(float)，和 CUDA C 的数学函数一样。GPU 的并行来自同时运行的线程，而不是一条向量指令，所以逐元素调用在计算上没有损失。S 只影响访存：相邻的 S 个元素可以合成一条更宽的读写指令，S = 4 时一次读 16 字节（ld.global.v4.b32）。






  

    节点 4
    
链接、内联、再按参数选一条路

    
到节点 3 为止，模块里只有 __nv_asinf 的名字。节点 4 用三步把它变成真正的指令，都发生在 Triton 后端的 make_llir 和随后的 PTX 生成里。

  


  

  

    
这一步的细节：

    
· 库文件从哪来：默认是 Triton wheel 自带的 triton/backends/nvidia/lib/libdevice.10.bc，也可以用环境变量 TRITON_LIBDEVICE_PATH 或启动参数 extern_libs 换掉。

    
· 什么时候链接：只有模块里还有“有声明、无定义”的外部函数时才链接；没用 libdevice 的 kernel 整步跳过（has_extern_deps）。

    
· 缓存：库文件的内容哈希会算进编译缓存键，换一份 bitcode 就会重新编译。

  


  

  

  

    
次正规数与 ftz：绝对值小于 2⁻¹²⁶ ≈ 1.18×10⁻³⁸ 的 fp32 数叫次正规数。ftz（flush to zero）把它们当作 0 处理，换来更简单、更快的指令。对 asin 来说，极小的 x 本该得到 ≈ x，在 ftz 下预计得到 0；这一点留到 GPU 机器上验证。

    
什么时候选定：O3 之后，IR 里两条路都还在：ftz 版和普通版的 |x| 都会被算出来，再用 select 二选一。生成 PTX 时 reflect 才被换成常量，另一条路随之删掉。

  


  

    

      
编译方式次正规数单精度 sqrt

      
        
nvcc 默认保留（--ftz=false）IEEE 就近舍入（--prec-sqrt=true）

        
nvcc --use_fast_math冲成 0（隐含 --ftz=true）近似（隐含 --prec-sqrt=false）

        
Triton 3.7.1 默认，libdevice 函数内冲成 0（__CUDA_FTZ = 1）近似（__CUDA_PREC_SQRT = 0）

        
Triton，enable_reflect_ftz=False保留近似

      
    

  

  
在这两个开关上，Triton 默认编进来的 libdevice 代码更接近 nvcc 的 --use_fast_math，而不是 nvcc 的默认值。反射参数只影响 libdevice 函数内部；Triton 自己降级的指令不受它影响，例如 tl.exp 编出的是不带 ftz 的 ex2.approx.f32。


  

    
节点 3、4 连起来

    
    
      
  1. 布局决定每个线程持有 E 个元素（本例 8 个）。
    2. 
      
  2. 每个元素生成一次 call @__nv_asinf，模块里只有 1 条声明。
    3. 
      
  3. 链接按名字从 libdevice 拷入一份定义，设为 internal，带 alwaysinline。
    4. 
      
  4. O3 把 E 次调用内联成 E 份函数体，定义被删除，PTX 里没有 call。
    5. 
      
  5. 生成 PTX 时，reflect 按参数选定写法：默认是 ftz 加近似 sqrt。
    6. 
    

  






  

    节点 5
    
算一个数学函数的四条路线

    
节点 3、4 讲的是 libdevice 这一条路线。在 Triton 里算一个数学函数一共有四条路线，区别在于：函数体从哪里来，在哪一站进入管线。

  


  

  

    
三个实测细节：

    
· NVIDIA 上，A 和 B 常常是同一份代码：tl.log、tl.erf、tl.sqrt、tl.floor 编出来的 PTX 与 libdevice.log 等完全相同，因为后端把这些数学操作也改成了 __nv_* 调用。

    
· 路线 D：一个手写的 5 行文本 LLVM IR 文件（softsign(x) = x ÷ (1 + |x|)）通过 extern_libs 链接进来，内联成 abs.f32、add.f32、div.rn.f32，没有 call。不传 extern_libs 时，最后一步报 Unresolved extern function。

    
· 教程第二段演示的就是 extern_libs：把默认的 libdevice 换成指定路径的文件。教程拼路径的方式假设脚本位于 Triton 源码树里；在本仓库的快照位置或 pip 安装的环境中，这个路径不存在，编译会在计算缓存键时报 FileNotFoundError。pip 环境里的正确位置是 triton/backends/nvidia/lib/libdevice.10.bc。

  


  
同一个运算，有“快速档”和“精确档”

  
Triton 最顺手的写法默认都是快速档。要和 PyTorch eager 的结果尽量一致，就得主动换成精确档。PyTorch 2.13 的 Inductor 为此专门设了一组 eager_numerics 开关。

  

    

      
运算快速档精确档Inductor 的选择

      
        
exptl.exp
每元素 2 条：mul.f32、ex2.approx.f32		libdevice.exp
每元素 8 条：先把 x 拆成整数和小数部分		默认 libdevice.exp；设 TORCHINDUCTOR_USE_FAST_MATH=1 才用 tl_math.exp

        
sqrttl.sqrt、libdevice.sqrt
sqrt.approx.ftz.f32		tl.sqrt_rn
sqrt.rn.f32，IEEE 就近舍入		始终 tl.sqrt_rn

        
除法a / b、tl.fdiv
div.full.f32		tl.div_rn
div.rn.f32，IEEE 就近舍入		默认 a / b；打开 division_rounding 后用 div_rn

        
次正规数libdevice 函数内默认 ftzenable_reflect_ftz=False打开 disable_ftz 后传这个选项

        
库的版本Triton 自带的 libdevice.10.bc换成 CUDA 工具链的 libdeviceuse_pytorch_libdevice：两份库的多项式不同，erf、pow 会差约 1 ulp

      
    

  

  

    
快速版 exp 为什么不够准：它先算 x × log₂e，再做 2 的幂。乘积只保留 24 位有效数字，|x| 越大，乘积里丢掉的那一点误差被指数放大得越多。精确版先把 x 拆成整数部分和小数部分分别处理，误差不随 |x| 增长。

    
ulp 是浮点数最后一位的一个单位，用来衡量算出的结果离“正确舍入的值”有多远；差 1 ulp 就是只差最后一位。CUDA 文档给出的误差上界：标准 expf 是 2 ulp，快速版 __expf 是 2 + ⌊|1.173·x|⌋ ulp；sqrtf 是 0 ulp，fast math 下 1 ulp；快速除法 __fdividef 是 2 ulp。Triton 的快速档用的是同类做法，推断误差特性相同，可以到 GPU 机器上实测。

  


  

    
怎么选

    
    
      
  1. 函数在 tl.math 里（exp、log、sin、cos、sqrt、rsqrt、erf、floor、ceil、abs、fma 等），用 tl.math：写法最可移植。
    2. 
      
  2. 需要 tl.math 没有的函数（asin、pow、lgamma、tanh 等），用 libdevice，并先确认目标后端实现了它：CUDA 约 197 个，AMD 约 57 个。
    3. 
      
  3. 要和 PyTorch eager 尽量一致，换精确档：tl.sqrt_rn、tl.div_rn、libdevice.exp，必要时关掉 ftz、换 libdevice。
    4. 
      
  4. 厂商库里没有的函数，用自定义库；每个目标后端的链接规则不同，要分别验证。
    5. 
      
  5. 内联汇编只在需要某条特定指令、且只面向一个后端时使用。
    6.

AMD 后端的两处不同：

    
· 链接规则：NVIDIA 只要发现有未定义的外部函数，就把 extern_libs 里的库都交给链接器。AMD 只链接“键名出现在某个未定义函数名里”的库。本机实测同一个自定义库：键名取 softsign 时，符号 my_softsign_f32 包含它，库被链接并内联；键名取 mymath 时库没有被链接，编译不报错，最终 IR 里留着一次未解析的调用。

    
· 绑死 CUDA 的写法会被拒绝：kernel 里直接写 triton.language.extra.cuda.libdevice 时，AMD 后端发现名字带 __nv_ 的未定义函数就报错，提示改用后端中立的 triton.language.extra.libdevice。这一条来自阅读 triton_amd.cc，没有运行。

贯穿全课的三个取舍

    
    
      
  1. 前端只记名字，后端才给函数体。换来的是同一份 kernel 能在不同后端编译。代价是每个后端的函数集和 dtype 表各不相同，缺了就编译失败。
    2. 
      
  2. 链接加内联，而不是真的调用。换来的是运行时没有调用开销，函数体还能和周围代码一起优化。代价是代码量随每线程元素数 E 增长。
    3. 
      
  3. 默认偏快，精确要自己选。库用编译期分支容纳多种数值模式，Triton 默认选 ftz 和近似 sqrt；exp、sqrt、除法最顺手的写法也是快速档。要和 PyTorch eager 对齐，得逐项换成精确档。
    4. 
    

  

  

    
放到真实系统里：PyTorch 的 Inductor 会把一串逐元素运算融合成一个 Triton kernel，其中每个数学函数都走这条链。它默认生成 libdevice.exp 和 tl.sqrt_rn，并用 eager_numerics 这组开关控制除法舍入、ftz 和 libdevice 的版本，目的都是让编译结果贴近 eager。

    
换一个后端：机制不变，填进去的内容变。AMD 上符号是 __ocml_asin_f32，每个 warp 64 个线程所以 E = 4，链接的是 ocml.bc，次正规数默认保留。
