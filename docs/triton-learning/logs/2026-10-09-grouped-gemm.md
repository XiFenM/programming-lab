## 开课、术语与举例方式

- [高价值问题] “检查题目先稍等一下，CTA和SM分别是什么意思，区别在哪？”——SM 是 GPU 里的硬件计算单元，数量由型号决定；CTA 是一次发射里的一个任务单元，CUDA 叫线程块，Triton 叫 program，数量就是 grid。一个 CTA 从头到尾在同一个 SM 上运行，一个 SM 可以同时驻留多个 CTA。所以教程里的 `NUM_SM` 实际是 CTA 数，叫“虚拟 SM 数”只是设计意图。（来源：`msg-8e58be1fa4f2d6bc776c`、`msg-e4d964c98ff2f817690b`。）

- [转折] 节点 1 为什么用完整的例子重讲？——学习者指出：“举例讲解还是要详细一些，开头就是128*128的问题，让人产生误解以为这是某个之前讲到过的问题而简化了名称，没有讲清楚例子场景。”助手承认例子引用了到节点 3 才介绍的示例组，改用教程示例组把三种做法重讲一遍。学习者随后要求“嗯，麻烦也写进学习者画像中。”，这条偏好写入了学习者画像的讲解偏好。（来源：`msg-1bbff7e1ec658c52f5df`、`msg-bd2ab07680b2faf51b6c`、`msg-436ac7d8223f32d10071`。）

- [要点] 逐个调用、batched 补齐、grouped 三种做法，各自浪费在哪里？——场景是教程示例组：边长 1024、512、256、128 的四个 fp16 方阵乘法，块 128×128×32，60 个 SM，每个 SM 一个 CTA。逐个调用发射 4 次，每次都有一笔与矩阵大小无关的固定开销，后三次分别闲置 44、56、59 个 SM，合计 92 个时间单位；补齐到 1024 后只发射 1 次，但约 71% 的乘加在算 0；grouped 发射 1 次，三个小问题的 21 块填进问题 0 第二轮的空档，总共 64 个单位。92 和 64 来自简化假设，用来看清结构，不是性能预测。（来源：`msg-bd2ab07680b2faf51b6c`。）

- [要点] 逐个调用时，闲着的 SM 为什么不能提前去做后面的问题？——同一个 CUDA 流里的 kernel 按提交顺序串行执行，PyTorch 默认每个设备只有一个流，Triton 发射用的就是当前流（`triton/runtime/jit.py` 第 714 行）。换用多个流可以让小问题重叠，但发射次数没有减少，流之间的同步要自己管。（来源：`msg-bd2ab07680b2faf51b6c`。）

## 主机侧打包：地址表与偏移表

- [要点] 一组矩阵为什么不能当 kernel 参数传，教程怎样交给 kernel？——矩阵个数 G 运行时才知道，kernel 的参数个数在编译时定死。教程把每个矩阵的 `data_ptr()` 存进 int64 设备张量，kernel 里 `tl.load` 读出整数，再 `.to(tl.pointer_type(tl.float16))` 转成指针，相当于 C 里从 `int64_t table[G]` 取值后强转成 `half*`；编译产物里每个 kernel 有 3 个 `tt.int_to_ptr`。尺寸表和 ld 表是 [G, 3] 按行展平，ld 就是 `stride(0)`，行内步长假定为 1。（来源：`msg-8ead93f0dabbf7a14bfb`。）

- [要点] “地址只是一个整数”要付出哪些代价？——类型信息丢了：指针写死成 fp16，传 fp32 不报错，只是按 fp16 解读。生命周期没人管：地址表不持有原张量的引用。编译器失去对齐信息：张量参数在发射时会按首地址是否为 16 的倍数做特化，表里读出的地址没有这一步。另外每个 CTA 对每个问题读 3 次尺寸，每领一块再读 6 次地址和 ld。（来源：`msg-8ead93f0dabbf7a14bfb`。）

- [高价值问题] “也希望能详细举例讲讲triton这里的grouped_mm和pytorch的之间的区别”——核心关系是偏移表是地址表的特例：第 g 组的地址 = 基地址 + 起始行 × 每行字节数。例子是 3 个专家、X 为 [768, 1024]、`offs=[256, 384, 768]`：A 的地址是 X 首地址加 0、524288、786432 字节，和教程包装函数从三个切片算出的地址表完全一样。到 kernel 这一层两边用的是同一种表，差别在表由谁、在哪里生成。（来源：`msg-d4cf82e6998517b664bf`、`msg-ac5580f867fd011b363e`。）

- [转折] `grouped_mm` 的适用条件被助手自己更正。——节点 1 里助手照文档字符串说它“要求 CUDA、bfloat16、SM ≥ 80”。核对 v2.13.0 源码后更正：输入接受 fp32、bf16、fp16；CUTLASS 快速路径只在 sm_90 或 sm_100 且输入输出都是 bf16 时启用，其余情况把 `offs` 拷回主机、逐个专家调用普通矩阵乘。（来源：`msg-8ead93f0dabbf7a14bfb`、`msg-ac5580f867fd011b363e`；另见 Lesson 的教学更正。）

- [要点] 每个专家的行数要不要回到主机？——MoE 里每个专家收到多少 token 是 GPU 上的路由算出来的，主机想知道就得读回，读回会让主机等 GPU 把排队的工作做完，即一次同步。PyTorch 的 `offs` 是设备张量，快速路径先在设备上跑一个小 kernel，用 `A + offs[g-1] * stride` 算出每组地址，全程不读回，源码注释是 “fast path, no d2h sync needed”。教程的包装函数在主机上读形状、拼列表、再建五张表，这是包装函数的写法，不是 kernel 的限制。（来源：`msg-ac5580f867fd011b363e`。）

- [要点] 类型和对齐由谁把关？——PyTorch 的张量自带 dtype 和步长，进门就检查：float64 输入、输出维 500（每行 1000 字节，报 “strides should be multiple of 16 bytes”）、int64 的偏移表都被拒绝。教程版的地址表里只有整数，dtype 写死成 fp16，16 字节对齐靠 `tl.multiple_of` 这句保证，没有人检查。（来源：`msg-ac5580f867fd011b363e`。）

- [要点] 两种接口各能表达哪些尺寸？——PyTorch 版一次调用只有一个维度参差，由 `offs` 切分，其余两维由堆叠的权重统一规定；教程版的尺寸表每行独立，三个维度都可以逐问题不同。所以 PyTorch 版算不了教程的示例组，教程版能算 MoE 的例子。两边的共同点是整组共用一套块大小。（来源：`msg-ac5580f867fd011b363e`。）

## 静态调度、均衡与块大小

- [要点] 教程的调度规则是什么，为什么顺序走一遍问题表就够？——所有问题的块首尾相接排成一条队列，第 p 个 CTA 处理第 p、p+NUM_SM、p+2·NUM_SM…… 号块，谁做哪一块由固定规则决定，主机不参与。`tile_idx` 只增不减，问题又按顺序走，所以一趟 `for` 就够；`while` 处理同一个问题里连续领到多块的情况。示例组在 NUM_SM=84 时共 85 块，CTA 0 做第 0 号和第 84 号块。（来源：`msg-8ead93f0dabbf7a14bfb`。）

- [要点] 按步长领取保证了什么，不保证什么？——保证各 CTA 领到的块数最多差 1，不保证工作量相等，因为一块的工作量正比于 K 循环次数。示例组里 CTA 0 做 36 次，CTA 1–63 做 32 次，64–79 做 16 次，80–83 只做 8 次；整个 kernel 的耗时由最忙的 CTA 决定。NUM_SM 改成 128 时，43 个 CTA 扫一趟什么都没领到。（来源：`msg-8ead93f0dabbf7a14bfb`。）

- [要点] 8 个专家、M_0=4096、其余 M=128、N=K=1024、块 128×128×32、NUM_SM=60 时，各 CTA 的工作量均衡吗？——学习者首答正确：“一共256+7*8=312个tile。由于K_g都是1024，每个tile的处理工作量的K循环次数是一样的，为1024/32=32。而SM有60个，那么前12个CTA的工作量为6个tile，其他CTA的工作量为5个tile。”差一块是按整块分配能做到的最好结果，因为 312 不能被 60 整除；最忙与平均之比是 1.15。（来源：`msg-2bb53f27d26e07dd78d3`、`msg-16ee3747508653c83d0d`。）

- [纠错] 场景：同一道检查题，改成逐个专家调用时哪几次并行度差。我说“这7个矩阵乘只有8个tile，只用到了8个CTA，CTA整体利用率只有8/60” → 正确：8/60 是 SM 的利用率，不是 CTA 的；那 8 个 CTA 全都在忙，闲着的是另外 52 个 SM。原因：CTA 是任务，SM 是硬件，利用率说的是硬件有多少在干活。（来源：`msg-2bb53f27d26e07dd78d3`、`msg-16ee3747508653c83d0d`。）

- [要点] 教程示例组为什么比上面的 MoE 场景更不均衡？——学习者答对并补了关键的一句：“每个CTA处理tile时必完成一整个tile，没有对K维度上的并行切分。”各问题 K 不同，调度却只均分块数。CUTLASS 的 Stream-K 正是针对这一点：把所有块的 K 循环总量均分给各 CTA，一块的 K 范围可以切给两个 CTA，代价是部分和要额外合并；它的示例 47 自带的样例输出是 A100 上 2048³ 的矩阵乘快约 1.2 倍，这是厂商示例里的数字。（来源：`msg-2bb53f27d26e07dd78d3`、`msg-16ee3747508653c83d0d`。）

- [高价值问题] “更均衡就是更好吗？会不会因为块缩小而未能充分利用算力吞吐性能？”——不是。总耗时大致是最忙 CTA 的工作量乘以做单位工作的耗时，缩小块压低前者、抬高后者。换算成同一单位后，示例组里 128 的块最忙 36、64 的块最忙 33，只少 8%；而每次乘加摊到的读入量是 1/BN + 1/BM，从 1/64 变成 1/32，累计读入从 38.3 MB 变成 76.7 MB，每块的固定开销也变多。助手同时更正了自己在节点 3 直接比较两种块的 K 循环次数的做法。（来源：`msg-909fe6fe88dc99524037`、`msg-814550240341ab76b524`。）

- [要点] 小块在资源上有什么好处？——每个 CTA 占的资源变少，一个 SM 能同时驻留更多 CTA。sm_89、4 个 warp 的编译结果：128×128×32 每线程 255 个寄存器（已到上限）、共享内存 32768 字节，按寄存器算每个 SM 驻留 2 个 CTA；64×64×32 是 128 个寄存器、16384 字节、4 个 CTA。块大小最终要靠实测选：教程交给 autotune，PyTorch 默认用大块、平均行数或列数不超过 128 时才换小块。（来源：`msg-814550240341ab76b524`。）

- [要点] 想要更均衡，有没有不增加访存的办法？——调整问题的顺序。CUTLASS 的示例程序有 `--sort-problems`，把问题按 K 从大到小排；这样同一轮里相邻的块 K 相近。调度模型里 100 个随机尺寸的问题，随机顺序时最忙与平均之比是 1.09–1.27，按 K 降序是 1.03–1.05。排序的动机是助手的推断，源码没有写。（来源：`msg-814550240341ab76b524`。）

- [高价值问题] “为什么扫描问题表时，用 warp 内前缀和一次跳过 32 个问题可以说明问题数多时，"找任务"的开销需要专门优化？”——助手说明这是从设计反推的，不是 CUTLASS 的原话，依据有三条：它放弃了最容易写对的顺序扫描；它另外准备了由主机算好任务表的 `kHostPrecompute`；扫描的总步数是 CTA 数乘以问题数，连一块都领不到的 CTA 也要走完全表。256 个专家各 4 块、NUM_SM=128 时，教程版每个 CTA 走 256 步只为领 8 块，CUTLASS 每个 CTA 走 8 步。（来源：`msg-909fe6fe88dc99524037`、`msg-814550240341ab76b524`。）

- [要点] kernel 里的标量代码是谁在执行？——CTA 的每个线程各执行一遍。4 个 warp 共 128 个线程在同一时刻读同一个问题的尺寸、做同一个加法，其中 127 份是重复的。CUTLASS 利用这一点，让一个 warp 的 32 个线程各读一个不同的问题，再用 warp 内的前缀和得到每个问题的结束编号。（来源：`msg-814550240341ab76b524`。）

## 满块假定与三个方向的越界

- [要点] 地址公式 `a_ptr + m × lda + k` 在下标超出时，会落到哪里？——没有任何一步检查 m 和 k 是否在范围内。矩阵连续存放时，列号超出会绕到下一行的开头，行号超出会落到矩阵末尾之后。教程的 kernel 去掉了所有 mask，注释是 “assume full tile for now”。（来源：`msg-16ee3747508653c83d0d`。）

- [要点] M 不是块的整数倍时会发生什么？——例子是专家只收到 100 个 token，块 128×128×32，N=512，K=1024。C 的 100 行有效结果全部正确，但第 100–127 行照样被写出去，共 14,336 个元素、28,672 字节落在 C 之后。这是最危险的一种：逐个专家比较结果能通过，被写坏的是排在 C 后面的别的张量。（来源：`msg-16ee3747508653c83d0d`。）

- [要点] N 不是块的整数倍时会发生什么？——例子是输出维 480：最后一块负责第 384–511 列，其中第 480–511 列的地址绕到下一行的第 0–31 列，而那里的正确值由第 0 块负责，谁后写谁赢，127 行 × 32 列共 4,064 个有效元素处于竞争中；最后一行绕出去的 32 个元素写到 C 之后。结果可能每次运行都不一样。（来源：`msg-16ee3747508653c83d0d`。）

- [纠错] 场景：检查题把 K 改成 1000，A 是 [128, 1000]，B 是 [1000, 512]，块 128×128×32，问最后一次 K 循环读到了什么。我说“其中第1000到1023行和列会落到矩阵之外，读到的是原本内存就放在那边的数据” → 正确：这句话对 B 成立，对 A 大部分不成立。B 是行号超出，24 行 × 512 列落在 B 之后；A 是列号超出，第 m 行的第 1000–1023 列实际读到第 m+1 行的第 0–23 列，是 A 自己的真实数据，只有最后一行的 24 个元素落到 A 之后。原因：地址公式不检查范围，列越界先绕行，行越界才出界。（来源：`msg-68a3516df646ca2daf4f`、`msg-e7eab4a5d1cd5625b6a8`。）

- [要点] K 不是整数倍时，结果有没有可能碰巧全对，这对测试意味着什么？——学习者首答正确：“如果读到的矩阵之外的数据全为0，那么就不会影响到矩阵乘计算了。这对测试意味着会出现假的正确通过。”更准确的条件是 B 之后那 24 行是 0，A 那边读到什么都无所谓。对策是不给运气留余地：把 A、B 放进四周填满 NaN 的缓冲区，越界读只要影响到有效结果，结果就变成 NaN。（来源：`msg-68a3516df646ca2daf4f`、`msg-e7eab4a5d1cd5625b6a8`。）

- [要点] 逐个比较结果发现不了 M 方向的越界写，怎样设计测试抓住它？——学习者自己提出了保护区的做法：“可以为结果矩阵C申请一块相比于预期结果更大的显存空间……确保前半块的[100,512]符合预期正确结果，后半块的[100,512]数据相比之前应保持不变。”补充两点：保护区至少要有一整块那么大，只收到 1 个 token 时越界是 127 行；教程的包装函数在内部自己分配 C，所以练习的包装函数要能接收调用方提供的输出。（来源：`msg-68a3516df646ca2daf4f`、`msg-e7eab4a5d1cd5625b6a8`。）

- [要点] 同一个 K=1000 的场景，B 之后全是 0 和 A 之后全是 0 两种内存状态下，C 各有哪些行是对的？——学习者复查全对：前一种“C的结果数据都是对的”，因为多出的项乘的是 0；后一种“最后一行是对的，其余的行大概率是错的。除非A的行开头24列也都是0”，因为 A 的列越界大多读到下一行开头的真实数据，只有最后一行读到 0。（来源：`msg-4b6c31089853d369f467`、`msg-e7eab4a5d1cd5625b6a8`。）

## 对齐保证、异步拷贝与 TMA

- [要点] `tl.multiple_of(a_ptrs, [16, 16])` 是什么，指针版为什么要多写这一句？——它相当于 C 里的 `__builtin_assume_aligned`：一句保证，不检查，也不修正。张量当参数传入时 Triton 会在发射前检查首地址并自动打标记，而本课的指针是运行时从地址表读出来的，编译器对它一无所知。一次搬 16 字节的指令要求地址对齐，一次搬的宽度不到 4 字节时 Triton 不做流水，所以去掉这句既退回每次 2 字节的搬法，也失去流水。（来源：`msg-3ff70516e47d8fcab939`；三种搬法的指令见[图解页](../attachments/08-grouped-gemm/grouped-gemm-data-movement.html)。）

- [高价值问题] “异步拷贝对张量矩阵起始地址的16倍数对齐要求是对每一行的起始位置都要求是16的倍数吗？”——是的，要求落在每一条拷贝指令上：它搬同一行里连续的 8 个 fp16，起始地址必须是 16 的倍数。第 m 行的行首是“首地址 + m × 行步长的字节数”，所以要同时满足首地址是 16 的倍数、行步长的字节数是 16 的倍数。fp16 矩阵每行 100 个元素时每行 200 字节，首地址对齐也没用，奇数行全部不对齐。（来源：`msg-158655333c8d57d455f9`、`msg-442b3e3fd1f6ff9c0e0f`。）

- [高价值问题] “所以偶数行对齐，奇数行不对齐的情况下，就不能使用异步拷贝指令和TMA了是吗？否则会出现未定义行为。”——16 字节这一档不能用，但异步拷贝可以如实降档，TMA 不行。异步拷贝一次可以搬 4、8 或 16 个字节：每行 200 字节的矩阵可以如实保证 8，sm_89 上编译出 48 条 8 字节的异步拷贝，仍有流水；保证 16 是 24 条，保证 4 是 96 条，不写保证则是 64 条 2 字节的普通读，没有流水。TMA 没有 8 字节的模式，只能改变数据的摆放。（来源：`msg-2e65a243543b0bace989`、`msg-84a9ce08f070dadce21a`。）

- [纠错] 场景：节点 5 检查题，把输出维改成 500（指针版 B 是 [1024, 500]，C 是 [M, 500]），问有 `tl.multiple_of`、没有 mask 的指针版会出什么问题。我说“由于B和C的第二个维度是500，行步长为500*sizeof(fp16)=1000字节，不是16的倍数，所以对B矩阵的读和C矩阵的写会产生未定义行为” → 正确：指针版里只有 B 有对齐问题，C 没有。原因：教程只给 `a_ptrs` 和 `b_ptrs` 写了保证，写回 C 用的是每次 2 字节的普通写，不受行步长影响；异步拷贝也只用于从显存读进共享内存。（来源：`msg-4d9cc2b2711996612485`、`msg-da755451823ec78c1ef5`。）

- [纠错] 场景：同一题，题目写明每个专家的 token 数是任意的。我只分析了 N 方向：“对B矩阵的读的列末尾tile会使得读到下一行的开头，最后一行会读越界。对C矩阵的写的列末尾tile导致写到下一行的开头，使得下一行开头产生竞争写，最后一行还会写越界” → 正确：还漏了 M 方向。M 不是 128 的倍数时会读到 A 的末尾之后、写到 C 的末尾之后。原因：真实的 MoE 里参差的正是行数，而这是三种越界里最危险的一种。（来源：`msg-4d9cc2b2711996612485`、`msg-da755451823ec78c1ef5`。）

- [纠错] 场景：同一题第 2 问，描述符版（B 转置存放为 [500, 1024]）在 sm_90 上能不能直接用。我说“也是卡在了行步长的字节数对齐条件上。需要对齐16字节的倍数，但B和C的行步长是1000字节” → 正确：卡在 C 上，B 不卡。原因：行步长由最后一维决定，转置存放把 B 的最后一维从 N 换成了 K，每行 2048 字节；同一个 N=500，在指针版里坏的是 B，在描述符版里坏的是 C。（来源：`msg-4d9cc2b2711996612485`、`msg-da755451823ec78c1ef5`。）

- [要点] 输出的行步长不满足要求时，怎样改而不必拷贝？——学习者提出：“C矩阵也需要扩展到[M, 512]，但不一定需要补零，最终结果进行[:,:500]的切片即可。”PyTorch 的 `grouped_mm` 正是这样做的：输出形状是 [768, 500]，相邻两行相隔 504 个元素。实现时描述符里的形状仍写 500，只把行步长写宽，硬件就只写每行的前 500 列。（来源：`msg-4d9cc2b2711996612485`、`msg-da755451823ec78c1ef5`。）

- [高价值问题] “那如果在指针版中加上对C的tl.multiple_of，可以做到异步写回显存吗？”——不能。`cp.async` 只有从显存到共享内存一个方向，反方向的异步搬运只存在于 TMA 那一族指令里，需要 sm_90。给 C 加保证的收益是每线程 128 条 2 字节的写变成 16 条 16 字节的写，仍然是普通的写指令；而且加了保证就要对 C 的对齐负责。（来源：`msg-defd1276b482a84bfc79`、`msg-d6b70c09d6cb60b1e0f9`。）

- [要点] 描述符版的写回为什么能和计算重叠？——每算完一块：先等上一块的写回完成，把结果写进共享内存，发起从共享内存到显存的搬运后不等待，直接去领下一块。于是第 i 块的写回和第 i+1 块的计算是重叠的；这是固定 CTA 循环领多块带来的机会，一个 CTA 只算一块就没有东西可以重叠。（来源：`msg-d6b70c09d6cb60b1e0f9`。）

- [要点] 把输入维 K 从 1024 改成 1020 后，哪些保证和描述符不再成立？——学习者复查全对：“矩阵A的tl.multiple_of(…, [16, 16])不成立。因为行步长是1020*2=2040。若想保留流水，可以降档到8”；描述符版里“矩阵A和B（转置形状后）都不满足行步长的16倍数要求”。（来源：`msg-9aee30aab8e822828d34`、`msg-ff935af7181eb6b05dbe`。）

- [要点] 输入不对齐时能不能像输出那样多分配一点再切片？PyTorch 为什么对输入报错、对输出自己补齐？——学习者答对：输出的切片“可以通过view的方式实现无拷贝的结果输出”，而输入要补齐“就会引入拷贝输入矩阵的代价”，可能让 grouped 相对多次 mm 的优势消失，“与使用者的使用初衷不符”。补充：输入也可以只把行步长加宽、逻辑上的 K 仍是 1020，不必补零，但同样躲不开一次拷贝。（来源：`msg-9aee30aab8e822828d34`、`msg-ff935af7181eb6b05dbe`。）

- [纠错] 场景：同一道复查题，说明输入为什么不能靠多分配解决。我说“但是对于grouped_mm的输入矩阵描述符版，则必须要连续化” → 正确：要求的是行步长的字节数是 16 的倍数，不是连续。原因：对齐条件看的是相邻两行相隔多少字节；补过步长的张量在 PyTorch 里反而是不连续的，比如行间隔 504、每行只用 500 列的那个输出。（来源：`msg-9aee30aab8e822828d34`、`msg-ff935af7181eb6b05dbe`。）

- [要点] 块超出矩阵时 TMA 怎样处理，它把限制换成了什么？——描述符带着矩阵的真实形状，硬件知道哪些元素在界外：读的时候补 0，写的时候不写。所以描述符版没有满块的限制，100 行的 A 和 K=1000 都能算对；限制换成了对齐，行步长的字节数必须是 16 的倍数。描述符只能在设备上现场创建，每个 CTA 需要 768 字节的全局暂存区，这是必须先 `triton.set_allocator` 的原因。（来源：`msg-3ff70516e47d8fcab939`；创建过程见[图解页](../attachments/08-grouped-gemm/grouped-gemm-data-movement.html)。）

- [要点] 没有 TMA 的设备上，描述符版会变成什么？——TMA 从 sm_90 才有。在 sm_89 上 Triton 把描述符改写成指针加 mask，mask 由描述符里的形状生成，结果相同，但编译产物里没有异步拷贝；以 AMD gfx942 为目标时同样被改写。教程用 `supports_tma()` 把描述符版限制在 sm_90 及以上。（来源：`msg-3ff70516e47d8fcab939`、`msg-da2e6a7d5eb51204397f`。）

## 转置、补齐与预处理

- [高价值问题] “这里对B矩阵的转置是真的对内存上的数据进行了转置排布的转换还是只是给了一个转置的视图呢？”——两次转置要分开看。主机侧的 `B.T.contiguous()` 是真的拷贝重排：`B.T` 只是视图，内存没动，步长变成 (1, 2)；`.contiguous()` 才新开内存按 [N, K] 排好。kernel 里的 `tl.dot(a, b.T)` 不搬数据，编译产物里只是给共享内存里那一块贴上 `transposed = true` 的标签。（来源：`msg-8c9c16db1d20b39774da`、`msg-18e9cf49172816464b64`。）

- [要点] 为什么只把转置视图交给描述符版不行？——包装函数只传首地址和 `stride(0)`，视图的 `stride(0)` 是 1，kernel 会把内存当成每行 1 个元素来读；描述符要求最后一维连续，行内步长写死为 1；TMA 是原样搬运，不会重排。真实系统里通常不需要这次拷贝：PyTorch 线性层的权重本来就按 [输出维, 输入维] 存，也就是 [N, K]。（来源：`msg-18e9cf49172816464b64`。）

- [高价值问题] “那么先前所说的16字节对齐的维度填充拷贝是发生在其内部的还是需要预先做好呢？”——也要预先做好。描述符只描述一块已经存在的内存，创建时不读数据、不搬数据，也不补齐。输入的补齐是一次需要调用方预先完成的拷贝；输出的补齐只是分配方式，由分配输出的那个函数负责，不发生拷贝。（来源：`msg-b64bc372bdd9ce653978`、`msg-a37173bba7b19617f928`。）

- [转折] 预处理规则被整理成速查表。——学习者要求：“希望你能帮我整理一下在各种输入情形下的对于异步拷贝和描述符的需要做的预处理操作以及后续影响。”助手按对齐、尺寸、存放方向与连续性、设备给出四张表和三条原则，并按“嗯，麻烦请加进图解页中。”加进了[图解页](../attachments/08-grouped-gemm/grouped-gemm-data-movement.html)的速查表一节。（来源：`msg-eb4f571dd1085a67a1d4`、`msg-985b25a53f2e9241c099`、`msg-dc839996b036e7ab7dae`。）

## 真实规模与综合验收

- [要点] 把前五个节点放回 DeepSeek-V3 的一层 MoE，哪些问题真的会遇到？——隐藏维 7168，每层 256 个路由专家，中间维 2048，每个 token 激活 8 个专家，所以升维那一步 G=256、K=7168、N=2048，只有 M 参差。K 相同，按步长分配天然均衡，但每个 CTA 要扫 256 个问题；N、K 都是整块，行步长都是 16 字节的倍数；真正要处理的是 M 方向的不满块。解码时每个专家只有几行，块和问题的大小就不匹配了。（来源：`msg-ff935af7181eb6b05dbe`。）

- [要点] 用 60–90 秒讲清教程的 grouped GEMM，学习者的版本覆盖了什么，漏了什么？——覆盖了：按同样的块大小切分、按 pid 领取并“按照每个矩阵乘问题划分tile数量的前缀和对应到主问题”、编号每次加 NUM_SM、两项收益、三项代价，以及它“更适用于大量的、较小规模、K维度相对一致的gemm问题”，少量的大问题逐个发射就能占满 SM。漏了两句：矩阵个数运行时才知道，所以矩阵不是参数，地址、尺寸和行步长都存在设备上的表里；教程假定尺寸是块的整数倍，真实的 MoE 只有行数参差。原版念出来约两分钟，需要压到 80 秒左右。（来源：`msg-7c181d8cbfc9d302a364`、`msg-da2e6a7d5eb51204397f`。）

- [要点] 只判断行是否存在的 mask，和 M、N、K 三个方向都判断的 mask，哪一种还能保持 16 字节的异步拷贝？——学习者预测正确：前一种“只要对于不存在的一行都采用整段跳过就可以了”，后一种“一行中可能末尾不满16字节的部分需要进行mask”，一条拷贝指令却只能整段跳过。编译验证：只有行方向的 mask 时仍是 24 条 16 字节的异步拷贝；三个方向都有 mask 时没有异步拷贝，退回 64 条 2 字节的读。（来源：`msg-7c181d8cbfc9d302a364`、`msg-da2e6a7d5eb51204397f`。）

- [纠错] 场景：同一道预测题，判断 DeepSeek-V3 里为什么只做行方向的 mask 就够。我说“K是隐藏层维度、N是输出维度且都是8的倍数” → 正确：够用的条件是 N、K 是块大小的整数倍，N=2048 是 16 个 128，K=7168 是 224 个 32。原因：能不能省掉 N、K 方向的 mask 看的是是否整块；8 的倍数管的是对齐，是另一件事。（来源：`msg-7c181d8cbfc9d302a364`、`msg-da2e6a7d5eb51204397f`。）

- [纠错] 场景：设计题，为 K 相差很大的 group 设计谁空谁领的动态方案。我说“需要添加一个关于每个子任务是否已被领取的program间共享状态标记” → 正确：一个计数器就够。显存里放一个整数，含义是下一个没人领的块编号；每个 CTA 空闲时做一次原子的读出旧值并加 1，读到的旧值就是它领到的块。原因：每块一个标记要逐个清零、要搜索哪个还空着、多个 CTA 抢同一个标记时输的要重试；计数器没有这三样。它的代价是每领一块做一次原子操作，所有 CTA 争同一个地址，谁领到哪一块每次运行都不同；各块工作量相同时没有收益。（来源：`msg-7c181d8cbfc9d302a364`、`msg-da2e6a7d5eb51204397f`。）

- [纠错] 场景：同一题，改成动态领取后顺序扫描问题表还成立吗。我说“顺序扫描一遍问题表依旧成立，需要扫描问题表的共享状态来尝试领取问题子任务” → 正确：结论对，理由要换。计数器只增不减，同一个 CTA 先后领到的编号一定递增，这和静态方案里 `+= NUM_SM` 的性质一样，所以顺序走一遍就够。原因：扫描成立靠的是编号单调，不是去扫描共享状态。（来源：`msg-7c181d8cbfc9d302a364`、`msg-da2e6a7d5eb51204397f`。）

- [要点] 计数器方案下，两个 CTA 同时来领为什么不会领到同一块？一次领 4 个连续编号有什么利弊？——学习者复查全对：“因为领取操作是原子化的”；一次领 4 块减少了领取次数，坏处是“更容易分得不均衡”，并自己举了最不利的例子：“一个问题是（M，N，K）=（256，256，7168），另一个问题是（256，256，32）。这两个问题都会产生4个连续的编号块，但工作量相差很大。”调度模型里完成时间与平均工作量之比：静态 1.09–1.27，一次领 1 块 1.02–1.04，领 4 块 1.14–1.23，领 16 块 1.62–1.88，因为成批领到的块来自同一个问题。（来源：`msg-a0011ffc6ef333f5d65a`、`msg-2b78dcea081eb1c72313`。）

- [纠错] 场景：迁移题，一个没有 TMA、也没有异步拷贝的新后端什么都不做时，PyTorch 的 `grouped_mm` 走哪条路、代价是什么。我说“代价就是多次调用的发射开销和SM资源无法充分利用” → 正确：还漏了一项。回退路径要先把偏移表拷回主机，这会造成一次同步，打断异步执行。原因：行数在设备上，而回退是在主机上逐个专家循环。（来源：`msg-7c181d8cbfc9d302a364`、`msg-da2e6a7d5eb51204397f`。）

- [要点] 把 grouped kernel 接到这样的新后端上，哪些东西会变，优先保证什么？——学习者答：两个版本“在这个后端的数据搬运中依旧是采用同步的拷贝”，教程的 `num_sms()` “会固定写死启动的CTA数量为148”。补充：描述符版会被改写成指针加 mask；调度、地址表和行方向的 mask 与后端无关。优先级上，M 方向的正确性（写越界是静默的）和行数留在设备上，应排在搬运方式之前。（来源：`msg-7c181d8cbfc9d302a364`、`msg-da2e6a7d5eb51204397f`。）

## 练习：提交、定位与测试缺口

- [转折] 练习约定与测试方式。——学习者回复“同意接受。”后，助手建立验收测试：同一个文件分只编译层、CPU 解释器层（`TRITON_INTERPRET=1`）和 GPU 层，保护区测试排在普通数值测试之前；一份不入库的参考实现和 8 种故意写错的变体用来检查测试本身。约定与验收项见 [Lesson](../lessons/08-grouped-gemm.md#条件片段练习约定)。（来源：`msg-b9ddbc592b95b22b3337`、`msg-99d732233f846a606674`。）

- [转折] 首次求助时，贴出的失败不是原本的失败。——学习者贴出 `4 failed, 80 passed` 并说“我不知道问题出在哪，请你帮我找找。”，回溯指向一段调试 `print` 里的 `offs.cpu()`，助手据此解释了读回主机的断言。学习者随即更正：“噢不，不是这个。这个print调试是我后面加的。”原本的失败是堆叠接口的数值不一致，`Mismatched elements: 3112 / 6400 (48.6%)`，本机解释器复现了同样的数字。（来源：`msg-5f23149498c3afeaffcb`、`msg-9fd517b3563965ebdf0c`、`msg-8ee2a4e22be13c12c31f`、`msg-d980437348a2e538d71c`。）

- [要点] 验收测试怎样检查不把 `offs` 读回主机，为什么禁止读回？——传进来的 `offs` 是 `torch.Tensor` 的子类，对它调用 `.cpu()`、`.item()`、`.tolist()`、`.numpy()`、`int()`、`bool()` 都会抛 `AssertionError`，直接打印也会触发，因为打印张量内部调用 `.tolist()`；在设备上做运算不受影响。读回主机时，主机必须等 GPU 把排在前面的工作做完；PyTorch 的回退路径正是先 `offs.cpu()` 再逐组循环。这个检查拦不住经普通张量转存后再读回的数据。（来源：`msg-9fd517b3563965ebdf0c`。）

- [转折] A7 的原因是学习者自己得出的。——按约定 A7 不给提示，助手只给了三样：细化的现象（输出第 0–49 行正确，第 50–116 行被写入但数值不对，第 117 行只写了一部分，第 118–167 行从未被写入）、地址表的定义、和已经通过的列表接口逐表对比的方法。学习者随后提出：“是不是ptrs转成tensor后做偏移加时要带上element size的单位？”（来源：`msg-16ecccefec520bd9e313`、`msg-27cbe2af70b954c9c7b4`。）

- [纠错] 场景：解释堆叠接口里地址偏移为什么少了一个因子。我说“因为转成tensor后就丢失了原指针的size单位信息了，变成了int64整数” → 正确：结论对，原因要改。单位信息不是在转成张量时丢的，`x.data_ptr()` 返回的本来就是按字节计的 Python 整数，主机侧从头到尾没有带类型的指针。原因：带类型的指针只在 kernel 里 `.to(tl.pointer_type(tl.float16))` 之后才出现，那时 `+ n` 前进 n 个元素；所以 `g_lds` 用元素作单位，而地址表的偏移必须换算成字节，即行数 × 行步长 × 元素大小。（来源：`msg-27cbe2af70b954c9c7b4`、`msg-7c05d8aa69775adc07d6`。）

- [要点] 列表接口为什么没有遇到字节还是元素的问题？——`grouped_matmul` 从不对地址做算术：每个视图的 `data_ptr()` 已经包含偏移，PyTorch 替调用方做了“存储偏移 × 元素大小”。堆叠接口首版写的是 `group_a_ptrs[1:] += offs[:-1] * stride_x`，偏移少乘了 2：第 2 组本该从第 100 行开始，实际落在第 50 行；第 3 组落在第 50.5 行，写 67 行正好到第 117.5 行，这解释了上面的三段现象。PyTorch 的设备侧准备 kernel 写的是 `A_ptrs[tid] = A + offs[tid - 1] * tensor_StrideA[0]`，`A` 是带类型的指针，乘元素大小由 C++ 编译器完成。（来源：`msg-7c05d8aa69775adc07d6`。）

- [纠错] 场景：预测题，K=7168、`x` 有 262,144 行、`offs` 是 int32 时，偏移量在什么整数类型下算出来。我说“261120 * 7168 * 2（fp16）= 3743416320 ，在int32数值范围下计算，会超越了int32的数值范围，会溢出，地址就错了。所以这个offs还是设int64应该更稳妥一些” → 正确：判断和算式都对，修法要改。溢出的是乘积，不是 `offs`；接口上的 `offs` 保持 int32，先在设备上转成 int64 再乘，这不算读回主机。原因：PyTorch 的 int32 张量乘 Python 整数仍是 int32，溢出后悄悄回绕而不报错，例子里会得到 −551,550,976；PyTorch 的同一步里步长是 `int64_t`，C++ 先提升再乘。（来源：`msg-eeb8f443d0bc01a9d901`、`msg-f3fe57771d76e9bd4ad7`。）

- [纠错] 场景：首次提交的 `grouped_matmul`，决定 `RAGGED_NK`。我在遍历完所有问题之后写了 `if N % block_n==0 and K % block_k == 0:`，用的是循环里剩下的、最后一个问题的 N 和 K → 正确：只要有一个问题的 N 或 K 不是整块，就要选 `RAGGED_NK=True`。原因：约定是 `RAGGED_NK=False` 时调用方保证每个问题的 N、K 都是整块；不整块的问题排在整块问题前面时，它的结果含 NaN，C 的保护区被改写。原有测试的混合组恰好都以不整块的问题结尾，没有测出来；补上的两个组把不整块的问题放在最前和中间。（来源：`msg-9fd517b3563965ebdf0c`、`msg-eeb8f443d0bc01a9d901`。）

- [纠错] 场景：首次提交的输入检查。我写了 `if x.device.type != "cuda" or x.device != device:`，把非 CUDA 的张量一律拒绝 → 正确：给了 `num_sm` 时非 CUDA 设备上的张量可以运行，不给 `num_sm` 时才抛 `ValueError`。原因：第 07 课的约定是拒绝 CPU 输入，这一课的约定不同，CPU 解释器层靠的就是这一点；照原写法解释器层有 47 项失败。（来源：`msg-9fd517b3563965ebdf0c`。）

- [纠错] 场景：第二次提交的设备检查。我在循环里写的是 `device = group_a[i].device`，每个问题只和自己比较 → 正确：所有问题的 A、B 和 `out` 都要和同一个设备比较。原因：五张表只能建在一个设备上，问题 0 整体在一个设备、问题 1 整体在另一个设备时，表里会放着别的设备的地址，kernel 在 GPU 上解引用主机内存的地址就是非法访问。原有测试只覆盖同一问题内 A、B 设备不同的情形。（来源：`msg-f3fe57771d76e9bd4ad7`、`msg-3c636e0425ec1f0ea5c2`。）

- [转折] 学习者的实现两次暴露了验收测试的缺口。——混合组的顺序和跨问题的设备不一致，原有测试都没有覆盖，助手如实说明是自己的疏漏并补测试，总数从 84 变为 88，再变为 91。设备检查改用一个不发射的替身代替 kernel，使缺少检查的实现也不会真的把跨设备的地址交给 GPU；CPU 解释器层用 PyTorch 的 `meta` 设备充当第二个设备。（来源：`msg-9fd517b3563965ebdf0c`、`msg-f3fe57771d76e9bd4ad7`。）

- [转折] GPU 证据来自哪里？——学习者在一台 RTX 4090 D（PyTorch 2.13.0+cu130，Triton 3.7.1）上运行同一个测试文件并贴回输出：GPU 层 `91 passed`，解释器层 `82 passed, 9 skipped`；实现文件的 SHA-256 与本机的副本一致。堆叠接口的偏移已改为先转 int64 再相乘。（来源：`msg-3c636e0425ec1f0ea5c2`、`msg-17681330c5e7bf8c1a46`。）

## A6：每项检查保护哪个假定

- [要点] 包装函数为什么是做检查的唯一位置？——kernel 拿到的只有五张表里的整数。一个张量原本带着 dtype、维数、形状、各维步长、设备和对齐情况，进了表以后只剩首地址、M、N、K 和行步长，其余的信息 kernel 没有办法验证。所以检查漏掉时 kernel 通常不报错，而是照着假定继续算；一项检查背后必须有一条 kernel 的假定，没有假定的检查只增加调用方的成本。（来源：`msg-78c4b5955106142f70e4`、`msg-1b20b732b34781c42b25`。）

- [纠错] 场景：A6 的说明，逐项回答去掉检查后会怎样。我说块大小的检查“去掉会编译报错”、sm 数量的检查“去掉也会编译报错”、行内连续的检查“去掉应该会出现load错误” → 正确：实测大多不报错。fp32 的 A 结果含 NaN、无异常；`wide[:, ::2]` 有 96.5% 的元素不对、无异常，算出的恰好是 `wide[:, :64] @ B`；`num_sm` 为 0 或负数时一个 CTA 都不发射，输出从未被写入、无异常。只有块大小取 48 或 K 方向取 8 时才编译报错。原因：kernel 只拿到表里的整数，看不到这些信息。（来源：`msg-57f94a6481520a794e26`、`msg-78c4b5955106142f70e4`。）

- [纠错] 场景：A6 的说明，设备检查保护什么。我说“第六项设备检查，本kernel启动要求cuda。去掉可能会有编译或者计算错误” → 正确：它保护的是表里每个地址在 kernel 运行的设备上有效，不是需要 CUDA。原因：Triton 只验证五张表本身是不是设备上的张量，表里装的地址没有任何人检查。（来源：`msg-57f94a6481520a794e26`、`msg-78c4b5955106142f70e4`。）

- [纠错] 场景：A6 的第二问，哪一项检查即使去掉，数值测试也无法稳定发现。我选了维数检查：“如果多出来的维度全是1，可能也不会有异常”，并认为对齐检查“如果去掉，可能会异步拷贝报错” → 正确：答案是对齐检查。`tl.multiple_of` 不被检查，保证不成立时 kernel 请求的仍是同样的字节，被违反的只是 `cp.async` 的前提，这是未定义行为，没有报错这个环节；CPU 解释器完全忽略这个保证，行步长 200 字节的输入算出来和 `torch.matmul` 一致。原因：所以对齐相关的测试只能写成期望抛 `ValueError`，没有一项比较数值；维数检查去掉后行为不变，仍被后面的行内连续检查拦住。（来源：`msg-57f94a6481520a794e26`、`msg-78c4b5955106142f70e4`。）

- [纠错] 场景：A6 的复查题，`out` 是一个首地址对齐、行步长 200 字节的视图，问 kernel 的哪个假定被违反、包装函数拒绝它对不对。我说“对行步长的16字节对齐的假定违反了”，并认为“处理正确。否则不报错进入kernel，会导致后续的tl.multiple_of前提保证不成立” → 正确：kernel 对 C 没有任何对齐假定，这个 `out` 不该被拒绝。原因：保证只存在于调用了 `tl.multiple_of` 的指针上，kernel 里只有 A、B 的块指针两处，编译出的中间表示里 `tt.divisibility` 恰好出现 2 次；C 是 32 条 `st.global.b16`，每条只写 2 字节。这是节点 5 那个差距的第三次出现，很可能来自描述符版：那里 C 由 TMA 写回，才需要对齐。（来源：`msg-46da190459196415b579`、`msg-1b20b732b34781c42b25`。）

- [要点] dtype、行内连续、对齐三项去掉后都不报错，为什么前两项数值测试能稳定发现，对齐却不能？——学习者复查通过：“dtype影响了计算数据的底层方式……行内连续则影响了读取数据的方式……但对齐产生未定义行为，结果可能正确可能错误。”说得更确定一些：前两项改变的是 kernel 读到哪些字节、怎样解释它们，每次运行、每台设备都错成同一个样子；对齐不改变请求的字节和解释方式，结果交给硬件决定。（来源：`msg-46da190459196415b579`、`msg-1b20b732b34781c42b25`。）

- [要点] 把 kernel 里 B 的 `tl.multiple_of` 删掉、A 的保留，包装函数的对齐检查各自还有没有对应的假定？未对齐的 B 还会不会导致未定义行为？——学习者第二轮复查全对：“A的multiple_of的声明保证被保留了。但B和out没有保证，就没有对应的kernel假定”；“此时就不会出现未定义行为，因为本来就没声明保证，对B的数据读取是同步的。代价是失去了异步拷贝的收益。”编译结果一致：A 仍有 6 条 16 字节的 `cp.async`，B 变成 16 条 `ld.global.b16` 加 16 条 `st.shared.b16`，C 的 32 条 `st.global.b16` 不变。（来源：`msg-2a5ac3a4a0e68920c3b2`、`msg-526f6f52aab282c562d7`。）

## 学习者报告的实现问题

- [要点] kernel 里能不能用 `continue` 跳过 M 为 0 的问题？——学习者报告：“我之前采用了continue跳过，但发现triton似乎不支持continue，会报错。”复现的报错是 `unsupported AST node type: Continue`，`break` 也一样，代码生成器没有处理它们的函数；用 `if` 包住循环体可以编译。本课其实不用处理：M 为 0 时块数为 0，`while` 不会进入。（来源：`msg-2c0d015a39e51d08ff85`、`msg-9e2c5d859ab2b7b53fe2`。）

- [要点] 在循环里把读出的标量指针原地改写成块指针，会怎样？——学习者报告：“一开始写成了原地将变量扩展指针block，在循环体内会编译报错，而且循环偏移了。”报错是 `Loop-carried variable … has initial type pointer<fp16> but is re-assigned to <[…], pointer<fp16>> in loop`：跨迭代传递的变量类型必须不变。类型一致时能编译，但每一轮都在上一轮的结果上再加一次完整偏移，地址逐轮累加；教程的 `a_ptrs += BLOCK_SIZE_K` 也是原地改写，区别是每轮只加增量。（来源：`msg-2c0d015a39e51d08ff85`、`msg-9e2c5d859ab2b7b53fe2`。）

- [要点] 构造 mask 时，多个比较之间的括号为什么不能省？——`a < M & b < K` 报 `simultaneous multiple comparison is not supported`。Python 里 `&` 的优先级高于 `<`，表达式被解析成链式比较 `a < (M & b) < K`；这条规则在 NumPy 和 PyTorch 里相同，不是 Triton 特有的。（来源：`msg-2c0d015a39e51d08ff85`、`msg-9e2c5d859ab2b7b53fe2`。）

- [要点] 表里的行步长为什么必须取 `stride(0)`？——学习者的结论：“步长一定要通过stride接口读取，不能假设连续而读最后一维的size。”`[4, 100]` 的张量取 `[:, :64]` 后形状是 `(4, 64)`、步长是 `(100, 1)`；用列数代替不报错，只是结果错。验收测试里带保护区的视图和同一个张量的多个切片两类用例覆盖这一点。（来源：`msg-2c0d015a39e51d08ff85`、`msg-9e2c5d859ab2b7b53fe2`。）
