## 学习过程

- [要点] 为什么 padding 不会污染 max 和后续指数和？——在 `M=5,N=781` 的设计复述中，我正确给出
  `grid=(5,)`、`BLOCK_SIZE=1024`、781 个有效 lane 和 243 个 padding lane，并说“由于exp(-inf)为0，
  就不会在后续计算和时影响求和计算。”评审补齐了“减去有限 row max 后仍为 `-inf`”这一步；
  适用前提和 reduction 链条见 [Lesson 的 mask 与 reduction 说明](../lessons/02-fused-softmax.md#mask-与-reduction-单位元)。
  （来源：[B] #005，2026-08-03T09:20:57.499Z → #009，2026-08-03T09:25:09.512Z）
- [纠错] 场景：解释空 batch 与空 reduction domain 的接口区别。我说“在我看来都是空数据，都应该提示
  告警并返回”，又把 `N=0` 的问题部分归因于“浪费计算资源” → 正确：本练习允许 `M=0,N>0` 返回
  空结果，但明确拒绝列维度为 0。原因：前者没有需要归约的行，后者没有有效的行内计算域；这是本练习
  的接口约定，不能扩大为所有框架的统一行为。我后来复述“另一种是样本内为空，那么就无法计算了。
  所以要明确接口拒绝。”（来源：[B] #005，2026-08-03T09:20:57.499Z → #009；#019，
  2026-08-03T10:09:46.226Z → #024）
- [纠错] 场景：理解测试里的每行和断言。我说“我还以为是输入的每一行和” → 正确：应检查 softmax
  **输出**每行之和接近 1。原因：归一化约束属于输出，输入行和没有这项要求；独立不变量检查与
  reference 对照的用途见 [P01 评审提示](../lessons/02-fused-softmax.md#p01-r03r04-提示记录2026-08-03)。
  这次误解也来自提问没有先说清输入／输出。（来源：[B] #013，2026-08-03T09:38:54.922Z →
  #015；#016，2026-08-03T09:43:10.233Z）
- [纠错] 场景：把 `num_stages=2` 类比为两段工作。我说“两个阶段的工作是互相独立的” → 正确：这里
  讨论的是同一 program 内不同循环迭代的在途与重叠机会，不能把 stage 当成独立 worker，或把一行
  计算机械切成两段。原因：同一行的 load、max、exp、sum、归一化与 store 仍有依赖；实际流水由编译器
  安排。（来源：[A] #013，2026-07-31T05:33:53.918Z → #016，2026-07-31T05:36:15.836Z）
- [纠错] 场景：解释 stages 增加后的资源代价。我说“如果资源不足，会拖慢单个stage的耗时，进而拖慢
  整体耗时”，并类比为临时工效率低 → 正确：额外资源压力通常先减少每 SM 可驻留的 programs，
  不直接说明单个 stage 更慢。原因：资源占用限制并行驻留容量；若要讨论 spilling 等单 program
  变慢机制，还需相应证据。后来进一步校准：`stages=4` 不保证保存四个完整行，也不保证 registers
  与 shared memory 同时增长。（来源：[A] #013，2026-07-31T05:33:53.918Z → #016；
  [C] #006，2026-08-05T06:37:06.138Z → #009）
- [高价值问题] 我问“triton里的persistent 好像与其他所讲的cuda的persistent kernel不太一样”，
  因为记得 CUDA 版本会用 `while` 持续取任务。答疑区分了本课静态 grid-stride 与动态任务队列；
  随后我判断“耗时差异很大的大量任务更适合用动态的调度分配”。这个追问把判断依据从循环语法转向
  任务来源与成本差异，具体模型见 [Q02](../lessons/02-fused-softmax.md#q02triton-softmax-与-cuda-动态任务型-persistent-kernel-是否相同)。
  （来源：[A] #013，2026-07-31T05:33:53.918Z → #016；#017，2026-07-31T05:44:42.643Z → #018）
- [纠错] 场景：解释 100% occupancy。我已经判断它不能保证最佳性能，但仍说“只能说计算单元全都在
  被用，但不一定用得好” → 正确：只能说 warp 驻留容量已满，不能据此断定执行单元都在工作。
  原因：等待访存或依赖的 stalled warp 仍计入 active warps；active、eligible、issued 的区分见
  [Q03](../lessons/02-fused-softmax.md#q03occupancy-的正式定义是什么)。（来源：[A] #027，
  2026-07-31T06:07:57.694Z → #029，2026-07-31T06:08:50.464Z）
- [转折] 对 `M=10,P=3`，我先正确列出三个 program 分别处理的行，却只用“连续地合理安排”解释覆盖。
  经追问后，我改为“因为商和余数唯一就能唯一确定每一行是被哪一个program进行处理”。转折是从举例
  枚举行号到用 `r=p+kP` 的唯一分解解释不漏行、不重行；证明见
  [P02 预测复核](../lessons/02-fused-softmax.md#预测复核与术语校准)。（来源：[C] #006，
  2026-08-05T06:37:06.138Z → #009；#010，2026-08-05T07:01:00.914Z → #013）
- [纠错] 场景：实际 `grid=M` 时能否产生跨行循环流水。我说“如果能够在前一批program进行计算处理时，
  预先启动后一批program开始读取数据，也有可能实现软件流水” → 正确：不同 programs 的交错执行属于
  硬件调度，不能算作单个 program 内 `tl.range(num_stages=...)` 的跨迭代流水。原因：每个 program
  只有一次行迭代，没有自己的下一行可重叠。随后我复述“不同programs之间的执行属于硬件调度”，答疑
  又强调根本依据是 `num_stages` 的作用域。（来源：[C] #006，2026-08-05T06:37:06.138Z → #009；
  #010，2026-08-05T07:01:00.914Z → #013）
- [纠错] 场景：解释低 occupancy 的 stages 4 为什么仍可能更快。我先转向“为每一行划分小block”，
  后又说“因为增加了单program的数据并行度” → 正确：当前问题保持行分配算法，讨论的是多个独立
  迭代在途带来的指令级并行与延迟隐藏机会。原因：分行会引入另一种归约方案，stages 本身也不自动
  把当前行切成更多并行块。最后我复述“提升了指令级并行与延迟隐藏机会了”。（来源：[C] #006，
  2026-08-05T06:37:06.138Z → #009；#010 → #013；#014，2026-08-05T07:04:16.838Z）
- [高价值问题] 我问“Registers、shared memory、resident programs 和理论 occupancy该怎么测出来？
  这也能测出来吗？”答疑把编译产物中的静态资源、基于设备容量的理论推导、profiler 的运行时观测
  分开。随后我独立算出三个容量上限为 6、13、8，驻留上限 6、理论 occupancy 75%、grid 648；
  这是对当时给定 A100／官方特化数据的复算，不能作为所有实现的常量。证据分层与计算见
  [P02-Q04](../lessons/02-fused-softmax.md#p02-q04资源与-occupancy-怎样获得)和
  [资源复算确认](../lessons/02-fused-softmax.md#资源复算确认)。（来源：[C] #014，
  2026-08-05T07:04:16.838Z → #018；#019，2026-08-05T07:31:07.300Z → #022）
- [转折] 我提交默认 grid 推导后，Review 发现旧测试只经过显式 `num_programs` 路径，默认路径仍会
  因属性来源、零 shared memory 等问题失败。独立读取当前简化 kernel 后，`N=781` 的 stages 1/2/4
  得到相同 grid 864，区别于先前官方特化的 stages 4 → 648。之后 benchmark Review 又发现资源探测
  误用 `M` 生成 block。共同教训是资源/grid 必须来自实际 launch 所用的同一特化，不能复制官方数值，
  也不能用旧分支的通过结果证明新增默认分支。过程见
  [P02-B 首轮评审](../lessons/02-fused-softmax.md#p02-b-第一轮评审2026-08-05)与
  [P02-Q12](../lessons/02-fused-softmax.md#p02-q12直接复用-derive_resource_record-的最小方案)。
  （来源：[C] #039，2026-08-05T09:22:54.934Z → #044；#129–#130，2026-08-06T06:20:11.064Z
  → 2026-08-06T06:21:41.413Z；#146，2026-08-06T07:12:20.452Z）
- [转折] Benchmark 的公式 Review 发现 theoretical occupancy 错用了被小 `M` 截断后的全设备 grid。
  补充用例区分了“实际只 launch 一个 program”与“该特化按每 SM 资源推导的驻留上限”；后续复审确认
  公式修正。由此避免把 grid cap、资源理论上限和运行时 achieved occupancy 混成一个量。（来源：
  [C] #112，2026-08-06T03:55:42.745Z → #113；#137，2026-08-06T06:50:47.988Z）
- [转折] 首版 benchmark 重复探测资源，persistent 延迟约 0.95 ms；助手因此一度要求全部改为直接
  kernel launch。我反驳“要比较性能，就该比较端到端的”，并强调其他 providers 同样分配内存和做检查。
  最终实验问题改为准备后的 wrapper 调用：每个 case 的 JIT／资源与 grid 初始化放在计时外，计时内
  继续调用 wrapper，保留每次调用的分配与检查。约 0.95 ms 的数据应归入未缓存默认 API 场景，不能
  单凭数值把它判为错误，也不能与准备后的调用混用。测量边界见
  [P02-Q10](../lessons/02-fused-softmax.md#p02-q10为什么本实验选择-wrapper-level-端到端比较)。
  （来源：[C] #113，2026-08-06T03:59:30.446Z；#114，2026-08-06T04:14:24.542Z → #119；
  #120，2026-08-06T04:47:54.111Z → #122，2026-08-06T04:50:41.229Z）
- [转折] 我明确提出“benchmark不进行正确性检查。”最终把 reference 对照交给独立 GPU 功能测试，
  benchmark 负责准备、同步和计时。这个调整改变了检查位置，没有让性能结果取代正确性证据；三个
  benchmark shape 与各 stages 的功能覆盖记录在
  [P02-Q14](../lessons/02-fused-softmax.md#p02-q14benchmark-不进行正确性检查)。
  （来源：[C] #148，2026-08-06T07:22:37.457Z → #152，2026-08-06T07:26:26.211Z）
- [高价值问题] 我追问“关于benchmark结果，该如何理解呢？我看stage=4的kernel并不是表现最好的。”
  答疑用实际每 program 的行数重新检查原先预期：小 shape 只有一次迭代；`4096×781` 每 program
  只有 4–5 行，三个 stage 的理论 occupancy 却都相同。因此不能一律把 stage 4 较慢解释为 occupancy
  下降；短循环中流水成本难以摊薄只是当时的合理解释，尚无 profiler 或重复试验置信区间作进一步
  因果确认。具体观测与限定见 [P02-Q15](../lessons/02-fused-softmax.md#p02-q15为什么最终-benchmark-中-stage-4-不是最快)。
  （来源：[D] #001，2026-08-06T08:11:15.621Z → #006，2026-08-06T08:15:20.586Z）
- [转折] 同次结果复盘中，助手发现只有 `N=781` 的资源表，不能外推到 `N=2049`，于是补读新特化。
  后者三个 stage 的默认 grid 分别为 432、540、324；因此实验比较的是 stage 与各自资源/grid 一起
  变化后的默认策略。结论从泛化的“stage 效果”收紧到当前实现、shape 和默认策略；若研究流水深度
  的独立影响，需要共同显式 grid 等后续对照，不能从现有结果直接下单因素因果结论。（来源：[D]
  #003，2026-08-06T08:11:56.833Z → #006，2026-08-06T08:15:20.586Z）
- [要点] 图中的有效 GB/s 能当作实际 DRAM 带宽吗？——结课后的解释专门区分了逻辑工作量与硬件流量，

  这里没有学习者独立回答这项问题的证据。（来源：[D] #006，2026-08-06T08:15:20.586Z）
- [高价值问题] 我要求不做 P03 编码，只比较 log-softmax 与 softmax 的区别和额外注意点。讲解中的

  实际稳定计算路径。稳定公式、输出不变量和非有限输入边界见
  [P03-Q16](../lessons/02-fused-softmax.md#p03-q16log-softmax-与-softmax-的差异和额外注意点)。
  此例来自助手讲解中的最小实验，没有在材料中看到我独立推导或实现它。（来源：[E] #001，
  2026-08-07T01:24:23.780Z → #004，2026-08-07T01:28:49.518Z）
