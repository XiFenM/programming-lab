## 学习过程

- [要点] 参数跨行共享，是否意味着一行输入变化会改变另一行的前向输出？——学习者回答：
  “第一行的均值、方差和最终输出都不会改变。因为均值和方差只与第一行的初始值有关。”保留其对
  前向依赖范围的判断；稳定结论见 [Lesson E-01](../lessons/05-layer-norm.md#e-01)。（来源：
  `msg-37cbb1fc429f73cae229`；反馈：`msg-bbbf2f8bc512fddc180e`）

- [纠错] 场景：逐行 program 的地址合法性。学习者发现总元素数边界会混入下一行，却提出“应改成
  mask = offsets < M”。正确：mask 应比较行内列号与 `N`；`M` 是行数，张量线性偏移也不是这里的
  mask 变量。澄清后，学习者在 `M=5,N=3,B=4,pid=2` 中给出 `[T,T,T,F]`、有效偏移
  `[6,7,8]`，并在综合例中独立解释了跨行误读。见 [Lesson E-02](../lessons/05-layer-norm.md#e-02)。
  （原回答：`msg-02aaf958a17f922adf4f`；纠正：`msg-b5f6f05604217b651e69`；重新区分：
  `msg-2ee6278dbc0909179995`；迁移：`msg-d940d44f77525cbaa7e5`）

- [要点] load 时给 padding 补零，为什么还不足以保证方差正确？——在 `N=5,B=8,mean=2` 的
  变式中，学习者自行指出无效位置会在减均值后贡献均值平方，并算出额外方差为 `2.4`。稳定结论见
  [Lesson E-02](../lessons/05-layer-norm.md#e-02)。（来源：`msg-aecae4b86b2b51a0a51d`；反馈：
  `msg-6e53c19c5cdd6459811d`）

- [纠错] 场景：汇总两行对同一参数的梯度。学习者分别算对 `dw_j` 的贡献 `3` 与 `-5`，却说
  “汇总后 w_j 的梯度为 2”。正确：`dw_j=-2`；带符号的行贡献会互相抵消。`db_j=8` 原本正确。
  见 [Lesson E-03](../lessons/05-layer-norm.md#e-03)。（来源：`msg-361675db0c4325a2e779`；纠正：
  `msg-bea19d7a8035e7590e09`）

- [纠错] 场景：保存全部 program 的参数梯度贡献。学习者说“临时贡献数组形状应该是 `[N]`”。
  正确：`[N]` 只是单个 program 的局部向量；若逐行独立保存，需要 `[M,N]`，再沿行维归约为
  `[N]`。澄清后，学习者给出 `M=4,N=3,pid=2` 的写入偏移 `[6,7,8]`。见
  [Lesson E-03](../lessons/05-layer-norm.md#e-03)。（原回答：`msg-fc660260527a8859c4fc`；纠正：
  `msg-f4ddcf5d5c52364124a4`；后续回答：`msg-5611921115842aec990e`）

- [要点] 把组数改为 `G=M`，能否删除第二个归约 kernel？——学习者在综合例中说明不能：各行
  贡献只是更分散地暂存，仍未形成共享参数的最终梯度；同时缓冲区从 `[G,N]` 扩大到 `[M,N]`。
  见 [Lesson E-06](../lessons/05-layer-norm.md#e-06)。（来源：`msg-d940d44f77525cbaa7e5`）

- [转折] 常量行的前向输出为 `b`，是否足以断言输入梯度为零？——学习者独立给出
  `dx=[2r/3,-r/3,-r/3]`，明确否定该断言，并把原因连回行内分量耦合。这个反例由助手提出，
  不是学习者原有误解。见 [Lesson E-05](../lessons/05-layer-norm.md#e-05)。（题目：
  `msg-7c7ca30888ab4dfd2277`；回答：`msg-c5cf0e30fe8c6909be1c`）

- [高价值问题] “目前主流的框架对于 LayerNorm 的反向计算都是这样的两阶段且需要临时槽的设计吗？”
  ——当时核对的源码表明实现会按归约方向、形状和后端选取不同组织：多个 kernel 不等同于参数梯度
  必须保存逐行部分和，部分实现按 CTA 保存较少的部分和。版本化比较见
  [课程补充讨论](../lessons/05-layer-norm.md#production-design)；不把它泛化为所有版本或性能结论。
  （来源：`msg-0579bf5688e682503bd0`；回答：`msg-62deb7600a8378ec0044`）

- [要点] `atomic_cas(lock,0,1)` 返回什么？——学习者正确回答：第一次返回旧值 `0` 并把锁改成
  `1`；A 未释放时，B 再调用返回旧值 `1`，锁仍为 `1`。随后独立构造
  `load_A → load_B → store_A → store_B`，说明拆分 load/store 会让两者都进入临界区。
  （来源：`msg-75cb4fcd8d45952eeb03`、`msg-f2df5cbc7066a6dd4de2`；反馈：
  `msg-f68790028a5116782d3c`、`msg-962ad3ebf123043a9243`）

- [转折] 学习者追问：“为什么 B 看到 relaxed 锁变为可获取状态，不能保证另一个位置的更新也已经
  按要求对 B 可见？”关键差值是：锁槽的原子竞争与受保护 `buffer` 的跨 program 可见性是两件事；
  relaxed 不为周围普通访问建立交接，生产者 release 与消费者 acquire 才形成对应同步链。
  （来源：`msg-b22f9d9ecd5de47c06ab`；回答：`msg-382c5cbad9965f040899`）

- [纠错] 场景：解释普通 `load/store` 与跨 program 可见性。学习者尝试概括为“store 和 load 这些
  操作本质上是异步的，仅发出读取和写入的指令”。正确差值：普通访问可以流水化、重排或命中旧缓存，
  但不应等同于显式异步操作；同一计算链的数据依赖只保证先取得读取结果再计算，并不保证读到另一
  program 刚写的版本。跨 program 仍需适当同步；同 stream 的 kernel 边界也可提供交接。
  （原回答：`msg-1fdbf673651e32b57b11`；纠正：`msg-8f838f017a2abb88abcd`）

- [纠错] 场景：为什么 release 前还需要 `tl.debug_barrier()`。学习者一度理解为“只要有一个线程
  完成了 store 工作，就直接会触发”解锁，随后又归因为“不确定哪个线程负责解锁”。正确：解锁仍是
  被某个执行线程执行到的指令；barrier 的必要性与是否知道该线程身份无关。它让当前 block 内所有
  协作线程的写入先汇合，再由 release/acquire 把完整更新交给下一 program。
  （原回答：`msg-23b3dd3194b5143ec1f1`、`msg-b552c155f3a4e5be3375`；纠正：
  `msg-0bac50b0c2701aab3bb8`、`msg-26d4b530d966dc82868d`；转折：
  `msg-01026b2be0d556c8c8cf`）

- [要点] 官方反向 kernel 没有沿 `N` 循环，是否遗漏了宽行？——学习者经源码核对后总结“是外层
  wrapper 设置的原因”。固定教程的 wrapper 保证 `BLOCK_SIZE_N >= N` 并在反向复用该值；绕过这个
  前提则结论不成立。阅读 kernel 时必须连同 wrapper 的输入拒绝和 launch 参数一起看。
  （来源：`msg-f22eadc5284891f20e65`、`msg-c779bb11d3980643e20f`；回答：
  `msg-e174c950f835ed75121b`）

- [纠错] 场景：首次反向数值 Review。学习者观察 `dw/db` 有问题；逐项隔离后，真实根因是第一阶段
  `dw` 使用原始 `x`，而应使用 `x_hat`。当轮 `db` 全部符合参考，只是测试在 `dw` 断言失败后未继续
  检查。这个过程避免把“没有执行到”误判为“也算错”。（来源：`msg-8536512a30e50c3796ea`；证据：
  `msg-a2df5a234170b59ca9e7`、`msg-8d8de76a31733e0afa62`；结论：
  `msg-7e3baa5bc9de4b7b0d77`）

- [纠错] 场景：FP16 方差 padding。把 `other=mean` 用于 FP16 load 会先把 FP32 mean 量化到
  输入 dtype；再转回 FP32 并减原 mean，padding 可能留下残差。正确不变量是无效 lane 在 FP32 方差
  归约中严格贡献零。学习者修订后，对应近常量行回归通过。（定位：
  `msg-7e3baa5bc9de4b7b0d77`；复验：`msg-24658425215e5cd52b12`）

- [转折] 练习实现采用共享 `[G,N]` 槽与锁，而最初契约写成 `G=M`。学习者明确选择“保留当前共享
  分组方案，并相应修订契约”，使验收与实际设计重新一致；这不是 `dw` 数学错误的原因。
  （来源：`msg-3019f35060033d6d8e8f`；后续：`msg-7a831a5b1cbc65ee7323`）

- [纠错] 场景：FP16 的加权上游梯度。若先在 FP16 中形成 `dy*w`，接近的值可能已舍入为相同结果；
  乘积之后再转 FP32 无法恢复信息。学习者修订为两个 `dx` 循环都先把操作数转 FP32，再相乘；在
  常量行变式中独立推导 `dx=r[2delta/3,-delta/3,-delta/3]`，并解释了为何迟转精度不足。
  （问题与修订：`msg-cf31c67d94c43dc21dc9`、`msg-9630f7991fa41cf9ae55`、
  `msg-2828a42c86cec2768116`；独立解释：`msg-0d8531540ca001fca16d`）

- [纠错] 场景：均值除法的精度边界。学习者正确指出 `tl.div_rn` 只改善当前 FP32 除法的舍入，不能
  修复此前求和已有的误差；但把常量行均值偏差对应的每列 `dw` 贡献直接写成
  `-eta/sqrt(epsilon)`。一般式应是 `-eta*r`，因为保存的 `rstd` 也由实际方差决定。进一步检查后，
  学习者给出偏差均值下的方差 `(1/N)sum(eta^2)=eta^2`。
  （原回答：`msg-1eb16800796616bd5b0f`；纠正：`msg-1053550370117eaee607`；补齐：
  `msg-28bfc66366010a7aad57`）

- [纠错] 场景：新形状 `(M,N)=(129,131)` 的尾部。学习者正确给出 `BLOCK_SIZE=G=64`，以及
  pid 128 属于组 0、与 pid 0 和 64 共享槽，却把最后一轮的有效列数写成 `1`。正确是 3 个，即列
  `128,129,130`；换成 `N=130` 后，学习者独立给出前四个 mask 为 `[T,T,F,F]`。
  （原回答：`msg-eb9ae965d0fa30cc691b`；纠正：`msg-52d822197df761832bcb`；迁移：
  `msg-25d2ef9264e6635ce7fb`）

- [纠错] 场景：补齐反向设备检查时，条件被拼成 `x.devicex.device.type`，使反向在进入 kernel 前
  抛出 `AttributeError`。学习者确认“噢，我漏写了”并修复；完整复验恢复为 95 passed、8 个双 GPU
  用例因硬件条件跳过。这里保留的是修改接口边界后必须重跑完整路径的实践转折。
  （提交：`msg-28bfc66366010a7aad57`；诊断：`msg-de2716792a33178a27ca`；修订：
  `msg-2f68cc002842f6f37b89`；复验：`msg-cd82349e540eb6bdc5b5`）
