## 开课导入

kernel 里经常要用超越函数，比如 `asin`、`erf`、`lgamma`、`pow`。前几课用过的 `tl.math.exp2` 会被 Triton 直接降级成一条硬件指令 `ex2.approx`，但大多数函数没有对应的单条指令。它们需要靠范围约简、多项式逼近和特殊值处理拼出来，还要保证误差上界。自己写这些既难又容易出错。好在 GPU 厂商已经提供了验证过的实现，形式是 LLVM bitcode：NVIDIA 的 libdevice（`libdevice.10.bc`，Triton wheel 自带，约 463 KiB），AMD 的 ocml／ockl。

Triton 要解决的矛盾是，同一行 `libdevice.asin(x)` 必须同时满足四点：
- 写的时候，前端不知道将来用哪个厂商的库；
- 编译时，要映射到不同厂商的符号（`__nv_asinf` 或 `__ocml_asin_f32`）；
- 要按 dtype 选中 float 或 double 版本；
- 运行时，不能真的为每个线程的每个元素付一次函数调用的开销。

Triton 的办法分成两半。前端只记下“调用哪个符号”；到了 LLVM IR 阶段，后端才把厂商的 bitcode 链接进来，再由 O3 优化把它内联。这个设计带来几项取舍：dtype 覆盖不全（不支持 fp16）；精确的库函数和近似的硬件指令之间要权衡速度与精度；ftz、近似 sqrt 这类编译期开关会改变结果；每个后端只实现一部分函数，影响可移植性。

这一课和你的工作直接相关。在非 NV 加速器上接入 Triton 时，数学函数库的映射和链接是必须补上的一环；PyTorch Inductor 生成的 Triton kernel 也大量调用 libdevice。

**完成标准**：
- 能对着下面的骨架，讲清每一段的输入、输出和负责者；
- 遇到没见过的后端或 dtype，能预测它会在哪一步成功或失败；
- 写出并验证一个调用 libdevice 的 kernel。

### 全流程骨架

先定义三个符号：
- `x`：kernel 里的一个块张量，形状 `[BLOCK_SIZE]`，元素类型为 `T`，主例中 `T = fp32`。
- `num_warps`：每个 program 的 warp 数，默认 4，每个 warp 32 个线程。
- `E`：每个线程持有的 `x` 元素个数，由 TTGIR 的布局决定，节点 3 会讲。

```text
Python:  y = libdevice.asin(x)                       x: [BLOCK_SIZE], T
  │ ① AST→TTIR：module_map 把接口模块 triton.language.extra.libdevice
  │    整体换成后端实现 triton.language.extra.cuda.libdevice
  │ ② extern_elementwise：用 (T,) 查表 → symbol "__nv_asinf"，返回 fp32
  ▼
TTIR:    tt.extern_elementwise %x {symbol="__nv_asinf", pure=true} : tensor<1024xf32>
  │ ③ TTGIR 分配布局：每线程持有 E 个元素（本机探针中 E = 1024 / (32×4) = 8）
  ▼
LLVM IR: 每个元素一条 call @__nv_asinf(float)，此时函数只有声明、没有定义
  │ ④ make_llir：有外部依赖 → link_extern_libs(libdevice.10.bc, LinkOnlyNeeded)
  │    → 链入的函数改为 internal → nvvm-reflect-ftz=1 → O3 优化
  ▼
PTX:     没有 call；asin 已内联为 abs / fma 多项式 / sqrt.approx.ftz 等指令
  │ ⑤ ptxas
  ▼
cubin
```

路线分六个节点：
1. 接口模块替换（本次讲）
2. 按 dtype 分派（本次讲）
3. 布局与逐元素 LLVM 调用
4. 链接、reflect 与内联
5. 选择与取舍：`tl.math`、libdevice、`inline_asm_elementwise`、自定义 bitcode，以及教程第二段自定义路径的前提
6. 迁移到 AMD 和非 NV 后端

六个节点讲完后，依次是：我做串讲、综合验收（含一道 60–90 秒口述题）、O4 练习、GPU 机器上的数值对照、结课确认。

## 节点 1：接口模块与后端替换

**结论**：`triton.language.extra.libdevice` 只是一个接口模块，里面 198 个函数的函数体全是 `...`。真正的实现由各后端提供。编译器把 Python AST 翻译成 TTIR 时，会按目标后端给出的 `module_map` 把这个接口模块整体换掉。

**机制**：
- **实现在哪**：CUDA 的实现是 `triton.language.extra.cuda.libdevice`（源码在 `third_party/nvidia/language/cuda/`，197 个函数）；AMD 的是 `...extra.hip.libdevice`（57 个）。`extra/__init__.py` 在 import 时自动发现并注册这些后端子包。
- **怎样声明映射**：后端实现 `get_module_map()`。CUDA 的返回值是 `{"triton.language.extra.libdevice": cuda.libdevice}`，见 `third_party/nvidia/backend/compiler.py:225`。
- **在哪里替换**：`CodeGenerator` 构建全局作用域时（`code_generator.py:309` 起）分两种情况处理：
  - 全局名本身是模块，并且在 map 里，就换成映射目标；
  - 全局名是从接口模块导入的函数，就按 `__module__` 换成目标模块里的同名函数。
  
  此外，访问 `libdevice.asin` 这样的属性时，`visit_Attribute`（`:1507`）会沿 map 一直替换到不动点。

**为什么这样设计**：让 kernel 源码和后端解耦。同一份 kernel 能在 CUDA 和 ROCm 上编译，选哪个实现由编译目标决定，而不是由 import 语句决定。直接写 `from triton.language.extra.cuda import libdevice` 也能用，但 kernel 就绑死在 CUDA 上了。代价是：接口只是名字的集合，不保证每个后端都实现了每个名字。

**真实系统**：PyTorch v2.13.0 的 Inductor 生成的 Triton 代码里写的是 `libdevice.erf(...)`、`libdevice.asin(...)`，导入的正是后端中立的接口模块（见 `torch/_inductor/runtime/triton_compat.py`）。它为旧版 Triton 准备的回退链里，除了 `tl.extra.cuda.libdevice`，还有 `tl.extra.intel.libdevice`。可见第三方的 Intel XPU 后端也是按同样的模式提供自己的实现。

**边界**：接口是各后端函数名的**并集**。例如 `fast_tanhf` 只有 AMD 实现，对应 `__triton_hip_fast_tanhf`，CUDA 没有。kernel 用了当前后端没实现的函数时，替换后的模块里找不到这个属性，编译在 AST→TTIR 阶段就失败了，与 dtype 无关。

## 节点 2：按 dtype 分派，生成 TTIR 外部调用

**结论**：后端实现里的每个函数，本质上是一张表：“参数 dtype 元组 → (符号名, 返回 dtype)”。`core.extern_elementwise` 在编译期按实参的 dtype 查这张表，生成一条带 `symbol` 属性的逐元素操作 `tt.extern_elementwise`。查不到就编译失败，不做隐式类型提升。

**机制**：以 CUDA 的 `asin` 为例：

```python
@core.extern
def asin(arg0, _semantic=None):
    return core.extern_elementwise(
        "", "", [arg0], {
            (core.dtype("fp32"), ): ("__nv_asinf", core.dtype("fp32")),
            (core.dtype("fp64"), ): ("__nv_asin", core.dtype("fp64")),
        }, is_pure=True, _semantic=_semantic)
```

`extern_elementwise`（`core.py:3418`）做三件事：
1. 把每个实参转成张量，收集它们的 dtype 元组 `(T₁, T₂, …)`；
2. 用这个元组查表得到返回 dtype。有多个实参时先互相广播，结果的形状取广播后的形状，元素类型取表里的返回类型；
3. `dispatch` 取出符号名，交给 `builder.create_extern_elementwise(...)` 生成 TTIR。

前两个参数 `lib_name` 和 `lib_path` 在 CUDA 实现里都是空串。前端只记符号名，不关心库文件在哪；库文件由后端在节点 4 链接。

本机 compile-only 的实际 TTIR（fp32）：

```text
%x_6 = tt.extern_elementwise %x_5 {libname = "", libpath = "", pure = true, symbol = "__nv_asinf"}
       : (tensor<1024xf32>) -> tensor<1024xf32>
```

换成 fp64 时选中 `__nv_asin`。换成 fp16 时报 `KeyError: (triton.language.float16)`，外层包成 `CompilationError`，并指向 `libdevice.asin(x)` 那一行。

**为什么这样设计**：
- libdevice 沿用 C 的命名习惯，用不同的名字区分精度：`__nv_asinf` 处理 float，`__nv_asin` 处理 double。这张表把一个 Python 名字映射到正确的变体上。
- `is_pure=True` 声明这个调用没有副作用，结果只取决于输入。编译器因此可以合并重复计算，结果没人用时也可以直接删掉这个调用。
- 不做隐式提升：fp16→fp32→fp16 的来回转换会改变精度和开销，应当由写 kernel 的人显式决定。这是我的推断，源码没有写明动机。

**真实系统**：Inductor 在 `exp`、`asin`、`erf` 等函数的代码生成外面包了一层装饰器 `@maybe_upcast_float32()`。输入是 fp16 或 bf16 时，它在参数后面拼上 `.to(tl.float32)`，需要时再把结果转回原来的 dtype，正好补上这张表不覆盖半精度的缺口。另外，Inductor 的 `exp` 默认生成 `libdevice.exp`，只有设置 `TORCHINDUCTOR_USE_FAST_MATH=1` 时才改用 `tl_math.exp`。为什么这样选，节点 5 再讲。

**边界**：表的键是**精确的** dtype 元组，fp16、bf16 和整数都不会自动匹配。对 `pow`、`atan2` 这类多参数函数，每一种参数 dtype 组合都必须出现在表里。

## 节点 3：布局决定每线程元素数，逐元素生成 LLVM 调用

**结论**：`tt.extern_elementwise` 会被拆到每个元素上。TTGIR 布局决定每个线程持有哪 E 个元素。降级到 LLVM 时，模块里只加**一条**函数声明，再为每个元素各生成一条标量调用 `call @__nv_asinf(float)`。库函数本身是标量的，并行来自线程，而不是把调用向量化。

**机制**：
- **布局**：`#ttg.blocked<{sizePerThread=[S], threadsPerWarp=[32], warpsPerCTA=[num_warps]}>`，S 是每个线程连续持有的元素数。一个布局块覆盖 `S·32·num_warps` 个元素，`BLOCK_SIZE` 更大时布局块重复铺开。因此当 `BLOCK_SIZE` 不小于一个布局块时，`E = BLOCK_SIZE / (32·num_warps)`，与 S 无关；S 只决定这 E 个元素里有几个是连续的。
- **降级**：`ElementwiseOpConversionBase::matchAndRewrite`（`include/triton/Conversion/TritonGPUToLLVM/ElementwiseOpToLLVMBase.h:110`）先把各操作数拆成本线程的 E 个标量，对每个元素调用一次 `createDestOps`，最后再打包回去。`ExternElementwiseOpConversion`（`lib/Conversion/TritonGPUToLLVM/ElementwiseOpToLLVM.cpp:193`）在 `createDestOps` 里先用 `appendOrGetExternFuncOp` 取得该符号的声明（同一模块只建一次），再生成一条调用。
- **本机观察**：主例 `BLOCK_SIZE=1024`、`num_warps=4`：

| 编译条件 | S | E | 链接前的 LLVM IR | PTX 访存 |
| --- | --- | --- | --- | --- |
| 无对齐提示 | 1 | 8 | 1 条 `declare`，8 条 `call @__nv_asinf` | 8 × `ld.global.b32` |
| 指针与 `n_elements` 按 16 特化 | 4 | 8 | 同上 | 2 × `ld.global.v4.b32` |

真实启动时，Triton 会检查指针是否 16 字节对齐、整数能否被 16 整除，并据此特化，所以第二行更接近实际情况。但两种情况下 PTX 里都是 8 份 `asin` 展开（8 条 `sqrt.approx.ftz.f32`、48 条 `fma.rn.ftz.f32`）。**访存被向量化了，数学计算没有。**

**为什么这样设计**：libdevice 函数和 CUDA C 的数学函数一样，签名是标量的 `float(float)`。GPU 按 SIMT 执行：一个 warp 的 32 个线程同时对各自的寄存器执行同一条标量指令，向量宽度已经由 warp 提供，所以逐元素标量调用在算术上没有损失。S 的作用是把访存合并成 128 位事务。

**和 `is_pure` 的联系**：
- `pure=true` 的 `ExternElementwiseOp` 不声明任何内存副作用，而且允许投机执行；`pure=false` 时会声明读写副作用（`lib/Dialect/Triton/IR/Ops.cpp:1307`）。只有无副作用的操作，才能被消除重复计算、删除无用结果、提到循环外。
- 降级阶段的 `maybeDeduplicate`（`ElementwiseOpToLLVMBase.h:58`）同样要求无副作用。当轴分析证明一个线程的某几个元素必然相等（比如输入是广播出来的），就只算一次、复用结果。

**真实代价**：节点 4 会讲到，这 E 条调用最后都会被内联，所以每个线程的代码里有 E 份函数体。
- fp32 的 `asin` 每个元素约 6 条 FMA，fp64 版约 34 条 `fma.rn.f64`。
- 用 wheel 自带的 `ptxas -v` 在本机就能看寄存器用量：E=8 时，fp32 版用 30 个寄存器，fp64 版用 36 个，都没有溢出。

**边界**：E 随 `BLOCK_SIZE/num_warps` 线性增长，每个线程的指令数和同时存活的寄存器也会跟着涨。我推断，对 fp64 或 `lgamma` 这类计算量大的函数，大 `BLOCK_SIZE` 配少 warp 时更容易出现溢出；这一点在本机就能用 `ptxas -v` 验证。

## 节点 4：链接 bitcode、reflect 与内联

**结论**：函数体直到 LLVM IR 阶段才进入 kernel，过程分四步：
1. 模块里还有未解析的外部函数时，后端按名字从 libdevice bitcode 中**只拉取用到的定义**；
2. 把拉进来的函数改成 internal；
3. O3 优化把这些带 `alwaysinline` 的函数内联；
4. libdevice 内部用 `__nvvm_reflect` 写的编译期分支，按 Triton 设置的参数折叠成其中一种变体。

最终 PTX 里没有 `call`。

**机制**（除标注外均在 `third_party/nvidia/backend/compiler.py`）：
1. **确定库路径**（`CUDAOptions.__post_init__`，`:133`）：`extern_libs` 里没有 `libdevice` 时，先用环境变量 `TRITON_LIBDEVICE_PATH`，否则用 wheel 自带的 `triton/backends/nvidia/lib/libdevice.10.bc`。`hash()`（`:143`）把路径换成**文件内容的哈希**再计入编译缓存键，所以换了 bitcode，旧缓存自然失效。
2. **设置 reflect 参数**（`make_llir`，`:415`）：`enable_reflect_ftz` 默认为 True，模块里会加上 `!{i32 4, !"nvvm-reflect-ftz", i32 1}`。
3. **按需链接**（`:418`）：先由 `has_extern_deps`（`triton_nvidia.cc:378`）检查模块里有没有“外部链接、没有定义、也不是 intrinsic”的函数，没有就跳过整步。有的话调用 `link_extern_libs`（`python/src/llvm.cc:871`）：
   - 解析 bitcode，并把它的目标三元组和数据布局对齐到 kernel 模块；
   - 用 `LinkOnlyNeeded` 只拉入被引用到的定义；
   - 把拉进来的函数设为 internal。源码注释给的理由是：后端把 external 链接当作 kernel 函数的标志。
4. **O3 优化**（`:422`）：内联这些函数，并删除没用到的部分。

本机观察：链接后模块里只定义了两个函数：`asin_kernel`（`ptx_kernel`）和 `__nv_asinf`（`internal`，属性里有 `alwaysinline`）。CUDA 映射表引用了 313 个 `__nv_*` 符号，这次只拉进来一个。

**reflect 是什么**：libdevice 只编译一次，却要服务多种编译模式，所以函数体里写的是 `if (__nvvm_reflect("__CUDA_FTZ")) … else …` 这样的分支。LLVM 的 NVVMReflect pass 会把这些调用替换成常量，死分支随之被删掉。`__CUDA_FTZ` 取自模块标志 `nvvm-reflect-ftz`；按 LLVM NVPTXUsage 文档，**没有指定的参数一律取 0**。本机对照：

| 选项 | PTX 中 asin 的关键指令 |
| --- | --- |
| 默认（`enable_reflect_ftz=True`） | `abs.ftz.f32`、`fma.rn.ftz.f32`、`sqrt.approx.ftz.f32` |
| `enable_reflect_ftz=False` | `abs.f32`、`fma.rn.f32`、`sqrt.approx.f32` |

两种情况下 sqrt 都是近似版本，因为 Triton 没有设置 `__CUDA_PREC_SQRT`，它按 0 处理。

**为什么这样设计**：
- **到 LLVM IR 阶段才链接**：bitcode 本来就是 LLVM IR。TTIR/TTGIR 上的布局、访存合并、流水线等 pass 只需知道“这是一个纯的逐元素操作”，用不到函数体；用哪个库文件也完全交给后端决定。
- **`LinkOnlyNeeded`**：库里有数百个函数，全部拉进来，每次编译都要背上整个库。
- **internal + `alwaysinline` + O3**：去掉真实的函数调用和调用约定，让多项式计算能和访存、其他元素的计算交错调度。
- **reflect**：一份 bitcode 容纳多种变体，编译期选定，运行时零开销。

**对照 nvcc**：NVCC 文档（v13.4）写明，默认 `--ftz=false`（保留次正规数）、`--prec-sqrt=true`（IEEE 就近舍入），而 `--use_fast_math` 相当于 `--ftz=true --prec-div=false --prec-sqrt=false --fmad=true`。所以在 ftz 和 sqrt 这两个开关上，Triton 默认编进来的 libdevice 代码更接近 nvcc 的 `--use_fast_math`，而不是 nvcc 的默认值。

**边界**：
- **ftz 只影响次正规数**（fp32 中 |x| < 2⁻¹²⁶ ≈ 1.18×10⁻³⁸），这类值会被当作 0。极小的 x 本该得到 `asin(x) ≈ x`，在 ftz 下预计得到 0。常见 `atol` 量级的测试发现不了这种差异，可以到 GPU 机器上验证。
- **`enable_reflect_ftz` 只作用于 libdevice 内部经 reflect 选择的代码**，Triton 自己降级出来的指令不受影响。本机对照：`tl.exp` 编出的是不带 ftz 的 `ex2.approx.f32`，`libdevice.exp` 编出的是 `ex2.approx.ftz.f32`。
- **链接路径写错时**，错误出现在计算缓存键、读取文件内容的那一刻，比生成任何 IR 都早。教程第二段在本仓库里运行就会撞上这一点，节点 5 细讲。

## 节点 5：算一个数学函数的四条路线

**结论**：四条路线的区别在于函数体从哪里来、在哪一站进入管线。`tl.math` 和 libdevice 并不是“硬件指令”对“库”的关系：在 NVIDIA 上，`tl.math` 的大多数函数最后调用的就是 libdevice。

| 路线 | 写法 | 函数体从哪来 |
| --- | --- | --- |
| A：`tl.math` | `tl.exp(x)`、`tl.log(x)` | 由后端决定。本机测到，NVIDIA 上直接生成指令的有 `exp`、`sqrt_rn`、除法、`abs`；`log`、`sin`、`erf`、`sqrt`、`floor` 等被改成 `__nv_*` 调用，PTX 与 `libdevice.log` 等完全相同 |
| B：libdevice | `libdevice.asin(x)` | 厂商库，链接后内联（节点 3、4） |
| C：内联汇编 | `tl.inline_asm_elementwise("rsqrt.approx.f32 $0, $1;", …)` | 你写的指令文本，不经过链接，原样出现在最终汇编里 |
| D：自定义库 | 自己写映射表，用 `extern_libs` 传入库文件 | 你的库，走和 B 完全相同的链接、内联 |

**为什么有 A 和 B 两套名字**：A 是后端中立的写法，kernel 只说“我要 exp”，怎么实现由每个后端决定。B 是点名要厂商库里的某个函数。A 只有十几个函数，B 在 CUDA 上约有 197 个，所以 `asin`、`pow`、`lgamma` 只能走 B。

**真正要权衡的是精度**：三个运算各有快速版和精确版，Triton 最顺手的写法都是快速版。

| 运算 | 快速版 | 精确版 |
| --- | --- | --- |
| exp | `tl.exp`，每元素 2 条指令 | `libdevice.exp`，每元素 8 条 |
| sqrt | `tl.sqrt`，近似 | `tl.sqrt_rn`，IEEE 就近舍入 |
| 除法 | `a / b`，近似的 `div.full` | `tl.div_rn`，IEEE 的 `div.rn` |

快速版 exp 不够准，是因为它先算 x × log₂e，再做 2 的幂。乘积只有 24 位有效数字，|x| 越大，丢掉的那点误差被指数放大得越多。CUDA 文档给的误差上界：标准 `expf` 是 2 ulp，快速版是 2 + ⌊|1.173·x|⌋ ulp。ulp 是浮点数最后一位的一个单位，差 1 ulp 就是只差最后一位。Triton 的快速版用的是同类做法，我推断误差特性相同，可以到 GPU 上实测。

**真实系统**：PyTorch 2.13 的 Inductor 希望编译结果和 eager 接近，所以 sqrt 一律生成 `tl.sqrt_rn`，exp 默认生成 `libdevice.exp`。它还有一组 `eager_numerics` 开关，对应的正是这几个节点学的选项：
- `division_rounding`：除法改用 `div_rn`。
- `disable_ftz`：传 `enable_reflect_ftz=False`。
- `use_pytorch_libdevice`：把 Triton 自带的 libdevice 换成 CUDA 工具链的那份。源码注释说，两份库的多项式不同，`erf`、`pow` 会差约 1 ulp。

**边界**：
- A 和 B 都只接受 fp32／fp64。`tl.math` 的源码写明了理由：很多加速器不支持 fp16 的数学运算，应让用户显式转换。这证实了我在节点 2 标为推断的那句话。
- 教程第二段的自定义路径只在 Triton 源码树里成立。在本仓库的快照位置或 pip 环境里运行，会在计算缓存键时报 `FileNotFoundError`。
- C 不可移植：同一段 PTX 文本拿到 AMD 目标上，汇编器报 `invalid instruction`。

**怎么选**：能用 `tl.math` 就用它；要它没有的函数，用 libdevice；要和 eager 对齐，把上表逐项换成精确版。

## 节点 6：换一个后端，哪些变、哪些不变

**结论**：四个节点的机制是 Triton 的公共代码，所有后端共用；后端只负责往每一环里填自己的内容。本机把同一个 `libdevice.asin` kernel 以 AMD 为目标完整编译了一遍：

| 环节 | NVIDIA（sm_90） | AMD（gfx942） |
| --- | --- | --- |
| 查表得到的符号 | `__nv_asinf` | `__ocml_asin_f32` |
| 每个 warp 的线程数 | 32，所以 E = 8 | 64，所以 E = 4 |
| 实际链接的库 | `libdevice.10.bc` | 只有 `ocml.bc` |
| 内联之后 | 0 次调用 | 0 次调用 |
| 次正规数默认 | 冲成 0 | 保留 |

**给新后端加 libdevice 支持，要补六样东西**：
1. 接口模块到自己实现模块的映射；
2. 实现模块里的各个函数；
3. 每个函数的“dtype → 符号”表；
4. 库文件和默认路径；
5. 按需链接，并保证表里的符号名和库里的定义一致；
6. 让库函数被内联，并把数值开关传给库。

前五样漏掉时各有固定的报错，我都在本机复现了，页面的表里逐条列出。

**边界**：链接规则因后端而异。NVIDIA 只要发现未定义的函数，就把 `extern_libs` 里的库都交给链接器。AMD 只链接“键名出现在某个未定义函数名里”的库。本机实测同一个自定义库：键名不匹配时，AMD 编译不报错，但最终留下一次未解析的调用。

## 串讲：把整课连成一条线

还是那一行 `y = libdevice.asin(x)`：fp32，`BLOCK_SIZE=1024`，`num_warps=4`，目标 NVIDIA。

1. **写的时候**，`libdevice` 只是后端中立的接口模块，里面的函数是空壳。
2. **翻译成 TTIR 时**，编译器按目标后端把接口模块换成 CUDA 的实现。实现是一张“dtype → 符号”的表，fp32 查到 `__nv_asinf`，TTIR 里就记下一条带符号名的逐元素操作。这一步只记“要调用谁”。fp16 查不到，编译直接失败。
3. **TTGIR 加上布局**，把 1024 个元素分给 128 个线程，每个线程 8 个。
4. **降级到 LLVM IR**，编译器替一个线程写程序：1 条声明，8 次标量调用。函数体这时还不在。
5. **链接**：模块里有未定义的函数，后端就按名字从 libdevice 里拷入 `__nv_asinf` 这一份定义。
6. **O3 内联**：8 次调用变成 8 份函数体，定义本身被删除。
7. **生成 PTX**：反射参数把每份函数体里的编译期分支折叠成一种写法，默认是 ftz 加近似 sqrt。`ptxas` 再把它汇编成机器码并缓存。

运行时，每个线程执行的是 8 份展开后的普通指令，没有任何函数调用，也不再查表或链接。

**贯穿全课的三个取舍：**
- **前端只记名字，后端才给函数体。** 换来同一份 kernel 能在不同后端编译。代价是每个后端的函数集和 dtype 表各不相同，缺了就编译失败。
- **链接加内联，而不是真的调用。** 换来运行时没有调用开销。代价是代码量随每线程元素数 E 增长。
- **默认偏快，精确要自己选。** libdevice 默认按 ftz 和近似 sqrt 展开，`tl.exp`、`tl.sqrt`、`/` 也都是快速版。要和 PyTorch eager 对齐，得逐项换成精确版。

**放到真实系统里**：Inductor 把一串逐元素运算融合成一个 Triton kernel，其中每个数学函数都走这条链。它默认生成 `libdevice.exp` 和 `tl.sqrt_rn`，再用 `eager_numerics` 这组开关控制除法舍入、ftz 和 libdevice 的版本。

**换到 AMD**：机制不变，填进去的内容变了。符号是 `__ocml_asin_f32`；每个 warp 有 64 个线程，所以 E = 4；链接的是 `ocml.bc`；次正规数默认保留。给自家加速器做后端时，要补的就是节点 6 那六样东西。

综合

1. 从python到机器码一般需要以下这些环节：
  
  1. 首先，从python代码由triton编译器前端转为TTIR。在这里，先根据目标后端，将triton libdevice接口模块替换成目标后端的模块，然后再根据输入的数据类型和要调用的函数通过查表得到需要调用的函数符号。在这里，描述的依旧是一整块张量的操作。
    
  2. 第二，由TTIR再通过triton编译器lowering转为TTGIR。在这里，是根据目标后端，转为对应的pass。对于多线程并行的GPU而言，这一阶段的主要目标是为了将整块的张量按照特定布局分配给各个线程进行处理，形成线程与张量元素之间的持有关系。
    
  3. 第三，再将TTGIR交由LLVM进行处理，成为LLVM IR。LLVM的处理过程基本分为三步：1、转换，从TTGIR的张量描述方式，转为线程描述方式。根据线程和张量元素的持有关系描述每一个线程要执行的代码步骤。其中，对于需要调用的符号函数，只有声明，没有定义。2、链接，再从libdevice库中将与声明对应的函数定义链接进来。3、O3优化。在O3优化中，会将函数定义内联嵌入到原本的调用位置，并删除原本的调用操作和函数定义。最后就生产了LLVM IR。
    
  4. 然后，再根据目标后端的汇编和机器码进行下降。产生AMD的汇编和二进制机器码hsaco。
    
  5. 最后的机器码没有函数调用是因为中间LLVM O3优化时，对函数调用进行了内联优化，将函数定义体嵌入了调用位置。于是不再需要函数调用，省去了调用的开销。

## 你的问题：为什么先存进变量再 `if` 会报错

我复现了，报错是：

```text
initial value for `x` is of type bf16[...], but the then block redefines it as fp32[...]
```

原因是：**普通赋值会把编译期的值变成运行期的值**。

1. `x.dtype == tl.bfloat16` 的结果，本来是一个 Python 的布尔值，编译时就知道是真是假。
2. 一旦写成 `is_bf16 = ...`，Triton 处理赋值时会把它转成一个张量。从这一刻起，编译器把 `is_bf16` 当成“运行时才知道的数据”。
3. `if` 的处理分两种：条件是普通布尔值时，编译期就选定一个分支，另一个分支根本不看；条件是张量时，就成了运行期分支，**两个分支都要编译**。
4. 运行期分支要求同一个变量在两条路径上类型一致。而你的 `then` 分支把 `x` 改成了 fp32，另一条路径上它还是 bf16，于是报错。

直接写 `if x.dtype == tl.bfloat16:` 没有问题，是因为条件没有经过赋值，仍然是普通布尔值，走的是编译期分支。

这和 C++ 里 `if constexpr` 与普通 `if` 的区别是一回事：前者只编译选中的分支，后者两个分支都要能通过类型检查，一个变量也不可能在运行时才决定自己的类型。

如果确实想先存再用，可以给变量加上 `tl.constexpr` 注解，告诉 Triton 它是编译期常量：

```python
is_bf16: tl.constexpr = x.dtype == tl.bfloat16
```

这样写我也实测过，能通过编译，生成的 IR 里没有运行期分支。注意这种变量不能再被重新赋值。

出处是 Triton v3.7.1 的 `python/triton/compiler/code_generator.py`：`visit_Assign`（第 707 行起）负责把值转成张量，`visit_AnnAssign`（第 678 行起）处理 `constexpr` 注解，`visit_If`（第 928 行起）区分两种分支。

这属于语言层面的答疑，不影响 A6 的独立性。A5 的结果和这次答疑已经记进课程记录。接下来可以写 A6 了，目标是 `16 passed, 44 skipped`。

这个问题问得好，而且图解页那一行确实容易让人误解。我把两家库里链接进来的函数体取出来对比了，结论是：**AMD 并没有做更多的工作，只是 fma 这一种指令用得更多。**

## 为什么不一样

`asin` 在两个后端上来自两个不同的库：NVIDIA 用 libdevice 的 `__nv_asinf`，AMD 用 ocml 的 `__ocml_asin_f32`。两家各写了一套算法。数学上的做法相同：

- |x| 较小时，直接用多项式逼近；
- |x| 较大时，用恒等式 asin(x) = π/2 − 2·asin(√((1−|x|)/2)) 换算。

但具体写法不同，所以指令也不同。

## AMD 多出的 3 条 fma 来自哪里

| 步骤 | NVIDIA | AMD | fma 差 |
| --- | --- | --- | --- |
| 算 (1 − \|x\|) ÷ 2 | 一条减法，一条乘法 | 一条 fma | +1 |
| 逼近多项式 | 5 个系数，4 条 fma | 6 个系数，5 条 fma | +1 |
| 最后一步 | 先选好用哪个变量，两个分支共用 1 条 fma | 两个分支各算一遍再选结果，2 条 fma | +1 |
| π/2 − 2q | 1 条 fma | 1 条 fma | 0 |

合计 NVIDIA 6 条，AMD 9 条。

## AMD 的工作量并不更大

只数 fma 会产生错觉。第一行里，AMD 的 1 条 fma 顶替的是 NVIDIA 的 2 条普通指令。把每个元素的全部算术指令都算上：

- NVIDIA 约 19 条；
- AMD 约 17 条。

两边相当，AMD 还略少。AMD 的指令集也帮了忙：取绝对值可以直接写在操作数上，不占一条指令；补回符号只用一条位操作指令。

## 两个值得注意的细节

- **分界点不同**：NVIDIA 在 |x| > 0.57 时换算，AMD 在 |x| ≥ 0.5 时换算。
- **π/2 的写法不同**：NVIDIA 直接用 fp32 的 π/2，误差约 4×10⁻⁸。AMD 把两个 fp32 常数放进同一条 fma 里相乘，乘积在 fma 内部不舍入，得到的 π/2 误差只有约 10⁻¹⁴，指令数没有增加。

多一项系数、更精确的 π/2，看上去是 AMD 这套写法更看重精度。这一点是我从代码推断的，两家的精度目标我没有查到文档。

## 和本课的联系

这就是节点 5 里那件事的具体例子：同一个数学函数，不同的库用不同的多项式，结果可能差最后一位。Inductor 的 `use_pytorch_libdevice` 开关处理的正是这类差异；跨后端对比结果时，这也是差异的来源之一。
