**004 · 助手** · `2026-10-05T08:05:48.526Z` · `msg-8ead93f0dabbf7a14bfb`

第 08 课开始，主题是 Grouped GEMM（[教程快照](docs/triton-tutorials/official/08-grouped-gemm.py)）。课程记录建在 [lessons/08-grouped-gemm.md](docs/triton-learning/lessons/08-grouped-gemm.md)，当前位置写在 Triton 档案的 Checkpoint 里。

本课四个目标：讲清数据流（O1）、分析调度与失效边界（O2）、解释 TMA 描述符并迁移到真实系统（O3）、实现并验证一个支持任意尺寸的 kernel（O4，需要实践）。性能对比不设门槛。结课需要你确认，第 09 课不会自动开始。

## 为什么学这一课

任务是一次算一组矩阵乘法 C_g = A_g · B_g，每个问题的尺寸可以不同。最贴近你工作的例子是 MoE 层：每个专家是一个权重矩阵，路由之后各专家收到的 token 数不一样，于是得到一组行数参差不齐的矩阵乘法。

逐个调用矩阵乘 kernel 有两个问题：每次调用都要付一次发射开销；同一个 CUDA 流上的 kernel 先后执行，小问题的 tile 数比 SM 数少时，大部分 SM 空着。Grouped GEMM 把所有问题的 tile 合成一份任务，一次发射做完。代价是 kernel 得在设备上自己找活干：间接寻址、调度逻辑，以及由此丢掉的编译期信息。

学完你应该能：对着代码讲清一块 tile 从"被哪个 CTA 领走"到"写回哪个 C"的全过程；判断一组给定尺寸在这种调度下是否均衡；指出教程实现在哪些输入上会出错；解释 TMA 版本换掉了什么；最后自己写一个不要求整块尺寸的版本。

## 全流程骨架

符号：

- G：组里的问题数，即 `group_size`。
- (M_g, N_g, K_g)：第 g 个问题的尺寸。A_g 是 [M_g, K_g]，B_g 是 [K_g, N_g]，C_g 是 [M_g, N_g]。
- BM、BN、BK：`BLOCK_SIZE_M/N/K`。一个 tile 是 C 上 BM×BN 的一块，K 方向每次处理 BK 列。
- T_g = ⌈M_g/BM⌉ · ⌈N_g/BN⌉：第 g 个问题的 tile 数；T 是它们的总和。
- NUM_SM：发射的 CTA 数。CTA 就是 Lesson 02 里的一个 program 实例。

```text
主机侧（group_gemm_fn）
  为每个 g 新建 C_g，然后打包成 5 个设备张量：
    A、B、C 三张地址表   int64 [G]      ← tensor.data_ptr()
    尺寸表               int32 [G, 3]   ← (M_g, N_g, K_g)
    ld 表                int32 [G, 3]   ← 三个矩阵各自的 stride(0)
  一次发射：grid = (NUM_SM,)

设备侧（每个 CTA，pid = 0 … NUM_SM−1）
  tile_idx = pid；last_problem_end = 0
  for g in 0 … G−1：                          # 按顺序走过每个问题
      读 (M_g, N_g, K_g)，算出 T_g
      while tile_idx 落在 [last_problem_end, last_problem_end + T_g)：
          读地址和 ld，把整数转成指针
          由 tile_idx − last_problem_end 得到 (tile_m, tile_n)
          常规 GEMM：沿 K 循环，fp32 累加，转 fp16 写回 C_g 的这一块
          tile_idx += NUM_SM                   # 领下一块
      last_problem_end += T_g
```

路线共六个节点：

1. 问题与收益
2. 主机侧打包与地址表
3. 设备上的静态调度
4. tile 内的 GEMM、满 tile 假定与对齐提示
5. TMA 与 tensor descriptor
6. 真实系统与迁移

今天讲前三个。完成标准是：能对着骨架讲清每一步读什么、算什么、为什么这样设计，并对一组没见过的尺寸判断负载和出错位置。

前置不用再问：persistent kernel 你在 Lesson 02 学过，分块矩阵乘在 Lesson 03 写过，本课直接拿它们对照。

## 节点 1：为什么要 grouped

**结论**：grouped 只付一次发射开销，并且小问题能和别的问题一起把 SM 填满。付出的是设备上的调度逻辑，以及整组只能共用一套块大小。

**机制**，三种做法对比：

| 做法 | 发射次数 | 对尺寸的要求 | 小问题时的 SM 利用 |
| --- | --- | --- | --- |
| 逐个调用 | G | 无 | 每次只有 T_g 个 CTA，其余 SM 空着 |
| batched（如 `torch.bmm`） | 1 | 形状必须相同，否则补齐到最大形状 | 满，但补齐部分是白算 |
| grouped | 1 | 无 | 所有问题的 tile 一起分给 CTA |

**为什么**：128×128 的问题在 128×128 的块下只有 1 个 tile，这次调用里只有 1 个 SM 在干活。batched 的补齐同样浪费：token 数为 4096 和 128 的两个专家补齐到 4096 后，第二个专家约 97% 的计算是白算。

**真实系统**：

- PyTorch 2.13 有 `torch.nn.functional.grouped_mm`，文档写明用途是 MoE：专家权重形状相同、各专家 token 数参差。它目前要求 CUDA、bfloat16、SM ≥ 80。
- cuBLAS 12.5（2024 年 6 月）加入 `gemmGroupedBatched` 系列接口。NVIDIA 称它是 batched 接口的推广，允许不同尺寸在一次发射中并行，并报告在 MoE 生成场景比循环调用 batched GEMM 快 1.2 倍。这是厂商数字。
- CUTLASS 的 grouped GEMM 有两种调度模式。教程开头那句"调度是静态的，在设备上完成"对应其中的 `kDeviceOnly`，节点 3 会对照它的源码。

**边界**：问题数少、每个都大到能填满所有 SM 时，grouped 没有优势。此时发射开销占比很小，逐个调用还能为每个问题单独选块大小。

## 节点 2：主机侧打包与地址表

**结论**：矩阵个数 G 运行时才知道，kernel 的参数个数却在编译时定死，所以矩阵不能一个个当参数传。教程把每个矩阵的首地址当成 64 位整数存进设备张量，kernel 运行时读出整数，再转成指针。

**机制**：

```python
# 主机侧
A_addrs.append(A.data_ptr())                      # Python 整数：A 在显存中的首地址
d_a_ptrs = torch.tensor(A_addrs, device=DEVICE)   # int64 设备张量，形状 [G]

# kernel 内
a_ptr = tl.load(group_a_ptrs + g).to(tl.pointer_type(tl.float16))
```

用 C 来类比：有一个 `int64_t table[G]`，取出 `table[g]` 后强转成 `half*`。编译产物里对应 `tt.int_to_ptr`，我在本机只编译时看到每个 kernel 有 3 个，分别给 A、B、C。

尺寸表和 ld 表是 [G, 3] 按行展平，所以下标是 `g * 3 + j`。ld（leading dimension）是 BLAS 的叫法，就是 `stride(0)`：相邻两行的首元素相隔多少个元素。行内步长被假定为 1，所以每个矩阵只传一个步长，Lesson 03 里是两个。

**为什么**：PyTorch 的 `grouped_mm` 走的是另一条路。它要求把各组的行堆成一个连续的大矩阵，再用偏移表标出每组在哪结束。

- 地址表：矩阵可以散落在显存各处，直接接入已有张量，不用先拷到一起。
- 偏移表：只有一个基地址，类型、对齐和生命周期都由那一个张量保证。

**代价**，都来自"地址只是一个整数"：

- **类型信息丢了**。kernel 把指针写死成 `tl.float16`。传 fp32 矩阵不会报错，只会把内存按 fp16 解读，结果全错。
- **生命周期没人管**。地址表不持有原张量的引用，原张量被释放后地址就悬空。
- **编译器失去对齐信息**。普通 kernel 的张量参数在发射时会检查首地址是否是 16 的倍数，并据此特化（`triton/backends/compiler.py` 第 84–90 行）；从内存里读出来的地址没有这一步。它直接影响性能：我去掉教程里的 `tl.multiple_of` 提示重新编译，K 循环就不再做异步预取了。节点 4 细讲。
- **多出标量读取**。每个 CTA 对每个问题读 3 次尺寸，每领一块再读 6 次地址和 ld。

## 节点 3：设备上的静态调度

**结论**：把所有问题的 tile 首尾相接排成一条队列，编号 0 到 T−1。第 p 个 CTA 处理编号 p、p+NUM_SM、p+2·NUM_SM…… 的 tile。谁做哪一块由固定规则决定，每个 CTA 自己在设备上算，主机不参与。思路和 Lesson 02 的 persistent kernel 相同，只是任务从"行"变成了"跨多个问题的 tile"。

**机制**：用教程的示例组，四个方阵问题，边长 1024、512、256、128；取 BM=BN=128、BK=32、NUM_SM=84。

| 问题 g | 边长 | tile 数 T_g | 全局编号 | 每块的 K 循环次数 |
| --- | --- | --- | --- | --- |
| 0 | 1024 | 64 | 0–63 | 32 |
| 1 | 512 | 16 | 64–79 | 16 |
| 2 | 256 | 4 | 80–83 | 8 |
| 3 | 128 | 1 | 84 | 4 |

CTA 0 的执行过程，对照教程第 114–169 行：

1. `tile_idx = 0`。走到 g=0，区间是 [0, 64)，0 在里面，于是算问题 0 的第 (0, 0) 块。然后 `tile_idx` 变成 84，出了区间。
2. g=1 的区间 [64, 80) 和 g=2 的区间 [80, 84) 都不含 84，跳过。
3. g=3 的区间是 [84, 85)，84 在里面，于是算问题 3 唯一的那一块。

其余 CTA 各只领到一块：CTA 1–63 在问题 0，64–79 在问题 1，80–83 在问题 2。

两个细节：

- `tile_idx` 只增不减，问题又是按顺序走的，所以一趟 `for` 就够。`while` 处理的是同一个问题里连续领到多块的情况。
- 块在问题内的坐标是 `tile_m = t // num_n_tiles`、`tile_n = t % num_n_tiles`，按行优先，没有 Lesson 03 的 grouped ordering。

**为什么这样设计**：

| 方案 | 主机要做什么 | 每个 CTA 的额外工作 |
| --- | --- | --- |
| 每块一个 CTA（grid = T） | 先算出 T | 仍要扫描问题表找到自己属于谁，而且只干一块 |
| 固定 CTA 数、按步长领取（教程） | 不用算，grid 与数据无关 | 扫描一趟，顺路领多块 |
| 主机预计算（CUTLASS 的 `kHostPrecompute`） | 把任务序列算好传下去 | 查表，不用扫描 |

教程的方案让主机完全不碰尺寸数据，并把"扫描问题表"的成本摊到多块上。

**负载**：按步长领取保证各 CTA 领到的块数最多差 1，但不保证工作量相等，因为一块的工作量正比于 K 循环次数 K_g/BK。上面的例子里：

- CTA 0 做 32+4=36 次，CTA 1–63 做 32 次，64–79 做 16 次，80–83 只做 8 次，平均 27.9 次。
- 整个 kernel 的耗时由最忙的 CTA 决定，后 20 个 CTA 早早做完就闲着。
- NUM_SM 改成 128 时，85 块只够 85 个 CTA，剩下 43 个扫一趟、什么都没领到就退出。
- 块缩小到 64×64 时共 340 块，每个 CTA 领 4–5 块，最忙与平均之比从 1.29 降到 1.18。块越多，每个 CTA 领到的块越能跨越不同问题，越均衡。

这些数字来自我按 kernel 控制流写的调度模型，不是 GPU 上的计时。

**NUM_SM**：注释叫"虚拟 SM 数"，实际含义就是 CTA 数，不必等于物理 SM 数。autotune 的 6 个配置里既有写死的 84 和 128，也有查询到的真实 SM 数。`key=['group_size']` 表示只有 G 变了才重新调优；G 相同而尺寸分布变了，会沿用之前选出的配置。

**真实系统**：CUTLASS v3.9.2 的 grouped GEMM 是同一个结构，循环体末尾是 `problem_visitor.advance(gridDim.x)`，即按网格大小推进。两处值得对照：

- 线程块数取"SM 数 × 每个 SM 能同时驻留的线程块数"，而不是手写常数。
- 扫描问题表时，一个 warp 的 32 个线程各读一个问题，用 warp 内前缀和一次跳过 32 个问题。这说明问题数多时，"找任务"的开销需要专门优化。教程版是逐个问题顺序扫。

这两个词我上一条没讲清楚就用了。一句话：SM 是硬件，CTA 是软件任务，CTA 被派到 SM 上执行。

## 各自是什么

**SM（Streaming Multiprocessor，流式多处理器）** 是 GPU 里的计算单元，一块 GPU 有几十到一百多个。每个 SM 自带执行单元、一组寄存器、一块共享内存和自己的调度器。它是物理资源，数量出厂就固定，可以用 `torch.cuda.get_device_properties(0).multi_processor_count` 查到。

**CTA（Cooperative Thread Array，协作线程阵列）** 是一次 kernel 发射里的一个任务单元。它在不同地方有三个名字，指的是同一个东西：

- CUDA 里叫线程块（thread block）。
- Triton 里叫 program，`tl.program_id(0)` 就是 CTA 的编号。
- 硬件和汇编文档里叫 CTA。上一条的编译产物里有 `shared::cta` 字样，意思就是"这个 CTA 自己的共享内存"。

一个 CTA 有 `num_warps × 32` 个线程，它们共用一块共享内存、可以互相同步，"协作"指的就是这一点。发射时写的 `grid` 就是 CTA 的个数。

## 两者的关系

| | SM | CTA |
| --- | --- | --- |
| 性质 | 硬件 | 软件任务 |
| 数量由谁决定 | GPU 型号 | 你发射时写的 grid |
| 类比 | CPU 的核心 | 分派到核心上的任务 |

发射之后，GPU 把 CTA 派到 SM 上，规则有三条：

- **一个 CTA 从头到尾在同一个 SM 上跑**，不会中途换地方。
- **一个 SM 可以同时驻留多个 CTA**，前提是它的寄存器和共享内存够分。Lesson 02 里算的 occupancy，就是"一个 SM 能同时驻留几个 CTA"。
- **CTA 多到放不下时，多出来的排队**，等前面的 CTA 结束再补上。

## 放回这一课

- **`NUM_SM` 这个名字有误导性**。它实际是 CTA 的个数，即 grid 的大小。叫"虚拟 SM 数"是因为设计意图是让每个 SM 上正好有一个常驻的 CTA，但它可以设得比真实 SM 数多或少。
- **"小问题让 SM 空着"的意思**：一个问题只有 8 块，就只发射 8 个 CTA，最多占 8 个 SM，其余 SM 在这次调用里无事可做。
- **检查题里的假设**："每个 SM 同一时刻只跑一个 CTA"是为了简化，把"CTA 的工作量"直接等同于"SM 的忙碌时间"。真实情况下一个 SM 可能驻留多个 CTA。

## 例子场景

用教程自己的示例组（[第 372–374 行](docs/triton-tutorials/official/08-grouped-gemm.py#L372-L374)）：四个互不相关的矩阵乘法，都是 fp16 方阵。块大小取 BM=BN=128、BK=32。

| 问题 | A、B、C 的形状 | C 被切成多少块 | 每块沿 K 方向循环几次 |
| --- | --- | --- | --- |
| 0 | 1024×1024 | 8×8 = 64 | 32 |
| 1 | 512×512 | 4×4 = 16 | 16 |
| 2 | 256×256 | 2×2 = 4 | 8 |
| 3 | 128×128 | 1 | 4 |

再加两条假设，只为了让数字好算：

- GPU 有 60 个 SM，每个 SM 同一时刻只跑一个 CTA。
- 一块的耗时正比于它的 K 循环次数，把"循环一次"当作 1 个时间单位。

目标是把这四个 C 都算出来。下面依次看三种做法。

## 做法一：逐个调用，发射 4 次

每次发射都是 Lesson 03 那种矩阵乘 kernel：C 有多少块就发射多少个 CTA，每个 CTA 算一块。

| 发射 | 问题 | CTA 数 | 同时在忙的 SM | 闲着的 SM | 耗时 |
| --- | --- | --- | --- | --- | --- |
| 1 | 0 | 64 | 第一轮 60，第二轮 4 | 第一轮 0，第二轮 56 | 64 |
| 2 | 1 | 16 | 16 | 44 | 16 |
| 3 | 2 | 4 | 4 | 56 | 8 |
| 4 | 3 | 1 | 1 | 59 | 4 |

发射 1 的 CTA 比 SM 多 4 个，所以先跑 60 个，剩下 4 个等第一轮结束再跑，共 64 个单位。四次发射合计 92 个单位。

这里有两笔浪费。

**闲着的 SM 不能提前去做后面的问题。** PyTorch 把 GPU 操作提交到一个叫"流"的队列里，默认每个设备只有一个流。按 PyTorch 文档的说法，同一个流里的操作按创建顺序串行执行。Triton 发射 kernel 用的就是 PyTorch 当前的流（`triton/runtime/jit.py` 第 714 行）。所以发射 2 必须等发射 1 的最后 4 块算完才开始；发射 2、3、4 期间，分别有 44、56、59 个 SM 无事可做。

**每次发射都有一笔固定开销。** 主机每次都要做一遍与矩阵大小无关的工作：Python 侧整理参数、查找已编译的 kernel，驱动把任务交给 GPU。发射 4 只算一块、只循环 4 次，这笔固定开销相对它的计算量就很显眼。具体是多少微秒，本机没有 GPU 量不了，练习阶段我会安排在你的 GPU 上实测。

顺带一提：换用多个流可以让小问题重叠执行，但发射次数没有减少，流之间的同步还得自己管。

## 做法二：batched，补齐后发射 1 次

`torch.bmm` 一次算一批矩阵乘法，但它要求输入是规整的三维张量 [G, M, K] 和 [G, K, N]，即一批里每个问题的形状必须相同。这四个问题边长不同，要用它，只能把小矩阵用 0 补成 1024×1024，算完再把每个结果左上角真正需要的部分切出来。补的 0 不影响结果，但照样要算。

矩阵乘的计算量是 M·N·K 次乘加：

| 问题 | 真实需要 | 补齐后实际计算 | 有用的比例 |
| --- | --- | --- | --- |
| 0 | 1024³ ≈ 10.74 亿 | 10.74 亿 | 100% |
| 1 | 512³ ≈ 1.34 亿 | 10.74 亿 | 12.5% |
| 2 | 256³ ≈ 0.17 亿 | 10.74 亿 | 1.6% |
| 3 | 128³ ≈ 0.02 亿 | 10.74 亿 | 0.2% |
| 合计 | 12.27 亿 | 42.95 亿 | 28.6% |

发射降到 1 次，SM 也都有活干，但约 71% 的乘加在算 0。此外还要为补齐后的张量分配显存，并把原数据拷进去。

放到 MoE 里：各专家的权重形状相同，N 和 K 一样，只有行数 M_g（收到的 token 数）不同。补齐就是把每个专家的行数都补到最多的那个专家。假设一个专家收到 4096 个 token，另一个只收到 128 个，后者补到 4096 行后真数据只占 128/4096 ≈ 3%。上一条那句"约 97% 是白算"说的就是这个情况。

## 做法三：grouped，发射 1 次，不补齐

把四个问题的块首尾相接排成一条队列，共 85 块：

| 问题 | 块数 | 队列里的编号 |
| --- | --- | --- |
| 0 | 64 | 0–63 |
| 1 | 16 | 64–79 |
| 2 | 4 | 80–83 |
| 3 | 1 | 84 |

发射 60 个 CTA。第 p 个 CTA 先做 p 号块，做完再做 p+60 号块（如果有）。

- **第一轮**：60 个 CTA 做 0–59 号块，全是问题 0 的大块。
- **第二轮**：还剩 60–84 号共 25 块，由 CTA 0–24 接着做。其中 60–63 号是问题 0 剩下的 4 块，64–84 号正好是三个小问题的全部 21 块。

最忙的是 CTA 0–3，各做两块大块，共 64 个单位，整个 kernel 也在这时结束。

和做法一对比：逐个调用时，问题 0 自己就要 64 个单位，而它的第二轮里只有 4 个 SM 在忙；三个小问题排在后面，再花 28 个单位。grouped 让三个小问题的 21 块在问题 0 的第二轮里，由本来闲着的 CTA 顺手做完。总耗时从 92 降到 64，和单独算问题 0 一样。

## 三种做法放在一起

| 做法 | 发射次数 | 算 0 的乘加 | SM 的利用 |
| --- | --- | --- | --- |
| 逐个调用 | 4 | 无 | 后三次发射分别闲置 44、56、59 个 SM |
| batched 补齐 | 1 | 约 71% | 满，但大部分在算 0 |
| grouped | 1 | 无 | 小问题填进大问题留下的空档 |

92 和 64 这两个数来自开头的两条简化假设，用来看清结构，不是性能预测：真实的 SM 可以同时驻留多个 CTA，发射开销也没有算进去。

**013 · 助手** · `2026-10-05T10:19:57.052Z` · `msg-ac5580f867fd011b363e`

源码核对和本机运行都做完了，下面是详细对比。先纠正一处：上一条我照文档字符串写了 `grouped_mm`"要求 CUDA、bfloat16、SM ≥ 80"，按 v2.13.0 源码这不准确，第 3 点会给出正确的条件。

另外澄清名字：Triton 没有叫 `grouped_mm` 的函数。下面说的"教程版"指教程里的包装函数 `group_gemm_fn` 加它的 kernel；"PyTorch 版"指 `torch.nn.functional.grouped_mm`。两者算的是同一件事，差别在"一组矩阵怎样交给 kernel"。

## 例子场景

一个 MoE 层的一次前向计算，dtype 用 fp16（和教程一致）：

- **专家**：共 3 个。每个专家有一个权重矩阵，形状都是 [1024, 512]，即输入 1024 维、输出 512 维。
- **token**：这一批共 768 个，每个是 1024 维向量。路由结果是专家 0 负责 256 个，专家 1 负责 128 个，专家 2 负责 384 个。
- **要算的**：每个专家把分给它的 token 乘上自己的权重，得到 [行数, 512] 的结果。

MoE 的实现会先把 token 按专家编号重排，所以同一个专家的 token 在内存里本来就连在一起：

```text
X：[768, 1024]，一整块连续内存             W：[3, 1024, 512]，一整块连续内存
  第   0–255 行   专家 0 的 256 个 token      W[0]   专家 0 的权重
  第 256–383 行   专家 1 的 128 个 token      W[1]   专家 1 的权重
  第 384–767 行   专家 2 的 384 个 token      W[2]   专家 2 的权重
```

这些尺寸都是 128 的倍数，所以教程的 kernel 也能处理。

## 两种交法

**PyTorch 版**交三样东西：堆叠的 X、堆叠的 W，和一张偏移表。偏移表第 g 项是"专家 g 的 token 到第几行为止（不含）"。

```python
offs = torch.tensor([256, 384, 768], dtype=torch.int32)
Y = F.grouped_mm(X, W, offs=offs)      # Y：[768, 512]，行的顺序与 X 相同
```

**教程版**交两个列表，每个元素是一个独立的二维张量：

```python
group_A = [X[0:256], X[256:384], X[384:768]]
group_B = [W[0], W[1], W[2]]
group_C = group_gemm_fn(group_A, group_B)   # 三个新张量：[256,512]、[128,512]、[384,512]
```

包装函数逐个读取每个矩阵的地址、形状和步长，生成五张表。我在本机 CPU 上用同样的语句算出了这个例子的表：

| 表 | 这个例子里的内容 |
| --- | --- |
| A 地址表 | X 的首地址 + 0、+524288、+786432 字节 |
| B 地址表 | W 的首地址 + 0、+1048576、+2097152 字节 |
| C 地址表 | 三块互不相干的新内存 |
| 尺寸表 (M, N, K) | (256, 512, 1024)、(128, 512, 1024)、(384, 512, 1024) |
| ld 表 | 每个问题都是 (1024, 512, 512) |

524288 的来历：X 每行有 1024 个 fp16，占 2048 字节；专家 1 从第 256 行开始，256 × 2048 = 524288。

## 核心关系：偏移表是地址表的特例

当各组数据首尾相接放在同一个张量里时，有：

```text
第 g 组的地址 = 基地址 + 第 g 组的起始行 × 每行字节数
```

PyTorch 内部正是这样算的。它的快速路径在调用真正的 grouped GEMM 之前，先在设备上跑一个很小的 kernel，每个专家一个线程，做三件事：

- 用 `A + offs[g-1] * stride` 算出每组的地址。
- 用 `offs[g] - offs[g-1]` 算出每组的行数。
- 填好每组的 leading dimension。

把例子的数字代进去，得到的 A 地址是 +0、+524288、+786432 字节，和教程包装函数算出的地址表完全一样。

所以到了 kernel 这一层，两边用的是同一种东西：每组一个指针、一组尺寸、一个 leading dimension。差别在这些表由谁、在哪里生成：

```text
教程版                                      PyTorch 版（快速路径）
主机：读每个张量的地址、形状、步长          主机：只传 X、W、Y 的基地址和 offs 的地址
主机：拼成 5 个 Python 列表                 设备：小 kernel 用 offs 算出每组的指针、尺寸、ld
主机到设备：拷贝 5 张表                     设备：grouped GEMM kernel 读这些表
设备：grouped GEMM kernel 读这些表
```

## 由此带来的区别

### 1. 哪些尺寸可以不同

- **PyTorch 版**：一次调用里只有一个维度参差，这里是行数，由 `offs` 切分。输入维和输出维由 W 的形状统一规定。
- **教程版**：尺寸表每行独立，三个维度都可以逐问题不同。

所以 PyTorch 版算不了教程的示例组，那四个问题的三个维度全都不同。反过来，教程版能算这个 MoE 例子。

### 2. 行数信息要不要回主机

MoE 里每个专家收到多少 token，是 GPU 上的路由计算得出的。主机想知道这个数，就得从 GPU 读回来；读回会让主机停下来，等 GPU 把排队的活全部干完。这叫一次同步。

- **PyTorch 版**：`offs` 是设备张量，可以直接在设备上由路由结果求出。快速路径全程不读回，源码注释写的是 "fast path, no d2h sync needed"。
- **教程版**：包装函数在主机上读 `A.shape`、拼 Python 列表，再建五个设备张量。每次调用有五次主机到设备的小拷贝，而且前提是主机已经知道每组的行数。教程的 benchmark 特意把这段准备工作排除在计时之外（第 403 行的注释）。

这是包装函数的写法问题，不是 kernel 的限制。kernel 只认设备上的表，grid 又与尺寸无关（节点 3），所以这些表完全可以改成在设备上生成。

### 3. 能用在哪些硬件和类型上

按 PyTorch v2.13.0 源码：

- **输入类型**：fp32、bf16、fp16 都接受。
- **快速路径**：只在 NVIDIA sm_90 或 sm_100（Hopper、Blackwell），且输入输出都是 bf16 时启用，内部调用 CUTLASS 的 grouped GEMM。
- **其余情况走回退**：把 `offs` 拷回主机，逐个专家调用普通矩阵乘。这就是节点 1 的"做法一"，还多一次同步。

按这个条件，你的 RTX 4070 Ti（sm_89）走的是回退，这是从源码推出的，没有实机验证。AMD 默认也走回退，另有一条要用环境变量开启的路径。本机 CPU 上跑的同样是回退。

教程版的 kernel 是纯 Triton 写的，不依赖厂商库。指针版我在本机以 sm_90、sm_89 和 AMD gfx942 为目标都只编译通过了。它的限制是写死 fp16、假定满 tile。

### 4. 类型和对齐由谁把关

- **PyTorch 版**：张量自带 dtype 和步长，进门先检查。我在 CPU 上试了三种错误输入，都被拒绝：

| 错误输入 | 报错 |
| --- | --- |
| float64 的 X 和 W | Expected mat_a to be Float32, BFloat16 or Float16 matrix, got Double |
| 输出维改成 500（每行 1000 字节） | strides should be multiple of 16 bytes |
| int64 的偏移表 | Offsets have to be int32 |

- **教程版**：地址表里只有整数。dtype 写死成 fp16；16 字节对齐靠 `tl.multiple_of` 这句承诺，没有人检查。同样把输出维改成 500，包装函数不会报错，后果留到节点 4 讲。

### 5. 其他区别

| 方面 | 教程版 | PyTorch 版 |
| --- | --- | --- |
| 数据放在哪 | 各矩阵可以散在显存各处，也可以指进同一个大张量 | 各组的行必须首尾相接放在同一个张量里 |
| 输出 | 三个独立张量的列表 | 一个 [768, 512] 的张量，行顺序与 X 相同 |
| 求导 | 只是一个前向 kernel | 普通算子，可以自动求导 |

求导这一条我在 CPU 上验证过：给一个稠密的上游梯度，得到的两个梯度与逐个专家循环的结果一致。

### 一个相同点

两边都是整组共用一套块大小。PyTorch 源码里的注释是"假定各个 GEMM 大小相近"，它按平均行数选块：这个例子平均 256 行，在 sm_90 上会选 128×256×64 的块。

## 为什么各自这样选

- **PyTorch 版面向的就是 MoE**。token 已经按专家排好，权重已经是堆叠的张量，行数在设备上。偏移表让这三件事都不需要额外拷贝或同步，张量接口还能做检查和求导。
- **教程版演示的是通用的 grouped GEMM**，沿用 BLAS 和 CUTLASS 的传统接口：每个问题一个指针、一组尺寸、一个 leading dimension。任意形状、任意位置的矩阵都能放进一组。

## 问题一：更均衡就是更好吗

**结论**：不是。总耗时大致等于"最忙的 CTA 的工作量"乘以"做单位工作的耗时"。缩小块能压低前者，却会抬高后者。

### 例子场景

还是教程示例组：四个方阵问题，边长 1024、512、256、128，NUM_SM=84，BK=32。比较 128×128 和 64×64 两种块。

先统一单位。128×128 的块做一次 K 循环，是 128×128×32 次乘加，记作 1 个单位。64×64 的块做一次 K 循环只有它的四分之一。节点 3 里我直接比较了两种块的"K 循环次数"，那样不公平，应该换算成同一单位：

| | 128×128 的块 | 64×64 的块 |
| --- | --- | --- |
| 总块数 | 85 | 340 |
| 最忙的 CTA 的工作量 | 36 | 33 |
| 各 CTA 的平均工作量 | 27.86 | 27.86 |
| 最忙与平均之比 | 1.29 | 1.18 |

所以均衡带来的好处是：最忙的 CTA 从 36 降到 33，少了 8%。即使做到完全均衡，也只能降到 27.86。

### 缩小块付出的代价

**访存量翻倍。** 这是 Lesson 03 讲过的数据复用。一块要读入 A 的 BM×K 个元素和 B 的 K×BN 个元素，完成 BM×BN×K 次乘加，所以每次乘加摊到的读入量是 1/BN + 1/BM。128 的块是 1/64，64 的块是 1/32。放到例子里：

- 问题 0 的 A 矩阵，128 的块时被整体读 8 遍，64 的块时读 16 遍。
- 整组输入一共 5.6 MB。128 的块累计读入 38.3 MB，64 的块累计读入 76.7 MB。

编译产物能印证这一点。我以 sm_89（你的 GPU 架构）为目标编译了两种块：矩阵乘指令从 64 条降到 16 条，是四分之一；异步拷贝指令只从 24 条降到 12 条，是一半。

**每块的固定开销变多。** 块数从 85 变成 340。每一块都要读 6 个标量（地址和 ld）、清零累加器、预热并排空预取流水、写回 C。这些开销不随块的大小等比缩小。

**每次循环里真正在算的比例下降。** 每次 K 循环都有固定的管理动作：推进指针、提交并等待异步拷贝、判断循环条件。128 的块一次循环配 64 条矩阵乘指令，64 的块只配 16 条，管理动作的占比就上升了。

### 公平起见：小块也有一个好处

小块让每个 CTA 占的资源变少，一个 SM 能同时驻留更多 CTA。sm_89、4 个 warp 下的编译结果：

| | 128×128×32 | 64×64×32 |
| --- | --- | --- |
| 每线程寄存器数 | 255（已到上限） | 128 |
| 每个 CTA 的共享内存 | 32768 字节 | 16384 字节 |
| 按寄存器算，每个 SM 可驻留的 CTA 数 | 2 | 4 |

最后一行用的是 Lesson 02 的 occupancy 公式，寄存器总数取那一课用过的 65536。你的 GPU 上的实际值要读 `max_num_regs` 核对。

### 所以怎么选

这是要靠实测决定的取舍，两个真实系统的做法是：

- **教程**把块大小和 NUM_SM 都交给 autotune。6 个配置里 128×128 和 64×64 各配了两种 NUM_SM，在真实的 group 上各跑一遍，取最快的。
- **PyTorch 的 `grouped_mm`** 用经验规则：默认用大块，sm_90 上是 128×256×64；只有平均行数或列数不超过 128 时，才换成 64×128×128。也就是能用大块就用大块，问题小到填不满时才缩小。

### 想要均衡，有不花算力的办法

可以调整问题的顺序。CUTLASS 的示例程序有一个 `--sort-problems` 选项，把问题按 K 从大到小排序。源码没有写动机，下面是我的推断和模型验证。

按步长领取时，每个 CTA 在同一轮里领到的块，来自队列里相邻的 84 块。排序之后这 84 块的 K 相近，各 CTA 每一轮的工作量就接近。

我用调度模型试了 100 个随机尺寸的问题：三个维度各自从 128 到 1024 之间随机取 128 的倍数，块 128×128×32，NUM_SM=84，做 3 次随机试验。

| 问题的顺序 | 最忙与平均之比 |
| --- | --- |
| 随机 | 1.09 – 1.27 |
| 按 K 降序 | 1.03 – 1.05 |

块大小没有变，访存量也没有变。教程的示例组本身就是按 K 降序排的。

## 问题二：为什么说 CUTLASS 的做法说明"找任务"需要优化

### 先说清"找任务"是什么

一个 CTA 手里有一个 `tile_idx`，要知道它属于哪个问题。这需要每个问题在队列里的结束编号，也就是块数的前缀和，然后找出第一个结束编号大于 `tile_idx` 的问题。

### 例子场景

设一个 MoE 层有 256 个专家，这一批每个专家都分到 4 块，队列共 1024 块。NUM_SM=128，所以每个 CTA 领 8 块。第 p 个 CTA 领的是 p、p+128、p+256…… 号块；每个问题占 4 个编号，所以它相邻两块之间隔着 32 个问题。

### 教程的做法：一次看一个问题

对每个问题读 3 个整数，算出块数，累加，再比较。

- `for` 循环不会提前结束，每个 CTA 都要把 256 个问题走完，共 256 步、768 次读取，只为领 8 块。平均每领一块要先走 32 步。
- 这些步是串行的：后一步的队列位置依赖前一步的累加结果。
- 128 个 CTA 合计 32768 步，用来调度 1024 块。

还有一层浪费。kernel 里的标量代码，是 CTA 的每个线程各执行一遍的。4 个 warp 共 128 个线程，在同一时刻读同一个问题的尺寸，做同一个加法，其中 127 份是重复的。

### CUTLASS 的做法：一次看 32 个问题

它让一个 warp 的 32 个线程各读一个不同的问题，一步读进 32 个。然后线程之间交换数据并相加，5 轮之后每个线程手里就是自己那个问题的结束编号。

用 8 个线程示意（真实是 32 个）：

```text
8 个线程各读一个问题的块数：     4   1  16   4  64   1   4  16
前缀和，即每个问题的结束编号：   4   5  21  25  89  90  94 110
```

接下来只需要两个判断：

- 如果 `tile_idx` 不小于最后一个线程的结束编号 110，这 8 个问题整组跳过，再取下一组。
- 否则数一数有几个线程的结束编号不超过 `tile_idx`。比如 `tile_idx=30` 时有 4 个（4、5、21、25），所以它属于第 4 号问题，范围是 25 到 88。

回到 256 个专家的场景：相邻两块隔 32 个问题，CUTLASS 每领一块只需前进 1 组。每个 CTA 走完全表是 8 步，教程版是 256 步。

### 为什么这能说明开销需要优化

这是我的推断，CUTLASS 的源码注释只描述了做法，没有写动机。依据有三条：

- **它放弃了最简单的写法。** 顺序扫描最容易写对。CUTLASS 的版本要做 warp 内通信，每个线程保存不同的状态，注释里还提到要节省寄存器。只有简单版本的开销在它关心的场景里看得见，这种复杂度才值得。
- **它还准备了第二套方案。** `kHostPrecompute` 模式由主机把"每个 CTA 依次做哪个问题的哪一块"整张表算好，设备上完全不扫描。示例程序提供了对比两种模式的开关，还能单独计量主机侧的准备时间。为同一件事维护两套实现并提供对比手段，说明两边的开销都需要权衡。
- **开销的增长方式对它不利。** 扫描的总步数是 CTA 数乘以问题数，连一块都领不到的 CTA 也要走完全表。而问题多且小的时候，每块的计算量很小。PyTorch 的 `grouped_mm` 允许一次最多 1023 组，可见几百组是真实规模。

**边界**：教程示例只有 4 个问题，扫描只有 4 步，完全可以忽略。所以教程用最简单的写法是合理的。

## 节点 4：tile 内的 GEMM 与"假定满 tile"

**结论**：一块内部做的就是 Lesson 03 的分块矩阵乘，只是去掉了所有 mask。这要求每个问题的 M、N、K 都是块大小的整数倍。不满足时 kernel 不会报错，而是读写矩阵之外的内存，而且三个维度的出错方式各不相同。

### 机制

教程第 140–163 行，省略了调度部分：

```python
a_ptrs = a_ptr + offs_am[:, None] * lda + offs_k[None, :]     # [BM, BK] 个地址
b_ptrs = b_ptr + offs_k[:, None] * ldb + offs_bn[None, :]     # [BK, BN] 个地址
accumulator = tl.zeros((BLOCK_SIZE_M, BLOCK_SIZE_N), dtype=tl.float32)
for kk in range(0, tl.cdiv(k, BLOCK_SIZE_K)):
    a = tl.load(a_ptrs)            # 没有 mask
    b = tl.load(b_ptrs)            # 没有 mask
    accumulator += tl.dot(a, b)
    a_ptrs += BLOCK_SIZE_K
    b_ptrs += BLOCK_SIZE_K * ldb
c = accumulator.to(tl.float16)
c_ptrs = c_ptr + ldc * offs_cm[:, None] + offs_cn[None, :]
tl.store(c_ptrs, c)                # 没有 mask
```

和你在 Lesson 03 写的 kernel 对照：

| | Lesson 03 你的 kernel | 第 08 课教程 |
| --- | --- | --- |
| 边界 | 读和写都带 mask | 没有 mask |
| 步长 | 每个矩阵两个 | 每个矩阵一个 ld，行内步长固定为 1 |
| 精度 | fp16 读入，fp32 累加，fp16 写回 | 相同 |
| 指针来源 | kernel 参数 | 从地址表读出 |

关键在地址公式：第 m 行第 k 列的地址是 `a_ptr + m × lda + k`，没有任何一步检查 m 和 k 是否在范围内。对一个连续存放的矩阵（lda 等于列数），这意味着：

- **列号超出**时，地址会绕到下一行的开头。
- **行号超出**时，地址会落到矩阵末尾之后。

### 例子场景

从上一个 MoE 例子里取一个专家，只看它这一个问题：

- 权重 B 是 [1024, 512]，即 K=1024、N=512。
- 标准情况下这个专家收到 128 个 token：A 是 [128, 1024]，C 是 [128, 512]。
- 块取 BM=BN=128、BK=32。C 被切成 1×4 = 4 块，每块 K 循环 32 次。
- 三个矩阵都连续存放，所以 lda=1024，ldb=512，ldc=512。

下面每次只改一个维度，让它不再是块的整数倍。数字来自我按 kernel 的地址公式写的内存模型：把 A、B、C 放进一条一维内存，两侧留出保护区，逐块执行同样的读写，统计落在矩阵之外的地址。

### 情况一：M 不是整数倍

专家只收到 100 个 token，A 变成 [100, 1024]，C 变成 [100, 512]。块数按 `cdiv(100, 128) = 1` 行算，仍是 4 块，每块照样处理 128 行。

- **读**：第 100–127 行不存在，地址落到 A 的末尾之后。28 行 × 1024 列，4 块各读一遍，共 114,688 个元素的越界读。读到的是 A 后面恰好放着的东西。
- **算**：C 的第 m 行只用到 A 的第 m 行，所以垃圾只影响第 100–127 行的结果，前 100 行不受影响。
- **写**：store 照样写 128 行。第 100–127 行落到 C 的末尾之后，共 14,336 个元素、28,672 字节。

结果是：C 的 100 行有效结果全部正确，同时有 28 KB 不属于它的内存被写坏。这是最危险的一种。这个专家自己的结果是对的，逐个专家比较也能通过；被写坏的是内存里排在 C 后面的别的张量。

### 情况二：N 不是整数倍

把输出维从 512 改成 480，B 变成 [1024, 480]，C 变成 [128, 480]，ldb 和 ldc 都是 480。块数是 `cdiv(480, 128) = 4`，最后一块负责第 384–511 列，其中第 480–511 这 32 列不存在。

- **地址绕行**：`c_ptr + m × 480 + n` 在 n 取 480 到 511 时，等于 `c_ptr + (m+1) × 480 + (n − 480)`，也就是下一行的第 0–31 列。
- **两个 CTA 写同一个地址**：最后一块把多算出来的 32 列写进了下一行的开头，而那里的正确值由第 0 块负责。谁后写谁赢。127 行 × 32 列，共 4,064 个有效元素处于这种竞争中。
- **多算出来的值本身也是错位的**：读 B 时同样绕行，用的是 B 下一行开头的数据。
- **最后一行**绕出去的 32 个元素落在 C 之后，是 64 字节的越界写。

结果是：C 内部第 1–127 行的前 32 列可能是错的，而且每次运行可能不一样。

### 两种情况放在一起

| | M 不整除（100 行） | N 不整除（480 列） |
| --- | --- | --- |
| 越界读 | A 之后 114,688 个元素 | B 之后 32 个元素 |
| 写到 C 之外 | 14,336 个元素 | 32 个元素 |
| C 内部的有效结果 | 全对 | 4,064 个元素被两个 CTA 竞争写入 |
| 逐个比较能否发现 | 不能 | 取决于谁后写，可能时有时无 |

这些是按地址运算推出的结果。真机上的越界读写是未定义行为：可能悄悄读写别的数据，也可能直接报错。

### 为什么教程这样写

教程的注释是 "assume full tile for now"，是为了突出调度逻辑做的简化。它的示例和 benchmark 尺寸都是 128 到 8192 之间的 2 的幂，对所有 autotune 配置都是整数倍，所以它自己的测试不会触发这些问题。

### 真实系统

真实的 MoE 里每个专家收到的 token 数是任意的，所以真实实现必须处理不满的块。有两条路：

- **加 mask**，即 Lesson 03 的做法。这也是你在本课练习里要写的。
- **用 tensor descriptor**。描述符带着矩阵的真实形状，由硬件处理边界。PyTorch `grouped_mm` 的快速路径走的是这条路，节点 5 细讲。

## 节点 5：数据怎样从显存搬进 SM

**结论**：编译器知道的越多，搬得越快。不知道地址是否对齐时，每个线程一次只搬 2 个字节；得到对齐保证后，一次搬 16 个字节，并且边搬边算；拿到描述符后，整块交给硬件，线程连地址都不用算。

描述符的接口你在 Lesson 06 用过。这一课看的是它背后发生了什么，以及为什么指针版要多写一句 `tl.multiple_of`。

### 例子场景

指针版 kernel，一个 CTA 有 4 个 warp，共 128 个线程。块取 128×128×32。每轮 K 循环要把 A 的一块（128 行 × 32 列）和 B 的一块（32 行 × 128 列）从显存搬进共享内存，都是 fp16，合计 16384 字节，平均每个线程 128 字节。

下面的数字来自我在本机的只编译结果，目标是 sm_89（你的 4070 Ti 这一代）和 sm_90（带 TMA 的 Hopper）。

### 三种搬法

| | 逐个元素 | 异步拷贝 | TMA |
| --- | --- | --- | --- |
| 出现在哪 | 指针版去掉 `tl.multiple_of` | 指针版原样 | 描述符版，sm_90 |
| 谁发指令 | 128 个线程 | 128 个线程 | 1 个线程 |
| 每轮的指令 | 每线程 64 条读、64 条写，每条 2 字节 | 每线程 8 条拷贝，每条 16 字节 | 整个 CTA 2 条 |
| 谁算地址 | 线程 | 线程 | 硬件 |
| 边搬边算 | 不能 | 能，3 级流水 | 能 |
| 块超出矩阵 | 读到别的内存 | 读到别的内存 | 界外补 0 |

### 对齐提示

`tl.multiple_of(a_ptrs, [16, 16])` 相当于 C 里的 `__builtin_assume_aligned`：一句保证，不检查，也不修正。

- **为什么这里要写**：张量当参数传入时，Triton 在发射前检查首地址是否是 16 的倍数，成立就自动给指针打标记。本课的指针是运行时从地址表读出来的，编译器对它一无所知。
- **编译器拿它做什么**：一次搬 16 字节的指令要求地址对齐。有了保证才敢用它；而一次搬的宽度不到 4 字节时，Triton 不做流水。所以去掉这句，既退回 2 字节的搬法，也失去流水。
- **保证什么时候不成立**：需要首地址对齐，并且行步长的字节数是 16 的倍数。fp16 矩阵每行 100 个元素时，每行 200 字节，奇数行的起点就不对齐。此时编译器照样生成 16 字节的指令，按 NVIDIA 的指令手册，这属于未定义行为。
- **真实系统的做法**：PyTorch 的 `grouped_mm` 不靠保证，而是进门就检查，你上次见过那条 "strides should be multiple of 16 bytes" 的报错。

一个细节：教程只给 A、B 的地址写了保证，没有给 C 写。所以写回 C 仍是每线程 128 条 2 字节的写。

### TMA 与描述符

Lesson 06 之外的新内容有三点。

**描述符只能在设备上现场创建。** 形状来自尺寸表，问题个数运行时才知道，而 kernel 的参数个数固定，所以没法由主机做好再传进来。教程把创建放在 `if` 里，每个 CTA 只为自己要处理的问题创建。

**现场创建有成本。**

- 硬件要求描述符对象放在全局内存里，所以每个 CTA 需要一小块全局暂存区：3 个描述符，共 768 字节。
- 发射时 Triton 调用你注册的分配器，一次申请"CTA 数 × 768"字节。这就是这个 kernel 必须先 `triton.set_allocator` 的原因。
- 每个描述符要用 13 条指令逐个字段填写，再整体拷到全局内存。这只在 CTA 开始处理一个新问题时发生，不在 K 循环里。

**它顺带解决了节点 4 的问题。** 描述符带着矩阵的真实形状，硬件知道哪些元素在界外：读的时候补 0，写的时候不写。所以描述符版没有"满 tile"的限制，100 行的 A 和 K=1000 都能算对。它的限制换成了对齐：行步长的字节数必须是 16 的倍数。

### 在你的 GPU 上

TMA 从 sm_90 才有。在 sm_89 上，Triton 会把描述符改写成指针加 mask，mask 由描述符里的形状生成。结果相同，但搬法退回最普通的那种：我编译出来的产物里没有异步拷贝。教程用 `supports_tma()` 把描述符版限制在 sm_90 及以上，所以它在你的机器上不会被调用，但 kernel 本身能编译。两个版本在 sm_89 上谁快，我没有测。

### B 为什么转置存放

描述符版要求 B 按 [N, K] 存放，kernel 里读出一块后再写 `b.T`。TMA 是把数据原样搬进共享内存，不重排；这样存放时，A 和 B 的块都以 K 为连续方向。PyTorch 文档对 FP8 输入提的是同一个要求：左矩阵按行存，右矩阵按列存。硬件层面为什么这样要求，我没有核到原文，不展开。

**028 · 助手** · `2026-10-06T08:40:30.228Z` · `msg-442b3e3fd1f6ff9c0e0f`

是的，每一行的行首都要是 16 的倍数，只有矩阵首地址对齐还不够。更准确地说，要求落在每一条拷贝指令上：它一次搬 16 个字节，起始地址必须是 16 的倍数。

## 为什么会落到"每一行"上

一条拷贝指令搬的是同一行里连续的 8 个 fp16。以 A 的一块（128 行 × 32 列）为例，每一行被切成 4 段，每段 8 个元素、16 个字节：

```text
一行里的 4 段，起点分别是：
行首 + 0   行首 + 16   行首 + 32   行首 + 48   （字节）
```

行内各段之间正好相隔 16 字节。所以只要行首是 16 的倍数，这一行的 4 段就都对齐；行首不对齐，这一行的 4 段就全都不对齐。

## 每一行的行首对齐需要什么

第 m 行的行首地址是：

```text
首地址 + m × 行步长的字节数
```

要让它对所有 m 都是 16 的倍数，需要两个条件同时成立：

- 首地址是 16 的倍数。
- 行步长的字节数是 16 的倍数。对 fp16 来说，就是行步长是 8 个元素的倍数。

用两个 fp16 矩阵对比，假设首地址都对齐：

| 行号 | 每行 1024 个元素（2048 字节） | 每行 100 个元素（200 字节） |
| --- | --- | --- |
| 0 | 0，对齐 | 0，对齐 |
| 1 | 2048，对齐 | 200，余 8，不对齐 |
| 2 | 4096，对齐 | 400，对齐 |
| 3 | 6144，对齐 | 600，余 8，不对齐 |

第二个矩阵的首地址没有问题，但奇数行全部不对齐。图解页"对齐实验"里的表格显示的就是这个，把行步长改成 100 可以看到。

## 两点补充

- **块在行内的起点也要对齐**。教程里它天然满足：K 方向每轮前进 32 个元素，即 64 字节；N 方向块的起点是 128 的倍数。
- **规则对每个这样搬运的矩阵都一样**，各看各的行步长。这不只是异步拷贝的要求：任何一次访问 16 字节的指令都如此，TMA 也是。没有保证时编译器用的 2 字节读法，只需要 2 字节对齐，fp16 天然满足。

对，16 字节这一档不能用。在不对齐的地址上执行 16 字节的搬运属于未定义行为，而且编译器和运行时都不会拦你，所以只能靠你不做虚假的保证。

## 异步拷贝：可以如实降档

异步拷贝指令一次可以搬 4、8 或 16 个字节。保证不必非写 16，写多少取决于你能如实保证多少。

还是那个例子：fp16 矩阵每行 100 个元素，即每行 200 字节。200 是 8 的倍数，所以每一行的行首都是 8 的倍数。这时可以如实写 `tl.multiple_of(a_ptrs, [8, 8])`。

我把保证的数值换成几档分别编译，目标 sm_89：

| 保证的倍数 | 编译器选的搬法 | 每条指令搬多少 | K 循环有流水吗 |
| --- | --- | --- | --- |
| 16 | 24 条异步拷贝 | 16 字节 | 有 |
| 8 | 48 条异步拷贝 | 8 字节 | 有 |
| 4 | 96 条异步拷贝 | 4 字节 | 有 |
| 2 或不写 | 64 条普通读 | 2 字节 | 没有 |

所以每行 200 字节的矩阵，正确的选择是保证 8：指令多一倍，但仍然是异步拷贝，仍有流水。只有连 4 字节都保证不了时，才会退回最慢的那种。

## TMA：没有降档

TMA 的要求是硬性的：搬运块的地址必须是 16 字节对齐，行步长的字节数必须是 16 的倍数，没有 8 字节的模式。奇数行不对齐的矩阵不能直接交给它。要用 TMA，只能改变数据的摆放，让行步长变成 16 字节的倍数；否则就不用 TMA。

## 小结

| 矩阵的情况 | 异步拷贝 | TMA |
| --- | --- | --- |
| 每行行首都是 16 的倍数 | 保证 16，一次搬 16 字节 | 可以用 |
| 每行行首只是 8 的倍数 | 保证 8，一次搬 8 字节 | 不能直接用 |
| 保证不了 4 的倍数 | 不要写保证，退回逐个元素 | 不能直接用 |

这也是 PyTorch 选择"进门检查"而不是"相信调用方"的原因：它的快速路径建立在 TMA 上，没有降档的余地。

| 矩阵 | 指针版的形状 | 行步长 | 描述符版的形状 | 行步长 |
| --- | --- | --- | --- | --- |
| A | [M, 1024] | 2048 字节，满足 | [M, 1024] | 2048 字节，满足 |
| B | [1024, 500] | 1000 字节，不满足 | [500, 1024] | 2048 字节，满足 |
| C | [M, 500] | 1000 字节，但没有保证，不受影响 | [M, 500] | 1000 字节，不满足 |

转置存放把 B 的最后一维从 N 换成了 K，所以同一个 N=500，在指针版里坏的是 B，在描述符版里坏的是 C。

**第 3 题**

- **C 的修法是对的**，包括"不必补零，切片即可"。PyTorch 就是这样做的：我在 CPU 上用同样的尺寸跑了一次 `grouped_mm`，输出的形状是 [768, 500]，但相邻两行相隔 504 个元素。504 是不小于 500 的最小的 8 的倍数，你说的 512 也可以。
- **实现时要注意一点**：描述符里的形状仍然写 500，只把行步长写成 504 或 512。这样硬件只写每行的前 500 列。
- **B 在描述符版里不用改**，原因同第 2 题。
- **你对 B 的修法放在指针版里是成立的**。把每个专家的 B 补零到 512 列，既让 B 的行步长对齐，又让 N 变成整数个块（512 = 4 × 128），连节点 4 的 N 方向问题一起消掉。代价是要拷贝一次权重。权重是静态的，可以在加载模型时做一次。

**034 · 助手** · `2026-10-06T09:44:27.951Z` · `msg-d6b70c09d6cb60b1e0f9`

不能。加上保证后写回会变快，但它仍然是普通的写指令，不是异步拷贝。

## 为什么不能

异步拷贝指令 `cp.async` 只有一个方向：从显存到共享内存。NVIDIA 的指令手册对它的定义就是源地址在显存、目的地址在共享内存，没有反方向的版本。

反方向的异步搬运只存在于 TMA 那一族指令里，需要 sm_90。

## 三种写回方式

| | 指针版原样 | 指针版，给 C 加保证 | 描述符版，sm_90 |
| --- | --- | --- | --- |
| 每线程的指令 | 128 条普通写，每条 2 字节 | 16 条普通写，每条 16 字节 | 整个 CTA 1 条 TMA 搬运 |
| 是否异步 | 否 | 否 | 是 |
| 前提 | 无 | C 首地址对齐，行步长是 16 字节的倍数 | 同左，外加 TMA 硬件 |

中间一列的数字来自我之前编译的那个只做写回的小 kernel。所以给 C 加保证的收益是指令数降到八分之一，而不是变成异步。

## 描述符版的异步写回是什么样

编译产物里，每算完一块，顺序是这样的：

```text
等上一块的写回完成          // 共享内存里的结果缓冲区要复用
把这一块的结果写进共享内存
发起搬运：共享内存 → 显存   // 发出后不等
领下一块，开始它的读和计算
……
所有块做完后，再等最后一次写回完成
```

也就是说，第 i 块的写回和第 i+1 块的计算是重叠的。这是固定 CTA 循环领多块带来的机会：一个 CTA 只算一块的话，写完就结束了，没有东西可以重叠。

## 为什么读比写更需要异步

这一段是我的推理，不是手册原话。

- **读**：计算要用的数据必须先到。不提前发起，计算就得停下来等，所以要提前两三轮把数据搬在路上。
- **写**：结果算完才有，没法提前；写出去之后，这个 CTA 后面的计算也不再用它。没有人在等这份数据。

所以异步对读的价值大得多，这也是 `cp.async` 只做读方向的合理解释。

## 一个提醒

给 C 加保证，就要对 C 负责。回到上一题 N=500 的场景：C 的行步长是 1000 字节，保证不成立。你当时说"C 的写会产生未定义行为"，在教程原样的代码里不成立，但加上这句之后就成立了。

**结论**：真实的 MoE 层里，三个维度只有 M 是参差的。这决定了前五个节点里哪些问题真的会遇到。

### 例子场景

DeepSeek-V3 的一层 MoE，数字来自它的技术报告第 4.2 节：

- 隐藏维 7168，每层 256 个路由专家，每个专家的中间维 2048。
- 每个 token 激活 8 个路由专家。

取专家里升维的那一步矩阵乘。对每个专家 g：A 是 [M_g, 7168]，B 是 [7168, 2048]，C 是 [M_g, 2048]。所以 G=256，K=7168，N=2048，对所有专家都相同。一批有 T 个 token 时，总行数是 8T，平均每个专家 T/32 行。

取 T=4096，平均每个专家 128 行，实际有多有少。块用 128 × 128 × 32。

### 每个节点在这里的落点

| 节点 | 在这个场景里 |
| --- | --- |
| 1 收益 | 逐个调用要发射 256 次。一个 128 行的专家只有 1 × 16 = 16 块，一次调用只占 16 个 SM |
| 2 交法 | token 已按专家排好，行数在设备上，适合偏移表 |
| 3 调度 | K 都是 7168，每块的工作量相同，按步长分配天然均衡；但每个 CTA 要扫 256 个问题 |
| 4 边界 | N=2048 是 16 个整块，K=7168 是 224 个整轮；只有 M 不整，遇到的正是写到 C 之外的那一种 |
| 5 对齐 | A 每行 14336 字节，B、C 每行 4096 字节，都是 16 的倍数，保证成立，TMA 也可用 |

所以真实实现要补的东西很集中：处理 M 方向的不满块，并控制"找任务"的开销。N、K 和对齐在这个配置下都不是问题。

**边界**：这是训练和预填充的情形。解码时一步只有很少的 token，平均每个专家只有几行，很多专家一行都没有。块的大小和问题的大小就不匹配了，这也是 PyTorch 按平均行数换小块的原因。

## 串讲：一块数据的一生

沿用上面的场景，假设每个专家恰好 128 行，发射 128 个 CTA。

1. **准备**。主机不知道每个专家的行数，它们在设备上。地址、尺寸、ld 三类表要么由包装函数在主机上建好再拷下去，要么像 PyTorch 那样由一个小 kernel 在设备上从偏移表展开。
2. **一次发射**。256 个专家各 16 块，共 4096 块，首尾相接排成一条队列。grid 固定是 128，与尺寸无关。
3. **领任务**。第 p 个 CTA 领第 p、p+128、p+256…… 号块，共 32 块。它按顺序走一遍 256 个问题，用块数的前缀和判断手里的编号落在哪个问题里。K 相同，所以 128 个 CTA 的工作量相等。
4. **定位数据**。从地址表读出一个整数，转成指针；从 ld 表读出行步长。编译器对这个指针一无所知，对齐要靠你保证。
5. **K 循环，224 轮**。每轮把 A 的 128 × 32 和 B 的 32 × 128 搬进共享内存：有保证时用 16 字节的异步拷贝，三轮的数据同时在路上；有 TMA 时由硬件按描述符整块搬。然后做矩阵乘，结果累加在 fp32 里。
6. **写回**。转成 fp16，写到 C_g 的对应位置。行数不足 128 的专家，要靠 mask 或描述符挡住界外的行。
7. **下一块**。编号加 128，回到第 3 步，直到队列走完。

贯穿全程的取舍有四组：

- **一次发射**换来满载的 SM，付出设备上的扫描。
- **静态分配**不需要任何同步，但只均分块数，不均分工作量。
- **大块**数据复用高，但对小问题浪费，而且整组只能用一种块。
- **靠保证**没有检查的开销，但错了没人拦；**靠检查**安全，但不满足时只能拒绝。

综合验收：
1. 在grouped GEMM中，一组尺寸不同的矩阵乘问题会按照同样的分块大小进行划分，一个矩阵乘问题整体成为了tile级别的小块矩阵乘的子任务，这些子任务的BLOCK的M和N方向大小是一样的。而后，将有并行的CTA program按照pid顺序认领这些子任务，并按照每个矩阵乘问题划分tile数量的前缀和对应到主问题。然后再根据认领到子任务信息，通过标量计算，获取到需要的数据地址、数据形状等信息。接着，进行tile上的矩阵乘和K方向的循环累加。最终再将计算结果放到子任务对应的结果矩阵位置。而后CTA program不一定只处理一个tile，后续根据整个问题规模情况，再处理其他tile的子任务。本教程中会处理将逐渐将编号增加NUM_SM，处理对应的tile。如此，将一组尺寸不同的矩阵乘问题用一次发射的kernel完成了计算。这种做法相比于逐个调用省去了多次发射的发射开销，避免了小矩阵乘问题对SM资源利用率不足的情况，提高了SM利用率。但其中的代价是使得一组矩阵乘任务的分块大小被固定了，分块方式对于单独的矩阵乘问题可能不是最优的。此外，还引入了标量计算的规划调度开销，每个CTA program需要自己计算所需要计算的tile任务的元数据信息。如果这组gemm问题的K方向大小不一致，还有CTA工作量不均衡的问题。于是，grouped GEMM更适用于大量的、较小规模、K维度相对一致的gemm问题，不太适合于少量的大规模gemm问题。少量的大规模gemm可能单独一个一个发射就足够打满SM利用率了。

> Grouped GEMM 要一次算完一组尺寸不同的矩阵乘。逐个调用有两个问题：每次都有发射开销；小问题的块数比 SM 少，大部分 SM 空着。它的做法是把每个问题按同样的块大小切开，所有块首尾相接排成一条队列，只发射一次、固定数量的 CTA，第 p 个 CTA 处理第 p、p+NUM_SM…… 号块。矩阵个数运行时才知道，所以矩阵不是参数，而是把地址、尺寸和行步长存进设备上的表；kernel 用块数的前缀和找到自己的块属于哪个问题，再读出地址，块内就是普通的分块矩阵乘。代价有三个：每个 CTA 要扫描问题表；整组共用一种块大小；调度只均分块数，各问题 K 不同时工作量不均衡。教程还假定尺寸是块的整数倍，真实的 MoE 只有行数参差，用行方向的 mask 或 TMA 描述符处理。所以它适合大量、较小、K 相近的问题。

### 2. 预测

结论和理由都对。我编译验证了，sm_89 和 sm_90 的结果相同：

| 写法 | K 循环里的搬运 |
| --- | --- |
| 没有 mask | 24 条 16 字节的异步拷贝 |
| 甲：只有行方向的 mask | 24 条 16 字节的异步拷贝，不变 |
| 乙：三个方向都有 mask | 没有异步拷贝，退回 64 条 2 字节的读 |

一处要更精确：甲够用的条件不是"N、K 是 8 的倍数"，而是"N、K 是块大小的整数倍"。DeepSeek-V3 里 N=2048 是 16 个 128，K=7168 是 224 个 32。8 的倍数管的是对齐，是另一件事。

### 3. 设计

方向是对的：需要共享状态，领取必须是原子操作，解决的是谁空谁领。但"每块一个标记"偏重，标准做法只要一个计数器。

**例子**：教程示例组，84 个 CTA，85 块。静态分配下 CTA 0 做完 32 个单位的大块还要再做第 84 号块，共 36 个单位。如果改成谁空谁领，第 84 号块会被最早空闲的 CTA 领走，那是只做了 8 个单位的某个 CTA，总耗时降到 32。

**计数器方案**：

- **共享状态**：显存里的一个整数，含义是"下一个没人领的块编号"，发射前清零。
- **领取**：每个 CTA 空闲时做一次原子的"读出旧值并加 1"。读到的旧值就是它领到的块编号；旧值超过总块数就退出。

**和你的方案相比**：

| | 每块一个标记 | 一个计数器 |
| --- | --- | --- |
| 共享状态 | 每块一个，发射前都要清零 | 1 个整数 |
| 找下一块 | 要搜索哪个标记还空着 | 不用找，读到的就是 |
| 失败的尝试 | 多个 CTA 抢同一个标记，输的要重试 | 没有 |

**扫描为什么仍然成立**：你的结论对，但理由要换一个。计数器只增不减，所以同一个 CTA 先后领到的编号一定是递增的。这和静态方案里 `+= NUM_SM` 的性质一样，顺序走一遍问题表就够。

**代价**：每领一块做一次原子操作，所有 CTA 都争同一个地址；谁领到哪块每次运行不同，性能问题不好复现；每次发射前要多写一次显存来清零。在 MoE 里各块工作量相同，它没有收益。

### 4. 迁移

- **(a) 对，漏了一项代价**。回退路径要先把偏移表拷回主机，这会打断异步执行，造成一次同步。
- **(b) 对**。补上机制：描述符版会被改写成指针加 mask。我用 AMD 的 gfx942 做目标编译过，两个版本都能编译。另外值得说出哪些东西不变：调度、地址表、行方向的 mask 都与后端无关。
- **(c) 你的优先级合理**。我会再加两条，并排在搬运方式之前：
  - M 方向的正确性。写越界是静默的，出了问题很难查。
  - 行数留在设备上，不回主机。不这样做，一次发射的收益会被同步吃掉。

你观察得对：B 在内存里是真的按转置后的顺序重新排过的，不是视图。不过这次重排发生在 kernel 之外，kernel 里那个 `b.T` 是另一回事。教程里一共有两次"转置"，要分开看。

## 第一次：主机侧，真的拷贝重排

教程在准备数据时写的是（第 387 行）：

```python
B_T = B.T.contiguous()
```

这一行做了两件事。用一个小例子看：B 是 3 行 2 列，K=3、N=2，元素依次是 0 到 5。下面是我在本机实际运行的结果：

| | 形状 | 步长 | 和 B 是同一块内存吗 | 内存里的顺序 |
| --- | --- | --- | --- | --- |
| `B` | [3, 2] | (2, 1) | — | 0 1 2 3 4 5 |
| `B.T` | [2, 3] | (1, 2) | 是 | 0 1 2 3 4 5 |
| `B.T.contiguous()` | [2, 3] | (3, 1) | 否 | 0 2 4 1 3 5 |

- `B.T` 只是视图：内存没动，只是换了一种读法，步长变成 (1, 2)，行内不再连续。
- `.contiguous()` 才是重排：新开一块内存，按 [N, K] 的行优先顺序把数据拷进去。

交给描述符版 kernel 的是第三行。所以 kernel 拿到的地址，指向的确实是一块按 [N, K] 排好的内存。

## 为什么只给视图不行

- **包装函数只传首地址和 `stride(0)`**。视图的首地址和 B 相同，`stride(0)` 是 1。kernel 会把这块内存当成"每行 1 个元素"来读，全错。
- **描述符要求最后一维连续**。kernel 里写的是 `strides=[ldb, 1]`，行内步长写死为 1。视图的行内步长是 N，描述不了。
- **TMA 是原样搬运**。它把显存里的一块原封不动地放进共享内存，不会替你重排。

## 第二次：kernel 里的 `b.T`，不搬数据

kernel 第 310 行是 `tl.dot(a, b.T)`。这里的 `b` 是已经搬进共享内存的一块，形状 [BN, BK]。数学上需要的是 [BK, BN]，所以写了 `.T`。

这一次不移动任何数据。我看了编译产物：`b.T` 变成了对共享内存里那一块的"重新贴标签"，标签上多了一项 `transposed = true`。矩阵乘指令据此知道第二个操作数是按转置的顺序摆放的，直接按那个顺序去读。

所以完整的过程是：

```text
主机：  B [K, N]  ——拷贝重排——>  B_T [N, K]         （真的动了内存，只做一次）
显存：  B_T 的一块 [BN, BK]
          │  TMA 原样搬运
共享内存：同样的一块 [BN, BK]
          │  b.T：只改标签，不动数据
矩阵乘：  按"第二个操作数是转置摆放的"来读
```

## 这次拷贝的代价和真实情况

- **教程里**：`B.T.contiguous()` 写在准备数据的部分，不在计时范围内，所以 benchmark 里看不到这笔开销。
- **真实系统里通常不需要这次拷贝**。PyTorch 的线性层权重本来就是按 [输出维, 输入维] 存的，也就是 [N, K]，前向计算写成 `x @ W.T`。MoE 的专家权重沿用这个习惯，天然就是描述符版想要的排法。`grouped_mm` 的文档说的也是这种情况。教程需要拷贝，只是因为它的例子是从 [K, N] 的 B 出发的。

练习里的指针版仍然按教程指针版的约定，B 是 [K, N]，不涉及转置。

**049 · 助手** · `2026-10-07T04:45:31.903Z` · `msg-a37173bba7b19617f928`

也要预先做好。描述符只负责描述一块已经存在的内存：创建它时不读数据、不搬数据，也不会替你补齐。对齐和转置是同一个道理，布局必须在创建描述符之前就已经是对的。

不过"补齐"分输入和输出两种情况，代价不一样。

## 输入和输出的区别

| | 需要做什么 | 要拷贝数据吗 | 谁来做 |
| --- | --- | --- | --- |
| 输入 A、B | 把数据放进一个行步长更宽的缓冲区 | 要，拷一遍 | 调用方，预先做好 |
| 输出 C | 分配时就把行步长留宽 | 不要 | 谁分配输出，谁负责 |

**输入**的数据已经躺在内存里了，行步长是既成事实。要改，只能新开一块更宽的缓冲区，把数据拷过去。以 fp16 的 A 是 [M, 1020] 为例：

```python
buffer = torch.empty((M, 1024), dtype=torch.float16, device=A.device)
buffer[:, :1020] = A            # 真的拷贝了一遍
A_aligned = buffer[:, :1020]    # 形状仍是 [M, 1020]，相邻两行相隔 1024 个元素
```

**输出**还没有数据，所以不存在拷贝，只是分配时多要一点空间：

```python
buffer = torch.empty((M, 504), dtype=torch.float16, device=device)
C = buffer[:, :500]             # kernel 直接往这里写，写完就是结果
```

## 各家是怎么做的

- **Triton 的描述符和 kernel**：都不做。步长不满足要求时，编译后的 kernel 不会检查，行为未定义；只有 Triton 的解释器会报错。
- **教程的包装函数**：也没做。它用 `torch.empty((M, N))` 分配 C，N 不是 8 的倍数时，描述符版的 C 就不满足要求。
- **PyTorch 的 `grouped_mm`**：
  - 对输入不补齐也不拷贝，直接报错，让调用方预先处理。
  - 对输出，因为是它自己分配的，所以它自己把行步长留宽。上次我跑出来的那个形状 [768, 500]、行间隔 504 的结果就是这样来的。这是分配时的选择，没有发生拷贝。

所以更准确的说法是：输入的补齐是一次需要预先完成的拷贝；输出的补齐只是分配方式，发生在分配输出的那个函数内部。

## 和练习的关系

练习里的指针版不需要做任何补齐。按约定，A、B 不对齐时包装函数直接抛 `ValueError`，和 PyTorch 对输入的处理一致；C 没有对齐保证，所以怎么分配都可以。

**051 · 助手** · `2026-10-07T04:49:05.564Z` · `msg-985b25a53f2e9241c099`

下面按"输入是什么样"来整理，分对齐、尺寸、存放方向和设备四张表。每一格写的是调用前要做什么，以及做与不做的后果。

先说贯穿全部的三条原则：

- kernel 和描述符都不会改动内存里的布局，所有要求必须在调用前就成立。
- 输入的布局要改，只能拷贝一遍；输出只需要在分配时留好。
- 指针版靠的是保证，没人检查；描述符版在 TMA 上是硬性要求。两者不满足时的行为都没有保证。

## 一、对齐

这里的"行步长"指相邻两行相隔的字节数。fp16 时，16 字节的倍数相当于 8 个元素的倍数。

| 输入的情形 | 指针版加异步拷贝 | 描述符版 |
| --- | --- | --- |
| 首地址和行步长都是 16 的倍数 | 不用处理。保证 16，每条指令搬 16 字节，有流水 | 不用处理，可以直接用 |
| 行步长只是 8 或 4 的倍数 | 不用拷贝。把保证改成 8 或 4，指令数变成 2 倍或 4 倍，仍有流水 | 输入必须先拷贝到行步长为 16 倍数的缓冲区 |
| 行步长连 4 的倍数都不是 | 不写保证，退回每次 2 字节的读，没有流水；或者拷贝补齐后保证 16 | 同上，必须拷贝 |
| 首地址不对齐，例如 `big[:, 4:]` | 保证 16 不成立。按实际情况降档，或者拷贝 | 必须拷贝 |
| 输出 C | 教程没有对 C 作保证，怎么分配都行 | 分配时把行步长留宽到 16 的倍数，再切片，不需要拷贝 |

## 二、尺寸不是块的整数倍

| 输入的情形 | 指针版 | 描述符版 |
| --- | --- | --- |
| 只有 M 不整 | 数据不用处理。kernel 里给读 A 和写 C 加行方向的 mask，异步拷贝保持不变 | 不用处理，界外的读补 0，界外的写被跳过 |
| N 或 K 不整，选择一 | 数据不用处理。三个方向都加 mask，代价是退回每次 2 字节的读，没有流水 | 不用处理，同上 |
| N 或 K 不整，选择二 | 调用前把 A、B 补零到整块，C 按整块分配后切片。要拷贝一次输入，换来保持异步拷贝 | 不需要这样做 |
| 完全不处理，也没有 mask | M：写坏 C 之后的内存；N：C 内部出现竞争写；K：全部结果都可能出错 | 不存在这个问题 |

描述符版虽然不怕尺寸不整，但第一张表的对齐要求照旧。比如 N=500 时，C 的行步长就不满足。

## 三、存放方向与连续性

| 输入的情形 | 指针版 | 描述符版 |
| --- | --- | --- |
| 行内不连续，例如 `x[:, ::2]` 或转置视图 | 必须先 `.contiguous()`，kernel 假定行内步长是 1 | 必须先 `.contiguous()`，描述符要求最后一维连续 |
| B 按 [K, N] 存放 | 直接用 | 需要 `B.T.contiguous()`，一次转置拷贝 |
| B 按 [N, K] 存放，即 PyTorch 线性层权重的习惯 | 需要转置拷贝成 [K, N] | 直接用。kernel 里的 `b.T` 不搬数据 |
| dtype 不是 fp16 | 教程把类型写死成 fp16，要先转换，或者改 kernel | 教程支持 fp16 和 FP8 两种 |

## 四、设备

| 设备 | 指针版 | 描述符版 |
| --- | --- | --- |
| sm_90 及以上 | 异步拷贝，无额外准备 | TMA 整块搬运。发射前必须 `triton.set_allocator`，每个 CTA 要 768 字节的全局暂存区 |
| sm_89 等没有 TMA 的设备 | 异步拷贝照常可用 | 描述符被改写成指针加 mask。结果正确，但没有异步拷贝 |
| 其他后端，例如 AMD | 能编译，搬运方式由后端决定 | 同样被改写成指针加 mask |

## 放到真实场景里看

真实的 MoE 层需要预处理的东西很少：

- **权重**是静态的。按 [N, K]、行步长为 16 字节的倍数存一次，两个版本都能直接用。
- **激活**每次调用都在变，拷贝代价最高。好在隐藏维通常是 8 的倍数，也是块的整数倍，对齐和 N、K 的整块要求天然满足。
- **真正每次都不同的只有行数**。指针版用行方向的 mask，描述符版什么都不用做。
- **输出**在分配时留宽即可，没有拷贝。

这些结论里，异步拷贝的档位、mask 对流水的影响、描述符在 sm_89 和 AMD 上的改写，来自本机的只编译结果；`grouped_mm` 的行为来自它的源码和 CPU 上的运行。都没有在 GPU 上实测过。

- **空的问题表现为重复的值**。测试里各组的行数是 100、0、1、67，对应的 `offs` 是 `[100, 100, 101, 168]`，第 1 个问题没有行。

## 这 4 个失败的原因

失败来自 [lesson08_grouped_gemm.py:205-211](gpu/triton/lesson08_grouped_gemm.py#L205-L211) 那段调试用的 `print`，不是 kernel 或表的计算报出来的。它的最后一行 `{offs.cpu()=}` 把 `offs` 拷回了主机，而约定写的是“不得把 `offs` 读回主机”。

- **测试怎样发现的**：传给你的 `offs` 是测试文件里的一个 `torch.Tensor` 子类 [`_NoHostRead`](gpu/triton/lesson08_grouped_gemm_test.py#L548)。对它调用 `.cpu()`、`.item()`、`.tolist()`、`.numpy()`、`int()`、`bool()` 都会抛 `AssertionError`。在设备上做加减乘、切片、`torch.cat` 不受影响。
- **直接写 `{offs=}` 也会失败**：打印张量内部会调用 `.tolist()`。回溯里那句 `.tolist()` 是 pytest 打印局部变量 `self` 时自己触发的，与你的代码无关。
- **为什么禁止读回**：读回主机时，主机必须等 GPU 把排在前面的工作全部做完。PyTorch v2.13.0 的快速路径在 `GroupedBlas.cpp` 里注释为 “fast path, no d2h sync needed”，而回退路径（`GroupedMMUtils.h`）正是先 `offs.cpu()` 再逐组循环。
- **处理办法**：把整段 `print` 删掉。`{group_gemm_sizes=}` 那一行也在把由 `offs` 算出的数据读回主机，测试拦不住它，但性质相同。想看表的内容，可以在 pytest 之外用普通张量调用这个函数。

**067 · 助手** · `2026-10-09T02:44:05.553Z` · `msg-7c05d8aa69775adc07d6`

对，结论正确：地址表里存的是按字节计的整数地址，行偏移要换算成字节再加，也就是“行数 × 行步长（元素）× 元素大小（字节）”。

原因有一处要说得更准：单位信息不是在转成张量时丢的。`x.data_ptr()` 返回的本来就是一个 Python 整数，主机侧从头到尾没有“带类型的指针”，它只在 kernel 里才出现：

| 位置 | 相当于 C 里的 | `+ n` 前进多少 |
| --- | --- | --- |
| 主机侧的地址（`data_ptr()`、int64 张量） | `uintptr_t` | n 字节 |
| kernel 里 `.to(tl.pointer_type(tl.float16))` 之后 | `half*` | n 个元素，即 2n 字节 |

- **`g_lds` 用元素作单位**：它在 kernel 里转型之后才被使用。
- **地址表的偏移必须用字节**：它在转型之前就加上去了。
- **`grouped_matmul` 没遇到这个问题**：每个视图的 `data_ptr()` 已经含偏移，PyTorch 替你做了“存储偏移 × 元素大小”这一步。

这也解释了上一条表里的三段现象：

- 偏移少乘了 2，第 2 组本该从第 100 行开始，实际落在第 50 行。
- 第 3 组本该从第 101 行开始，实际落在第 50.5 行，写 67 行正好到第 117.5 行。所以第 50–116 行被覆盖，第 117 行只写了一半。
- 第 118–167 行没有任何一组去写。

PyTorch v2.13.0 做的是同一步，在 `GroupMMCommon.cuh` 的设备侧准备 kernel 里：`A_ptrs[tid] = A + offs[tid - 1] * tensor_StrideA[0]`。那里的 `A` 是带类型的指针 `DtypeA*`，乘元素大小由 C++ 编译器完成，所以源码里看不到这个因子。

| 你遇到的问题 | 实测的报错 | 原因 | 可行的写法 |
| --- | --- | --- | --- |
| `continue` 跳过 M 为 0 的问题 | `unsupported AST node type: Continue` | 代码生成器没有处理 `continue` 的函数，`break` 也一样 | 用 `if` 包住循环体。本课其实不用处理：M 为 0 时块数为 0，`while` 不会进入 |
| 循环里把标量指针原地改写成块指针 | `Loop-carried variable … has initial type pointer<fp16> but is re-assigned to <[…], pointer<fp16>> in loop` | 跨迭代传递的变量类型必须不变 | 每轮用新名字从基地址重新算，这是你现在的做法 |
| mask 的比较不加括号 | `simultaneous multiple comparison is not supported` | Python 里 `&` 的优先级高于 `<`，`a < M & b < K` 被解析成链式比较 `a < (M & b) < K` | 每个比较都加括号 |
| 行步长用列数代替 | 不报错，结果错 | 视图的行步长不等于列数 | 一律取 `stride(0)` |

三处补充：

- **`continue` 为什么不支持**：源码只能确认“没有对应的处理函数”。更深的原因是我的推断：Triton 把循环编译成只有一个入口和一个出口的结构化区域，中途跳出没有对应的表达方式。
- **“循环偏移了”的那一半**：类型一致时这种写法能通过编译，但每一轮都在上一轮的结果上再加一次完整偏移，地址逐轮累加。教程的 `a_ptrs += BLOCK_SIZE_K` 也是原地改写，区别在于它每轮只加增量。
- **括号和行步长都不是 Triton 特有的**：括号规则在 NumPy 和 PyTorch 里相同。行步长的例子是 `[4, 100]` 的张量取 `[:, :64]`，形状是 `(4, 64)`，步长是 `(100, 1)`；PyTorch 的 `grouped_mm` 返回的输出本身就可能带补齐过的行步长。
