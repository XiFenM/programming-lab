**009 · 助手 / 正式回答** · `2026-08-05T06:40:43.330Z`

你的第 1 题映射完全正确，第 2 题方向基本正确；第 3、4 题需要把“program 内软件流水”和“program 间硬件调度”分开。

1. 唯一覆盖证明

不能只说“合理安排”，可以用整数除法证明。任意行 `r` 都有唯一的商和余数：

```text
p = r % P
k = r // P
r = p + kP
```

因此，行 `r` 必然由 program `p` 的第 `k` 次迭代处理；商和余数唯一，所以既不会遗漏，也不会重复。

2. 资源趋势

你的方向正确：更多在途迭代可能延长中间值的生命周期或增加 buffering，因而可能增加资源占用、减少 resident programs。

但需要保留两个限定：

- 不保证 registers 和 shared memory 都增加，必须看编译结果。
- `num_stages=4` 不等于“保存四个完整行”。数据可能位于 registers、shared memory，或者被编译器以其他方式调度。

3. 软件流水的作用范围

这一题目前不正确。

```text
num_stages
    └── 作用于一个 program 内部的 tl.range 循环迭代

GPU scheduler
    └── 在不同 programs/warps 之间交错执行
```

如果实际 `grid=M`，每个 program 只有一次行循环迭代，那么它没有“下一行迭代”可以与当前行重叠。不同 programs 同时或分批执行属于硬件调度，不是 `tl.range(num_stages=...)` 创建的软件流水。

4. 低 occupancy 仍可能更快

你提出的“小 block 分行处理”已经改变了算法：一行被多个 blocks 分割后，需要额外的跨 block reduction，不能用它解释原 kernel 中 stages 4 的表现。

正确的取舍是：

```text
stages 增加
  ├── 可能增强单 program 的指令级并行和延迟隐藏
  └── 可能增加资源占用，减少 resident warps
```

所以 stages 4 即使 occupancy 更低，仍可能因更好地隐藏访存延迟而更快。判断时至少要在相同 shape、grid 和 `num_warps` 下比较：

- compiled registers/shared memory
- resident programs 与理论 occupancy
- 稳态 kernel latency
- 有效 GB/s

预测记录已写入 [P02 实践前预测](/workspace/docs/triton-learning/lessons/02-fused-softmax.md:1222)。

**018 · 助手 / 正式回答** · `2026-08-05T07:07:03.744Z`

能获得，但它们分属三类证据，不能都叫“实测”。

1. 编译器报告的静态资源

Triton kernel 编译后可以读取：

```python
compiled = persistent_kernel.warmup(
    ...,
    BLOCK_SIZE=block_size,
    num_stages=num_stages,
    num_warps=8,
    grid=(1,),
)
compiled._init_handles()

registers_per_thread = compiled.n_regs
shared_bytes_per_program = compiled.metadata.shared
```

- `n_regs`：每个线程使用的 registers。
- `metadata.shared`：每个 Triton program 静态分配的 shared memory。
- 这属于编译结果，不是运行时平均值。
- `_init_handles()` 和 `n_regs` 是版本敏感 API，需要集中封装。

官方教程也是这样读取的，见 [02-fused-softmax.py](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:142)。

2. 根据资源推导理论上限

设备提供每 SM 的资源总量，然后计算：

```text
register_limit =
    registers_per_sm
    / (registers_per_thread × warp_size × num_warps)

shared_limit =
    shared_bytes_per_sm / shared_bytes_per_program

thread_limit =
    max_threads_per_sm / (warp_size × num_warps)

resident_programs_per_sm =
    min(register_limit, shared_limit, thread_limit)
```

再得到：

```text
max_warps_per_sm = max_threads_per_sm / warp_size

theoretical_occupancy =
    resident_programs_per_sm × num_warps
    / max_warps_per_sm

grid = min(M, SM_count × resident_programs_per_sm)
```

所以 resident programs 和 theoretical occupancy 是推导值，不是直接测量值。实际硬件还有资源分配粒度等细节，这里的公式是教程级估算。

3. Profiler 运行时观测

Nsight Compute 可以观察 achieved occupancy，即运行过程中平均有多少 active warps：

```text
sm__warps_active.avg.pct_of_peak_sustained_active
```

本机已经安装 Nsight Compute，并提供 `LaunchStats`、`Occupancy` sections。它会显著拖慢程序，只用于解释性 profiling，不放进 pytest 或常规 benchmark。

### P02B-R07

把 Pydantic `BaseModel` 换成：

```python
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class Resource:
    registers_per_thread: int
    shared_bytes_per_program: int
    num_SM: int
    registers_per_sm: int
    shared_bytes_per_sm: int
    warp_size: int
    max_threads_per_sm: int
```

含义是：

- `frozen=True`：创建后不能修改字段，适合表示编译资源快照。
- `slots=True`：禁止动态添加属性，减少对象开销，也能更早发现字段名拼写错误。
- dataclass 不做 Pydantic 式的运行时类型转换；这里的数据来自 Triton/Torch 内部属性，不需要那套能力。

构造和访问方式完全不变：

```python
resource = Resource(
    registers_per_thread=registers_per_thread,
    shared_bytes_per_program=shared_bytes_per_program,
    num_SM=num_SM,
    registers_per_sm=registers_per_sm,
    shared_bytes_per_sm=shared_bytes_per_sm,
    warp_size=warp_size,
    max_threads_per_sm=max_threads_per_sm,
)

```

**106 · 助手 / 正式回答** · `2026-08-06T03:27:33.861Z`

`Benchmark` 只有单数 `line_arg`，不能直接指定多个变量。做法是把 `(provider, num_stages)` 打包成一个复合值，再在 benchmark 函数里解包。

```python
import matplotlib.pyplot as plt
import triton


LINE_CONFIGS = (
    ("torch_naive", None),
    ("torch_fused", None),
    ("triton_naive", None),
    ("triton_persistent", 1),
    ("triton_persistent", 2),
    ("triton_persistent", 4),
)

X_VALUES = [
    (index, size_m, size_n)
    for index, (size_m, size_n) in enumerate(SHAPES)
]


@triton.testing.perf_report(
    triton.testing.Benchmark(
        x_names=["shape_index", "size_m", "size_n"],
        x_vals=X_VALUES,
        line_arg="provider_config",
        line_vals=list(LINE_CONFIGS),
        line_names=[
            "torch_naive",
            "torch_fused",
            "triton_naive",
            "triton_persistent-s1",
            "triton_persistent-s2",
            "triton_persistent-s4",
        ],
        xlabel="shape (M x N)",
        ylabel="effective GB/s",
        plot_name="lesson02_softmax",
        args={},
    )
)
def benchmark(
    shape_index: int,
    size_m: int,
    size_n: int,
    provider_config: tuple[str, int | None],
) -> float:
    del shape_index  # 仅用于横坐标位置

    provider, num_stages = provider_config
    record = measure_case(
        size_m=size_m,
        size_n=size_n,
        provider=provider,
        num_stages=num_stages,
        warmup_ms=WARMUP_MS,
        rep_ms=REP_MS,
    )
    return record.effective_gbps
```

之所以增加 `shape_index`，是因为 Triton 3.7.1 只会使用第一个 `x_name` 画横轴。如果直接写：

```python
x_names=["size_m", "size_n"]
```

后两个 shape 的 `size_m` 都是 4096，会画到同一个横坐标上。

运行后可以手动替换横轴标签：

```python
benchmark.run(show_plots=False)

axis = plt.gcf().axes[0]
axis.set_xticks(
    range(len(SHAPES)),
    [f"{m}x{n}" for m, n in SHAPES],
)

plt.savefig("lesson02_softmax.png")
```

注意不要直接使用 `benchmark.run(save_path=...)`，因为 Triton 会在你修改刻度前保存图片。若设置 `styles`，其数量也必须和六个 `line_vals` 一致。

这个模式的对应关系是：

```text
line_arg="provider_config"
             │
             ▼
("triton_persistent", 4)
             │
             ▼
provider="triton_persistent"
num_stages=4
```

**116 · 助手 / 正式回答** · `2026-08-06T04:15:45.875Z`

对，理解方向正确。不过更准确地说：不要等 `do_bench` 内的“第一次调用”做准备，而要在调用 `do_bench` 之前准备好。

当前 persistent closure 每次都会调用 [完整 wrapper](/workspace/gpu/triton/lesson02_fused_softmax_benchmark.py:139)，而 wrapper 又会重复执行：

1. 分配 output；
2. `kernel.warmup()`；
3. 读取 registers/shared memory；
4. 计算 grid；
5. 启动 kernel。

虽然编译结果可能被 Triton 缓存，但资源读取、grid 计算、output 分配等路径仍会重复执行。

而且 `do_bench` 并非只调用一次函数。它大致执行：

```text
1 次初始调用
5 次耗时估算
n_warmup 次预热
n_repeat 次正式采样
```

所以正确结构是：

```text
每个 benchmark case：
  校验参数
  创建 input/reference/output
  计算 BLOCK_SIZE
  kernel.warmup()
  读取 resource
  计算一次 grid
  非计时 direct launch + 正确性检查
  synchronize

  do_bench(
      lambda: 使用既有 output/grid 直接 launch kernel
  )
```

需要区分两种 warm-up：

- `kernel.warmup()`：用于编译 specialization 和读取资源，在 `do_bench` 外执行一次。
- `do_bench(warmup=...)`：用于反复执行最终的被测 kernel，使运行状态稳定；它里面不应再做资源计算。

同一个 case 内，grid 和 output 都可以复用。kernel 每轮都会覆盖有效输出，所以不需要重复分配 output。

但不同 case 不应盲目共用 grid：

- `M` 改变：需要重新执行 `min(M, capacity)`；
- `N/BLOCK_SIZE` 改变：编译资源可能改变；
- `num_stages`、`num_warps`、dtype、device 改变：specialization 或资源占用可能改变。

因此本练习最清晰的方案是：每次 `measure_case` 准备一次资源和 grid，该次 `do_bench` 的所有调用都复用它。以后若做全局缓存，可以缓存 specialization 的资源容量，但仍要针对每个 `M` 重新计算最终 grid。

另外，普通 Triton kernel 不需要资源 grid 推导，直接准备：

```python
grid = (size_m,)
```

然后同样让计时闭包只做 direct kernel launch。该理解已记录到 [P02-Q08](/workspace/docs/triton-learning/lessons/02-fused-softmax.md:1624)。

- 调用 wrapper：测量端到端 Python API，包括 output 分配。
- 直接调用 kernel：测量稳态 kernel latency。

本阶段要比较 `num_stages`，所以应该采用第二种：

```python
# do_bench 之前，只执行一次
output = torch.empty_like(x)
block_size = triton.next_power_of_2(size_n)

compiled = ops.persistent_fused_softmax_kernel.warmup(...)
resource = ops.get_gpu_resource(compiled, x.device)
grid = ops.compute_grid(resource, size_m)


# do_bench 内反复调用
def launch() -> None:
    ops.persistent_fused_softmax_kernel[grid](
        x,
        output,
        size_m,
        size_n,
        BLOCK_SIZE=block_size,
        num_stages=num_stages,
        num_warps=NUM_WARPS,
    )
```

然后：

```python
launch()                         # 非计时启动
torch.testing.assert_close(...) # 正确性检查
torch.cuda.synchronize()

bench_result = triton.testing.do_bench(
    launch,
    warmup=warmup_ms,
    rep=rep_ms,
    quantiles=QUANTILES,
)
```

关键不是“尽量排除一切开销”，而是先明确 benchmark 要回答的问题：

- direct kernel benchmark 回答：“GPU kernel 本身有多快？”
- wrapper-level benchmark 回答：“应用调用这个公开接口一次，需要多长时间？”

你希望回答第二个问题，那么四种 provider 就应该处于相同 API 层级：

```python

ops.fused_softmax(x)

    x,
    num_stages=num_stages,
    num_programs=grid[0],
)
```

这些调用内部的以下工作都应该计时：

- 参数检查；
- output 和中间 tensor 分配；
- Python/dispatcher 开销；
- kernel 或 PyTorch op 执行。

但仍要区分“一次性初始化”和“每次调用成本”。我们现在选定的场景是：

```text
prepared steady-state end-to-end provider latency
```

也就是：

```text
计时外：
  input/reference
  首次 JIT
  persistent resource/grid 计算
  正确性检查

计时内：
  每次完整调用 provider function/wrapper
  包括检查、分配、dispatch 和计算
```

persistent 的流程因此是：

```python
# 每个 shape/stage 在 do_bench 前计算一次
compiled = ...
resource = ops.get_gpu_resource(compiled, x.device)

    x,
    num_stages=num_stages,
    num_programs=grid[0],
)
```

```text
JIT and persistent resource/grid setup excluded
output allocation and wrapper validation included
```
