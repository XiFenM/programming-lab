## 1. 这节课真正的新东西

这不是“更复杂的逐元素 kernel”，而是两个新模型的组合：

- 一个 program 在一整行内完成两次 reduction：`max` 和 `sum`。
- 只启动能够驻留在 GPU 上的 persistent programs，让它们循环处理所有行。

数学上，对每一行：

```text
softmax(x[j]) = exp(x[j] - max(x)) / Σ exp(x[k] - max(x))
```

减去最大值不会改变结果，因为分子和分母同时除以了 `exp(max(x))`；但它能让指数输入不大于 0，避免普通有限大数造成 `exp` 上溢。

## 2. Fusion 为什么有价值

naive PyTorch 版本分五步：

```text
row max
-> subtract
-> exp
-> row sum
-> divide
```

如果每一步都生成全局内存中的中间 tensor，总计大约搬运：

```text
读取：5MN + 2M
写入：3MN + 2M
合计：8MN + 4M 个元素
```

融合 kernel 理想情况下只需要：

```text
读取输入：MN
写回输出：MN
合计：2MN 个元素
```

因此大矩阵的理论流量比接近 4 倍。这里节省的是 DRAM 往返，并没有减少 max、exp、sum、divide 这些数学工作。

## 3. 一行如何映射到一个静态 block

Triton reduction 需要编译期已知的块形状，因此 wrapper 计算：

```python
BLOCK_SIZE = triton.next_power_of_2(n_cols)
```

官方测试使用 `N=781`，所以：

```text
BLOCK_SIZE = 1024
有效 lanes：0..780，共 781 个
padding lanes：781..1023，共 243 个
```

这些 padding 只是 program 内部的逻辑位置，不会真的创建一个补齐后的输入 tensor。

加载时使用：

```python
row = tl.load(input_ptrs, mask=mask, other=-float("inf"))
```

`-inf` 很关键：

```text
max(valid values, -inf) = max(valid values)
exp(-inf - finite_max) = 0
sum(valid exponentials, 0) 不变
```

所以一个 `-inf` padding 同时服务了 max reduction 和后续的 sum reduction。如果填 0，当有效数据全是负数时，0 会错误地成为行最大值。

接下来：

```python
row_minus_max = row - tl.max(row, axis=0)
numerator = tl.exp(row_minus_max)
denominator = tl.sum(numerator, axis=0)
softmax_output = numerator / denominator
```

数据形状变化是：

```text
[BLOCK_SIZE] --max--> scalar --broadcast subtract--> [BLOCK_SIZE]
[BLOCK_SIZE] --sum--> scalar --broadcast divide----> [BLOCK_SIZE]
```

最后用原来的 mask，只写回前 `N` 列。

## 4. Persistent grid

普通写法可能启动 `M` 个 program，一行一个。本例先根据编译后的资源用量计算 occupancy：

```text
register 限制
shared-memory 限制
        ↓ 取较小值
每个 SM 可驻留的 program 数
```

然后：

```text
P = min(NUM_SM × occupancy, M)
```

当前 A100 有 108 个 SM。假设每个 SM 能驻留 2 个这样的 program，则只启动 216 个 program。

这些 program 按 grid stride 处理行：

```text
pid 0 -> rows 0, P, 2P, ...
pid 1 -> rows 1, P+1, 2P+1, ...
...
```

对应源码：

```python
row_start = tl.program_id(0)
row_step = tl.num_programs(0)

for row_idx in tl.range(row_start, n_rows, row_step):
    ...
```

因此需要牢牢记住：

```text
一个循环迭代处理一行
一个 persistent program 处理多行
所有 persistent programs 合起来覆盖整个矩阵
```

`num_stages` 控制循环的软件流水，而 `num_warps` 控制一个 program 使用多少 warps。当前 A100 的最大 shared memory 是 166,912 bytes，因此官方 heuristic 选择 `num_stages=2`。

## 5. 官方实现的边界

这个教程 wrapper 并不是通用 softmax：

- 只接受能够解包为 `M, N` 的二维输入。
- 传入了 row stride，却没有传 column stride，因此实际假设 `stride(1) == 1`。
- 一整行 padding 后必须能装进可用片上资源。
- 没有明确处理空列、超大列宽、特殊 dtype 或错误 device。
- `tl.exp` 是快速近似实现，验证应使用容差。
- `kernel._init_handles()` 是 Triton 私有 API，升级版本时可能变化。
- 数值稳定不代表所有特殊值都安全，例如 `+inf - +inf` 仍可能得到 `NaN`。

## 6. 本机实测

官方完整脚本已在 A100、PyTorch 2.13.0、Triton 3.7.1 上执行成功：

- `1823×781` 不规则矩阵正确性断言通过。
- 98 个列宽、3 个 provider 的 benchmark 完成。
- 进程退出码为 0。

部分结果：

| N | Triton GB/s | Torch GB/s | Naive GB/s |
|---:|---:|---:|---:|
| 256 | 382.24 | 551.64 | 175.71 |
| 1024 | 1093.50 | 1038.57 | 353.95 |
| 4096 | 1411.88 | 1333.05 | 349.84 |
| 8192 | 1478.84 | 1152.54 | 375.33 |
| 10240 | 1461.68 | 1510.18 | 384.26 |

它支持两个结论：

- Triton fusion 明显快于由多个 eager 操作组成的 naive baseline。
- Triton 并非在每个列宽上都快于高度优化的 `torch.softmax`。

这里的 GB/s 使用 `2 × numel × element_size / time`，表示统一的有效工作量，不是 profiler 测得的真实 DRAM 流量。

**012 · 助手 / 正式回答** · `2026-07-31T04:55:28.023Z`

最关键的区分是：

```text
persistent programs：解决“启动多少个 program、每个 program 处理哪些行”
software pipeline：解决“一个 program 连续处理多行时，怎样重叠不同迭代以隐藏等待”
```

它们分别工作在“任务调度层”和“指令调度层”，不是同一个概念。

## 一、Persistent programs

### 1. 普通 grid 与 persistent grid 的区别

最直接的 softmax 写法可以是：

```text
grid = (M,)
program 0 -> row 0
program 1 -> row 1
...
program M-1 -> row M-1
```

这会创建 `M` 个 program instance。GPU 根据资源容量把它们分成多批执行。

Persistent 版本不创建 `M` 个 program，而是只创建大约能同时驻留在所有 SM 上的数量 `P`：

```text
grid = (P,)
P ≈ SM 数量 × 每个 SM 可驻留的 program 数
```

这两种方式都只有一次 kernel launch。Persistent 减少的是 program/CTA 实例数量，不是 kernel launch 次数。

这些 program 启动后不会处理完一行就退出，而是在 kernel 内循环处理更多行，所以生命周期更长，称为 persistent。

### 2. 哪几行代码实现了 persistent

设备侧的行分配在 [02-fused-softmax.py:88](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:88)：

```python
row_start = tl.program_id(0)
row_step = tl.num_programs(0)

for row_idx in tl.range(row_start, n_rows, row_step, ...):
    ...
```

假设最终启动 `P=3` 个 program，`M=10`：

```text
pid 0 -> rows 0, 3, 6, 9
pid 1 -> rows 1, 4, 7
pid 2 -> rows 2, 5, 8
```

`tl.num_programs(0)` 返回 axis 0 实际启动的 program 数量，也就是 `P`。[Triton 官方定义](https://triton-lang.org/main/python-api/generated/triton.language.num_programs.html)

这不是动态工作队列，没有 program 去抢下一行。每个 program 的行序列从一开始就由：

```text
row_idx = pid + k × P
```

静态确定了。

### 3. `P` 是怎样计算出来的

首先读取硬件资源：

```python
NUM_SM = properties["multiprocessor_count"]
NUM_REGS = properties["max_num_regs"]
SIZE_SMEM = properties["max_shared_mem"]
WARP_SIZE = properties["warpSize"]
```

对应 [02-fused-softmax.py:115](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:115)。

但只知道硬件资源还不够。必须先知道当前 softmax 特化会使用多少 registers 和 shared memory，因此 wrapper 先编译 kernel：

```python
kernel = softmax_kernel.warmup(...)
kernel._init_handles()

n_regs = kernel.n_regs
size_smem = kernel.metadata.shared
```

对应 [02-fused-softmax.py:142](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:142)。

然后 NVIDIA 分支估算 register 限制：

```python
occupancy = NUM_REGS // (n_regs * WARP_SIZE * num_warps)
```

再考虑 shared-memory 限制：

```python
occupancy = min(
    register_occupancy,
    SIZE_SMEM // size_smem,
)
```

对应 [02-fused-softmax.py:167](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:167)。

这里的 `occupancy` 不是百分比，而是：

```text
每个 SM 最多可同时驻留多少个当前 program
```

最后：

```python
num_programs = NUM_SM * occupancy
num_programs = min(num_programs, n_rows)
```

并真正启动：

```python
kernel[(num_programs, 1, 1)](...)
```

对应 [02-fused-softmax.py:169](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:169) 和 [02-fused-softmax.py:173](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:173)。

### 4. 用本机数字算一次

对于本机 A100、`N=781`、`BLOCK_SIZE=1024`、`num_warps=8`、`num_stages=2`：

```text
每线程 registers = 32
每 program warps = 8
每 warp threads = 32
```

所以一个 program 大约占用：

```text
32 registers/thread × 32 threads/warp × 8 warps
= 8192 registers
```

每个 SM 有 65,536 registers：

```text
register occupancy = 65536 / 8192 = 8 programs/SM
```

每个 program 使用 4,128 bytes shared memory：

```text
shared-memory occupancy = 166912 / 4128 = 40 programs/SM
```

取两者较小值：

```text
occupancy = min(8, 40) = 8
```

A100 有 108 个 SM：

```text
P = 108 × 8 = 864 programs
```

对于 benchmark 的 `M=4096`：

```text
前 640 个 program：每个处理 5 行
其余 224 个 program：每个处理 4 行
```

所有 program 的工作量最多相差一行。

这个 occupancy 公式是教程级估算。完整硬件限制还可能包含最大 resident blocks、最大线程数等，但它表达了核心关系：program 占用的片上资源越多，一个 SM 能同时驻留的 program 越少。

## 二、`num_stages` 软件流水

### 1. 真正启动软件流水的是哪一行

wrapper 先选择 stages：

```python
num_stages = 4 if SIZE_SMEM > 200000 else 2
```

对应 [02-fused-softmax.py:136](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:136)。

当前 A100：

```text
SIZE_SMEM = 166912 < 200000
所以 num_stages = 2
```

这个值作为编译期参数传入 kernel。真正对循环施加流水属性的是 [02-fused-softmax.py:90](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:90)：

```python
for row_idx in tl.range(
    row_start,
    n_rows,
    row_step,
    num_stages=num_stages,
):
```

官方对 `tl.range(..., num_stages=S)` 的定义是：编译器尝试让 `S` 个循环迭代同时处于 in-flight 状态，并流水化循环中的多数 load。[Triton `tl.range` 文档](https://triton-lang.org/main/python-api/generated/triton.language.range.html)

这里一个“循环迭代”就是一整行 softmax，不是其中某一条语句。

### 2. 没有软件流水时

概念上，`pid 0` 会严格串行处理自己的行：

```text
row 0:
  load
  max
  subtract
  exp
  sum
  divide
  store

row P:
  load
  max
  subtract
  exp
  sum
  divide
  store

row 2P:
  ...
```

问题在于 global-memory load 有较长延迟。执行完 row 0 后才开始加载 row P，可能让执行单元等待数据。

### 3. 两级流水的整体流程

`num_stages=2` 表示编译器尝试同时保留两个循环迭代在途。

概念时间线可以画成：

| 时间片 | 较早的行 | 较晚的行 |
|---|---|---|
| Prologue | 发起/准备 row A 的 load | — |
| Steady 1 | 对 row A 做 reduction/exp | 提前处理 row B 的地址和 load |
| Steady 2 | 写回 row A | 计算 row B，同时准备 row C |
| Steady 3 | 写回 row B | 计算 row C，同时准备 row D |
| Epilogue | 排空最后一行 | — |

简化成：

```text
时间 ─────────────────────────────────────────>

row A: [load......][max/exp/sum/divide][store]
row B:             [load......][max/exp/sum/divide][store]
row C:                        [load......][max/exp/sum/divide][store]
```

实际重叠后的目标更接近：

```text
row A: [load......][compute...........][store]
row B:       [load......][compute...........][store]
row C:                     [load......][compute...........][store]
```

当 row A 做 reduction 和指数计算时，row B 的部分内存请求已经在途。这样 row A 完成后，row B 不必从零开始等待全部加载。

### 4. 它不是把代码固定切成两个阶段

`num_stages=2` 不表示：

```text
stage 1 = load
stage 2 = compute
```

也不表示：

- 创建两个 program；
- 创建两个 CPU 线程；
- 一个 warp 专门 load、另一个 warp 专门 compute；
- 同一行的 max、exp、sum 可以任意乱序。

同一行内部的数据依赖仍然必须满足：

```text
load
  ↓
max
  ↓
subtract
  ↓
exp
  ↓
sum
  ↓
divide
  ↓
store
```

编译器能够重叠的是不同独立行的工作，例如：

```text
计算 row A
+
加载 row B
```

具体哪些 load 被提前、使用 registers 还是 shared-memory buffer、指令相隔多少周期，由 Triton 编译器和后端决定。源码只是提供“最多让几个迭代在途”的编译提示。

### 5. 为什么需要额外片上空间

如果 row A 还没有算完，就开始加载 row B，那么两行的数据会在一段时间内同时存活：

```text
row A 的中间值仍需保留
row B 的输入已经开始到达
```

这就需要 multi-buffering：

```text
buffer A -> 当前计算行
buffer B -> 下一行
```

四级流水可能需要同时保存更多行的部分状态：

```text
buffer A
buffer B
buffer C
buffer D
```

因此 stages 越深，通常需要更多 registers 或 shared memory。

## 三、本机 stages 实验

我用同一个官方 kernel 编译了 `S=1/2/4`：

| stages | registers/thread | shared/program | occupancy | programs | 探索性延迟 |
|---:|---:|---:|---:|---:|---:|
| 1 | 32 | 32 B | 8 | 864 | 0.027193 ms |
| 2 | 32 | 4,128 B | 8 | 864 | 0.029188 ms |
| 4 | 40 | 12,320 B | 6 | 648 | 0.028467 ms |

三个版本都通过了与 `torch.softmax` 的正确性对照。

可以看到：

```text
1 -> 2 stages:
shared memory 增加约 4 KiB

2 -> 4 stages:
shared memory 再增加约 8 KiB
registers/thread 从 32 增加到 40
occupancy 从 8 降到 6
```

这正好展示了核心取舍：

```text
更深流水
  -> 更多独立行在途
  -> 可能更好地隐藏内存延迟
  -> 但需要更多片上状态
  -> 可能降低 occupancy
  -> 不一定更快
```

本次测量中 1 stage 略快，但差异很小，而且只是一轮理解性实验，不能据此宣布 1 stage 普遍最优。官方的 `2/4` 选择只是手写 heuristic，不是 autotune 的结论。

## 四、为什么把 persistent 和软件流水组合起来

两者是互相配合的：

```text
Host wrapper
  -> 选择 BLOCK_SIZE、num_warps、num_stages
  -> 编译 kernel
  -> 读取 register/shared-memory 用量
  -> 估算 occupancy
  -> 启动 P 个 persistent programs

每个 persistent program
  -> 根据 pid 得到第一行
  -> 根据 P 得到 row_step
  -> 循环处理 pid, pid+P, pid+2P, ...
  -> 编译器在这个循环中流水化多行
```

Persistent 提供了一个重复、稳定、行与行相互独立的循环。如果每个 program 只处理一行，program 内部就没有“下一行迭代”可供这条 `tl.range` 流水。

可以把它们理解成：

```text
persistent：
让少量工人长期留在车间，每个工人连续加工多件产品

software pipeline：
同一个工人加工产品 A 的后半段时，提前准备产品 B 的原料
```

为什么适合 softmax：

- 每行工作形式相同；
- 行与行相互独立；
- 每行都经历 load、reduction、exp、store；
- global-memory 等待可以与其他行的计算重叠；
- 行工作量基本均匀，静态 grid-stride 分配不容易严重失衡。

可能的缺点：

- stages 太深会增加资源占用并降低 occupancy；
- persistent program 长时间占据 SM，可能影响其他并发 kernel；
- 如果不同行工作量差异很大，静态分配可能失衡；
- program 数估计过少会利用不足，估计过多则不再真正“全部驻留”。

## Triton 与 CUDA persistent kernel 的关系

你的记忆没有错。经典 CUDA persistent kernel 确实经常写成：

```cpp
while (true) {
    Task task = dequeue();
    if (task.is_stop()) {
        break;
    }
    process(task);
}
```

但 `while + 动态任务队列` 是 persistent kernel 的一种形式，不是唯一形式。

它们的共同核心是：

```text
不为每个 task 创建一个独立 block
启动有限数量的长期 worker blocks
每个 block 在退出前处理多个 tasks
```

Persistent Threads 相关研究也把 load balancing、CPU–GPU 协作和 producer–consumer locality 等列为典型用途，同时指出它并非总能提升性能。[Persistent Threads 研究](https://escholarship.org/uc/item/3j76d3td)

### 形式一：静态 grid-stride persistent

```cpp
__global__ void softmax_rows(..., int num_rows) {
    for (int row = blockIdx.x;
         row < num_rows;
         row += gridDim.x) {
        process_one_row(row);
    }
}
```

Host 只启动有限 blocks：

```cpp
int blocks = num_sms * blocks_per_sm;
softmax_rows<<<blocks, threads_per_block>>>(...);
```

任务在 launch 前已经全部确定，block 通过自己的 ID 直接算出负责哪些任务。NVIDIA 也推荐通过限制 block 数量和 grid-stride loop 实现线程复用、摊薄初始化成本。[NVIDIA Grid-Stride Loop](https://developer.nvidia.com/blog/cuda-pro-tip-write-flexible-kernels-with-grid-stride-loops/)

这正是本课 Triton softmax 的类型：

```text
tl.program_id(0)   ≈ blockIdx.x
tl.num_programs(0) ≈ gridDim.x
Triton program     ≈ CUDA thread block / CTA
```

对应循环：

```python
for row_idx in tl.range(
    tl.program_id(0),
    n_rows,
    tl.num_programs(0),
):
    process_one_row(row_idx)
```

官方教程明确描述为：每个 program 按 program 总数作为 stride 处理一组行。[Triton Fused Softmax](https://triton-lang.org/main/getting-started/tutorials/02-fused-softmax.html)

### 形式二：动态有限任务队列

```cpp
__global__ void workers(
    Task* tasks,
    int task_count,
    int* next_task
) {
    while (true) {
        int task_id = atomicAdd(next_task, 1);

        if (task_id >= task_count) {
            break;
        }

        process(tasks[task_id]);
    }
}
```

适合任务成本差异很大的情况。例如不同图节点、稀疏块或不规则搜索任务。如果静态分配，某个 block 可能很快结束，另一个却拿到几个特别重的任务；动态队列可以让空闲 block 继续取任务。

代价包括：

- atomic counter 或队列竞争；
- 更复杂的终止条件；
- 任务元数据访存；
- 执行顺序更难预测。

### 形式三：在线常驻服务

你记忆中“持续接收传过来的 task”更接近这一类：

```cpp
while (!stop_flag) {
    if (queue_has_task()) {
        Task task = dequeue();
        process(task);
    }
}
```

任务可能在 kernel 已经运行后才由 host 或其他 device kernel 放入队列。它可以避免大量小 kernel 的反复 launch，但需要处理：

- 空队列等待；
- host/device 内存可见性；
- stop flag；
- 队列容量和 backpressure；
- GPU 被长期占用；
- 与其他 kernel 的并发和公平性。

## 为什么本课不需要动态队列

Softmax 的任务是矩阵的 `M` 行：

- 行数在 launch 前已知；
- 每行列数相同；
- 同一 shape 下每行工作量基本一致；
- 每个 program 的行数最多相差 1。

因此静态分配已经很好：

```text
pid p -> p, p+P, p+2P, ...
```

没有必要为每一行执行 atomic dequeue。

更准确地说，本课实现是：

> occupancy-limited、静态 grid-stride 的 persistent kernel。

它不是：

> 持续等待外部任务的 server-style persistent kernel。

两者属于同一个 persistent execution 家族，只是任务来源不同：

| 类型 | 任务来源 | 循环 |
|---|---|---|
| Triton softmax | 静态行号公式 | 有界 `for` |
| CUDA 动态 worker | atomic counter/队列 | 有界 `while` |
| 在线常驻服务 | 运行期间持续到达的队列 | 长期 `while` |

这轮复述和 Q02 已记录在 [Lesson 02 答疑记录](/workspace/docs/triton-learning/lessons/02-fused-softmax.md:671)。

**026 · 助手 / 正式回答** · `2026-07-31T05:53:10.973Z`

有。CUDA 中比较正式的定义是：

\[
\text{Occupancy}
=
\frac{\text{每个 SM 上驻留的 active warps 数}}
{\text{该 SM 最多支持的 active warps 数}}
\]

这是 NVIDIA CUDA Programming Guide 和 Best Practices Guide 使用的定义。[CUDA Programming Guide](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)、[CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#occupancy)

### “Active”是什么意思

这里的 active 不是“正在执行指令”，而是：

> 已经驻留在 SM 上，并且尚未执行结束。

因此，一个正在等待 global memory 的 warp 仍然是 active warp。

可以把 warp 状态区分为：

| 状态 | 含义 |
|---|---|
| Active | 已驻留在 SM 上，尚未结束 |
| Eligible | 当前依赖已经满足，可以发射下一条指令 |
| Issued | 本周期实际被 scheduler 选中执行 |

所以可能出现：

```text
64 个 active warps
0 个 eligible warps
```

此时 occupancy 是 100%，但所有 warp 都在等待，计算单元仍然可能空闲。Nsight Compute 也明确区分 active、eligible 和 issued warps。[Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/2023.2/ProfilingGuide/index.html)

### Occupancy 是怎么被资源限制的

一个 Triton program 在 NVIDIA GPU 上大致对应一个 CUDA thread block/CTA。每个 program 需要：

- 一定数量的 warps/threads；
- registers；
- shared memory；
- block slot 等硬件资源。

因此每个 SM 能同时容纳的 program 数大致是：

\[
B_{\text{resident}}
=
\min
\begin{cases}
\text{block 数量上限}\\
\lfloor T_{SM}/T_{program}\rfloor\\
\lfloor R_{SM}/R_{program}\rfloor\\
\lfloor S_{SM}/S_{program}\rfloor
\end{cases}
\]

然后再换算成正式的 warp occupancy：

\[
\text{Occupancy}
=
\frac{B_{\text{resident}}\times\text{warps per program}}
{\text{max warps per SM}}
\]

真实硬件还会对 registers 和 shared memory 按分配粒度取整，因此这是解释模型，不是完整的架构计算器。

### 本课源码中的 `occupancy` 不完全是正式 occupancy

官方代码在 [02-fused-softmax.py](/workspace/docs/triton-tutorials/official/02-fused-softmax.py:142) 中计算：

```python
occupancy = NUM_REGS // (n_regs * WARP_SIZE * num_warps)
occupancy = min(occupancy, SIZE_SMEM // size_smem)
num_programs = NUM_SM * occupancy
```

这里的 `occupancy` 实际保存的是：

```text
每个 SM 能驻留多少个 Triton programs
```

它是一个类似 `8`、`6` 的整数，不是正式定义下的 `100%`、`75%`。变量名稍微有些宽泛。

所以一个 Triton program 包含 8 个 warps。

|---:|---:|---:|---:|
| 1 | 8 | `8 × 8 = 64` | `64 / 64 = 100%` |
| 2 | 8 | `8 × 8 = 64` | `64 / 64 = 100%` |
| 4 | 6 | `6 × 8 = 48` | `48 / 64 = 75%` |

所以此前“occupancy 从 8 降到 6”更严谨的说法是：

```text
resident programs/SM：8 → 6
理论 warp occupancy：100% → 75%
```

### Occupancy 为什么重要，但不是越高越好

occupancy 高意味着 scheduler 通常有更多 warp 可供切换。当一个 warp 等待内存或依赖时，可以执行另一个 eligible warp，从而隐藏延迟。

但它不直接代表性能：

```text
高 occupancy
≠ 高计算利用率
≠ 高内存带宽
≠ 高性能
```

`num_stages` 增大时：

```text
好处：单个 program 内有更多迭代在途，增加软件流水和指令级并行
代价：消耗更多 registers/shared memory，减少 resident programs 和 warp occupancy
```

因此这里是在权衡两种延迟隐藏方式：

```text
更多 resident warps             更深的软件流水
线程级并行 TLP          ↔        program 内并行 ILP
```

即使 stages 4 只有 75% occupancy，也可能因为内部流水更好而更快；反过来，100% occupancy 也可能因为所有 warp 同时等待而很慢。
