```text
Benchmark / perf_report：组织实验矩阵、表格和曲线
            ↓
do_bench：预热、重复执行、GPU 计时、统计分位数
            ↓
被测函数：Torch 或 Triton 算子的一次调用
```

官方代码位于 [01-vector-add.py](/workspace/docs/triton-tutorials/official/01-vector-add.py:107)。

## 1. `Benchmark` 如何描述实验矩阵

```python
triton.testing.Benchmark(
    x_names=["size"],
    x_vals=[2**i for i in range(12, 28)],
    x_log=True,
    line_arg="provider",
    line_vals=["triton", "torch"],
    line_names=["Triton", "Torch"],
    ylabel="GB/s",
    plot_name="vector-add-performance",
    args={},
)
```

这里不是在计时，而是在声明实验：

- `x_names=["size"]`：benchmark 函数的横轴参数名。
- `x_vals`：输入规模从 \(2^{12}\) 到 \(2^{27}\)，共 16 种。
- `x_log=True`：绘图时横轴使用对数刻度。
- `line_arg="provider"`：不同曲线由哪个函数参数区分。
- `line_vals`：分别传入 `"triton"` 和 `"torch"`。
- `line_names`：图例显示名称。
- `args`：不随横轴或曲线变化的固定参数。

最终相当于遍历：

```text
16 种 size × 2 种 provider = 32 个 benchmark 配置
```

`@perf_report(...)` 会把普通 `benchmark()` 函数包装成带 `.run()` 方法的对象：

```python
benchmark.run(
    print_data=True,
    show_plots=True,
)
```

在无图形界面的容器中，更适合：

```python
benchmark.run(
    print_data=True,
    show_plots=False,
    save_path="...",
)
```

## 2. 真正计时的是 `do_bench`

官方代码为：

```python
quantiles = [0.5, 0.2, 0.8]
ms, min_ms, max_ms = triton.testing.do_bench(
    lambda: add(x, y),
    quantiles=quantiles,
)
```

在当前 Triton 3.7.1 中，`do_bench` 大致执行：

1. 调用并同步一次 `fn()`。
2. 执行 5 次，估算单次运行时间。
3. 根据估算结果计算预热次数和正式采样次数。
4. 预热。
5. 使用 GPU event 测量每个正式样本。
6. 最后同步 GPU，并计算统计结果。

一个容易忽略的地方是：

```python
warmup=25
rep=100
```

表示目标累计时间分别约为 25ms 和 100ms，不是预热 25 次、测试 100 次。例如估计一次运行需要 0.02ms，那么正式采样次数大约是：

```text
100ms / 0.02ms = 5000 次
```

### 首次 JIT 是否计入

不计入正式样本。

`do_bench` 开始时执行的第一次 `fn()` 会触发当前配置的 Triton JIT 编译，然后同步；正式 GPU event 计时发生在后面。因此，当我们依次测试四种 `BLOCK_SIZE` 时，每个新特化都会编译，但编译时间不会进入对应的稳态延迟。

这不意味着编译不存在，只意味着我们测量的是稳态运行性能，而不是首次调用延迟。

## 3. 为什么不能直接用普通 Python 计时

这种代码是错误或至少不完整的：

```python
start = time.perf_counter()
output = axpby(...)
elapsed = time.perf_counter() - start
```

GPU launch 是异步的。CPU 可能只等到 kernel 被提交，就停止计时，而 GPU 仍在运行。

手写计时时至少要在前后同步：

```python
torch.cuda.synchronize()
start = time.perf_counter()
output = axpby(...)
torch.cuda.synchronize()
elapsed = time.perf_counter() - start
```

但 `do_bench` 使用设备 event，拥有预热、重复和统计功能，更适合微秒级 GPU kernel。当前版本还会在正式样本前清理 L2 cache，以降低缓存残留造成的偏差。

## 4. 分位数的含义

```python
quantiles = [0.5, 0.2, 0.8]
```

返回顺序就是：

```text
p50 耗时、p20 耗时、p80 耗时
```

官方变量名：

```python
ms, min_ms, max_ms
```

只是简化命名，`min_ms` 并不是绝对最小值，`max_ms` 也不是绝对最大值。

通常：

```text
p20 time <= p50 time <= p80 time
```

但是吞吐量与耗时成反比。因此官方返回：

```python
gbps(ms), gbps(max_ms), gbps(min_ms)
```

对应：

```text
中心吞吐量、吞吐量下界、吞吐量上界
```

这就是为什么后两个参数的顺序看起来反了。

## 5. 有效带宽如何计算

向量加法或融合 AXPBY 对每个元素的最低数据流量都是：

```text
读取 x       1 个元素
读取 y       1 个元素
写出 output  1 个元素
合计         3 个元素
```

所以：

```text
bytes = 3 × N × element_size
```

耗时以毫秒返回，因此：

```text
GB/s =
    3 × N × element_size × 1e-9
    --------------------------------
    milliseconds × 1e-3
```

float32 的 `element_size()` 是 4，因此每个元素按 12 字节计算。

这叫“有效带宽”，不是硬件计数器测得的实际 DRAM 流量。它没有准确计入缓存命中、缓存写回、额外临时 tensor 和其他内部流量。

## 6. 如何解读性能曲线

曲线通常会经历两个区域：

- 小输入：kernel launch 和固定开销占主导，GPU 还没来得及充分并行，有效 GB/s 较低且容易波动。
- 大输入：数据量足够大，逐渐接近内存带宽平台区，此时更适合比较 block size。

因此不能只看一个输入规模，也不能预设 `BLOCK_SIZE=1024` 一定最快。块大小会同时改变：

- program instance 数量；
- 每个 program 的逻辑工作量；
- 编译器的线程/warp 映射；
- 寄存器和其他资源使用；
- 尾块中无效 lane 的比例。

## 7. 迁移到我们的 AXPBY 练习

我们的目标是对 [lesson01_vector_ops.py](/workspace/gpu/triton/lesson01_vector_ops.py:56) 中的 `axpby` 比较：

```text
BLOCK_SIZE = 128, 256, 512, 1024
size       = 2**12, 2**16, 2**20, 2**24，或更密集的范围
```

AXPBY 仍可按“两读一写”计算有效 GB/s，因为它是融合 kernel：

```text
output = alpha * x + beta * y
```

如果加入 PyTorch eager baseline：

```python
alpha * x + beta * y
```

需要明确说明它很可能产生中间 tensor 和多个 kernel。因此两边都按 12N 字节计算时，表示的是端到端“有效吞吐量”，不是声称 PyTorch 实际只移动了 12N 字节。这恰好可以体现融合的价值。

**012 · 助手 / 正式回答** · `2026-07-23T08:08:13.108Z`

可以设置多个 `x_names`，但你这里推荐这样划分：

- `size`：横轴变量，放在 `x_names`
- `block_size`：不同曲线，放在 `line_arg`

```python
triton.testing.Benchmark(
    x_names=["size"],
    x_vals=[2**12, 2**16, 2**20, 2**24],
    x_log=True,
    line_arg="block_size",
    line_vals=[128, 256, 512, 1024],
    line_names=["128", "256", "512", "1024"],
    styles=[
        ("blue", "-"),
        ("green", "-"),
        ("orange", "-"),
        ("red", "-"),
    ],
    ylabel="GB/s",
    plot_name="axpby-block-size",
    args={},
)
```

被装饰函数对应写成：

```python
def benchmark(size, block_size):
    ...
```

`perf_report` 内部会自动执行类似：

```python
for size in x_vals:
    for block_size in line_vals:
        benchmark(size=size, block_size=block_size)
```

因此自然得到：

```text
4 种 size × 4 种 block_size = 16 组实验
```

`x_names` 多参数适合的是这种成组变化：

```python
x_names=["m", "n"]
x_vals=[
    (128, 256),
    (256, 512),
]
```

它会分别调用：

```python
benchmark(m=128, n=256, ...)
benchmark(m=256, n=512, ...)
```

需要注意：

- 它不会自动计算 `m × n` 的笛卡尔积。
- 当前绘图实现只把第一个 `x_name` 当作真正横坐标。
- 如果把 `size` 和 `block_size` 都放进 `x_names`，需要手动列出全部 `(size, block_size)`，而且四种 block size 不会自然成为四条曲线。

所以，虽然二者都是会变化的函数参数，但 `x_names` 更准确的含义是“横轴配置参数”，并不是“所有自变量”。

这部分答疑也已记录在 [Lesson 01 的 Q10](/workspace/docs/triton-learning/lessons/01-vector-add.md:732)。

**016 · 助手 / 正式回答** · `2026-07-23T08:13:09.912Z`

`x_names` 是 `List[str]`，因为 Triton 用一个统一接口表示“一个或多个共同描述实验配置的参数”。即使只有一个参数，也必须写：

```python
x_names=["size"]
```

而不是：

```python
x_names="size"
```

如果误传字符串，内部逻辑可能把它当可迭代对象拆成 `"s"、"i"、"z"、"e"`，所以类型标注要求列表。

## 多个 `x_names` 的两种行为

### 1. `x_vals` 是 tuple/list：按位置配对

```python
x_names=["m", "n"]
x_vals=[
    (128, 256),
    (256, 512),
]
```

内部近似执行：

```python
dict(zip(["m", "n"], (128, 256)))
# {"m": 128, "n": 256}
```

因此会调用：

```python
benchmark(m=128, n=256, ...)
benchmark(m=256, n=512, ...)
```

如果还有：

```python
line_arg="provider"
line_vals=["triton", "torch"]
```

完整调用就是：

```text
benchmark(m=128, n=256, provider="triton")
benchmark(m=128, n=256, provider="torch")
benchmark(m=256, n=512, provider="triton")
benchmark(m=256, n=512, provider="torch")
```

结果表类似：

```text
  m    n    Triton (GB/s)    Torch (GB/s)
128  256         ...              ...
256  512         ...              ...
```

tuple 长度必须与 `x_names` 数量一致，否则会抛出 `ValueError`。

```text
(m=128, n=128, k=128)
(m=256, n=256, k=256)
```

```text
128 × 128 × 128
256 × 256 × 256
```


```python

```

> 一组共同描述每个横轴实验点的参数，而不是多条独立横轴。

你的实验需要让 `size` 形成横轴、`block_size` 形成不同曲线，所以仍应写：

```python
x_names=["size"]
```

> program 相互独立，可以被并行调度，但不会全部同时驻留在 GPU 上。

- 是否增加一个调度波次；
- program 的资源使用；
- SM 分配；
- 当时的运行波动。

**048 · 助手 / 正式回答** · `2026-07-24T06:53:16.236Z`

关键在于：这里的 GB/s 是计算出来的“有效带宽”，不是 GPU 硬件直接报告的真实 DRAM 带宽。

公式是：

```text
有效 GB/s = 有效字节数 / 测量时间
```

比较两个尺寸：

```text
tail_gbps / exact_gbps
  = (N_tail / N_exact) × (t_exact / t_tail)
```

## 情况一：时间相同，分子略微增加

对于：

```text
N_exact = 2**20
N_tail  = 2**20 + 17
```

有效字节数比例为：

```text
N_tail / N_exact
= 1 + 17 / 2**20
≈ 1.0000162
```

如果两者测得的 p50 都是 15.360µs，那么时间完全相同，但尾块的有效元素多了 17 个，所以计算出的 GB/s 会自然上升约 0.00162%。

你的 BS=128 正是这样：

```text
exact: 819.200 GB/s
tail:  819.213 GB/s
```

这并不表示硬件带宽真的提高了，只是：

```text
稍大的有效字节数 / 相同的测量时间
```

## 情况二：尾块的独立测量时间碰巧更短

你的 BS=256 是：

```text
exact p50 = 16.384µs
tail  p50 = 15.360µs
```

少了一个 1.024µs 的时间档位，于是：

```text
exact: 768.000 GB/s
tail:  819.213 GB/s
```

表面上增加约 6.67%。

但这不能证明尾块真的更快，因为：

- 两次 benchmark 是独立采样；
- p20–p80 区间高度重叠；
- 独立复测时变化方向会反转；
- 当前测量值都落在 1.024µs 的离散档位上；
- 一个档位对 15µs kernel 就相当于约 6%–7%。

GPU 时钟状态、SM 调度波次、系统活动和计时离散，都可能使两个非常接近的分布得到不同的 p50 档位。

## 这次不是重新优化了代码

同一个 block size 下：

- `BLOCK_SIZE` 没有变化；
- dtype 和 provider 没有变化；
- `n_elements` 是运行时参数；
- 通常仍使用同一份 JIT kernel specialization；
- 只是 grid 多启动了一个 program。

因此不能先把 GB/s 上升解释为编译器重新生成了更优代码。

理论上，grid 大小改变可能影响 SM 任务分配和调度波次，但你当前观察到的变化只有一两个计时档位，而且跨轮次不稳定，没有足够证据把它归因于真实调度优化。

## 应当怎样表述结论

对于这种区间重叠、跨轮次方向变化的结果，最准确的结论是：

> 在当前计时粒度和实验方法下，没有检测到尾块带来稳定的性能差异。

而不是：

> 尾块使 kernel 更快。

1. 约 0.00162%：时间相同、有效字节略增导致的公式性上升。

```python
gbps = (
```

这里的“计时台阶”是我对 **quantization step（量化步长）** 的通俗称呼，不是 CUDA 的正式术语。

### 1.024 µs 是怎么观察出来的？

你这次的时间值包括：

```text
14.336 µs = 14 × 1.024 µs
15.360 µs = 15 × 1.024 µs
16.384 µs = 16 × 1.024 µs
17.408 µs = 17 × 1.024 µs
```

我进一步检查了 `do_bench(..., return_mode="all")` 的原始样本，不同数据规模都呈现：

```text
8192, 9216, 10240, ... ns
15360, 16384, 17408, ... ns
123904, 124928, 125952, ... ns
```

相邻值均相差 `1024 ns = 1.024 µs`。所以这不是 CSV 显示精度或 p50 四舍五入造成的，而是当前 CUDA Event 测量路径呈现出的离散时间网格。

### “台阶”是什么意思？

可以类比最小刻度为 1 mm 的尺子。物体真实长度可以是 10.2 mm 或 10.7 mm，但仪器未必能分别报告这些值。

计时过程可以简化为：

```text
真实运行时间
    ↓ CUDA Event 有限分辨率
离散的原始时间样本
    ↓ do_bench 统计
p20 / p50 / p80
```

因此，kernel 的真实时间可以发生小于 1.024 µs 的变化，但测量结果可能：

- 没有变化，仍落在同一档；
- 或跨过量化边界，一次跳到相邻档。

这不表示 GPU kernel 只能以 1.024 µs 为单位执行。

### 为什么恰好是 1.024 µs？

当前 Triton 在 NVIDIA backend 上使用 `torch.cuda.Event`，底层通过 `cudaEventElapsedTime` 计时。NVIDIA 官方只说明 CUDA Event 分辨率约为 0.5 µs，并没有承诺 A100 或所有环境都固定使用 1.024 µs。[CUDA Runtime API](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-runtime-api/group__CUDART__EVENT.html)

因此严谨的说法是：

> 1.024 µs 是当前 A100、驱动和 CUDA 软件栈中实测到的有效量化步长。

公开资料不足以确定其内部精确来源，不能把它当成 CUDA 的通用定律。

### 为什么它影响很大？

对约 `15.360 µs` 的 kernel：

```text
1.024 / 15.360 = 6.67%
```

因此 p50 只要跳一个台阶，计算出的 GB/s 就可能变化约 6%。这正是之前尾块实验出现明显带宽跳动的重要原因之一。

**065 · 助手 / 正式回答** · `2026-07-24T08:05:28.473Z`

核心区别是：**这部分访存不是“执行后被优化掉”，而是从一开始就是条件访存，predicate 为 false 时根本不执行。**

可以把它理解为：

```python
if mask[i]:
    value = load(pointer[i])
else:
    value = other  # 或未定义占位值
```

条件为 false 时，`load` 没有被“优化掉”，就像 `if False: read_file()` 里的读文件操作从未执行。

### 从 Triton 到 PTX

我检查了当前 AXPBY 编译出的 PTX：

```ptx
setp.lt.s32  %p1, %r15, %r14;
@%p1 ld.global.b32 { %r1 }, [ %rd1 + 0 ];
@%p1 st.global.b32 [ %rd5 + 0 ], { %r5 };
```

含义是：

```text
%p1 = offset < n_elements

如果 %p1 为真：
    执行 ld.global / st.global
否则：
    该 lane 不执行内存指令
```

`@%p1` 就是 guard predicate。NVIDIA 的 PTX 模型允许每条指令带谓词；false predicate 的 lane 不写结果，也不求值该指令的地址或读取操作数。[NVIDIA PTX Predicated Execution](https://docs.nvidia.com/cuda/parallel-thread-execution/#predicated-execution)

因此正确的转换关系是：

```text
Triton mask
    ↓ 编译
PTX predicate
    ↓ GPU 执行
只有 predicate=true 的 lane 提出内存请求
```

这是一项由 `mask` 明确要求的正确性语义，不是 GPU 猜测出这些访问“没用”之后进行的优化。

### 用 `[T,T,F,F]` 理解

假设尾块是：

```text
offsets = [8, 9, 10, 11]
mask    = [T, T, F, F]
```

概念上会发生：

```text
offset 8：执行 load
offset 9：执行 load
offset 10：不执行 load
offset 11：不执行 load
```

地址 `10`、`11` 的算术值可能已经在寄存器中计算出来，但它们不会被内存指令解引用，也不会产生对应 lane 的内存请求。

### 为什么物理流量仍可能大于两个 float？

这又是另一个层次。GPU 会合并 active lane 的地址，并按照 memory transaction 粒度访问显存。A100 这类 GPU 的 global-memory access 使用 32-byte segment；即使两个有效 float 只有 8 字节，也可能搬运覆盖它们的一个或多个完整 32-byte segment。[CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory)

所以：

| 概念 | 结论 |
| --- | --- |
| false lane 的地址访问 | 没有发生 |
| active lane 请求的数据 | 发生 |
| 物理传输字节 | 可能因 32-byte transaction 大于有效字节 |
| 有效 GB/s | 只按算法中的有效元素计算，不等于真实 DRAM 带宽 |

因此不能说 false lane 读取了数据，也不能断言实际 DRAM 只传输了有效元素那么多字节。

最后要保留一个重要认识：mask 只阻止无效 lane 的内存访问，**不会缩小固定 block tensor，也不会免除 program、warp、谓词计算、地址计算和部分算术调度成本**。所以尾 program 不是完全免费，但也不会产生完整 `BLOCK_SIZE` 的有效访存。
