**006 · 助手 / 正式回答** · `2026-08-06T08:15:20.586Z`

你观察得对：`stage=4` 不是最好并不异常，也不表示实现有 bug。`num_stages` 是流水深度，不是“优化等级”。

可以用下面这个关系理解：

```text
更深流水的收益：隐藏更多 load 延迟
更深流水的代价：填充/排空 + buffering + 资源占用 + resident programs 下降
```

只有收益大于代价时，增加 stages 才会更快。

### 按 shape 分析

| Shape | stage 4 没有获益的主要原因 |
| --- | --- |
| `256 x 781` | grid=256，每个 program 只处理一行，没有后续循环迭代可以流水化 |
| `4096 x 781` | grid=864，每个 program 仅处理4–5行，stage 4 几乎没有足够长的稳态流水区间 |
| `4096 x 2049` | stage 4 的 shared memory 增长到约49 KB，使 resident programs/SM 降到3 |

`4096 x 781` 尤其值得注意：

```text
stage 1/2/4 occupancy：全部 100%
grid：全部 864
```

所以这里 stage 4 较慢不能归因于 occupancy 下降。更可能是循环只有4–5次，流水填充和排空成本没有被摊薄。

概念上相当于：

```text
填充：准备 row0、row1、row2、row3
稳态：计算旧行，同时准备新行
排空：完成剩余在途行
```

但总共只有4–5行时，几乎刚填满就开始排空了。

### `N=2049` 的资源情况不同

我补充读取了这个 specialization 的实际编译资源：

| stages | registers/thread | shared/program | resident/SM | grid | 理论 occupancy |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 63 | 32 B | 4 | 432 | 50.0% |
| 2 | 48 | 16,416 B | 5 | 540 | 62.5% |
| 4 | 62 | 49,184 B | 3 | 324 | 37.5% |

stage 4 只有：

```text
3 programs/SM × 8 warps/program = 24 resident warps/SM
```

这确实减少了硬件延迟隐藏能力。

但还有一个很好的反例：stage 2 的 occupancy 是 62.5%，高于 stage 1 的 50%，性能却仍然更慢。因此再次说明：

> occupancy 描述能够驻留多少 warps，不直接决定这些 warps 是否高效执行。

### 当前 benchmark 的重要解释边界

在 `N=2049` 中，修改 stage 时，自动推导出的 grid 也变了：

```text
stage 1 -> grid 432
stage 2 -> grid 540
stage 4 -> grid 324
```

因此当前 benchmark 比较的是：

> 每个 stage 按其资源推导出的完整默认策略谁更快。

它不能证明性能差异完全由 `num_stages` 本身造成，因为同时变化的还有：

- shared memory 和 registers
- resident programs
- occupancy
- grid
- 每个 program 处理的行数

如果以后想单独研究 stages，应让三个版本使用共同的显式 grid，例如都使用324；再固定 stage 单独 sweep grid。但这属于后续性能专题，不需要现在展开。

### 整体结果应该怎样读

- `torch_naive` 物化多个中间 tensor、发射多个操作，所以最慢。
- `torch_fused` 消除了大量中间全局内存流量。
- `triton_naive` 每行一个 program，硬件可以直接调度大量独立行，本次总体最好。
- persistent 减少 program 数并循环处理多行，但 softmax 行之间没有数据复用，所以它不是必然优化。
- `num_stages=4` 只有在循环足够长、确实存在待隐藏的访存延迟、资源代价又可接受时才可能胜出。

另外，图中的有效 GB/s 是按“一次逻辑读取加一次逻辑写回”计算的，并不是实际 DRAM 带宽；它没有计算 PyTorch naive 的中间流量、padding、shared-memory traffic 和 reduction/exp 成本。

这次实验真正支持的结论是：

> 对当前 softmax、shape 和默认 grid 策略，stage 1 最合适；更多 stages 并不构成单调优化。
