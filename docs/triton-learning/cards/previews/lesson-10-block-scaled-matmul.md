## 01. 低精度矩阵乘里，一个 scale 管的元素都乘同一个系数。为什么 FP4（E2M1）要沿 K 每 32 或 16 个元素配一个 scale，而 FP8（E4M3）往往一个整张量 scale 就够？用“格式能覆盖几档”（一档是 2^k 到 2^(k+1)）说明，并说一个离群值在两种做法下影响多大范围。

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：乘一个 scale 只是把所有数在 log₂ 轴上一起平移，窗口宽度由元素格式决定：E2M1 只有约 3.58 档，E4M3 约 17.8 档。

- **整张量 scale**：整张量只能平移一次，比最大值小超过窗口宽度的数就掉出窗口，变成 0 或只剩最小值；一个离群值把 scale 拉大，每一块都受害。
- **块 scale**：每块各自平移，窗口只需盖住块内的跨度，离群值只坏它所在的那一块：整行共用一个 scale 时，远离离群值的整块小数都会掉出窗口；每块一个 scale 时，受害的只有含离群值的那一块。
- **FP8**：E4M3 的窗口约 17.8 档：一组从 0.01 到 12 的数跨 log₂(12 ÷ 0.01) ≈ 10.2 档，一个整张量 scale 就装得下；同一组数放进 E2M1 的 3.58 档就装不下。

**边界**：块缩放对 FP4 是必需，对 FP8 是改善；块越小越贴合局部范围，但 scale 要存的、要搬的、要乘的都越多。

### 锚点

平移不加宽；3.58 档对 17.8 档；离群值只坏一块

## 02. MXFP4 和 NVFP4 的元素都是 E2M1：MXFP4 每 32 个元素配一个 E8M0 块 scale（只能是 2 的幂），每个数平均 4.25 位；NVFP4 每 16 个元素配一个 E4M3 块 scale，外加每张量一个 FP32 scale，每个数平均 4.5 位。这两种块 scale 类型各带来什么好处、付出什么代价？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：MXFP4 的 E8M0 scale 范围宽、各块互不影响，但只能整档移动，对不准 E2M1 的最大值 6；NVFP4 的 E4M3 scale 能对准 6，但窗口窄，要靠每张量的 FP32 scale 定位，量化还要多读一趟。

- **NVFP4**：E4M3 的 3 位尾数能把块最大值细调到 6 附近，顶端格点用得满；块更小，一个离群值只连累 15 个数。代价是 E4M3 只有约 17.8 档：每张量 scale 只决定这个窗口放在哪，量化前得先求整张量的 amax，多一趟显存往返。

### 锚点

E8M0：范围宽、对不准 6；E4M3：对得准 6、窗口窄、多一趟

## 03. NVFP4 的两级 scale：每张量 s\_enc = 6 × 448 / amax\_张量；每块的 scale = amax\_块 / 6 × s\_enc，再舍入成 E4M3（最大 448，最小正数 2⁻⁹，约 17.8 档）。若一张激活张量各块的 amax 从 3×10⁴ 到 2×10⁻³，哪些块会出问题？为什么每张量 scale 解决不了？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：每张量 scale 只决定 E4M3 那 17.8 档的窗口放在哪里，不能把窗口变宽；各块的 scale 相差 log₂(1.5×10⁷) ≈ 23.8 档，装不进去。

- **后果**：s\_enc 把最大那块的 scale 对到 448；比它小 14.8 到 18.8 档的块，scale 落进次正规数、精度变差；更小的块 scale 舍成 0，整块变 0，对这个 0 求倒数还会得到 inf 或 NaN。
- **对照 MXFP4**：E8M0 有 254 档，每块各取各的 2 的幂，最小那块的 scale 是 2⁻¹¹，没有这个问题。
- **修法**：把第二级 scale 做细，比如每个 token（每行）一个 FP32；或者这张张量改用 MXFP4、FP8 或 BF16。

**边界**：E2M1 本身“最大和次大格点差 1.5 倍”的舍入误差每块都有，不是这里的问题；换元素格式（比如 E1M2）也救不了已经是 0 的 scale。

### 锚点

平移不加宽；23.8 档大于 17.8 档；最小块的 scale 下溢

## 04. vLLM 服务里，某一层的输入激活在线量化成 NVFP4，第二级 scale 由整个 batch 共用一个 FP32（s\_enc = 6 × 448 / 整个 batch 的 amax），块 scale 存成 E4M3（最小正数 2⁻⁹）。平时各块 amax 在 0.01 到 10 之间。某次 batch 里混进一个异常 token，它有一块的 amax 是 10⁴：同一 batch 里有些 token 输出明显出错，有些没事，单独跑出错的 token 又正常。为什么一个 token 的结果会取决于同一 batch 里还有谁？怎样修，代价是什么？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：整个 batch 共用的第二级 scale 被异常 token 抬高，所有块的 scale 在 E4M3 窗口里一起上移，幅度小的块 scale 下溢。

- **谁出错**：块 scale 小于 2⁻¹⁰（这里约是 amax 小于 0.022）的块整块变 0，0.022 到 0.35 的块精度变差；变 0 的单位是块，所以只有含这类块的 token 明显出错。
- **单独跑**：没有异常 token，第二级 scale 不会被抬高；一个 token 的结果于是取决于同一 batch 里还有谁，线上很难排查。
- **修法**：第二级 scale 改成每个 token 一个：影响限制在异常 token 自己，量化一趟就能做完；代价只是每行多一个 FP32，矩阵乘结束后按行乘回去。

**边界**：异常 token 自己的块 amax 从 0.01 到 10⁴，相差约 20 档，它自己的小块仍会变 0。

### 锚点

共享的第二级 scale 被抬高；块 scale 小于 2⁻¹⁰ 变 0；按 token 设第二级 scale

## 05. MXFP4 量化时，OCP 规则取块 scale X = 2^e，e = ⌊log₂(amax)⌋ − 2（amax 是块内最大绝对值）；Triton 3.7.1 的 triton\_kernels 默认用向上取整 X = 2^⌈log₂(amax ÷ 6)⌉。OCP 为什么对 log₂(amax) 向下取整再减 2？和向上取整相比，两种取法各把误差留在哪里？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：向下取整得到 amax 的二进制指数，也就是不超过 amax 的最大 2 的幂；减 2 是因为 E2M1 能表示的最大 2 的幂是 4。这样块最大值缩放后落在最上面一档 \[4, 8)，其余的数离“≤ 0.25 就变 0”这条线最远。

- **向下取的代价**：\[4, 8) 这一档只有 4 和 6：amax 的尾数大于 1.5 时最大值饱和成 6，误差最多约 25%，比如 7.99 存成 6。
- **向上取整**：保证不截断，但这些块的每个数都多除一个 2，小值更容易变 0。例：一块 \[7.5, 3.0, 0.4\]，向下取存成 6、3、0.5；向上取还原成 8、3、0。
- **总误差**：2²² 个随机数上两种取法的总误差相近，区别在误差落在块最大值上还是小值上。

**边界**：测试或对接其他实现时，先确认对方用哪种取法：尾数大于 1.5 的块上，两种取法的 scale 相差 2 倍。

### 锚点

最大值进 \[4, 8)；向下取截断最大值，向上取让小数变 0

## 06. 块缩放矩阵乘 C = A·B：A 的每行、B 的每列沿 K 每 V 个元素共用一个块 scale，另外可能有每张量（或每行、每列）的 scale。一个 scale 能放在计算的哪一步乘，由什么决定？按这条规则，这两类 scale 各能放在哪？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：能放在哪一步，只看 scale 沿哪个下标变化：不随 k 变的 scale 可以提到整个 K 求和的外面，矩阵乘结束后每个输出乘一次；块 scale 只能提到块内求和的外面。

- **公式**：C\[m,n\] = s^A·s^B·Σ\_j (X^A\[m,j\]·X^B\[n,j\]·Σ\_{k∈块 j} P^A\[m,k\]·P^B\[k,n\])：最外层共 M·N 次乘法，中间层每块乘一次，P 是低精度元素。
- **三种放法**：块 scale 因此有三种放法，数学上等价：乘在元素上（解码成 bf16 再乘，Triton 无原生指令时的后备、AMD CDNA3 的模拟）、乘在每块的部分和上（DeepSeek-V3 在 Hopper 上每 128 个 K 取出部分和）、在 MMA 指令内部乘（Blackwell 的 tcgen05.mma、sm\_120 的块缩放 mma.sync、CDNA4 的 scaled MFMA）。
- **怎样选**：由硬件决定：在哪里乘最便宜，乘积和累加能保留多少精度。

**边界**：tl.dot\_scaled 只处理块 scale 与元素这两层；不随 k 变的 scale（比如 NVFP4 的每张量 FP32）要在 kernel 的 epilogue 里自己乘。

### 锚点

看 scale 沿哪个下标变；三层公式；元素、部分和、指令内

## 07. 写块缩放矩阵乘 kernel 时，scale 的分块（沿 K 每 V 个元素一块，量化时就定了）与 kernel 的分块（BLOCK\_M、BLOCK\_N、BLOCK\_K）必须怎样对齐？为什么 K 方向和 M、N 方向的要求不同？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：K 方向必须嵌套而不必相等：kernel 的 K 块要由整数个 scale 块组成，并从 scale 块的边界开始；M、N 方向不需要对齐。

- **为什么 K**：不同 scale 块的乘积一旦进了同一个部分和就分不开：V = 16 时，覆盖 k ∈ \[8, 24) 的部分和，前一半该乘第 0 块的 scale，后一半该乘第 1 块的，只剩一个和就没法各乘各的。类比 4 KB 的页与 64 字节的 cache line：大小成整数倍、起点相同，页边界才一定是 cache line 边界。
- **为什么 M、N**：每个输出元素各自累加，不同行、不同列的数从不相加；DeepGEMM 的 BLOCK\_N = 112 就跨过了 N 方向的权重 scale 边界，按列挑选两个 scale。
- **接口**：tl.dot\_scaled 只检查 scale 张量的形状（大小），不知道这块数据从全局第几个 k 开始，起点要靠 kernel 自己保证。

**边界**：split-K 的每一段必须从 V 的倍数开始，用教程的 5D 预排布局时要从 4V 的倍数开始；K 不是 V 的倍数时，先补 0 补齐。

### 锚点

K 嵌套：整数倍、同起点；M、N 各自累加

## 08. H100（sm\_90）有 FP8 张量核（wgmma 支持 E4M3，每条指令 K = 32），但没有块缩放指令，累加器在寄存器里；Triton 3.7.1 把 MXFP8 的 tl.dot\_scaled 编成 bf16 矩阵乘，用不上 FP8 张量核。若改成把 MXFP8（V = 32）的块 scale 乘在部分和上：每 V 个 K 先用 FP8 张量核算出部分和，再乘 sA·sB 加进总累加器。和乘在元素上相比，这样多付什么代价？DeepGEMM 为什么改成每 128 个 K 才乘一次 scale？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：代价有三项：乘 scale 的次数变多、部分和与总累加器同时占寄存器、每段都要等异步 wgmma 出结果；每 128 个 K 一组把乘 scale 和等待都降到 V = 32 时的 1/4，还顺带修了 FP8 累加的精度。

- **乘几次**：一个 BM × BN 的输出块在一个 scale 块上：乘在部分和上，每个部分和乘一次，共 BM·BN 次；乘在元素上，每个输入元素乘一次，共 V·(BM + BN) 次。比值 BM·BN / (V·(BM + BN)) 在 128 × 256、V = 32 时约 2.7。
- **摊到每次乘加**：乘在元素上每次乘加摊到 1/BM + 1/BN 次乘 scale（128 × 256 时约 1/85），乘在部分和上摊到 1/V 次，所以 V 大于约 85 时部分和更省；V = 128 时比值约 0.67。
- **累加精度**：H800 的 FP8 累加只保留约 14 位，每 128 个元素把部分和提升到 FP32 累加，顺带修了精度；这和少乘 scale 一起，是 DeepGEMM 取 BLOCK\_K = 128 的两个理由。

**边界**：这里只数乘 scale 的次数：没算解码的成本，次数也不等于时间；多出的乘法能否藏在 MMA 后面，要靠测量。

### 锚点

多乘 scale、两套累加器、每段等待；BM·BN 对 V·(BM + BN)；128 一组降到 1/4、兼修累加精度

## 09. Triton 3.7.1 的块缩放教程在 sm\_100（B200）上，把逻辑形状 \[M, K/V\] 的 scale 在主机端预排成 (M/128, K/V/4, 32, 4, 4)；kernel 里再用 reshape(rep\_m, rep\_k, 32, 4, 4).trans(0, 3, 2, 1, 4).reshape(BLOCK\_M, BLOCK\_K // V) 还原成逻辑形状交给 tl.dot\_scaled。为什么要这样预排？那串 reshape、trans 为什么不搬数据？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：块内的 (32, 4, 4) 就是 TMEM 要的字节顺序：一块 128 行 × 4 个 scale（512 字节）放成 32 个 lane × 4 列，第 m 行在 lane m % 32、第 m / 32 列，每个 32 位格子装同一行相邻 4 个 K 块的 scale。

- **搬运**：TMA 把若干整块搬进 SMEM，一个线程发 tcgen05.cp .32x128b.warpx4，把每块原样拷进 TMEM；全程不经过寄存器，也不重排字节。
- **外层**：kc（第几组 4 个 scale）放在块的紧外层、mb（第几个 128 行组）放最外层，一个 K 步要用的块就是连续的。
- **reshape 与 trans**：只换取址规则：编译器（UseShmemForScales）认出这串固定写法，改写成 SMEM 描述符上的 memdesc\_reshape 和 memdesc\_trans，不生成读写指令。

**边界**：这是模式匹配：换一种存法或写法匹配不上，就走通用路径（每个 warp 读进寄存器再 tcgen05.st），结果照样对但更慢；预排是快路径的前提，不是结果正确的前提。

### 锚点

块内 = TMEM 顺序；TMA → SMEM → tcgen05.cp；视图不搬数据

## 10. 在 sm\_100 上用 Triton 3.7.1 建二维 TMA 描述符：A 的块 scale 按逻辑形状 \[M, K/V\] 行优先存（每个 scale 1 字节），每次搬的块是 \[BLOCK\_M, BLOCK\_K/V\]：NVFP4 为 \[128, 16\]，MXFP4 为 \[128, 8\]，MXFP8 为 \[128, 4\]，K = 8192。TMA 的三条规则“每维不超过 256 个元素”“最内维的字节数是 16 的倍数”“行距是 16 字节的倍数”各约束哪个形状，哪些格式因此建不起来？用主机端的 TensorDescriptor 时，这个错误在哪一步暴露？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：前两条约束一次搬运的块（CUDA 文档叫 box），第三条约束整个张量；整个张量每维可以到 2³²，不受 256 的限制。

- **结果**：块的最内维：NVFP4 是 16 字节，可以建；MXFP4 的 8 字节、MXFP8 的 4 字节违反 16 字节规则，建不起来。行距是 512 或 256 字节，都满足。
- **主机端**：块最内维不足 16 字节时，编译和在 Python 端构造 TensorDescriptor 都能通过；按 CUDA 文档，要到启动 kernel、调用 cuTensorMapEncodeTiled 时才被拒（未在 sm\_100 上实测）。行距不是 16 字节的倍数时则不同，构造 TensorDescriptor 这一步就断言失败。
- **kernel 内**：在 kernel 里用 tl.make\_tensor\_descriptor 建描述符时，编译期就检查最后一维至少 16 字节。
- **转置存**：按 \[K/V, M\] 存、块取 \[BLOCK\_K/V, 128\] 时，最内维是 128 字节，三种格式都能建；对 M 的要求只来自行距，M 是 16 的倍数即可。

**边界**：教程的 5D 描述符，块是 \[1, rep\_m, rep\_k, 2, 256\]，三条都满足；这种布局本身还要求 M 是 128 的倍数。

### 锚点

块对张量；最内维 ≥ 16 字节；主机端：最内维启动时才被拒，行距构造时就查

## 11. Triton 3.7.1 编译同一行 tl.dot\_scaled（MXFP4 × MXFP4，两侧都带 scale）时，按什么规则决定走原生块缩放指令、走软件换算还是编译失败？按这条规则，B200（sm\_100）、RTX 5090（sm\_120）、MI355X（gfx950，CDNA4）、RTX 4090（sm\_89）和 MI300X（gfx942，CDNA3）各落在哪一类？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：目标有块缩放指令、两侧都带 scale、格式受这条指令支持时走原生，scale 在指令内乘；否则走软件换算：解码成 bf16、逐元素乘 scale、再做 bf16 矩阵乘；CDNA3 的模拟路径只接一侧带 scale，两侧都带时编译失败。

- **原生**：sm\_100 的 tcgen05.mma，scale 和累加器都在 TMEM；sm\_120 的块缩放 mma.sync，scale 和累加器都在寄存器；gfx950 的 scaled MFMA，scale 在 VGPR，只认 E8M0。
- **软件换算**：sm\_89 没有块缩放指令，解码后用 bf16 的 mma.sync，只省显存不省算力。
- **编译失败**：gfx942 只登记了一侧带 scale 的模拟路径（比如 bf16 × MXFP4），两侧都带 scale 时报 Unsupported DotScaleOp。

**边界**：“不走原生”有两种原因要分开：一侧根本不是低精度格式（如 bf16 × MXFP4）时，块缩放指令要求两侧都是 FP8、FP6 或 FP4，所有目标都走软件换算；一侧是 FP4 却不带 scale 时，sm\_120 退回软件换算，是因为 Triton 3.7.1 的原生模式要求两侧都有 scale，不是指令本身的格式限制。

### 锚点

原生要指令、两侧 scale、格式三者都满足；否则软件换算；CDNA3 两侧带 scale 编译失败

## 13. MI300X（bf16 稠密峰值 1307.4 TFLOPS，显存带宽 5.3 TB/s，显存 192 GB）上，Triton 3.7.1 的一侧模拟路径先用 upcast\_mxfp 把 MXFP4 权重解码并乘 scale，再做 bf16 MFMA。一个 MoE 专家的权重 N × K（N、K 都是几千）存 bf16（方式 A）还是 MXFP4（方式 B）：解码时每个专家 M = 8，预填充时 M = 4096，B 比 A 快、慢还是差不多？依据是什么？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：解码（M = 8）时 B 最多快约 3.6 倍；预填充（M = 4096）时 B 最多和 A 持平，解码藏不住时慢约四成。依据是拿计算强度和平衡点（约 247 FLOP/字节，即约 123 次乘加/字节）比。

- **解码 M = 8**：强度远低于平衡点，受访存限制：B 读的字节约为 A 的 1/3.6，最多快约 3.6 倍；前提是解码跟得上带宽，这要用掉向量单元约八成的吞吐。
- **预填充 M = 4096**：受计算限制，B 少读的只是一小部分字节（激活和输出不变），换不来时间；只看解码能不能藏进 MFMA（约占 MFMA 时间的四成）：藏住时差不多，藏不住时 B 慢约四成。
- **容量**：与负载无关，B 的权重小约 3.8 倍，省下的显存可以给 KV cache。

**边界**：强度要计入激活、权重、scale 和输出的字节，单位要和平衡点一致；靠近平衡点时，结论对解码代价很敏感，要实测。

### 锚点

解码最多快约 3.6 倍、预填充最多持平；平衡点 123 次乘加/字节；容量始终都有

## 14. 一个 W4A16 矩阵乘（bf16 激活 × FP4 权重，权重先在向量单元解码再做矩阵乘）里，显存搬字节、矩阵单元做乘加、向量单元做解码，三种资源同时工作。怎样量化回答两个问题：解码能不能藏进矩阵乘的时间？解码速度跟不跟得上显存带宽？以 MI300X 为例：MFMA 每秒 653.7 万亿次乘加，向量单元按 lane 计每秒 40.9 万亿条指令，显存 5.3 TB/s，权重连 scale 每个 FP4 占 0.53125 字节。

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：先算每种资源单独把活干完要多久（t\_mem、t\_mfma、t\_valu），再看它们能不能同时干：能同时干就取最长的一项，不能就相加。

- **解码对 MFMA**：t\_valu / t\_mfma = (c ÷ P\_valu) ÷ (BLOCK\_M ÷ P\_mfma) = 16c / BLOCK\_M：P\_valu 是向量单元每秒按 lane 计的指令数，P\_mfma 是 MFMA 每秒的乘加数，16 = 653.7 ÷ 40.9；c 是每解码一个 FP4、每个 lane 要执行几条向量指令，BLOCK\_M 是一个解码出的 FP4 参与的乘加次数。
- **藏得住的门槛**：CDNA3 一条 16 个周期的 MFMA 发出 4 个周期后，才能同时发射向量指令，留出 12 个周期的空档，所以比值不超过约 0.75 才可能全部藏住。
- **解码对带宽**：受访存限制、每个 FP4 只解码一次时，t\_valu / t\_mem = (c ÷ 40.9 万亿) ÷ (0.53125 ÷ 5.3 TB/s) ≈ 0.244c；要跟上 5.3 TB/s，c 不能超过约 4.1。
- **c 从哪来**：从能运行的配置编出的代码里数：每个 wave 每个 K 步的非 MFMA 向量指令数 ÷ 每个 lane 解码的 FP4 数，例如 MI300X 上 BLOCK\_K = 128 的配置是 104 ÷ 32 ≈ 3.25；只编译不会检查 LDS 上限，先确认配置放得下。

**边界**：峰值跑不满，能否真的并行要看调度和驻留的 wave 数；最终要用 rocprofiler-compute 之类的工具实测各资源的利用率。

### 锚点

各资源忙碌时间；重叠取最大、不重叠相加；16c/BM 与 0.244c

## 15. 在 Triton 3.7.1 的软件换算路径里（A 是 bf16 激活，B 是要解码成 bf16 的 FP4 权重），一个 CTA 的输出块由 warpsPerCTA 规定的若干 warp（AMD 上叫 wave）分工计算，写法是 \[M 方向的 wave 数, N 方向的 wave 数\]。以 AMD CDNA 上 128 × 128 的 CTA 块、8 个 wave 排成 \[1, 8\] 和 \[2, 4\] 为例，排法怎样影响每个权重元素被解码几次、每一份参与几次乘加？

类型：技术问答 · 层级：机制 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：每个 wave 只算自己的子块，在自己的寄存器里存累加器、解码自己要用的那部分 B；wave 之间不共享寄存器，M 方向有几个 wave，同一列 B 就被解码几份。

**边界**：这里只比较了解码次数和从 LDS 读取的量；CDNA3 的 LDS 带宽没有查到官方数字，两种排法没有折算成时间。

### 锚点

M 方向几个 wave 就解码几份；排法决定复用次数；排法由编译器定

## 17. 估算 RTX 5090（每个 SM 有 4 个调度器，每个调度器每周期发射 1 条 warp 指令，频率 2407 MHz）上一个 kernel 发射指令要多少时间。已知的可能是每个 warp 每个 K 步的 warp 指令数（从 SASS 数出），也可能是“每个元素、每个 lane 约执行几条指令”（线程级条数）。怎样换算、要乘哪些量？以 M = 16 的软件换算路径为例：每个 warp 每个 K 步 1842 条，16 个 K 步，最忙的 SM 上 2 个 CTA × 4 个 warp。

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：看最忙的 SM、按调度器算：每个调度器要发射的 warp 指令总数 ÷ 频率。例子里是 2 个 warp × 16 个 K 步 × 1842 条 = 58,944 条，÷ 2407 MHz ≈ 24.5 µs。

- **两种条数**：warp 指令是调度器发射一次、warp 里 32 个 lane 各执行一次；线程级条数是一个 lane 为它负责的一个元素执行几条。warp 指令数 = 元素数 × 线程级条数 ÷ 32，就像一条 AVX2 指令同时处理 8 个 float。
- **要乘的**：每个 warp 每个 K 步的条数 × K 步数 × 每个调度器分到的 warp 数（这里 8 个 warp 分给 4 个调度器，每个 2 个）。
- **等价写法**：也可以全用线程级：线程级总条数 ÷（每个 SM 128 个 lane × 频率）；关键是单价和速率用同一种单位。

**边界**：估算前先拿答案已知的情况试一遍：同一方法算出的发射时间若比实测总时间还长几倍，就是单位或系数错了。

### 锚点

warp 指令 = 元素 × 线程级条数 ÷ 32；× K 步 × 每调度器 warp 数 ÷ 频率；先核对已知结果

## 18. 估算一个 kernel 的总时间：已知最忙的 SM 上发射指令要 t\_issue，把最少要搬的字节搬完要 t\_mem。两部分完全重叠时总时间是 max(t\_issue, t\_mem)，完全不重叠时是两者之和。实际更靠近哪一端，由什么决定？以 RTX 5090 上 M = 16 的 W8A16 变式为例（bf16 激活 × MXFP8 权重）：t\_issue ≈ 20.3 µs，t\_mem ≈ 39.1 µs，每个 SM 同一时刻只驻留 1 个 CTA。

## 19. 判断一组数能不能用某种低精度浮点格式表示时，要比较“这组数跨了几档”（一档是 2^k 到 2^(k+1)）和“格式能覆盖几档”。格式的档数怎样量？以 E2M1（正值 0.5、1、1.5、2、3、4、6）为例，为什么是约 3.58 档而不是 3 档？

### 答案

**结论**：按 log₂(最大值 ÷ 最小正值) 量：E2M1 是 log₂(6 ÷ 0.5) = log₂ 12 ≈ 3.58 档。

**边界**：判断装不装得下只用这种“比倍数”的量法，不用“指数编码有几个”。

log₂(最大 ÷ 最小正值)；+1 次正规，−0.42 未用

## 20. 块缩放 FP4 里，若块内有一个约 8 倍的离群值、块 scale 对齐离群值，同块其余正常值都挤在块最大值的 1/8 以下，这时 E3M0 在这些正常值上比 E2M1 准。为什么“离群值毕竟是少数，所以仍选 E2M1”这句理由不完整？真实系统又怎样从块大小、量化前的变换和层的精度三方面压低离群值的损失？

## 21. MXFP4 量化中，元素已经除以块 scale，得到 |v| < 8 的浮点数，要按就近取偶（落在两个格点正中间时取尾数位为 0 的那个）舍入到 E2M1 的格点 {0, 0.5, 1, 1.5, 2, 3, 4, 6}，超过 6 的饱和到 6。怎样用普通的整数舍入实现？

类型：技术问答 · 层级：原子 · 等级：B

### 答案

**结论**：格点在每一档内部是等距的：先按 |v| 定这一档的间距 s（\[0, 2) 是 0.5，\[2, 4) 是 1，\[4, 8) 是 2），再算 round(|v| ÷ s) × s。

- **精确**：s 是 2 的幂，除法和乘法都是精确的；舍入到这一档的上界（比如 1.9 → 2）也对，它正好是下一档的第一个格点。
- **取偶**：“偶”指尾数位为 0。档内的格点是 s × k，k 的奇偶就是尾数位，所以平局取偶就是 k 取偶，torch.round 默认就这样处理平局。
- **饱和**：饱和放在舍入之后：7 舍入成 8，再截到 6；“≤ 0.25 变 0”不用单独处理，0.25 ÷ 0.5 = 0.5，取偶后正好是 0。

**边界**：全程在 float32 里算：2.500000238 不是平局，应舍成 3；先降成 bf16 会变成 2.5，取偶后错成 2。

### 锚点

按档定 s；round(|v|/s)·s；k 取偶即尾数位为 0

## 23. 块缩放教程的 scale 形状链：逻辑 \[M, K/V\] → 物理 (M/128, K/V/4, 32, 4, 4) → TMA 视图 (1, M/128, K/V/4, 2, 256) → kernel 里的 reshape、trans、reshape。怎样用“把下标拆成数位”的方法推导这串形状？哪些数字由硬件固定，哪些随分块、格式和输入大小变化？

类型：技术问答 · 层级：机制 · 等级：B

### 答案

**结论**：把行号、列号按混合进制拆开：m = 128·mb + 32·g + r，j = 4·kc + c；reshape 只合并或拆分相邻的数位，不动字节；trans 改变数位的先后。

- **块内**：(r, g, c) = (32, 4, 4) 由 TMEM 决定：32 个 lane，128 行折成 4 列，一个 32 位格子装 4 个 1 字节的 scale，都是硬件固定的。
- **块外**：kc 在块的紧外层、mb 在最外层，由 K 循环决定；2 × 256 由 TMA 规则决定；首维的 1 只是占位，可以去掉。
- **会变的**：M/128 和 K/V/4 随输入与格式变化；rep\_m = BLOCK\_M/128 和 rep\_k = BLOCK\_K/V/4 随分块变化，所以 BLOCK\_M 必须是 128 的倍数，BLOCK\_K 必须是 4V 的倍数。

**边界**：整条链上唯一真正搬字节的，是主机端从逻辑矩阵排成物理顺序那一步：reshape 成 (mb, g, r, kc, c)，再 permute(0, 3, 2, 1, 4)。

### 锚点

拆数位；reshape 不动字节；32/4/4 来自硬件、2×256 来自 TMA

## 26. PyTorch 里没有可以直接 .to() 过去的 MXFP4 类型。量化后已经得到落在 E2M1 格点上的浮点值（比如 3.0、−0.5），怎样把它们变成 4 位编码，并沿 K 把相邻两个编码打包进一个字节（第 j 个字节的低 4 位放第 2j 个元素）？

类型：技术问答 · 层级：原子 · 等级：B

### 答案

**结论**：编码就是这个值在有序格点表 {0, 0.5, 1, 1.5, 2, 3, 4, 6} 里的下标，负数再加 8；打包是 byte = lo | (hi << 4)。

- **为什么是下标**：非负数的位模式当无符号整数比大小，顺序和数值一致，道理和 IEEE 浮点一样；符号是单独的最高位，所以 −3 是 13、−0.5 是 9、−0 是 8。
- **整张量**：编码放在整数张量里，用步长为 2 的切片取出偶数列和奇数列：codes\[..., 0::2\] | (codes\[..., 1::2\] << 4)。例：\[3.0, −0.5\] 的编码是 \[5, 9\]，打成 0x95。
- **解包（延伸）**：byte & 0xF 是元素 2j，byte >> 4 是元素 2j+1，再交错放回；低 3 位查表，最高位（bit 3）是符号位，整张量上用 torch.where(sign == 1, -v, v) 放回符号（分支改成两边都算、再按条件挑），最后乘 2^(scale 字节 − 127)。

**边界**：浮点张量不能移位（左移对 Float 未实现），编码必须放在整数张量里，最后的 packed 是 uint8。

### 锚点

值 → 下标 → 负数加 8；lo | (hi << 4)；用整数张量

## 28. Triton 3.7.1 在没有原生块缩放指令可用时，把 tl.dot\_scaled 拆成软件换算。以 RTX 5090 上的一条软件路径为例：A 是不带 scale 的 MXFP4，B 是带 scale 的 MXFP4。哪些操作数要做“解码”、哪些要做“scale 处理”，各由什么决定？其中哪一部分可以用 fast\_math=True 省掉？

类型：技术问答 · 层级：机制 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：解码看存储格式：以 FP4 存放的操作数都要把 4 位码换成 bf16，与有没有 scale 无关；scale 处理看有没有 scale：只有带 scale 的操作数才乘 scale、做 NaN 处理。例子里 A、B 都要解码，只有 B 做 scale 处理。

**边界**：只有能保证量化不会产生 0xFF 的 scale 时，才适合打开 fast\_math。

适用范围：vllm · 8530aed2b78a19eb00e242031c22bb78d615eea2

**结论**：MI300X 原生的 FP8 是 FNUZ 变体：bias 是 8 而不是 7，同样的位表示的值正好是 OCP E4M3 的一半，而且 0x80 在 OCP 里是 −0，在 FNUZ 里是 NaN。直接复用字节，反量化的值整体小一半，原来的 −0 变成 NaN。

- **格式差别**：FNUZ 没有 −0 和 Inf，0x80 是唯一的 NaN，最大值 240（OCP E4M3 是 448）；比如字节 0x7E 在 OCP 里是 448，在 FNUZ 里是 224。
- **转换**：vLLM 做三步：把字节 0x80 改成 0；把同样的位按 FNUZ 重新解读；把权重 scale 和输入 scale 都乘 2。同样的位在 FNUZ 里只有一半大，scale 翻倍后反量化的结果不变。

**边界**：这是 CDNA3 的问题：MI350 系列（CDNA4）改用了 OCP 格式，不需要这一步；换到别的加速器时，先查清它原生的 FP8 是哪一种变体。

### 锚点

FNUZ：bias 8、同位值减半、0x80 是 NaN；0x80 → 0、按 FNUZ 解读、scale × 2

## 30. 在 Triton 3.7.1 里给 NVIDIA 的 TMA 建描述符：一块 scale 是 16 行 × 16 个字节，这 16 行在显存里首尾相接（行距正好 16 字节）。想在描述符里把它们表示成一段连续的 256 字节，而不是 16 段 16 字节，该怎样表达？

类型：技术问答 · 层级：原子 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：没有单独的“连续”声明，形状和步长本身就是声明：把首尾相接的几行在形状里合成一维，比如 \[16, 16\] 写成 \[256\]，在主机端先把张量 reshape 成合并后的形状，再建描述符。

## 31. 解释在都配块 scale 的前提下，4 位元素格式为什么选 E2M1（1 位尾数），而不是范围更宽的 E3M0（0 位尾数）。

类型：真实纠错 · 层级：机制 · 等级：A

### 场景

一张激活张量每行近似服从均值为 0 的正态分布；同事提议用 E3M0（非负值 0、0.25、0.5、1、2、4、8、16，约 6 档）代替 E2M1（约 3.58 档）。两种格式都按块最大值取 scale 时比较精度。

### 正确

点积误差由块内较大的数主导：E2M1 在块最大值往下的 1/4 到 1 这一段有 5 个格点，E3M0 只有 3 个；E3M0 多出的格点在 1/8 以下，那里的数小，舍入误差本来就小。

### 错误

考虑到同一个token内的数大致服从均值为0的正态分布，那我认为接近0的小范围有更多格点会更好，所以业界可能选E2M1加块scale。

### 说明

**结论**：结论（选 E2M1）对，理由反了：0 附近格点多的是 E3M0。

- **格点**：把块最大值记为 1：E2M1 是 0、1/12、1/6、1/4、1/3、1/2、2/3、1；E3M0 是 0、1/64、1/32、1/16、1/8、1/4、1/2、1。
- **为什么**：小数整个舍成 0，误差也不超过它本身；块 scale 已把块最大值对到格式顶端，元素格式只需把顶端往下几档切细，所以位数给尾数更划算。
- **量级**：合成正态数据上，E3M0 加块 scale 的误差约是 E2M1 的 1.8 倍。

**边界**：块内有大离群值、正常值都挤在 1/8 以下时，E3M0 反而更准；那时要靠更小的块、旋转等手段压低离群值的损失。

## 32. 说明 MX 格式的 E8M0 scale 能表示的指数范围，以及量化器为什么把 e 截到 \[−127, 127\]。

类型：真实纠错 · 层级：原子 · 等级：A

### 场景

写 MXFP4 量化器时，规则是“e = ⌊log₂(amax)⌋ − 2，截到 \[−127, 127\]，scale 字节 = e + 127”，学习者对截断范围有疑问。

### 正确

E8M0 是无符号字节减 127，字节 255 留给 NaN，可用的指数是 −127 到 127；截到 −127 保证 scale 字节落在 0 到 254，永远写不出 255。

### 错误

为什么是截到\[-127, 127\]，而不是\[-128, 128\]。因为UE8M0的指数上范围不应该是\[-128,128\]吗？

### 说明

**结论**：E8M0 不是补码：字节 0 到 255 减 127 得到 −127 到 128，255 是 NaN，所以最大到 127；\[−128, 128\] 有 257 个整数，8 位只有 256 个编码。

- **对齐**：bias 取 127，是为了和 FP32 的指数字段对齐：Triton 的软件路径把字节左移 7 位，直接当 bf16 的位模式用。
- **NaN**：FP4 自己没有 NaN，一块数据要标记无效只能靠 scale；scale 为 NaN 时整块都是 NaN。
- **截断**：全零块的 log₂ 0 = −∞，截到 −127 即可；若允许 −128，字节 −1 在 uint8 里回绕成 255，整块解出来全是 NaN。

**边界**：字节 0 表示 2⁻¹²⁷，在 FP32 里是次正规数；“左移 23 位当 FP32”的写法会把它变成 0。

## 33. 判断在有低精度 MMA 指令、但没有块缩放指令的硬件上，块 scale 应乘在元素上还是部分和上。

类型：真实纠错 · 层级：机制 · 等级：A

### 场景

块 scale 可以乘在输入元素上、部分和上或 MMA 指令内部；这里讨论没有指令内缩放、只有 FP8 等低精度 MMA 的硬件。

### 正确

乘在部分和上的硬前提是 scale 块不比一条 MMA 指令的 K 小；而且 2 的幂 scale 在一定窗口内可以乘在元素上、结果仍留在低精度格式里，所以“乘在元素上就用不了低精度 MMA”不成立。

### 错误

对于一款有低精度MMA指令的硬件，我想利用低精度MMA的高性能，那么我肯定是会把scale在部分和上是吧？因为如果放在输入元素上，那么已经提升精度了，就没法用低精度MMA了。

### 说明

**结论**：方向对，但缺一个前提和一个例外。

- **前提**：一条 MMA 算出的部分和不能跨 scale 块：Hopper 的 FP8 WGMMA 每条 K = 32，NVFP4 的 V = 16 就做不到。

**边界**：拆指数的做法要求同一 K 块里各块的指数落在约 15 档的窗口内，超出的块会损失精度；这是可行性分析，没有核实哪个系统这样做。

## 34. 说明块缩放 kernel 把预排的 scale 还原成逻辑形状时，中间那次 trans 起什么作用，以及漏掉或写错的后果。

类型：真实纠错 · 层级：原子 · 等级：A

适用范围：triton · 3.7.1

### 场景

Triton 3.7.1 的 sm\_100 块缩放教程把 scale 预排成 \[M/128, K/V/4, 32, 4, 4\]，kernel 里用 reshape、trans(0, 3, 2, 1, 4)、reshape 还原。假设 TMEM 的格子从 32 位变成 64 位，物理形状变成 \[M/128, K/V/8, 32, 4, 8\]；问 trans(0, 3, 2, 1, 4) 的维度顺序要不要改、为什么。

### 正确

trans 不读写数据，它让最后一次 reshape 合出的下标正好是 tl.dot\_scaled 要的行号 32g + r 和列号 8kc + c（64 位格子一格装 8 个 scale）；访存是否连续，在定物理排法时就定了。

### 错误

trans 的维度顺序不用变。因为调整维度顺序是为了让行和列的层级维度放在一起，应该是可以更好的连续访存。

### 说明

**结论**：结论（不用改）和“让行、列的数位各自挨在一起”都对，“为了更好的连续访存”不对：sm\_100 上它只是 SMEM 描述符上的一个视图。

- **漏掉**：以原来的 32 位布局为例：把 \[1, 4, 32, 4, 4\] 直接 reshape 成 \[128, 16\]，行号变成 32·kc + r、列号变成 4g + c，逻辑位置 (37, 10) 会取到第 69 行第 6 列的 scale，结果算错而不是变慢。
- **写错**：块内排法换成 (g, r, c) 后应写 trans(0, 2, 3, 1, 4)；照抄旧的 trans，各维大小的乘积不变，照样能编译通过，只有数值核对抓得到。

**边界**：漏掉或写错 trans 还会让编译器认不出这串写法，退回通用路径。

## 35. 说明在 MI300X 上把 MoE 专家权重从 bf16 改存 MXFP4、矩阵乘仍用 bf16 MFMA 时，无论解码还是预填充都保留的好处是什么。

## 36. 用计算强度判断 MI300X 上一个 MoE 专家的矩阵乘（权重存 MXFP4）受访存还是计算限制，并说明算出的强度该怎样和平衡点比较。

类型：真实纠错 · 层级：原子 · 等级：A

### 场景

MI300X 的 bf16 稠密峰值 1307.4 TFLOPS、显存带宽 5.3 TB/s，平衡点约 247 FLOP/字节。DeepSeek-V3 式路由下每个专家 M = 128，权重 N = K = 1024 存 MXFP4（每 32 个 FP4 配 1 字节 scale），激活和输出都是 bf16。

### 正确

M·N·K ÷ 字节得到的是“次乘加/字节”，要和约 123 次乘加/字节比；按 FLOP 算要再乘 2，才和 247 比。字节计入激活、权重、scale 和 bf16 输出后，这里约 124 次乘加/字节，几乎正好落在平衡点上，访存和计算两种限制都要考虑。

### 错误

对于mxfp4的存法，计算强度为128\*1024\*1024/(2\*128\*1024+0.5\*1024\*1024+1024\*1024/32)=163.84 ，相比于平衡点依旧是低的。所以瓶颈依旧是访存

### 说明

**结论**：错在比较的单位：规格表的 TFLOPS 把一次乘加算 2 次运算（1307.4 TFLOPS 就是每秒 653.7 万亿次乘加），163.84 是次乘加/字节，拿它和 247 FLOP/字节比，等于把平衡点抬高了一倍。

- **输出字节**：原式和原题都没计入 bf16 输出的 262,144 字节（题目让先忽略激活和输出），这一项不算原答的错。计入后分母是 1,081,344 字节，134,217,728 ÷ 1,081,344 ≈ 124.1；输出若为 fp32，约 99.9，低于平衡点。
- **影响**：bf16 方式计入输出后约 51.2，比 123 和 247 都低，单位混用碰巧不改变结论；落在 123 和 247 之间的强度，单位一混就会判错。
- **做法**：每个强度都写上单位，平衡点只用一种：按乘加是 123，按 FLOP 是 247；字节要计入输入、scale 和输出。

**边界**：规格表里的稀疏 TFLOPS 是稠密值的 2 倍，估算稠密 GEMM 时不能用。

## 37. 说明每个专家 M = 128 时，M 的大小怎样影响 MXFP4 权重的解码能否藏进 MFMA，并据此判断方式 B 会不会比方式 A 慢。

类型：真实纠错 · 层级：机制 · 等级：A

### 场景

MI300X，bf16 激活 × 权重 N = K = 1024，BLOCK\_M = 128，8 个 wave 全沿 N 排（每个权重元素在 CTA 内只解码一次）；每个专家 M = 4096 时，按编译产物估，解码约为 MFMA 时间的 43%。现在每个专家只分到 M = 128：方式 A 存 bf16 权重，受访存限制，用时约 2.4T；方式 B 存 MXFP4、在 kernel 里解码，访存约 0.99T。T 是 MFMA 按峰值算完的时间，访存与计算按重叠估。

### 正确

解码相对 MFMA 的比例是 16c / BLOCK\_M（c 是每个 FP4 的向量指令数），与 M 无关：M = 128 时和 M = 4096 时一样约 43%。B 用时 1T（解码全藏住）到 1.43T（全藏不住），仍比 A 的约 2.4T 快约 1.7 到 2.4 倍。

### 错误

B可能还比A慢。到不了3.8倍是因为B还需要付出解码的开销。因为这时M数值小，我怀疑MFMA无法藏住解码开销。

### 说明

**结论**：错在把“藏不住”归因于 M 小：每个 CTA 把自己那块权重解码一次，每个解码出的 FP4 和这个 CTA 的 BLOCK\_M 行各做一次乘加，解码总量 N·K·cdiv(M, BLOCK\_M)，乘加总量 cdiv(M, BLOCK\_M)·BLOCK\_M·N·K，相除只剩 BLOCK\_M。

- **比较**：“藏不住”只说明 B 要多花时间，要把总时间算出来再和 A 比：B 最慢也只是 1.43T；访存与计算不重叠时，A 约 3.4T、B 约 2.0T 到 2.4T，B 仍更快。
- **为何到不了 3.8 倍**：激活和输出的字节不会变少，总字节只少约 2.4 倍；B 的访存约 0.99T，已和 MFMA 的 1T 相当，就算解码不花时间，也最多快约 2.4 倍。

**边界**：只有 M 小于 BLOCK\_M 时 M 才起作用：补齐的行让 MFMA 白算，解码只摊到 M 行有效的乘加上。

## 38. 解释量化代码里用 torch.pow(2, -e) 求 2^(−e) 时，结果为什么是 0。

类型：真实纠错 · 层级：原子 · 等级：B

适用范围：pytorch · 2.13.0

### 场景

在 PyTorch 2.13.0 中写 MXFP4 量化：一块数的 amax 是 15.6875，e = 1，存在 int32 张量里；计算 data \* torch.pow(2, -1\*e) 时，整块变成 0 和 −0。

### 正确

底数是 Python int、指数是 int32 张量，结果仍是 int32，2⁻¹ 在整数里是 0；要写成 2.0 \*\* -e、torch.exp2(-e.float()) 或 torch.ldexp(data, -e)。

### 错误

为什么会变成很多0？torch.pow(2, -1\*e)应该就只是一个1/2呀？

### 说明

**结论**：PyTorch 的类型提升规则：Python 标量只有在类别高于张量时才改变结果的 dtype，int 标量和 int 张量运算，结果仍是 int。

- **不报错**：torch.tensor(2) \*\* -1 会报错，但指数是张量时直接给出 0，相当于 C 里用 int 算 1/2；负数乘 +0 显示为 −0。
- **同类陷阱（延伸）**：uint8 的 scales − 127 会回绕：\[120, 127, 130\] 减 127 得到 \[249, 0, 3\]，要先转成 float32 或 int32 再减。

**边界**：遇到整数和浮点混算的怪结果，先打印 .dtype。

## 39. 判断块缩放 kernel 里把每个 K 步的前进量 BLOCK\_K // 2 误写成 BLOCK\_K 会发生什么，以及测试怎样才能抓到这种错。

## 40. 把 6 位的 FP6 编码沿 K 打包成字节时，按小端位流放置各位，并说明为什么只做往返测试发现不了位序约定上的错。

### 场景

MXFP6（E3M2）每个编码 6 位，约定把每行看成一条小端位流：第 i 个元素占第 6i 到 6i+5 位，位流第 b 位放在第 ⌊b/8⌋ 个字节的第 b mod 8 位。以编码 1、2、3、4 为例，字节写成最高位在左。

### 正确

第 0 个元素在第 0 个字节的最低 6 位：编码 1、2、3、4 打成 10000001 00110000 00010000，每个编码自己的最低位也落在位流里较低的位置。

### 错误

### 说明

**结论**：这种写法相当于把 3 个字节看成大端的 24 位数 w = b0 << 16 | b1 << 8 | b2，第 0 个元素占最高的 6 位。

## 41. 预测 RTX 5090 上块缩放矩阵乘原生路径与软件换算路径的耗时比时，正确估算软件路径的解码开销。

类型：真实纠错 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 场景

RTX 5090（sm\_120）、Triton 3.7.1：同一个 MXFP4 kernel 去掉 A 的 scale，迫使 sm\_120 走软件换算（A、B 的 FP4 都解码成 bf16），N = K = 8192，M = 16 与 M = 8192；学习者在运行前写预测，T 是 BF16 矩阵乘按峰值算完的时间。

### 正确

解码在每个 warp 自己的寄存器里做，A 也是 FP4、同样要解码；M = 16 时每个 warp 只负责 16 行 B × 8 行 A，每个 K 步解码 12,288 个元素、只做 65,536 次乘加，平均每个元素只参与 5.3 次（M = 8192 的选中配置是 21 次）。

### 错误

解码假设和amd的之前一样需要3.5条指令，那么解码的时间比例大概是(3.5/52.4)/(128/104.75) = 0.0547T，比矩阵乘加小很多。

### 说明

**结论**：按 128 次算，等于把 BLOCK\_M 当成了复用次数；按实际的 5.3 次，M = 16 时解码时间约为 1.6T，是估计的 30 倍。

- **式子**：原式的结构是 (每个元素的向量指令数 ÷ 向量单元的速率) ÷ (复用次数 ÷ 张量核的速率)：52.4 是 RTX 5090 每秒约 52.4 万亿条 lane 指令，104.75 是 BF16 张量核每秒约 104.75 万亿次乘加。
- **单价**：每个元素约 4 条线程级指令，和沿用的 3.5 条差不多：单价没估错，错在复用次数。
- **结果**：实测比值 M = 16 为 1.570、M = 8192 为 4.368，预测的 \[0.99, 1.01\] 和 \[7.8, 8.2\] 都被否定。
- **其他假设**：还默认了几部分完全重叠、两条路径都能跑到峰值。

**边界**：复用次数要按每个 warp 的子块和实际要解码的操作数来数；M 很小时 Triton 还会交换操作数。

## 42. 解释基准测试里两条路径搬同样多的字节、耗时却不同的原因。

## 44. 说明浮点数 v = 2^(E − bias) × (1 + M / 2^m) 里，指数段选的是哪一个 2 的幂，尾数段怎样表示两个 2 的幂之间的数。

类型：真实纠错 · 层级：原子 · 等级：B

### 场景

初学浮点表示时，学习者用“指数找 2 的幂、尾数在两个 2 的幂之间表示数”的直觉来读这个公式。

### 正确

指数取不超过 x 的最大 2 的幂，即 x 所在那一档 \[2^k, 2^(k+1)) 的左端；尾数把这一档等分成 2^m 份，M 是格点的编号。

### 错误

指数段 E（e 位）2^(E − bias)寻找确定要表示的数的最近的2的幂次，尾数段 M（m 位）在两个2的幂次之间进行表示数。

### 说明

**结论**：不是“最近的”：3.9 离 4 更近，但它在 \[2, 4) 这一档，指数取 2¹ = 2，剩下的 1.95 倍交给尾数。

## 45. 选择 MX scale 张量在 PyTorch 与 Triton 之间传递时的 dtype。

## 47. 请用约 60–90 秒向面试官讲清：FP4 矩阵乘为什么需要块缩放？元素格式为什么是 E2M1？MXFP4 和 NVFP4 怎样取舍？OCP 规则怎样取 MXFP4 的 scale，代价是什么？

类型：综合口述 · 层级：口述 · 等级：A

### 参考回答

**结论**：FP4 的 E2M1 只覆盖约 3.6 档，乘一个 scale 只能平移、不能加宽，所以沿 K 每 32 或 16 个元素配一个 scale，离群值只坏自己那一块。

- **元素格式**：块 scale 把块最大值对到格式顶端，误差的大头在顶端往下几档，所以 4 位里多给尾数：E2M1 比 E3M0 准。
- **MX 对 NVFP4**：MXFP4 是 32 个一块、E8M0 的 2 的幂 scale，4.25 位，对不准 6；NVFP4 是 16 个一块、E4M3 scale 加每张量 FP32，4.5 位，能对准 6，但每张量 scale 只平移 E4M3 的 17.8 档窗口，块间跨度太大时小块的 scale 会下溢。
- **取 scale**：OCP 取 ⌊log₂ amax⌋ − 2，让块最大值落进 \[4, 8)，代价是尾数大于 1.5 时最大值截到 6；向上取整不截断，但小值更容易变 0。

**边界**：这些都是精度上的取舍；性能上 scale 乘在哪一步、怎样排，由硬件决定。

### 评分锚点

说出 FP4 窗口约 3.6 档，scale 只平移不加宽；说出元素格式多给尾数的理由：误差集中在顶端几档；对比 MXFP4 与 NVFP4 的块大小、scale 类型、位数与各自代价；说出 NVFP4 每张量 scale 只定位窗口这一边界；说出 OCP 向下取整的做法与截断代价

## 48. 面试官问：“讲讲块缩放矩阵乘在 B200 上怎么做，换到别的卡会怎样。”以 Triton 3.7.1 教程的 MXFP4 × MXFP4 kernel 为例，用约 60–90 秒讲清：scale 在哪一步乘、怎样排、怎样进到矩阵单元，以及搬到 RTX 5090 和没有块缩放指令的硬件上会怎样。

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：scale 沿 K 变，只能逐块乘；B200 的 tcgen05.mma 在指令内部乘块 scale，FP4 的算力全部保住，代价转到了 scale 的布局上。

- **怎样排**：tcgen05.mma 要求 scale 在 TMEM 里按 32 个 lane × 4 列排，一个 32 位格子装同一行相邻 4 个 K 块的 scale，所以主机端预排成 (M/128, K/V/4, 32, 4, 4)。
- **怎样进去**：TMA 把整块搬进 SMEM，一个线程发 tcgen05.cp 原样拷进 TMEM；kernel 里的 reshape、trans 只是 SMEM 描述符上的视图，不搬数据。
- **别的卡**：RTX 5090 的块缩放 mma.sync 从寄存器读 scale、累加器也在寄存器，要缩小分块；MI355X 的 scaled MFMA 从 VGPR 读、只认 E8M0；RTX 4090 没有块缩放指令，解码成 bf16、逐元素乘 scale 再用 bf16 张量核；MI300X 上两侧都带 scale 时编译失败。

**边界**：预排只关乎性能，不影响结果；只有一侧带 scale 或格式不受指令支持时，有块缩放指令的卡也会退回软件换算。

### 评分锚点

说出 scale 只能逐块乘，B200 在指令内乘；说出 TMEM 的排法与 5D 预排的对应；说出 TMA → SMEM → tcgen05.cp → TMEM 的路径，以及视图不搬数据；至少说出两种其他硬件的落地与代价

## 49. 请用约 60–90 秒向面试官讲清：在 MI300X 上用 Triton 3.7.1 跑 MoE，专家权重存 bf16，还是存 MXFP4、在 kernel 里解码后用 bf16 MFMA？解码与预填充各怎样判断快慢，怎样量化解码的开销，部署时最终选哪个？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：先拿计算强度和平衡点（约 123 次乘加/字节，字节计入激活、权重、scale 和输出）比，判断瓶颈；再算显存、MFMA、向量单元各自要忙多久，能重叠就取最长、不能就相加。

- **解码**：M 小，受访存限制，MXFP4 少读约 3.6 倍字节，最多快约 3.6 倍；前提是解码跟得上带宽，每个 FP4 的向量指令要在约 4 条以内。
- **预填充**：受计算限制，少读字节换不来时间，MXFP4 最多一样快；解码相对 MFMA 的比例是 16c / BLOCK\_M，与 M 无关，藏不住时慢约四成。
- **部署**：选 MXFP4：权重小约 3.8 倍，省下的显存给 KV cache，能服务更多请求；并发多了，每个专家的 M 也随之变大。

**边界**：每个专家只分到约 128 行时，MXFP4 正好落在平衡点附近，访存和计算都要考虑；BLOCK\_M 变小时解码代价会改变结论，最终要实测。

### 评分锚点

用平衡点判断解码与预填充的瓶颈，强度计入全部字节、单位一致；说出解码跟不跟得上带宽的量化判据；说出 16c/BLOCK\_M 与 M 无关；说出容量才是始终保留的好处

## 50. 请用约 60–90 秒向面试官讲清你在 RTX 5090 上做的一次受控测量：同一个 MXFP4 kernel 去掉 A 的 scale，迫使 Triton 3.7.1 走软件换算，和原生块缩放指令相比；N = K = 8192，M = 16 与 M = 8192 的结果是什么？怎样解释？你的预测错在哪里？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：原生在两种 M 下都更快：M = 16 快 1.57 倍，M = 8192 快 4.37 倍；计算受限时优势远大于访存受限时，但都不是预测的“比值约 1”和“峰值比 8”。

- **M = 16**：软件路径既没到带宽上限、也没到算力上限；SASS 显示它每个 warp 每个 K 步多发约 11 倍的指令，发射约 24.5 µs 加等数据 20.2 µs，接近实测 45.1 µs，说明 warp 太少、两部分几乎不重叠。
- **M = 8192**：比值 = 峰值比 × 效率比 = 8 × (47.6% ÷ 87.3%)：软件路径的解码藏在较慢的 BF16 张量核后面，原生路径只到 FP4 峰值的一半不到。
- **预测错在哪**：把 BLOCK\_M 当成解码的复用次数；实际解码在每个 warp 里做、A 也要解码，M = 16 时每个元素只参与 5.3 次乘加。

**边界**：原生 M = 8192 还有约 0.33 ms 分不出来源，要用 Nsight Compute、频率与功耗记录，或单测 OMMA 的小 kernel 来分辨；指令数估算没有 profiler 证实。

### 评分锚点

给出两个比值，并说出方向与预测的差别；说出 M = 16 的瓶颈：发射解码指令加等数据、重叠差；用峰值比 × 效率比解释 M = 8192；说出预测里复用次数的错误；说出剩余的不确定与分辨办法
