## 01. Triton 向量 kernel 用一组局部指针执行 tl.load，并用 mask 屏蔽尾块越界位置。返回 tensor 的 shape 由什么决定，false 位置会消失吗？

类型：真实纠错 · 层级：原子 · 等级：A

适用范围：triton · 3.7.1

### 场景

Triton 3.7.1；每个 program 用 offsets 生成一组元素地址，尾块只有部分地址有效。

### 正确

返回 shape 跟随该 program 的局部 pointer tensor；mask 为 false 的逻辑位置仍然保留。

### 错误

根据输入tensor的形状决定的

### 说明

**结论**：tl.load 逐位置处理传入的指针，因此返回值具有这组局部指针的形状；mask 只控制各位置是否读取内存。

- **局部形状**：例如 offsets 有 4 个位置，x\_ptr + offsets 就有 4 个指针。即使 mask 为 \[True, True, False, False\]，load 结果仍有 4 个位置，而不会缩成 2 个。
- **无效位置**：false 位置不从对应地址读数据；指定 other 时得到该替代值，未指定时不能假设其数值有效。

**边界**：整个 PyTorch 输入有多少元素、wrapper 为输出分配多大空间，都不是这次局部 load 的 shape 来源。

## 02. Triton kernel 先用 tl.load 的 mask 屏蔽尾块越界位置，再对加载结果做 sum 或 max 归约。为什么仍需处理无效位置的值，不能只依靠 load mask？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：load mask 保证无效地址不被读取，却不会把无效逻辑位置从结果 tensor 中删除；后续归约仍会合并这些位置的值。

- **问题如何产生**：假设四个局部位置只有前两个有效。load 后仍有四个值；若后两个未定义，直接对四个值求和或求最大值，就可能污染本来有效的归约结果。
- **归约前处理**：应在归约前把无效位置设置为适合该运算的值。例如求和用 0，使无效项不增加总和；求最大值可用负无穷，使它不竞争最大值。

**边界**：最后的 store mask 只能控制结果写到哪里，不能从已污染的归约结果中撤销无效项的影响。

### 锚点

屏蔽读取 → 位置仍在 → 归约仍用值

## 03. Triton 尾块只对满足数值条件的元素写回，例如只保存大于阈值的结果。tl.store 的 mask 应怎样组合，才能保证越界地址永远不被写入？

类型：真实纠错 · 层级：原子 · 等级：A

适用范围：triton · 3.7.1

### 场景

Triton 3.7.1；offsets 可能越过长度 N，boundary\_mask 表示 offsets &lt; N，condition 表示数值满足写回要求。

### 正确

使用 boundary\_mask &amp; condition；地址有效和数值符合条件必须同时成立。

### 错误

如果写的mask没有考虑边界，就必须要让other=-inf了

### 说明

**结论**：是否允许访问地址，应由边界条件直接决定；是否需要保存该值，再由业务条件决定。两者取逻辑与，才是完整的写回条件。

- **填充值的局限**：例如 load 对无效位置填负无穷，它可能刚好通不过“大于阈值”的判断。但若以后改为“小于阈值”，无效位置就可能通过条件。
- **稳定的保护**：即使填充值通过了 condition，boundary\_mask 在越界位置仍为 false，因此最终 store 不会访问非法地址。

**边界**：other 是未读取位置的替代数值，不是 tl.store 自动继承的边界保护；不能靠某个特殊数值恰好被过滤来保证安全。

**来源记录：** [已核验结构化日志：L01 向量运算、真实 mask 纠错与基础 Benchmark 复盘；不消费 raw 对话。](../../logs/2026-07-27-vector-add.md)

## 04. Triton kernel 对一个合法输出地址执行 tl.store，但该位置的 mask 为 false。这个位置会被写成零、写成未定义值，还是保留原值？

类型：技术问答 · 层级：原子 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：该位置不发生写入，输出内存中原来是什么值，就继续保留什么值。

- **具体例子**：假设写回前输出是 \[7, 8\]，待写入值是 \[1, 2\]，store mask 是 \[True, False\]，写回后输出为 \[1, 8\]。
- **与 load 的区别**：masked load 需要产生一个局部结果，因此要考虑 false 位置的替代值；masked store 控制的是写入副作用，false 位置没有“写入替代值”这一步。

**边界**：若输出缓冲区此前未初始化，保留原值也不代表得到可用结果；不能把“没有写”当作“已经写零”。

### 锚点

false → 无写入副作用

## 05. Triton 向量 kernel 将 BLOCK\_SIZE 声明为 tl.constexpr，并用它构造块内 offsets。是否必须在源码里永远写死一个值，还是不同 kernel launch 可以选择不同值？

类型：技术问答 · 层级：原子 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：不同 launch 可以选择不同的 BLOCK\_SIZE；tl.constexpr 要求的是某一次编译特化中的值固定，而不是整个程序生命周期都只能用一个值。

- **固定在哪里**：编译器在生成这一版本的 kernel 时，需要知道 BLOCK\_SIZE，才能确定块级表达式的形状和相关编译决策。
- **怎样变化**：Python wrapper 可以在本次 launch 传入 256，下次传入 512；两次调用分别使用与该取值相匹配的特化。

**边界**：不能让同一次正在执行的特化根据运行时 tensor 值改变 BLOCK\_SIZE。需要区分 launch 前选配置与 kernel 执行时改变常量。

### 锚点

特化内固定；launch 间可选

### 来源

Triton 3.7.1 · L01 日志：constexpr 的取值范围

**来源记录：** [已核验结构化日志：L01 向量运算、真实 mask 纠错与基础 Benchmark 复盘；不消费 raw 对话。](../../logs/2026-07-27-vector-add.md)

## 06. 启动 Triton 向量 kernel 时，program 数需要按输入长度和 BLOCK\_SIZE 计算。什么情况下应使用 lambda META: ... 形式的 callable grid，而不是提前算好的 tuple grid？

类型：技术问答 · 层级：原子 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：当 grid 依赖的配置要等 Triton 绑定本次 meta-parameters 后才确定时，用 callable grid 延后计算。

- **配置尚未确定**：例如 autotune 正在选择 BLOCK\_SIZE，grid 也必须跟随当前候选配置变化。callable grid 接收本次 META，再据此计算覆盖输入所需的 program 数。
- **配置已经确定**：如果 wrapper 已知道输入长度 N 和本次 BLOCK\_SIZE，就可以提前计算 triton.cdiv(N, BLOCK\_SIZE)，并作为 tuple grid 传入。

**边界**：输入长度每次不同，并不自动要求 callable grid；关键是计算 grid 所需的值在什么时候才能确定。

### 锚点

看配置何时确定

### 来源

Triton 3.7.1 · L01 日志：callable grid

## 07. 在 Triton 向量 kernel 中，tl.arange(0, BLOCK\_SIZE) 为一个 program 构造块内位置。BLOCK\_SIZE 是否就是这个 program 使用的 GPU 硬件线程数？

类型：技术问答 · 层级：原子 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：不是。这里 BLOCK\_SIZE 决定逻辑 block tensor 中有多少个元素位置，不能直接当成实际线程数量。

- **program 层**：一个 program instance 执行一份块级 kernel，对这些逻辑位置进行加载、运算和写回。
- **硬件层**：编译器再把块级操作映射到 GPU 的线程和 warp；逻辑元素的组织与硬件执行资源的组织是不同层次。

**边界**：例如 BLOCK\_SIZE=4 只说明 arange 产生四个逻辑位置，不能据此断言 GPU 启动了四个线程。

### 锚点

program → block tensor → threads/warps

Triton 3.7.1 · L01 日志：抽象层复述

## 08. 一个 Triton 一维向量 kernel 用 ptr + offsets 读取元素。若 wrapper 开始接受每隔一个元素取一次的切片等非连续输入，为什么仅删除连续性检查还不够？

类型：技术问答 · 层级：原子 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：ptr + offsets 默认相邻逻辑元素也位于相邻存储位置。非连续一维 view 的逻辑索引必须先乘以 stride，才能对应正确地址。

- **stride 的含义**：这里 stride 是相邻两个逻辑元素在底层存储中相隔的元素数，不是字节数。stride 为 2 时，逻辑位置 1 应读取基址之后的第 2 个元素位置。
- **地址计算**：kernel 需要接收该输入的 stride，并按 ptr + offsets \* stride 生成指针；否则仍会读取连续存储中的元素，得到错误数据。

**边界**：wrapper 的接口范围必须与 kernel 的地址实现一致。放宽校验只能允许数据进入，不能自动改变实际访存方式。

### 锚点

逻辑 offset × 存储 stride

### 来源

Triton 3.7.1 · L01 日志：连续性契约与地址计算

**来源记录：** [已核验结构化日志：L01 向量运算、真实 mask 纠错与基础 Benchmark 复盘；不消费 raw 对话。](../../logs/2026-07-27-vector-add.md)

## 09. 比较向量 kernel 的整块输入与稍长的尾块输入时，报告的“有效 GB/s”反而升高了。仅凭这个指标，能否认定 GPU 的实际 DRAM 带宽或 kernel 优化效果提高？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：不能。有效 GB/s 用算法规定的有效读写字节数除以测得耗时，指标升高可能只是工作量与测量时间的比值变化。

- **符号定义**：令 N\_exact、N\_tail 分别表示整块和尾块用例的有效元素数，t\_exact、t\_tail 表示测得耗时，G 表示有效 GB/s。两组用例每个元素计入相同有效字节数时，有如下关系。

$$
\frac{G_{\mathrm{tail}}}{G_{\mathrm{exact}}}=\frac{N_{\mathrm{tail}}}{N_{\mathrm{exact}}}\frac{t_{\mathrm{exact}}}{t_{\mathrm{tail}}}
$$

- **如何解读**：尾块用例多几个有效元素，而两次时间恰好相同，分子变大就会让有效 GB/s 上升；测量波动使尾块时间更短也会产生同样现象。

**边界**：有效字节数不是硬件实际传输的 DRAM 字节数。没有对应的受控测量或硬件证据，不能把比值上升直接解释为物理带宽增加或已证明的 GPU 优化。

### 锚点

有效字节 / 测量时间；不是硬件流量计数

### 来源

L01 日志：尾块有效 GB/s 复盘

## 10. 使用 Triton 3.7.1 的 triton.testing.do\_bench 测量一个很短的 GPU kernel，并设置 rep=100。这个 100 控制什么，是否会把一次 kernel 调用的计时间隔拉长到 100 ms？

类型：技术问答 · 层级：原子 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：rep=100 表示约 100 ms 的总采样预算，不表示某一次 kernel 调用要被连续计时 100 ms。

- **总预算**：增加预算主要是在整轮测量中投入更多采样时间；被测 kernel 每次执行原本有多短，并不会因此自动变长。
- **为什么要区分**：若担心单次 kernel 太短、测量分辨能力不足，仅增加总采样预算并不等于延长每一个计时间隔。

**边界**：把多次调用放进同一个计时窗口后再求平均，是另一种测量设计，不能与 rep 的含义混为一谈。

### 锚点

总预算 ≠ 单次间隔

## 11. GPU 向量 kernel 单次耗时很短。若改为在同一个窗口内连续调用多次，再用总时间除以调用次数，所得平均延迟能直接替代原来的单次调用测量吗？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：不能直接替代。它测得的是连续批量执行场景中的每次平均成本，执行条件可能已经不同于原来的单次调用。

- **为什么有帮助**：把多次执行合在一个窗口中，可以延长被测时间，减小极短窗口对观察结果的影响。
- **为什么不是同一指标**：连续调用可能改变缓存状态、调用间间隔和发射方式。总时间除以次数会把这些批量场景的效果一起平均进去。

**边界**：应分别说明两种结果的测量方式和适用场景。批量结果更平滑，不等于它天然就是原单次指标的更精确版本。

### 锚点

窗口变长，也可能换了被测场景

## 12. 一项 GPU 尾块性能实验事先规定：延迟变化超过 5% 就判为不支持原预测。数据触发了该条件，之后才发现 5% 可能小于当前计时方法可分辨的变化。应怎样报告原实验结论？

类型：技术问答 · 层级：原子 · 等级：A

### 答案

**结论**：仍应按事先约定报告“原反证条件被触发”，并另行说明测量方法的限制；不能事后改标准，把同一结果重新称为支持原预测。

- **保留原判定**：事前标准记录了原本准备用什么数据判断预测。看到结果后放宽标准，会失去这次检验的可追溯性。
- **收紧实际结论**：阈值小于可分辨变化，说明现有测量可能不足以支持可靠的物理性能判断。因此要同时报告原规则下的结果与这个方法局限。
- **改进后续实验**：重新设计更适合测量能力的标准与计时方法，再用新实验检验预测；新标准用于新的检验。

**边界**：保留原判定不等于已经证实某个 GPU 机制，也不要求把受分辨率限制的数据解释得过于确定。

### 锚点

原规则判定；新发现改下一次

## 13. Triton 向量 kernel 的尾块用 mask 关闭越界位置的 tl.load/tl.store。为什么这些位置没有访存：GPU 先访问再消除结果，还是从执行条件上就不访问？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：访存从一开始就是有条件的：对应 predicate 为 false 时，该逻辑位置不会执行所指定地址的读取或写入。

- **执行条件**：在已核验的这份 kernel 中，底层 load/store 带有谓词条件。false 位置不是“先无条件访问，再由优化器撤销”，而是访存条件不成立。
- **物理事务**：其他有效位置的请求仍按 GPU 的内存事务粒度合并和传输。因此屏蔽了几个逻辑位置，并不意味着实际 DRAM 流量必定减少同样数量的字节。

**边界**：生成地址、计算谓词及调度这个 program 仍可能有成本。mask 关闭访存，不代表尾块没有执行开销。

### 锚点

条件访存 ≠ 事后优化；有效字节 ≠ 物理事务

## 14. 一个 Triton 向量 kernel 的最后一块只有部分位置有效，加载结果还可能参与归约，最终按条件写回。请用约 60 秒说明：mask 对局部形状、归约正确性和写回安全各负责什么？

类型：综合口述 · 层级：口述 · 等级：B

适用范围：triton · 3.7.1

### 参考回答

**结论**：mask 逐位置控制访存，但局部 tensor 仍保留固定形状；要保证整条计算链正确，还必须分别处理归约中的无效值和写回时的地址边界。

- **形状与读取**：load 的结果形状跟随该 program 的局部 pointer tensor。false 位置不读取对应地址，却仍占一个逻辑位置，不能当作已经被删除。
- **归约**：归约会合并保留下来的位置。应先为无效项提供不影响该归约的值；store mask 无法修复此前已经被污染的归约结果。
- **写回**：有条件写回时，把地址有效的 boundary\_mask 与数值条件 condition 取逻辑与。对于合法目标地址，false store 不写入，也不会自动写零。

**边界**：false predicate 禁止相应地址访问，但 program 仍可能执行地址计算和调度；有效访问仍受内存事务粒度影响，不能把 mask 当作零开销保证。

### 评分锚点

局部 pointer 形状；false lane 读取语义；归约前处理无效值；boundary 与 condition；不等于零开销

## 15. 比较 GPU 向量 kernel 的整块与尾块输入时，延迟差异很小，有效 GB/s 还出现反向变化。请用约 60 秒说明：从指标定义、采样口径和事前判据出发，怎样避免过度解释这组结果？

类型：综合口述 · 层级：口述 · 等级：B

适用范围：triton · 3.7.1

### 参考回答

**结论**：先明确比较的是哪种测量场景，再拆开有效工作量与耗时，最后按事前规则报告结果，并限制对 GPU 优化的因果推断。

- **指标**：有效 GB/s 是算法规定的有效读写字节数除以测量时间；尾块工作量稍增或测得时间稍降，都可能使该比值上升，不能直接证明实际 DRAM 带宽提升。
- **采样**：do\_bench 的 rep 指整轮采样预算。增加预算不等于把每次短 kernel 的计时间隔拉长。
- **批量口径**：把多次调用合在一个窗口后求平均，可以延长窗口，但可能改变缓存和发射条件；它与单次调用结果应分别解释。
- **判据**：即使后来发现阈值不适合计时分辨率，也要保留事前规则下的判定，再说明方法局限并改进下一次实验。

**边界**：现有证据只能支持与其测量设计相匹配的结论；没有受控证据时，不把微小波动写成已证明的 GPU 优化机制。

### 评分锚点

有效 GB/s 的分子分母；总预算与单次间隔；批量场景变化；保留事前判据；有边界的因果结论
