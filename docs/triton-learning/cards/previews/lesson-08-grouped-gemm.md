## 01. 要在一块 GPU 上算一组尺寸不同的矩阵乘法，例如 MoE 层里各专家收到的 token 数不同。有三种做法：逐个调用矩阵乘 kernel；把小矩阵补零到同一形状后用 batched 接口；用 grouped GEMM 一次发射。三种做法各把资源浪费在哪里？grouped 为此付出了什么？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：grouped 只发射一次，也不补齐：所有问题的块合成一份任务，小问题的块填进大问题留下的空档。代价是 kernel 要在设备上自己找任务，而且整组只能共用一套块大小。

- **逐个调用**：同一个 CUDA 流里的 kernel 按提交顺序串行执行。小问题的块数比 SM 少时，这次调用里大部分 SM 闲着，后面的问题也不能提前开始；每次发射还有一笔与矩阵大小无关的固定开销。
- **补齐**：batched 接口要求形状相同，只能把小矩阵补零到最大的形状。补的零不影响结果，但照样要算：边长 1024、512、256、128 的四个方阵补齐后，约 71% 的乘加在算零。
- **grouped 的代价**：每个 CTA 要扫描问题表才能找到自己的块；调度只均分块数，各问题 K 不同时工作量不均衡。

**边界**：它适合数量多、规模小、K 相近的问题；问题很少、每个都大到能占满所有 SM 时，逐个调用就够了。

### 锚点

串行的流让 SM 闲置；补齐在算零；grouped 要在设备上找任务

## 02. Triton kernel 的参数个数在编译时就固定了，而 grouped GEMM 要处理的矩阵个数 G 运行时才知道。Triton 3.7.1 的官方教程怎样把一组矩阵交给 kernel？这种交法让 kernel 和编译器失去了哪些信息？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：把每个矩阵的首地址当成 64 位整数存进设备上的张量，kernel 运行时读出整数再转成指针；尺寸和行步长也各存一张表。

- **主机侧**：地址表是 int64 的 \[G\]，每项是 tensor.data_ptr()；尺寸表和行步长表是 int32 的 \[G, 3\]，按行展平。行步长就是 stride(0)，行内步长被假定为 1。
- **kernel 侧**：tl.load 读出整数后 .to(tl.pointer_type(tl.float16))，相当于 C 里从 int64_t table\[G\] 取值再强转成 half\*。
- **丢掉的类型**：指针的元素类型写死在 kernel 里。传入 fp32 的矩阵不会报错，只是把内存按 fp16 解读。
- **丢掉的对齐**：张量直接当参数传入时，Triton 在发射时按首地址是否为 16 的倍数做特化；从表里读出的地址没有这一步，对齐只能靠 kernel 里写保证。

**边界**：地址表不持有原张量的引用，原张量被释放后地址就悬空；类型、对齐和生命周期都只能由包装函数来保证。

### 锚点

data_ptr 存进 int64 表再转成指针；丢类型、丢对齐、不管生命周期

## 03. MoE 层里，按专家排好的 token 堆成一个矩阵 X，每个专家的行数不同。PyTorch 2.13 的 grouped_mm(X, W, offs) 用一张偏移表描述各组，Triton 教程的 grouped GEMM 用每组一个地址的地址表。两种表是什么关系？它们分别由谁、在哪里生成，这为什么重要？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：pytorch · 2.13.0

### 答案

**结论**：偏移表是地址表的特例：各组首尾相接放在同一个张量里时，第 g 组的地址 = 基地址 + 起始行 × 每行字节数。到 kernel 这一层两边用的是同一种表，差别在表由谁、在哪里生成。

- **PyTorch**：offs 是设备上的张量。快速路径先在设备上跑一个小 kernel，从 offs 算出每组的地址和行数，全程不把行数读回主机。
- **教程**：包装函数在主机上逐个读矩阵的地址、形状和步长，拼成列表再拷到设备，前提是主机已经知道每组的行数。
- **为什么重要**：每个专家收到多少 token 是 GPU 上的路由算出来的。主机要知道它就得读回，读回会让主机等 GPU 把排队的工作全部做完。
- **能表达的尺寸**：偏移表一次只有一个维度参差；地址表里每个问题的三个维度都可以不同。

**边界**：PyTorch 2.13 的快速路径只在 sm_90 或 sm_100、且输入输出都是 bf16 时启用；其余情况退回为把 offs 拷回主机、逐组调用普通矩阵乘。

### 锚点

地址 = 基地址 + 起始行 × 每行字节数；行数留在设备上

## 04. Triton 教程的 grouped GEMM kernel 只发射固定的 NUM_SM 个 CTA，主机不做任何任务分配。每个 CTA 怎样知道自己该算哪些块？这条规则保证了什么，不保证什么？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：把所有问题的块首尾相接排成一条队列，第 p 个 CTA 处理第 p、p+NUM_SM、p+2·NUM_SM…… 号块；每个 CTA 用各问题块数的前缀和，判断手里的编号落在哪个问题里。

- **扫描**：编号只增不减，问题又按顺序走，所以对问题表顺序走一遍就够；同一个问题里连续领到多块时，用内层循环处理。
- **保证**：各 CTA 领到的块数最多差 1。
- **不保证**：一块的工作量正比于它的 K 循环次数。边长 1024、512、256、128 的四个方阵、块 128×128×32、84 个 CTA 时，最忙的 CTA 做 36 次 K 循环，最闲的只做 8 次，而整个 kernel 的耗时由最忙的那个决定。
- **NUM_SM**：它实际是 CTA 的个数，不必等于物理 SM 数；比总块数还大时，多出来的 CTA 扫一遍什么都领不到。

**边界**：各问题的 K 相同时每块工作量相同，这条规则天然均衡；MoE 层就是这种情况。

### 锚点

队列、步长 NUM_SM、前缀和；均分块数，不均分工作量

## 05. grouped GEMM 用静态的步长调度。把块从 128×128 缩小到 64×64 后，各 CTA 的工作量更均衡了。这是否意味着更快？以边长 1024、512、256、128 的四个 fp16 方阵、84 个 CTA 为例，说明缩小块换来什么、付出什么。

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：不一定。总耗时大致是最忙的 CTA 的工作量乘以做单位工作的耗时：缩小块压低前者，却抬高后者。

- **收益有限**：换算成同一单位后，最忙的 CTA 从 36 降到 33，只少 8%；即使完全均衡，也只能降到平均值。
- **访存翻倍**：每次乘加摊到的读入量是 1/BN + 1/BM，从 1/64 变成 1/32；整组累计读入从 38.3 MB 变成 76.7 MB。
- **固定开销**：块数变多，而每一块都要读地址和行步长、清零累加器、写回结果，这些不随块缩小而等比减少。
- **小块的好处**：每个 CTA 占的寄存器和共享内存减半，一个 SM 能同时驻留更多 CTA。

**边界**：最终要靠实测：教程把块大小交给 autotune，PyTorch 的 grouped_mm 默认用大块，平均行数或列数不超过 128 时才换小块。上面的数字来自调度模型和编译产物，不是 GPU 计时。

### 锚点

耗时 ≈ 最忙 CTA 的工作量 × 单位工作耗时

## 06. grouped GEMM 按块给 CTA 分配任务。各问题的 K 相差很大时，块数分得再均匀，CTA 的工作量也不均衡。根本原因是什么？有哪两种不缩小块的改进办法，各自的代价是什么？

## 07. grouped GEMM 的每个 CTA 都要先找出手里的块编号属于哪个问题。Triton 教程用顺序扫描。当问题很多时，例如 256 个专家、每个专家 4 块、128 个 CTA，这种扫描的开销有多大？CUTLASS 3.9.2 用了哪两种办法降低它？

## 08. Triton 教程的 grouped GEMM kernel 去掉了所有 mask，假定每个问题的 M、N、K 都是块大小的整数倍。矩阵连续存放时，如果 M、N、K 分别不是整数倍，各会发生什么？哪一种最难被与参考结果比较的测试发现？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：地址公式是 首地址 + 行 × 行步长 + 列，没有任何一步检查下标：列号超出会绕到下一行的开头，行号超出会落到矩阵末尾之后。三个方向的后果因此各不相同。

- **M 不整**：有效的行全部算对，但多出来的行照样被写出去，落在 C 之后。逐个比较结果能通过，被写坏的是排在 C 后面的别的张量，所以最难发现。
- **N 不整**：最后一块多出的列绕到下一行的开头，那里的正确值由另一块负责，两个 CTA 竞争写同一个地址，结果可能每次运行都不一样。
- **K 不整**：最后一轮多读的部分里，A 读到的是下一行开头的真实数据，B 读到的是 B 之后的内存，所有输出都可能出错。

**边界**：B 之后的内存恰好是 0 时，K 不整的结果会碰巧全对，测试出现假通过。真实设备上的越界读写是未定义行为，以上是按地址运算推出的结果。

### 锚点

M：写到 C 之后；N：绕行加竞争写；K：读到别处的数据

## 09. 一个 GPU kernel 可能越界读，也可能越界写，但把它的输出和参考实现逐个比较却全部通过。怎样设计测试，让越界读和越界写都必然暴露？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：把输入和输出都嵌进更大的缓冲区：输入四周填 NaN，输出四周填一个哨兵值，再把矩阵本身的视图交给被测函数。

- **越界写**：运行后检查输出四周的保护区是否仍然全是哨兵值。
- **越界读**：界外读到的 NaN 只要影响到有效结果，结果就变成 NaN；不这样做，界外恰好是 0 时测试会假通过。
- **保护区的大小**：每一侧至少留一整块。块是 128 行而矩阵只有 1 行时，越界可以达到 127 行。
- **对接口的要求**：被测函数必须能接收调用方提供的输出张量；视图的行步长大于列数，所以实现里的行步长要取真实的 stride(0)。

**边界**：保护区测试要排在普通数值测试之前，让越界写先在保护区里被报告出来。

### 锚点

输入填 NaN，输出填哨兵值，保护区至少一整块

## 10. Triton 3.7.1 教程的 grouped GEMM kernel 里，矩阵的指针是运行时从地址表读出来的，随后有一句 tl.multiple_of(a_ptrs, \[16, 16\])。这一句是什么性质的语句？为什么把张量直接当参数的普通 kernel 不用写？去掉它，K 循环里的数据搬运会怎样变化？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：它是一句不被检查的对齐保证，相当于 C 里的 \_\_builtin_assume_aligned：编译器据此才使用一次搬 16 字节的异步拷贝。

- **为什么要写**：张量当参数传入时，Triton 在发射前检查首地址并自动打上对齐标记；从地址表读出的指针，编译器对它一无所知。
- **去掉以后**：退回每次只搬 2 字节的普通读；一次搬的宽度不到 4 字节时 Triton 不做流水，所以连边搬边算也一起失去。
- **按指针生效**：保证只作用在写了这一句的指针上。只删掉 B 的那一句时，A 仍用 16 字节的异步拷贝，B 改为逐个元素同步读入。

**边界**：保证成立需要首地址和行步长的字节数都是 16 的倍数。不成立时编译器照样生成 16 字节的指令，这是未定义行为，没有任何报错；不写保证则没有这种风险，只是慢。

### 锚点

不被检查的保证；16 字节异步拷贝的前提

### 来源

Grouped GEMM 学习记录 10-09 · 不被检查的保证；16 字节异步拷贝的前提

## 11. 一个 fp16 矩阵首地址是 16 的倍数，但每行有 100 个元素，即行步长 200 字节。为什么 tl.multiple_of(ptrs, \[16, 16\]) 对它不成立？想继续用异步拷贝，应该怎样写保证？换成 TMA 描述符可以吗？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：对齐的要求落在每一条拷贝指令上。第 m 行的行首是 首地址 + m × 200 字节，奇数行余 8，不是 16 的倍数；但它们都是 8 的倍数，所以应当如实保证 8。

- **降档**：异步拷贝一次可以搬 4、8 或 16 字节。写成 tl.multiple_of(ptrs, \[8, 8\]) 后，编译器改用 8 字节的异步拷贝，指令数是 16 字节时的两倍，流水仍然保留。
- **各档对比**：同一个 K 循环在 sm_89 上：保证 16 是 24 条异步拷贝，保证 8 是 48 条，保证 4 是 96 条；不写保证是 64 条 2 字节的普通读，没有流水。
- **TMA**：TMA 没有 8 字节的模式。行步长不是 16 字节倍数的矩阵不能直接交给它，只能先改变数据的摆放。

**边界**：保证必须如实：能保证多少写多少。写大了是未定义行为，编译器和运行时都不会拦。

### 锚点

行首 = 首地址 + m × 行步长；异步拷贝可降档，TMA 不行

## 13. Triton 3.7.1 教程的描述符版 grouped GEMM 在 sm_90 上用 TMA 搬数据。块超出矩阵边界时，它和指针版的处理有什么不同？它解除了指针版的哪个限制，又带来哪些新的要求？在没有 TMA 的设备上它会变成什么？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：描述符带着矩阵的真实形状，硬件知道哪些元素在界外：读的时候补 0，写的时候不写。所以描述符版不再要求尺寸是块的整数倍，限制换成了对齐。

- **对齐**：行步长的字节数必须是 16 的倍数，而且没有降档的余地。
- **现场创建**：形状来自设备上的尺寸表，描述符只能在设备上现场创建；每个 CTA 需要 768 字节的全局暂存区，所以发射前必须先调用 triton.set_allocator。

**边界**：描述符只描述一块已经存在的内存，创建时不搬数据、不补齐；对齐和存放顺序必须在调用前就已经满足。

### 锚点

## 14. PyTorch 2.13 的 grouped_mm 遇到行步长不是 16 字节倍数的输入会直接报错；而它自己分配的输出却悄悄把行步长补宽，例如形状 \[768, 500\] 的输出，相邻两行相隔 504 个元素。同样是不满足对齐，为什么对输入和输出区别对待？

类型：技术问答 · 层级：机制 · 等级：B

适用范围：pytorch · 2.13.0

### 答案

**结论**：输出还没有数据，补齐只是分配时多留一点空间，不发生拷贝；输入的行步长是既成事实，要改只能把数据拷贝一遍。

- **输出**：多分配再切片即可，不必补零。描述符里的形状仍写 500，只把行步长写宽，硬件就只写每行的前 500 列。
- **输入**：要新开一块行步长更宽的缓冲区再拷过去。可以只加宽行步长、逻辑上的列数不变，这样不必补零，但拷贝躲不开。
- **为什么报错**：替调用方悄悄拷贝会把代价藏起来，grouped 相对逐组调用的优势可能就此消失；报错让调用方自己决定何时拷贝。

**边界**：这里要求的是行步长对齐，不是连续：补宽了行步长的输出在 PyTorch 里反而是不连续的张量。

### 锚点

输出：分配时留宽；输入：只能拷贝

## 15. Triton 教程的描述符版 grouped GEMM 要求 B 按 \[N, K\] 存放。准备数据时写的是 B.T.contiguous()，kernel 里又写了 tl.dot(a, b.T)。这两处转置各自有没有移动数据？只把 B.T 这个视图交给 kernel 为什么不行？

类型：技术问答 · 层级：机制 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：主机侧那一次真的拷贝重排了内存，kernel 里那一次不搬任何数据。

- **视图**：B.T 和 B 是同一块内存，只是换了读法：\[3, 2\] 的 B 转置后步长变成 (1, 2)，行内不再连续。
- **拷贝**：.contiguous() 才新开一块内存，按 \[N, K\] 的行优先顺序把数据排好。
- **kernel 里的 b.T**：它作用在已经搬进共享内存的一块上，编译产物里只是给这一块贴上转置的标记，矩阵乘指令按这个顺序去读。

**边界**：PyTorch 线性层的权重本来就按 \[输出维, 输入维\] 存，也就是 \[N, K\]，真实系统里通常不需要这次拷贝。

### 锚点

B.T 是视图，.contiguous() 才拷贝，kernel 里的 b.T 只改标记

## 17. 要让 grouped GEMM 的 kernel 支持任意行数 M，读 A 时必须加 mask。有两种写法：只判断这一行是否存在；或者 M、N、K 三个方向都判断。在 Triton 3.7.1 里，这两种写法对 K 循环里的 16 字节异步拷贝各有什么影响？原因是什么？什么场景下第一种就够？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：只有行方向的 mask 时，16 字节的异步拷贝保持不变；三个方向都加 mask 后，异步拷贝消失，退回逐个元素的读。

- **原因**：一条拷贝指令搬的是同一行里连续的 8 个元素，只能整段跳过。行方向的 mask 对一段里的 8 个元素取值相同；N、K 方向的 mask 可能只挡住一段的一部分，整段跳过就不够用了。
- **编译结果**：在 sm_89 和 sm_90 上，没有 mask 和只有行 mask 都是 24 条 16 字节的异步拷贝；三个方向都有 mask 时没有异步拷贝，只有 64 条 2 字节的读。
- **够用的场景**：各问题的 N、K 都是块大小的整数倍、只有行数参差时，行方向的 mask 就够了，MoE 层正是这样。

**边界**：够用的条件是 N、K 整块，不是 N、K 为 8 的倍数：后者管的是对齐，是另一件事。

### 锚点

一段 8 个元素只能整段跳过；行 mask 保住异步拷贝

## 24. grouped GEMM 的静态步长调度在各问题 K 相差很大时不均衡。要设计一个谁空谁领的动态方案：需要什么共享状态？每个 CTA 怎样领下一块？

### 场景

第 08 课综合验收的设计题，可以使用原子操作。

### 正确

显存里放一个整数计数器，含义是下一个没人领的块编号，发射前清零。每个 CTA 空闲时做一次原子的读出旧值并加 1，读到的旧值就是它领到的块；旧值超过总块数就退出。

## 25. PyTorch 2.13 的 grouped_mm 在不满足快速路径条件的设备上走回退路径。相对一次发射的 grouped GEMM，回退路径的代价有哪些？

类型：真实纠错 · 层级：原子 · 等级：A

适用范围：pytorch · 2.13.0

### 场景

第 08 课综合验收的迁移题：一个没有 TMA、也没有异步拷贝的新后端，对 grouped_mm 什么都不做。

### 正确

三项：逐组调用带来的多次发射；小问题占不满 SM；以及回退要先把偏移表拷回主机，这会造成一次同步，打断异步执行。

### 错误

代价就是多次调用的发射开销和SM资源无法充分利用

### 说明

**结论**：漏掉的是同步：各组的行数在设备上，而回退是在主机上逐组循环，循环之前必须把偏移表读回来。

- **同步的含义**：读回设备上的张量时，主机要等 GPU 把排在前面的工作全部做完才能继续。
- **快速路径的做法**：在设备上用一个小 kernel 从偏移表算出每组的地址和行数，全程不读回。

**边界**：所以给新后端做适配时，让行数留在设备上应当排在搬运方式之前；否则一次发射省下的时间会被这次同步吃掉。

## 26. x 是 \[总行数, K\] 的 fp16 张量，各组的行在 x 里首尾相接。要在设备上建一张 int64 的地址表，第 g 项是第 g 组第一行的地址：以 x.data_ptr() 为基础，加上的偏移量应该怎样算？

类型：真实纠错 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 场景

第 08 课练习的无提示变式：堆叠接口。首版的结果里前面的行正确，中间的行被写错，最后的行从未被写入。

### 正确

偏移量 = 起始行 × 行步长（元素）× 元素大小（字节），例如 offs\[:-1\].to(torch.int64) \* x.stride(0) \* x.element_size()。

### 错误

group_a_ptrs\[1:\] += offs\[:-1\] \* stride_x

### 说明

**结论**：data_ptr() 返回的是按字节计的整数。主机侧没有带类型的指针，给它加 n 就是前进 n 个字节。

- **两种单位**：kernel 里把整数转成 fp16 指针之后，加 n 才是前进 n 个元素。所以交给 kernel 的行步长用元素作单位，而地址表里的偏移必须换算成字节。
- **现象**：偏移少乘了 2，后面各组的地址落在一半行号的位置：它们覆盖了前面组已经算对的行，而输出末尾的行没有任何一组去写。
- **列表接口为什么没事**：把每组切成视图再取 data_ptr() 时，PyTorch 已经替调用方加上了以字节计的偏移。

**边界**：单位信息并不是在把地址存进张量时丢掉的，它在主机侧从来就不存在。

## 27. 偏移表 offs 是设备上的 int32 张量，记录各组的结束行。x 有 262,144 行，每行 7168 个 fp16 元素。要在设备上算每组起始行的字节偏移，应该怎样写才不会出错？

类型：真实纠错 · 层级：原子 · 等级：A

适用范围：pytorch · 2.13.0

### 场景

第 08 课练习里的预测题：堆叠接口修好之后，把规模换成 DeepSeek-V3 的输入维。

### 正确

接口上的 offs 保持 int32；计算时先在设备上把它转成 int64，再乘行步长和元素大小。

### 错误

所以这个offs还是设int64应该更稳妥一些

## 30. 一个用了 tl.multiple_of 的 Triton kernel，它的包装函数检查输入的 dtype、行内连续性和 16 字节对齐。这几项检查里，哪一项即使被删掉，数值测试也无法稳定发现？这类检查应该怎样测？

适用范围：triton · 3.7.1

对齐检查。它只能用参数测试覆盖：构造不对齐的输入，断言包装函数抛出 ValueError。

## 31. 指针版 grouped GEMM 的 kernel 只对 A、B 的指针调用了 tl.multiple_of，写回 C 用带 mask 的 tl.store。调用方提供的输出张量首地址对齐、行内连续，但行步长是 200 字节，不是 16 的倍数。包装函数应该拒绝它吗？

不应该拒绝。kernel 对 C 没有任何对齐假定：C 由逐个元素的 2 字节写指令写回，不受行步长影响。

## 32. 请用约 60–90 秒向面试官讲清：Triton 官方教程的 grouped GEMM kernel 怎样用一次发射算完一组尺寸不同的矩阵乘法？它相对逐个调用换来了什么、付出了什么？教程的实现有什么边界？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：把每个问题按同样的块大小切开，所有块首尾相接排成一条队列，只发射一次、固定数量的 CTA，每个 CTA 按步长领块；换来的是只付一次发射开销、小问题也能把 SM 填满。

- **怎样交给 kernel**：矩阵个数运行时才知道，所以矩阵不是参数：地址、尺寸和行步长都存在设备上的表里，kernel 读出整数再转成指针。

说出块排成队列、固定数量的 CTA 按步长领取；说明矩阵经设备上的地址表、尺寸表和行步长表交给 kernel；说出两项收益：一次发射、小问题也能填满 SM；至少说出两项代价：扫描、共用块大小、工作量不均；指出满块假定这一边界和真实 MoE 的处理办法

## 33. 请用约 60–90 秒回答面试官：一个 Triton kernel 的指针是运行时从地址表读出来的。要让它把数据从显存搬进共享内存时既快又不出错，对齐保证、异步拷贝和 TMA 描述符各起什么作用，各自在什么条件下失效？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：编译器知道得越多，搬得越快：不知道是否对齐时每次只搬 2 字节，有了对齐保证就用 16 字节的异步拷贝并做流水，有了描述符就整块交给硬件。

- **对齐保证**：tl.multiple_of 是不被检查的保证。它要求首地址和行步长的字节数都是 16 的倍数；不成立时是未定义行为，没有报错。
- **降档**：行步长只是 8 或 4 字节的倍数时，可以如实把保证降到 8 或 4，指令变多但流水还在；TMA 没有这个余地。
- **mask 的影响**：只加行方向的 mask 不影响异步拷贝；N、K 方向也加 mask 后退回逐个元素的读。
- **TMA**：描述符带着真实形状，界外的读补 0、界外不写，不再要求整块；但要对齐、要全局暂存区，没有 TMA 的设备上会被改写成指针加 mask。

**边界**：异步拷贝只有读这一个方向，写回显存的异步搬运只有 TMA 才有。

### 评分锚点

说明 tl.multiple_of 是不被检查的保证，以及它成立的两个条件；说出保证可以如实降到 8 或 4，而 TMA 不能降档；说明行方向的 mask 保住异步拷贝，三个方向的 mask 不行；说明描述符怎样处理界外，以及没有 TMA 时的回退；指出保证不成立是未定义行为，不会报错

## 34. 请用约 60–90 秒回答面试官：你写了一个从地址表取矩阵的 grouped GEMM kernel。它对输入有哪些假定？这些假定由谁来保证？你怎样测试它，哪些错误是数值测试测不出来的？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：kernel 只拿到表里的整数，自己验证不了任何假定，所以全部由包装函数检查；测试要同时覆盖数值、越界和参数检查三类。

- **假定与检查**：dtype、行内连续、同一设备、A 和 B 的对齐，每项检查对应 kernel 的一条假定；没有假定的检查，例如对输出的对齐检查，只会拒绝本来能处理的输入。
- **漏掉的后果**：漏掉检查通常不报错：类型不对时结果是 NaN，行内不连续时读到错位的数据，都是静默的。
- **越界**：只比较结果发现不了越界写。把输入嵌进 NaN、输出嵌进哨兵值的缓冲区，四周各留一整块。
- **测试的盲区**：对齐保证不成立是未定义行为，结果可能碰巧正确，只能用断言抛出 ValueError 的参数测试覆盖。

**边界**：测试输入还要变换特殊情形的位置：整组共用的标志如果只按最后一个问题来定，特殊问题排在前面时才会出错。

### 评分锚点
