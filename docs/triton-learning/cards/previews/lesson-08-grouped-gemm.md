## 01. 要在一块 GPU 上算一组尺寸不同的矩阵乘法，例如 MoE 层里各专家收到的 token 数不同。有三种做法：逐个调用矩阵乘 kernel；把小矩阵补零到同一形状后用 batched 接口；用 grouped GEMM 一次发射。三种做法各把资源浪费在哪里？grouped 为此付出了什么？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：逐个调用浪费的是闲着的 SM 和一次次的发射开销，补齐浪费的是算零的乘加；grouped 只发射一次、也不补齐，把所有问题的块合成一份任务，小问题的块填进大问题留下的空档。

- **逐个调用**：同一个 CUDA 流里的 kernel 按提交顺序串行执行。小问题的块数比 SM 少时，这次调用里大部分 SM 闲着，后面的问题也不能提前开始；每次发射还有一笔与矩阵大小无关的固定开销。
- **补齐**：batched 接口要求形状相同，只能把小矩阵补零到最大的形状。补的零不影响结果，但照样要算：边长 1024、512、256、128 的四个方阵补齐到 1024 后，约 71% 的乘加在算零。
- **grouped 的代价**：共三项：每个 CTA 要在设备上扫描问题表，才能找到自己的块；整组只能共用一套块大小；调度只均分块数，各问题 K 不同时工作量不均衡。

**边界**：它适合数量多、规模小、K 相近的问题；问题很少、每个都大到能占满所有 SM 时，逐个调用就够了。

### 锚点

逐个调用闲置 SM、多次发射；补齐在算零；grouped 要扫描、共用块大小、只均分块数

## 02. Triton kernel 的参数个数在编译时就固定了，而 grouped GEMM 要处理的矩阵个数 G 运行时才知道。Triton 3.7.1 的官方教程怎样把一组矩阵交给 kernel？这种交法让 kernel 和编译器失去了哪些信息？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：把每个矩阵的首地址当成 64 位整数存进设备上的张量，kernel 运行时读出整数再转成指针；尺寸和行步长也各存一张表。一个张量进了表就只剩一个整数，它的元素类型、对齐和生命周期信息都随之丢失。

- **主机侧**：地址表是 int64 的 \[G\]，每项是 tensor.data\_ptr()；尺寸表和行步长表是 \[G, 3\]，按行展平。行步长就是 stride(0)，行内步长被假定为 1。
- **kernel 侧**：tl.load 读出整数后 .to(tl.pointer\_type(tl.float16))，相当于 C 里从 int64\_t table\[G\] 取值再强转成 half\*。
- **丢掉的信息**：类型：指针的元素类型写死在 kernel 里，传入别的 dtype 不会被发现；对齐：编译器不知道读出的地址是不是 16 的倍数；生命周期：表不持有原张量的引用，原张量释放后地址就悬空。

**边界**：这些信息只能由包装函数在建表之前检查和保证。

### 锚点

data\_ptr 存进 int64 表再转成指针；丢类型、丢对齐、不管生命周期

## 03. MoE 层里，按专家排好的 token 堆成一个矩阵 X，每个专家的行数不同。PyTorch 2.13 的 grouped\_mm(X, W, offs) 用一张偏移表 offs 描述各组，Triton 教程的 grouped GEMM 用每组一个地址的地址表。两种表是什么关系，这层关系为什么让 PyTorch 不必把各组的行数读回主机？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：pytorch · 2.13.0

### 答案

**结论**：偏移表是地址表的特例：各组首尾相接放在同一个张量里，第 g 组的地址 = 基地址 + 起始行 × 每行字节数。地址表因此可以在设备上直接从 offs 算出来，行数不必回到主机。

- **例子**：3 个专家、X 为 \[768, 1024\] 的 fp16、offs=\[256, 384, 768\]：三组 A 的地址是 X 的首地址加 0、524288、786432 字节，和教程包装函数从三个切片得到的地址表完全一样。
- **PyTorch**：offs 是设备上的张量。快速路径先在设备上跑一个小 kernel，从 offs 算出每组的地址，全程不读回，源码注释是 “fast path, no d2h sync needed”；不满足快速路径条件时，回退路径会把 offs 拷回主机。
- **教程**：包装函数在主机上读形状、拼列表再建表，前提是主机已经知道每组的行数；这是包装函数的写法，不是 kernel 的限制。
- **为什么重要**：每个专家收到多少 token 是 GPU 上的路由算出来的。主机要知道就得读回，读回会让主机等 GPU 把排队的工作全部做完，即一次同步。

**边界**：偏移表一次只能让一个维度参差，其余两维由堆叠的权重统一规定；地址表里每个问题的三个维度都可以不同。

### 锚点

地址 = 基地址 + 起始行 × 每行字节数；行数留在设备上

## 04. Triton 3.7.1 官方教程的 grouped GEMM kernel 只发射固定的 NUM\_SM 个 CTA，主机不做任何任务分配。每个 CTA 怎样知道自己该算哪些块？这条规则保证了什么，不保证什么？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：把所有问题的块首尾相接排成一条队列，第 p 个 CTA 处理第 p、p+NUM\_SM、p+2·NUM\_SM…… 号块；每个 CTA 用各问题块数的前缀和，判断手里的编号落在哪个问题里。

- **扫描**：编号只增不减，问题又按顺序走，所以对问题表顺序走一遍就够；同一个问题里连续领到多块时，用内层循环处理。
- **保证**：各 CTA 领到的块数最多差 1。
- **不保证**：一块的工作量正比于它的 K 循环次数。边长 1024、512、256、128 的四个方阵、块 128×128×32、84 个 CTA 时，最忙的 CTA 做 36 次 K 循环，最闲的只做 8 次，而整个 kernel 的耗时由最忙的那个决定。

**边界**：各问题的 K 相同时每块工作量相同，只剩块数除不尽带来的最多一块的差距；MoE 层就是这种情况。

### 锚点

队列、步长 NUM\_SM、前缀和；均分块数，不均分工作量

## 05. Triton 3.7.1 教程的 grouped GEMM 用静态的步长调度，各问题 K 不同时 CTA 的工作量不均衡。把块从 128×128 缩小到 64×64，能让工作量更均衡。这是否意味着更快？请从总耗时由什么决定出发，说明缩小块换来什么、付出什么。

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：不一定。总耗时大致是最忙的 CTA 的工作量乘以做单位工作的耗时：缩小块压低前者，却抬高后者。

- **收益有限**：再均衡，最忙的 CTA 也只能降到平均值。教程示例组（边长 1024、512、256、128 的四个方阵，84 个 CTA）里，换算成同一单位后最忙的 CTA 只从 36 降到 33，约少 8%；这些数字是示意，不必背。
- **访存翻倍**：每次乘加摊到的读入量是 1/BM + 1/BN，从 1/64 变成 1/32，读入的总字节数翻倍。
- **固定开销**：块数变成原来的 4 倍，每领一块都要再读一次地址和行步长，这部分开销按块数计。
- **小块的好处**：每个 CTA 占的寄存器和共享内存减少，一个 SM 能同时驻留更多 CTA。

**边界**：最终要靠实测：教程把块大小交给 autotune；PyTorch 2.13 的 grouped\_mm 默认用大块，平均行数或列数不超过 128 时才换小块。示例数字来自调度模型，不是 GPU 计时。

### 锚点

耗时 ≈ 最忙 CTA 的工作量 × 单位工作耗时

## 06. grouped GEMM 的静态调度只均分块数，而一块必须由同一个 CTA 做完；各问题的 K 相差很大时，CTA 的工作量就不均衡。在 CUTLASS 3.9.2 里，有哪两种不缩小块的改进办法，各自靠什么改善均衡？

## 07. grouped GEMM 的每个 CTA 都要先找出手里的块编号属于哪个问题，Triton 教程的做法是逐个问题顺序扫描。问题很多时，例如 256 个专家、每个专家 4 块、128 个 CTA，每个 CTA 要扫描多少步？CUTLASS 3.9.2 有哪两种机制不需要这样逐个问题地扫描？

类型：技术问答 · 层级：机制 · 等级：B

适用范围：cutlass · 3.9.2

### 答案

**结论**：扫描的总步数是 CTA 数乘以问题数，和块的计算量无关：这个例子里每个 CTA 要走 256 步，只为领 8 块，连一块都领不到的 CTA 也要走完全表。

- **主机预计算**：另一种模式（kHostPrecompute）由主机把每个 CTA 依次做哪一块算成表，设备上不再扫描。

**边界**：说 CUTLASS 是为了降低扫描开销才这样设计，是从设计反推的，CUTLASS 没有这样写。

## 08. Triton 3.7.1 教程的 grouped GEMM kernel 去掉了所有 mask，假定每个问题的 M、N、K 都是块大小的整数倍。矩阵连续存放时，如果 M、N、K 分别不是整数倍，各会发生什么？哪一种最难被与参考结果比较的测试发现？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：地址公式是 首地址 + 行 × 行步长 + 列，没有任何一步检查下标：列号超出会绕到下一行的开头，行号超出会落到矩阵末尾之后。三个方向的后果因此各不相同。

- **M 不整**：有效的行全部算对，但多出来的行照样被写出去，落在 C 之后。逐个比较结果能通过，被写坏的是排在 C 后面的别的张量，所以最难发现。
- **N 不整**：最后一块多出的列绕到下一行的开头，那里的正确值由另一块负责，两个 CTA 竞争写同一个地址，结果可能每次运行都不一样。
- **K 不整**：最后一轮多读的部分里，A 读到的是下一行开头的真实数据，B 读到的是 B 之后的内存，所有输出都可能出错。

**边界**：B 之后的内存恰好是 0 时，K 不整的结果会碰巧全对，测试出现假通过。真实设备上的越界读写是未定义行为，以上是按地址运算推出的结果。

### 锚点

M：写到 C 之后；N：绕行加竞争写；K：读到别处的数据

## 09. 一个 GPU kernel 可能越界读，也可能越界写，但把它的输出和参考实现逐个比较却全部通过。怎样设计测试，才能可靠地暴露越界写，以及影响到结果的越界读？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：把输入和输出都嵌进更大的缓冲区：输入四周填 NaN，输出四周填一个哨兵值，再把矩阵本身的视图交给被测函数。

- **越界写**：运行后检查输出四周的保护区是否仍然全是哨兵值。
- **越界读**：界外读到的 NaN 只要影响到有效结果，结果就变成 NaN；不这样做，界外恰好是 0 时测试会假通过。
- **保护区的大小**：每一侧至少留一整块。块是 128 行而矩阵只有 1 行时，越界可以达到 127 行。
- **对接口的要求**：被测函数必须能接收调用方提供的输出张量，行步长也要取真实的 stride(0)：\[4, 100\] 的张量取 \[:, :64\] 后形状是 (4, 64)、步长是 (100, 1)，用列数代替行步长不会报错，只会读写错位。

**边界**：越界超出了保护区，或者越界写入的值恰好等于哨兵值时，这种测试会漏报。

### 锚点

输入填 NaN，输出填哨兵值，保护区至少一整块

## 10. Triton 3.7.1 教程的 grouped GEMM kernel 从地址表读出矩阵指针后，写了一句 tl.multiple\_of(a\_ptrs, \[16, 16\])；把张量直接当参数传入的普通 kernel 不用写这一句。这一句起什么作用？为什么从表里读出的指针需要它，直接传入的张量却不需要？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：它是一句不被检查的对齐保证，相当于 C 里的 \_\_builtin\_assume\_aligned：告诉编译器这些地址是 16 的倍数，编译器据此才用一次搬 16 字节的异步拷贝。

- **为什么要写**：张量当参数传入时，Triton 在发射前检查首地址是否为 16 的倍数，并按结果特化 kernel；从地址表读出的只是整数，编译器对它的对齐一无所知。
- **去掉以后**：退回每次只搬 2 字节的普通读；一次搬的宽度不到 4 字节时 Triton 不做流水，所以连边搬边算也一起失去。

**边界**：编译器和运行时都不检查这项保证。保证不成立属未定义行为：H100 上实测（Triton 3.7.1 与 3.8.0），首地址偏 2 字节或奇数行偏 8 字节都报 misaligned address，此后整个进程的 CUDA 都不能再用；其他后端未实测。不写保证就没有这种风险，只是慢。

### 锚点

不被检查的保证；16 字节异步拷贝的前提

## 11. 在 Triton 3.7.1（NVIDIA GPU）中，一个 fp16 矩阵首地址是 16 的倍数，但每行有 100 个元素，即行步长 200 字节。想让 K 循环继续用异步拷贝，tl.multiple\_of 最多能如实写成多少，为什么？换成 TMA 描述符搬这个矩阵，又会怎样？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：最多如实写 8。对齐的要求落在每一条拷贝指令上：第 m 行的行首是 首地址 + m × 200 字节，奇数行除以 16 余 8，但所有行首都是 8 的倍数。TMA 没有 8 字节这一档，不能直接搬它。

- **降档**：异步拷贝一次可以搬 4、8 或 16 字节。写成 tl.multiple\_of(ptrs, \[8, 8\]) 后，编译器改用 8 字节的异步拷贝：每条搬的字节减半、条数翻倍，流水仍然保留；不写保证则退回每次 2 字节的普通读，没有流水。
- **TMA**：描述符要求行步长的字节数是 16 的倍数，没有降档的余地；行步长 200 字节的矩阵只能先改变数据的摆放，例如拷进一块行步长加宽的缓冲区。

**边界**：保证必须如实：能保证多少写多少，写大了就是未定义行为。

### 锚点

行首 = 首地址 + m × 行步长；异步拷贝可降档，TMA 不行

## 13. Triton 3.7.1 教程的描述符版 grouped GEMM 在 sm\_90 上用 TMA 搬数据。块超出矩阵边界时，它怎样处理界外的元素？这让它摆脱了指针版的哪个限制，又换来了哪些新要求？

## 14. PyTorch 2.13 的 grouped\_mm 遇到行步长不是 16 字节倍数的输入会直接报错；而它自己分配的输出却悄悄把行步长补宽，例如形状 \[768, 500\] 的输出，相邻两行相隔 504 个元素。同样是不满足对齐，为什么对输入和输出区别对待？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：pytorch · 2.13.0

### 答案

**结论**：输出还没有数据，补齐只是分配时多留一点空间，不发生拷贝；输入的行步长是既成事实，要改只能把数据拷贝一遍。

- **输出**：多分配再切片即可，不必补零。描述符里的形状仍写 500，只把行步长写宽，硬件就只写每行的前 500 列。
- **输入**：要新开一块行步长更宽的缓冲区再拷过去。可以只加宽行步长、逻辑上的列数不变，这样不必补零，但拷贝躲不开。
- **为什么报错**：悄悄拷贝的代价会藏在调用里，可能抵消 grouped 相对逐组调用的优势；报错把是否拷贝、何时拷贝留给调用方决定。

**边界**：“为什么报错”是从行为反推的设计理由，没有核对 PyTorch 的设计说明；能确认的是行为本身：未对齐的输入被拒绝，输出由它自己补宽行步长。

### 锚点

输出：分配时留宽；输入：只能拷贝

## 15. Triton 3.7.1 教程的描述符版 grouped GEMM 要求 B 按 \[N, K\] 存放。准备数据时写的是 B.T.contiguous()，kernel 里又写了 tl.dot(a, b.T)。这两处转置各自有没有移动数据？只把 B.T 这个视图交给 kernel 为什么不行？

类型：技术问答 · 层级：机制 · 等级：B

适用范围：triton · 3.7.1

### 答案

**结论**：主机侧那一次真的拷贝重排了内存，kernel 里那一次不搬任何数据。

- **主机侧**：B.T 只是视图，和 B 是同一块内存，只换了读法：\[3, 2\] 的 B 转置后步长变成 (1, 2)，行内不再连续；.contiguous() 才新开一块内存，按 \[N, K\] 的行优先顺序把数据排好。
- **kernel 里的 b.T**：它作用在已经搬进共享内存的一块上；编译产物里只是给这一块贴上 transposed = true 的标签，不搬数据。
- **视图为什么不行**：包装函数只传首地址和 stride(0)，视图的 stride(0) 是 1；描述符要求最后一维连续；TMA 把数据原样搬进共享内存，不会重排。

**边界**：PyTorch 线性层的权重本来就按 \[输出维, 输入维\] 存，也就是 \[N, K\]，真实系统里通常不需要这次拷贝。

### 锚点

B.T 是视图，.contiguous() 才拷贝，kernel 里的 b.T 只改标记

## 17. 要让 grouped GEMM 的 kernel 支持任意行数 M，读 A 时必须加 mask；kernel 里各问题的 M、N、K 都是运行时从尺寸表读出的。有两种写法：只判断这一行是否存在；或者 M、N、K 三个方向都判断。在 Triton 3.7.1（NVIDIA GPU）里，这两种写法对 K 循环里的 16 字节异步拷贝各有什么影响，为什么？什么场景下第一种就够？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：只有行方向的 mask 时，16 字节的异步拷贝保持不变；三个方向都加 mask 后，异步拷贝消失，退回每次 2 字节的普通读，也没有流水。

- **宽度规则**：Triton 把一段连续元素合成一条拷贝，宽度取“指针连续且对齐的长度”和“mask 沿连续方向保持不变的长度”中较小的那个；每条拷贝只看一个 mask 位，要么整段拷，要么整段跳过补 0。这是 Triton 的规则，cp.async 指令本身可以只拷一段的一部分。
- **三向 mask**：N、K 是从表里读出的运行时值，编译器推不出 N、K 方向的 mask 能在几个元素内保持不变，只能按 1 个元素算：宽度 2 字节，不到 cp.async 最小的 4 字节。行方向的 mask 在一行里处处相同，不限制宽度。
- **够用的场景**：各问题的 N、K 都是块大小的整数倍、只有行数参差时，行方向的 mask 就够了，MoE 层正是这样。

**边界**：够用的条件是 N、K 整块，不是 N、K 为 8 的倍数：后者管的是对齐，是另一件事。

### 锚点

宽度取指针对齐与 mask 恒定长度的较小者；行 mask 保住异步拷贝

## 18. 要用 Triton 3.7.1 给一个没有 TMA、也没有异步拷贝指令的新加速器后端写 grouped GEMM。照搬官方教程的指针版和描述符版，哪些部分可以原样沿用，哪些取决于这个后端？应该优先保证哪些性质？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：调度、地址表和行方向的 mask 与后端无关，可以原样沿用；变的是数据搬运：两个版本都只能同步搬运，而描述符版能不能直接用，取决于这个后端的编译器会不会把描述符改写成指针加 mask。

先保 M 方向正确和行数不回主机，再谈搬运方式

## 19. 在 Triton 3.7.1 中，grouped GEMM 的 kernel 只收到五张整数表：三张地址表、一张尺寸表、一张行步长表。如果包装函数漏掉了对 dtype、行内连续性或 num\_sm 的检查，会发生什么？这说明检查应该放在哪里、依据什么来定？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 答案

**结论**：包装函数是最后一个能做检查的地方：张量进了表只剩首地址、M、N、K 和行步长，kernel 验证不了 dtype、连续性、设备和对齐，漏掉检查时通常不报错，而是照着假定继续算。所以每项检查都应当对应 kernel 的一条假定。

- **dtype**：把 fp32 的 A 交给按 fp16 读的 kernel：结果含 NaN，没有异常。
- **行内连续**：把每隔一列取一个元素的视图交进去：kernel 仍按相邻的列去读，绝大部分元素不对，没有异常。
- **num\_sm**：取 0 或负数时一个 CTA 都不发射，输出从未被写入，也没有异常。
- **少数例外**：块大小取 48，或 K 方向的块取 8 时，编译才会报错。

**边界**：没有对应假定的检查只会拒绝本来能正确处理的输入。上面的现象是在 CPU 解释器上删去检查后实测的。

### 锚点

包装函数是最后的检查点；检查漏掉时静默算错；每项检查对应一条假定

## 20. 在 Triton 3.7.1 的 kernel 里，p 是从地址表读出并转成指针的标量。在 K 循环里写 p = p + 行偏移\[:, None\] \* 行步长 + 列偏移\[None, :\]，想把它就地变成一块指针。这样写会怎样？就算类型一致，这种写法还有什么问题？

类型：技术问答 · 层级：原子 · 等级：B

适用范围：triton · 3.7.1

**结论**：编译报错：跨迭代传递的变量类型必须保持不变，而这里它从标量指针变成了一块指针。

- **报错信息**：Loop-carried variable … has initial type pointer<fp16> but is re-assigned to <\[…\], pointer<fp16>> in loop。

## 21. Triton 3.7.1 教程的描述符版 grouped GEMM 在 sm\_90 上用 TMA 写回结果，而且只发射固定数量的 CTA，每个 CTA 循环领取多块。与每块一个 CTA 的写法相比，这种结构给写回带来了什么机会？

适用范围：triton · 3.7.1

**结论**：第 i 块的写回可以和第 i+1 块的计算重叠：发起写回后不等它完成，直接去领下一块。每块一个 CTA 时，这个 CTA 写完就结束了，自己没有下一块可以和写回重叠。

## 23. grouped GEMM 的包装函数要为整组问题选一个特化标志：只有每个问题的 N、K 都是块大小的整数倍时，才能选只加行方向 mask 的快路径。首版在遍历问题的循环结束后，用循环变量里剩下的 N、K 来判断；验收测试里有含不整块问题的混合组，却全部通过。为什么没测出来？测试输入应该怎样设计？

类型：技术问答 · 层级：机制 · 等级：B

### 答案

**结论**：因为原有的混合组里，不整块的问题恰好都排在最后：循环结束后残留的正是它的 N、K，标志碰巧选对了。测试要把特殊问题分别放在最前、中间和最后。

- **正确写法**：标志由整组共同决定：遍历所有问题，只要有一个问题的 N 或 K 不是整块，就选三个方向都加 mask 的通用路径。

**边界**：一个量由整组共同决定时，测试都要变换特殊元素的位置；特殊元素只放在末尾，会漏掉“只看最后一个”这类错误。

## 26. Triton 3.7.1 教程的描述符版 grouped GEMM 用 TMA 读写 A、B、C，要求每个矩阵的行步长字节数都是 16 的倍数，并要求 B 按转置后的 \[N, K\] 存放。MoE 层的输出维 N=500、输入维 K=1024，数据是 fp16。A、B、C 中哪个矩阵不满足要求？

类型：真实纠错 · 层级：原子 · 等级：B

适用范围：triton · 3.7.1

## 27. grouped GEMM 的静态步长调度在各问题 K 相差很大时不均衡。要设计一个谁空谁领的动态方案：需要什么共享状态？每个 CTA 怎样领下一块？

类型：真实纠错 · 层级：机制 · 等级：A

### 场景

允许使用原子操作。

### 正确

显存里放一个整数计数器，含义是下一个没人领的块编号，发射前清零。每个 CTA 空闲时做一次原子的读出旧值并加 1，读到的旧值就是它领到的块；旧值不小于总块数就退出。

### 错误

需要添加一个关于每个子任务是否已被领取的program间共享状态标记

### 说明

**结论**：一个计数器就把找和抢合成了一步：读出旧值并加 1 是不可分割的，两个 CTA 读到的旧值一定不同。

- **标记方案的代价**：每块一个标记，发射前要逐个清零，领取时要搜索哪个还空着，多个 CTA 抢同一个标记时输的还要重试。

- **延伸**：计数器只增不减，同一个 CTA 先后领到的编号一定递增，所以它仍然只需顺序走一遍问题表。

**边界**：一次领多块可以减少原子操作，但均衡变粗：调度模型里一次领 16 块比静态分配还差，因为成批领到的块来自同一个问题。各块工作量相同时，动态领取没有收益。

## 28. PyTorch 2.13 的 grouped\_mm 在不满足快速路径条件的设备上走回退路径。相对一次发射的 grouped GEMM，回退路径的代价有哪些？

类型：真实纠错 · 层级：原子 · 等级：A

适用范围：pytorch · 2.13.0

### 场景

一个没有 TMA、也没有异步拷贝的新后端，对 grouped\_mm 什么都不做。

### 正确

三项：逐组调用带来的多次发射；小问题占不满 SM；以及回退要先把偏移表拷回主机，这会造成一次同步，打断异步执行。

### 错误

代价就是多次调用的发射开销和SM资源无法充分利用

### 说明

**结论**：漏掉的是同步：各组的行数在设备上，而回退是在主机上逐组循环，循环之前必须把偏移表读回来。

- **同步的含义**：读回设备上的张量时，主机要等 GPU 把排在前面的工作全部做完才能继续。
- **快速路径的做法**：在设备上用一个小 kernel 从偏移表算出每组的地址和行数，全程不读回。

**边界**：快速路径只在 sm\_90 或 sm\_100、且输入输出都是 bf16 时启用，其余情况都走这条回退路径。

## 29. 用 Triton 3.7.1 写堆叠接口时，x 是 \[总行数, K\] 的 fp16 张量，各组的行在 x 里首尾相接。要在设备上建一张 int64 的地址表，第 g 项是第 g 组第一行的地址：以 x.data\_ptr() 为基础，加上的偏移量应该怎样算？

类型：真实纠错 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 场景

堆叠接口的首版：输出里前面的行正确，中间的行被写错，最后的行从未被写入。

### 正确

偏移量 = 起始行 × 行步长（元素）× 元素大小（字节），例如 offs\[:-1\].to(torch.int64) \* x.stride(0) \* x.element\_size()。

### 错误

group\_a\_ptrs\[1:\] += offs\[:-1\] \* stride\_x

### 说明

**结论**：data\_ptr() 返回的是按字节计的整数。主机侧没有带类型的指针，给它加 n 就是前进 n 个字节。

- **两种单位**：kernel 里把整数转成 fp16 指针之后，加 n 才是前进 n 个元素。所以交给 kernel 的行步长用元素作单位，而地址表里的偏移必须换算成字节。
- **现象**：偏移少乘了 2，后面各组的地址落在一半行号的位置：它们覆盖了前面组已经算对的行，而输出末尾的行没有任何一组去写。
- **列表接口为什么没事**：把每组切成视图再取 data\_ptr() 时，PyTorch 已经替调用方加上了以字节计的偏移。

**边界**：单位信息并不是在把地址存进张量时丢掉的，它在主机侧从来就不存在。

## 30. 在 PyTorch 2.13 里，堆叠接口要在设备上按偏移表算各组第一行的字节偏移。接口规定 offs 是设备上的 int32 张量，记录各组的结束行，与 PyTorch grouped\_mm 的约定一致；x 有 262,144 行，每行 7168 个 fp16 元素。溢出会发生在哪一步？不改接口，应该怎样写？

类型：真实纠错 · 层级：原子 · 等级：A

适用范围：pytorch · 2.13.0

### 场景

把规模换成 DeepSeek-V3 的输入维 7168 时。

### 正确

溢出发生在乘法：起始行 × 行步长 × 元素大小的乘积超出了 int32。接口上的 offs 保持 int32，计算时先在设备上把它转成 int64，再乘行步长和元素大小。

### 错误

所以这个offs还是设int64应该更稳妥一些

### 说明

**结论**：判断溢出和列出的算式都对，错在修法：溢出的是乘积，不是 offs。行号最大 262,144，远小于 int32 的上限；而从第 261,120 行开始的一组（例如最后 1024 行那一组），字节偏移是 261,120 × 7168 × 2 = 3,743,416,320，已经超过上限。

- **不会报错**：PyTorch 的 int32 张量乘 Python 整数，结果仍是 int32，溢出后悄悄回绕；这个例子会得到 −551,550,976。
- **为什么不改接口**：偏移表本身不需要更宽的类型；PyTorch 的 grouped\_mm 要求的也是 int32，int64 的偏移表会被它的输入检查拒绝。
- **PyTorch 的做法**：它在设备侧的 C++ 代码里把 offs 和 int64 的步长相乘，C++ 先把 offs 提升到 int64 再乘。

**边界**：在设备上做类型转换不算把 offs 读回主机。

## 32. Triton 3.7.1 中，一个用了 tl.multiple\_of 的 kernel，它的包装函数检查输入的 dtype、维数、行内连续性和 16 字节对齐。这几项检查里，哪一项即使被删掉，数值测试也无法稳定发现？这类检查应该怎样测？

类型：真实纠错 · 层级：机制 · 等级：A

适用范围：triton · 3.7.1

### 场景

逐项分析删掉某项检查后，哪些测试还能发现问题。

### 正确

对齐检查。违反 tl.multiple\_of 的保证属未定义行为，结果取决于设备，不是数值比较能稳定发现的；只能用参数测试覆盖：构造不对齐的输入，断言包装函数在发射前抛出 ValueError。

### 错误

选了维数检查：“如果多出来的维度全是1，可能也不会有异常，因为也相当于原本的形状。这可能会导致数值测试也无法稳定发现。”

### 说明

**结论**：错在选了维数检查：去掉它，代码行为不变，\[1, 64, 64\] 这样的输入仍被后面的行内连续检查拦住、抛出 ValueError，没有被数值掩盖的隐患。

- **对齐为什么特殊**：编译器和运行时都不检查 tl.multiple\_of 的保证。保证不成立时，kernel 请求的字节和解释方式都不变，被违反的只是异步拷贝指令的前提：属未定义行为。H100 上实测（Triton 3.7.1 与 3.8.0）直接报 misaligned address，而且此后整个进程的 CUDA 都不能再用，测试会话跟着中断；其他后端未实测。
- **和另外两项的区别**：dtype 和行内连续性出错时，改变的是读到哪些字节、怎样解释它们，每次运行、每台设备都错成同一个样子，随机数据必然暴露。
- **解释器看不到**：Triton 的 CPU 解释器完全忽略这个保证，行步长 200 字节的输入算出来和 torch.matmul 一致。

**边界**：说删掉对齐检查“可能会报错”并不算错：H100 上确实报错。问题在于结果取决于设备，CPU 解释器上照样算对，不能把报错当作检查。

说明输入为什么不能像输出那样靠多分配来解决时。

### 正确

要求的是行步长（相邻两行的间隔）的字节数是 16 的倍数，不是整个张量连续。

### 错误

但是对于grouped\_mm的输入矩阵描述符版，则必须要连续化

### 说明

**结论**：错在把对齐说成了连续：对齐条件看的是相邻两行相隔多少字节，和张量是否连续无关。

- **连续也可能不满足**：K=1020 的 fp16 输入连续存放时，每行 2040 字节，不是 16 的倍数；连续化之后仍不满足。
- **不连续也可能满足**：grouped\_mm 自己分配的 \[768, 500\] 输出，相邻两行相隔 504 个元素、每行只用 500 列，在 PyTorch 里是不连续的张量，行步长却是 1008 字节，正好满足这条对齐要求。

**边界**：所以输入不满足时，要拷进一块行步长加宽到 16 字节倍数的缓冲区；.contiguous() 只在每行字节数本来就是 16 的倍数时才顺带满足要求。

## 35. 请用约 60–90 秒向面试官讲清：Triton 3.7.1 官方教程的 grouped GEMM kernel 怎样用一次发射算完一组尺寸不同的矩阵乘法？它相对逐个调用换来了什么、付出了什么？教程的实现有什么边界？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：把每个问题按同样的块大小切开，所有块首尾相接排成一条队列，只发射一次、固定数量的 CTA，每个 CTA 按步长领块；换来的是只付一次发射开销、小问题也能把 SM 填满。

- **怎样交给 kernel**：矩阵个数运行时才知道，所以矩阵不是参数：地址、尺寸和行步长都存在设备上的表里，kernel 读出整数再转成指针。
- **怎样领任务**：第 p 个 CTA 处理第 p、p+NUM\_SM…… 号块，用各问题块数的前缀和找到这一块属于哪个问题。
- **代价**：每个 CTA 要扫描问题表；整组共用一种块大小；调度只均分块数，各问题 K 不同时工作量不均衡。
- **教程的假定**：教程假定尺寸都是块的整数倍，不满足时会越界读写；真实的 MoE 只有行数参差，要补的主要是 M 方向的不满块。

**边界**：它适合数量多、规模小、K 相近的问题；问题很少且每个都能占满所有 SM 时，逐个调用就够了。

### 评分锚点

说出块排成队列、固定数量的 CTA 按步长领取；说明矩阵经设备上的地址表、尺寸表和行步长表交给 kernel；说出两项收益：一次发射、小问题也能填满 SM；至少说出两项代价：扫描、共用块大小、工作量不均；指出满块假定这一边界，以及真实 MoE 里只有行数参差

## 36. 请用约 60–90 秒回答面试官：在 Triton 3.7.1 的 NVIDIA 后端上，一个 kernel 的指针是运行时从地址表读出来的。要让它把数据从显存搬进共享内存时既快又不出错，对齐保证、异步拷贝和 TMA 描述符各起什么作用，各自在什么条件下失效？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：编译器知道得越多，搬得越快：不知道是否对齐时每次只搬 2 字节，有了对齐保证就用 16 字节的异步拷贝并做流水，有了描述符就整块交给硬件。

- **对齐保证**：tl.multiple\_of 是不被检查的保证，要求首地址和每一行的行首都是 16 字节的倍数；不成立属未定义行为：H100 上实测直接报 misaligned address，进程的 CUDA 随之不能再用，其他后端未实测。
- **降档**：行步长只是 8 或 4 字节的倍数时，可以如实把保证降到 8 或 4，条数变多但流水还在；TMA 没有这个余地。
- **mask 的影响**：只加行方向的 mask 不影响异步拷贝；N、K 方向也加 mask 后，编译器推不出 mask 在一段里保持不变，退回逐个元素的读。
- **TMA**：描述符带着真实形状，界外读补 0、界外不写，不再要求整块；但行步长必须 16 字节对齐，设备端现场创建还要全局暂存区。

**边界**：异步拷贝只有读这一个方向，写回显存的异步搬运只有 TMA 才有。

### 评分锚点

说明 tl.multiple\_of 是不被检查的保证，以及它要求每一行行首都对齐；说出保证可以如实降到 8 或 4，而 TMA 不能降档；说明行方向的 mask 保住异步拷贝，三个方向的 mask 不行；说明描述符怎样处理界外，以及它换来的对齐和暂存要求；指出保证不成立属未定义行为：H100 上实测报错且进程不能再用，其他后端未实测，不能把它当作检查

## 37. 请用约 60–90 秒回答面试官：你用 Triton 3.7.1 写了一个从地址表取矩阵的 grouped GEMM kernel。它对输入有哪些假定？这些假定由谁来保证？你怎样测试它，哪些错误是数值测试测不出来的？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：triton · 3.7.1

### 参考回答

**结论**：kernel 只拿到表里的整数，自己验证不了任何假定，所以全部由包装函数检查；测试要同时覆盖数值、越界和参数检查三类。

- **假定与检查**：dtype、行内连续、A 和 B 的对齐，每项检查对应 kernel 的一条假定；没有假定的检查，例如对输出的对齐检查，只会拒绝本来能处理的输入。
- **漏掉的后果**：漏掉检查通常不报错：类型不对时结果含 NaN，行内不连续时读到错位的数据，都是静默的。
- **越界**：只比较结果发现不了越界写。把输入嵌进 NaN、输出嵌进哨兵值的缓冲区，四周各留一整块。
- **测试的盲区**：对齐保证不成立是未定义行为：CPU 解释器上照样算对，H100 上直接报 misaligned address 并让进程的 CUDA 不能再用，所以只能用断言抛出 ValueError 的参数测试覆盖。

**边界**：测试输入还要变换特殊情形的位置：整组共用的标志如果只按最后一个问题来定，特殊问题排在前面时才会出错。

### 评分锚点

说明 kernel 只见到整数表，假定必须由包装函数检查；列举至少三项检查及其对应的假定；说明保护区测试怎样暴露越界读和越界写；指出对齐检查无法由数值测试发现，并说明原因；说出一条测试设计的教训，例如变换特殊输入的位置
