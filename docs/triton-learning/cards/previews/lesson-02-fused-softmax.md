## 01. Triton 按行计算 softmax 时，通常把一行的有效列补到较大的块宽度。假设有效输入非空且全部有限，为什么 tl.load 对超出有效列数的位置应填负无穷，而不能随意填零？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：负无穷不会改变有效元素的最大值，并且在减去行最大值、取指数后变成 0，从而既不影响 max，也不增加 softmax 的归一化分母。

- **先求最大值**：令 m 为有效输入的行最大值。额外的负无穷位置不会超过任何有限有效值，因此整块求 max 仍得到 m；若填零，在有效值全为负数时就会改变最大值。
- **再取指数求和**：padding 的负无穷减去有限 m 后仍为负无穷，取 exp 得 0。把它们加入指数和，对分母没有贡献；零填充则可能产生额外正贡献。
- **最终输出**：只有有效列的位置需要写回；padding 只是为块级计算补齐形状，不是 softmax 输入中新增的有效元素。

**边界**：上述推导要求有至少一个有效元素且有效输入有限。整行均为负无穷等情形可能遇到未定义运算，需要另行规定语义。

### 锚点

max 中不竞争 → exp 后为 0

## 02. 本课的 softmax 接口接收形状 \[M, N\] 的矩阵，其中 M 是行数，N 是每行参与 softmax 的列数。为什么约定 M=0 且 N&gt;0 可返回空结果，而 N=0 要拒绝？

类型：技术问答 · 层级：原子 · 等级：B

适用范围：programming-lab triton lesson02 · 2026-08-07 learning baseline

### 答案

**结论**：没有输入行，与有一个空的行内归约维度，是两种接口情况。本练习允许前者，明确拒绝后者。

- **没有行**：M=0 且 N&gt;0 表示没有需要处理的样本行，可以返回相同形状的空结果，不必执行任何行的 max 或 sum。
- **没有列**：N=0 表示每行没有参与 softmax 的元素，行最大值与归一化分母没有本练习所要求的有效计算域，因此 wrapper 直接拒绝该输入。

**边界**：这是 Triton Lesson 02 学习实现的接口约定；不能据此断言所有深度学习框架都会以同样方式处理空形状。

### 锚点

没有行 ≠ 行内归约域为空

## 03. 测试按行计算的 softmax kernel 时，假设每行非空且有效输入都为有限值，我们希望检查“每行元素之和接近 1”这一不变量。应该对输入矩阵 X 还是输出矩阵 Y 求行和，为什么？

类型：技术问答 · 层级：原子 · 等级：B

### 答案

**结论**：应检查输出 Y 的每行之和接近 1。softmax 把一行输入变成归一化权重，约束属于归一化后的输出，而不属于原始输入。

- **输入没有此约束**：输入可以是任意有限分数。例如输入行 \[2, 3\] 的和为 5，并不影响它成为合法的 softmax 输入。
- **输出为何归一化**：每个输出都是该位置的指数值除以整行指数和。将所有输出相加，分子合起来就是同一个分母，所以数学上的结果为 1。

**边界**：浮点结果按合理容差比较。仅通过行和检查仍不足以证明每个输出正确，还应与可靠 reference 逐元素对照。

### 锚点

归一化约束属于输出

## 04. Triton persistent softmax 中，一个 program 会在行循环里依次处理多行。该循环 tl.range(..., num\_stages=s) 的 num\_stages 描述什么流水范围，能把 s 理解成 s 个独立 worker 吗？

类型：技术问答 · 层级：原子 · 等级：A

适用范围：programming-lab triton lesson02 · 2026-08-07 learning baseline

### 答案

**结论**：不能。这里 num\_stages 为同一个 program 内不同循环迭代的在途与重叠提供机会，实际如何调度由编译器决定。

- **迭代是什么**：一次迭代计算一行 softmax。存在多次迭代时，编译器可以尝试让不同迭代中可独立推进的工作重叠。
- **依赖仍存在**：对于同一行，加载后才能求最大值，再计算指数、指数和、归一化和写回。这些依赖不会因为 num\_stages 变大而消失。

**边界**：stage 不是独立 program 或 worker，也不表示把一行机械切成 s 段并行处理；这里讨论的特定作用域是行循环的跨迭代流水。

### 锚点

同 program · 跨迭代 · 编译器安排

## 05. 对同一个 GPU kernel，增加软件流水深度后，若编译结果显示每个 program 使用更多寄存器或共享内存，这种资源变化为什么可能减少每个 SM 的并行驻留数量？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：每个 SM 的资源总量有限；一个 program 占用更多受限资源时，SM 能同时容纳的 program 数可能减少。

- **驻留的含义**：驻留是 program 的执行状态与资源已经放在该 SM 上，能够等待或参与调度；它描述的是同时容纳多少份工作。
- **容量如何受限**：可以把每个 program 需要的寄存器、共享内存等分别与 SM 的容量比较；其中最紧的约束会限制可同时驻留的数量。
- **不能直接推出什么**：并行驻留数降低，并不等价于某一次 stage 本身执行更慢。若要说单个 program 因 spilling 等原因变慢，还需要该机制的证据。

**边界**：增加 stages 不保证寄存器和共享内存都增长，也不保证正好保存同样数量的完整行；应检查实际编译特化的资源记录。

### 锚点

单份资源 ↑ → 同时驻留可能 ↓

## 06. 分析 GPU kernel 性能时，若 occupancy 达到 100%，是否就能判断计算执行单元都在忙？occupancy 实际描述哪一种“占满”？

类型：真实纠错 · 层级：原子 · 等级：A

### 场景

复习 GPU 的 warp 驻留指标：occupancy 比较每个 SM 上已驻留的 active warps 与硬件最多可驻留的 warps。

### 正确

100% 表示 warp 驻留容量已满，不能据此判断执行单元始终都在工作。

### 错误

只能说计算单元全都在被用，但不一定用得好

### 说明

**结论**：occupancy 衡量驻留容量的利用程度，不直接衡量这一时刻有多少计算指令正在执行。

- **为何会不同**：一个 warp 可以已经驻留，却因等待内存数据或前序指令结果而暂停推进。这类 stalled warp 仍计入 active warps。
- **状态层次**：active 表示已驻留；eligible 表示当时有可调度的就绪指令；issued 表示指令实际被发射。驻留并不自动意味着后两种状态。

**边界**：高 occupancy 可能帮助隐藏延迟，但不能单独证明最佳性能，更不能把 100% occupancy 直接翻译成“所有计算单元一直满负荷”。

## 07. persistent softmax 有 M 行输入，启动 P 个 program（P&gt;0）。编号 p 的 program 从行 p 开始，每次增加 P，直到行号达到 M。怎样证明这种 grid-stride 分配让每一行恰好被处理一次？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：对任意合法行号，除以 P 得到唯一的商和余数；余数确定负责它的 program，商确定该 program 的循环迭代，所以既不会漏行，也不会重行。

- **符号定义**：设 r 是行号，满足 0≤r&lt;M；p 是 program 编号，满足 0≤p&lt;P；k 是从 0 开始的迭代编号。它们满足以下对应关系。

$$
r=p+kP,\qquad p=r\bmod P,\qquad k=\lfloor r/P\rfloor
$$

- **不漏与不重**：存在这组商和余数，说明每个 r 都有对应的 program 和迭代；商余数唯一，说明不会有另一组 program 与迭代再次处理同一行。

**边界**：循环必须以 r&lt;M 为条件，并使用同一个正步长 P。证明依赖这套静态行分配规则，而不是仅凭某个数字例子看起来覆盖完整。

### 锚点

商余数唯一 → 行归属唯一

## 08. persistent softmax 共有 M 行，program p 依次处理 p、p+P、p+2P 等行，其中 P 是启动的 program 数。如果实际启动 P=M，为什么增加行循环的 num\_stages 不能产生同一 program 的跨行流水？

类型：技术问答 · 层级：机制 · 等级：A

适用范围：programming-lab triton lesson02 · 2026-08-07 learning baseline

### 答案

**结论**：因为每个 program 只会执行一次有效行迭代，没有自己的下一行工作可与当前行重叠。

- **按行号推导**：program p 的第一次行号是 p，属于有效范围；下一次行号是 p+M，已经不小于 M，因此循环立即结束。
- **流水所需条件**：tl.range 的跨迭代流水需要同一 program 内有多次迭代。这里只存在一行迭代，无法把下一行的工作提前放入流水。

**边界**：不同 programs 仍可能被 GPU 交错调度，但这属于硬件对不同工作的调度，不能当作该 program 行循环内部的跨迭代流水。

### 锚点

每 program 一行 → 无下一迭代

## 09. 同一个 persistent GPU kernel 保持行分配算法不变。增加软件流水深度后，即使每个 SM 的驻留数量和 occupancy 降低，执行时间为什么仍有可能缩短？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：流水可能让同一 program 中更多独立迭代的工作重叠，提高指令级并行与延迟隐藏能力；这部分收益有时可以抵消较少驻留工作的代价。

- **怎样隐藏延迟**：当某一行迭代等待加载结果时，另一行迭代中不依赖该结果的指令可能继续推进，减少 program 只有等待而没有可做工作的时间。
- **为何不矛盾**：occupancy 是相应测量口径下驻留 warp 数占硬件上限的比例，跨迭代并行则描述已驻留工作内部有多少独立指令可推进。驻留比例降低时，剩余工作的推进效率仍可能改善。

**边界**：这是一种需要测量核验的可能机制。stages 不会自动把一行切成更多块，也不保证每次增加流水深度都会提速。

### 锚点

跨迭代独立工作 → 延迟隐藏机会

## 10. persistent softmax 的 wrapper 会根据每个 program 的寄存器和共享内存用量，估算驻留数量并选择默认 grid。应从哪个编译版本获取资源记录，才能让这个 grid 对应真实执行？

## 11. persistent softmax 先按 GPU 资源估算可启动的 program 数，又因只有 M 行输入而把全设备 grid 限制为不超过 M。这个工作量截断会不会降低该编译特化的“资源理论 occupancy”？

类型：技术问答 · 层级：原子 · 等级：A

### 答案

**结论**：不会改写它按每个 SM 资源容量推导的理论驻留上限；但实际工作量可能太少，无法让设备达到这个上限。

- **理论上限**：资源理论 occupancy 回答“如果有足够多的工作，该特化最多能占用多少 warp 驻留容量”，依据是每份工作的资源需求和每个 SM 的资源容量。
- **实际启动量**：grid 回答“这次在整个设备上总共启动多少个 program”。小 M 限制的是这次有多少工作，而不是每个 SM 理论上装得下多少工作。
- **运行时观测**：achieved occupancy 是执行时实际观测到的驻留情况，会受工作量、调度及执行过程影响，需要与静态理论估算分开。

**边界**：不能把被 M 截断后的全设备 grid 直接代入每个 SM 的资源容量公式，否则会把启动规模和理论驻留能力混为一谈。

资源容量 · launch 数 · 运行时观测

## 15. 对一行有限输入 x，需要计算每个位置的 log-softmax。为什么“先计算 softmax 概率，再对概率取 log”可能丢失有限结果，而直接计算稳定的 log-softmax 可以避免这个问题？

类型：技术问答 · 层级：机制 · 等级：A

### 答案

**结论**：很小的 softmax 概率在浮点数中可能先下溢成 0，随后取 log 就得到负无穷。直接使用稳定的对数表达式，可以避免先形成这个已经丢失精度的最终概率。

- **定义所用量**：令 x\_i 为当前元素，m 为整行的最大值，j 遍历行内所有有效元素。先减去 m，再计算指数和的对数，最后从 x\_i−m 中减去它。

$$
\log\operatorname{softmax}(x_i)=(x_i-m)-\log\sum_j e^{x_j-m},\qquad m=\max_j x_j
$$

- **最小例子**：输入 \[0, -1000\] 时，第二项概率可能在浮点表示中成为 0；再取 log 只能得到负无穷。稳定公式保留原始分数 -1000，得到的第二项仍约为 -1000。

**边界**：这里假设行非空且输入有限。数学上等价的表达式不保证在浮点中同样稳定；非有限输入还需要单独约定和验证。

### 锚点

保留对数域 → 避免概率先下溢

## 16. persistent softmax 的一个 program 会通过行循环处理多行，num\_stages 控制该循环的流水设置。请用约 60 秒解释：为什么增加 num\_stages 不保证提速，应怎样理解重叠收益、驻留资源与实验归因？

类型：综合口述 · 层级：口述 · 等级：A

适用范围：programming-lab triton lesson02 · 2026-08-07 learning baseline

### 参考回答

**结论**：增加 stages 只是增加跨迭代重叠的机会。有没有足够迭代，以及重叠收益能否超过资源和流水成本，才决定实际是否更快。

- **作用域**：流水属于同一个 program 的行循环，不是新增独立 worker。若启动的 program 数等于行数，每个 program 只有一次行迭代，就没有自己的下一行可重叠。
- **潜在收益**：多次独立迭代在途时，一次迭代等待数据，另一次可能推进指令，从而增加指令级并行与延迟隐藏机会。
- **潜在代价**：若每个 program 使用更多受限资源，每个 SM 能同时驻留的 program 可能减少；但不能仅由驻留下降断言单个 stage 变慢。
- **实验结论**：如果 stages、资源占用和默认 grid 一起变化，结果评价的是整套策略。要缩小归因范围，需要共同显式 grid 等追加对照。

**边界**：occupancy 下降仍可能与加速同时出现，反过来相同 occupancy 也不保证相同速度；应以匹配当前配置的测量来判断。

### 评分锚点

同 program 跨迭代；单次迭代无跨行流水；延迟隐藏与驻留权衡；联动策略的因果边界
